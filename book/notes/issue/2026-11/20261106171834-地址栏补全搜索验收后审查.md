### 2.3 竞态条件

发现 **新增中-1**。其余导航回复的会话/Tab 与编辑版本守卫、原生建议回执、监听器清理保持原链，未发现其他确定问题。

- [ ] **[中-1] 导航未落地时 Tab 编辑旧地址，覆盖可见的 pending 文本**
  - 位置：`src/renderer/src/components/browser/Toolbar.tsx:358`，相关分流 `:621`、`:623`；提交置 draft 为 null 在 `:514`，实际 input 显示值在 `:762`。
  - 描述：navigate 的 IPC 成功表示主进程已经发起 loadURL，并不表示页面导航已提交。此后 draft 为 null，真实 mainUrl 仍可能是旧地址，input 通过 pendingShown 正确显示提交地址。但 editSnapshot、引擎匹配和搜索 entry 都只读 `draft ?? mainUrl`。在此窗口按 Tab，就会根据旧页面地址执行编辑；新空白 Tab 上旧 mainUrl 为空，结果是把整段待导航 URL 替换为单个 U+0009。可见输入与新保存的撤销快照也不一致。
  - 真实复现：在隔离 userData 的新空白 Tab 保持地址栏聚焦，访问延迟返回内容的 `http://127.0.0.1:8783/slow`。服务器已收到 `/slow`，但暂不响应。Enter 后 input 为该完整 URL，再按 Tab 后 input 为 `"\t"`。此测试走真实 browser.navigate、preload、IPC 和 loadURL，未替换导航函数。
  - 补充证据：模拟 IPC 已成功但页面快照未更新，提交 `bing.com` 后框内仍显示 `bing.com`；Tab 后也是 `"\t"`，没有搜索标签。也就是说新修订的完整引擎优先规则在 pending 态失效。模拟结果仅用于补充，慢页面实测为主证据。
  - 根因依据：主进程 `src/main/browser/ipc.ts:348` 发起 loadURL 后立即返回当前快照，renderer 的 pending 设计本就用于覆盖该窗口；本次新增 Tab/编辑快照没有纳入同一来源。
  - 建议方向：独立修复轮统一可编辑原文来源，纳入当前有效的 pendingShown；引擎识别仍必须使用用户原文/待导航原文，不能改用历史自动追加的 completion 展示串。将同一来源用于 Tab 插入、引擎 entry 与 undo 快照，补空白页/已有旧页、慢导航与快速连续编辑回归。
  - 影响：焦点没有离开也会丢掉正在显示的导航文本；重新聚焦或等导航落地可以绕过，故评为中。

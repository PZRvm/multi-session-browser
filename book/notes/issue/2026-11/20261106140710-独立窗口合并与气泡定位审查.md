### 2.3 竞态条件

结论：发现 1 个问题。

- [x] **[中-1] 合并快照覆盖主窗在途的乐观会话选择，成功响应后镜像无法恢复**
  - 位置：`src/main/browser/registry.ts:1161`；关联 `src/renderer/src/stores/sessions.ts:164`、`:348`、`src/main/sessions.ts:428`、`src/renderer/src/stores/browser.ts:367`。
  - 描述：A 的独立窗开始合并，元数据保存尚未完成时，用户在主窗点击 B。selectSession 先乐观设置 activeId=B，B 的 setActive 写盘排在 A 合并之后。A 保存完成后，新增的 onMergeSessionsChanged(stored) 推送全量快照，onChanged 无条件 adoptSnapshot，把镜像改回 A。随后 B 的 setActive 成功，主进程切到 B，但 selectSession 成功分支只更新工作区记忆，不恢复 activeId，也没有新的权威选择快照。最终磁盘与 registry 为 B，renderer 为 A；B 的浏览器快照会被 sessionId/activeId 守卫丢弃，造成列表、Tab 栏/地址栏与实际页面不一致。重新点击会话可恢复。
  - 证据：新增流程先 await mutateSnapshot（1144—1157），随后推送其 stored（1161），没有与主窗在途操作协商版本或重放；既有 selectSession（348—357）在成功分支没有 activeId 回填。内存 harness 加载当前完整 sessions store（真实 zustand），模拟 setActive Promise 排队与合并 onChanged 回调，输出：

    ```text
    RACE_REPRO {"diskActive":"B","registryActive":"B","rendererActive":"A"}
    ```

    harness 中磁盘/registry 由受控 API mock 表示；rendererActive 来自真实 store 代码，断言通过。该时序可由 A 合并保存屏障 + 主窗后点击 B 复现，并非把旧响应强行伪造成新请求。
  - 建议方向：为跨窗口的全量事实推送与主窗在途选择建立一致的版本/序列或命令成功后的权威收敛机制，使更新的选择成功后，renderer、registry 与落盘 activeId 重新一致。保留浏览器快照守卫；不要通过放宽会话匹配掩盖分叉。增加 A 合并保存中 → 主窗点 B → 两个请求完成后的三方一致性验证。

### 2.5 通知遗漏

结论：发现 1 个问题。

- [x] **[中-2] 同会话归并改变主窗激活 Tab，却未通知主窗原 Tab 的录制自动停止**
  - 位置：`src/main/browser/registry.ts:1170`；关联 `src/main/browser/manager.ts:837`、`src/main/browser/recording/index.ts:433`、`:444`、`:452`、`:509`。
  - 描述：主窗正在录制会话 A 的 Tab M，A 的独立窗持有另一个 Tab S。点击独立窗合并会把主窗激活页改为 S（manager.activate），但新流程只发同会话的 session-switched 和来源 Tab 的 tab-moved。录制钩子对同会话 session-switched 直接忽略；tab-moved 的 id=S，和被录 id=M 不同，也忽略。缺少携带主窗 windowId 的 tab-switched 通知，录制状态继续留在 M。页面已切到 S，原录制不会按 PRD 3.10 的切 Tab 自动停止规则结束，可能继续录后台原页；与按钮胶囊所处的新页面含义不一致。
  - 证据：mergeAllTabsToMain 在 manager.ts:837 执行 activate(activeId, WINDOW_ID_MAIN)，registry.ts:1171 只遍历 source.tabs 发 tab-moved。内存 harness 从当前源码提取 mergeWindowToMain、真实录制生命周期路由与三枚相关钩子，在持久化/页面 manager mock 下执行，得到：

    ```text
    RECORDING_REPRO {"mainActive":"tab-source","events":[["session-switched","A"],["tab-moved","A","tab-source","child"]],"stopRequests":[]}
    CONTROL explicit main tab-switched hook => stopRequests=[auto]
    ```

    主窗实际激活页的 mock 按 manager 批量原语的 activate 语义推进；事件路由和停录判据来自现有真实源码。直接调用携带 main windowId 的激活页变化钩子立即产生 auto 停止请求，确认缺失的是通知，并非录制状态机本身。已有验收仅检查每个迁移 Tab 的 tab-moved，未覆盖“被录 Tab 留在目标主窗但失去激活位”的场景。
  - 建议方向：归并改变目标主窗激活位时同步补全其生命周期通知，携带新激活 Tab 与 WINDOW_ID_MAIN，让录制钩子可匹配被录窗口并按既有规则停止。继续保留来源 Tab 的 tab-moved，以覆盖被录 Tab 本身来自子窗的情况；避免误停同会话其他独立窗内未受影响的录制。分别验证源窗正在录屏、目标主窗正在录屏、同会话另一未变化独立窗正在录屏三类情况。

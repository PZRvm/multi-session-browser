# 损坏图片被当作成功图标缓存

2026-11-16 历史图标提交压缩后的 Phase 5 复审发现，只记录，不修复。

位置：`src/main/browser/historyIcons.ts:45`、`:135`、`:234`；渲染端 `OmniboxSuggestPanel.tsx` 的 onError 仅更新本地失败状态。

当前按文件签名判断成功，PNG 只需要前八字节符合签名。若服务器返回截断 PNG，主进程仍生成 data URL、写缓存并停止尝试 `/favicon.ico`；renderer 解码失败显示搜索图标，但不使缓存失效。后续即使服务器修好原图，七天缓存周期内仍读取损坏内容。

复现：打包实际 historyIcons 模块，原 favicon 的响应仅含 PNG 八字节签名，根 favicon 返回完整有效 PNG。连续 resolve 两次，中间将原图响应改为有效图片。实际两次都返回同一份八字节数据，下载调用只有一次，根图标零请求；shutdown 后该损坏图片也按成功条目保存。

影响：持续显示搜索图标直到缓存到期或手工清理，且错过可用的根图标；现有回归只检查图片签名与 HTML 排除，未覆盖解码失败后的缓存补救。

建议后续以实际解码成功作为缓存成功条件，或让渲染端通过严格作用域通道报告失败、失效相应候选并继续下一候选；保留会话隔离和体积限制。

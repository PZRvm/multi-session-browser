# 普通网站 Service Worker 被误注入扩展桥

2026-11-13，验证码排查中发现，未修复。涉及 IPC 身份与权限边界，后续实施按 L 级处理。

## 已确认的问题

`src/main/extensions/runtime/preload-guard.ts:85` 对所有 `process.type === 'service-worker'` 放行，依赖 `electron-chrome-extensions` 的 preload 也使用同样条件。没有在执行注入前确认该 Worker 来自 `chrome-extension:`。`__msbExposeShimBridge` 随后经 contextBridge 暴露宿主 shim，依赖再暴露 `electron` 兼容桥。

隔离实例中，普通 localhost 网页注册的 Service Worker 能通过自己的 MessageChannel 返回以下结果：

```text
typeof globalThis.process          = undefined
typeof globalThis.require          = undefined
typeof globalThis.electron         = object
typeof globalThis.__msbShimBridge  = object
typeof globalThis.chrome           = undefined
```

shim 对象可枚举 `captureVisibleTab`、`download`、`tabStream`、`contexts`、`offscreenCreate`。本轮没有调用这些方法，未验证或声称可以绕过 IPC 身份检查。问题是扩展桥对象进入了普通网站上下文，不能因为页面顶层没有桥对象就判定所有网页上下文隔离正常。

安装版飞书页面的 DevTools 已有相同生成文件的加载失败日志，包含 `ReferenceError: location is not defined`。依赖的错误处理在隔离 Worker 中读取 `location.href`，可能掩盖更早的注入异常；不能仅凭这条异常确定原始异常内容。

## 复现与影响边界

用 `npm run dev:agent`、独立 `MSB_USER_DATA` 启动；本地站点注册 Service Worker，安装时 skipWaiting、激活时 clients.claim，再通过 MessageChannel 回传上述全局对象类型。2026-11-13 在两个独立本地站点均观察到桥对象。顶层网页、跨源 iframe 和 Dedicated Worker 没有这些对象。

普通站点 SW 仍能注册、激活及响应消息，不应写成全部 Worker 失效。误注入会改变网站可观察的运行环境；是否被豆包采样并导致人机验证尚未证明，详见[验证码排查记录](20261113170129-网站频繁验证码与浏览器身份排查.md)。

## 后续方向与验收

- 在任何桥暴露和依赖注入前限定扩展来源；从可信 Worker 身份获取来源，不信任页面自报参数。保留扩展后台 Worker 的现有能力。
- 普通 HTTP(S) Service Worker 的主世界不得出现上述桥对象，也不得产生扩展 preload 异常；页面、iframe、Dedicated Worker 同样复验。
- 扩展后台启动、消息、录屏和下载的回归通过；分别检查普通站点与扩展 Worker 的 sender 身份，不能只靠 renderer 名单兜底。
- 把原始异常与错误处理本身的异常区分开；不要为消除日志而吞掉异常或放宽权限。

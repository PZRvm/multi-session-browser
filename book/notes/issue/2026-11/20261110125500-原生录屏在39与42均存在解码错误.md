# 原生录屏在Electron39和42均出现H264解码错误

2026-11-10升级回归中发现：原应用工具栏录屏可以开始、暂停、恢复、停止，并弹出保存成功；但产物在严格解码时失败。独立前置宿主的带音频MP4完整解码通过，不能据此推定原应用入口文件有效。

## 复现与证据

本次构建的同一src/out/main在相同本机、相同本地动态图案下操作原有UI，未改生产录屏实现：

- Electron42.11.7：application-smoke42/native-recording.mp4，460751字节；H264纯视频10.146900秒。原始保存文件名会话 1_20261110-125028.mp4。
- Electron39.8.10：用主仓库现有官方二进制，通过ELECTRON_EXEC_PATH指定启动同一dev工程，使用application-smoke39独立userData；产物472981字节，原始文件名会话 1_20261110-125214.mp4。
- 两个产物和native-recording-decode.log均保留在tools/extension-preflight/out/.artifacts对应目录；无真实用户数据。

检查命令：`ffmpeg -v error -xerror -i <文件> -f null -`。两端均退出183，包含相同的`left block unavailable for requested intra mode`、`error while decoding MB 0 1`、`cbp too large (94) at 50 8`等错误。普通ffmpeg即使输出大量解码错误也可能退出0，因此不能只看普通退出码。

## 当前判断

旧版39也复现相同错误，没有证据将其归因于本次42升级。尚未定位是编码/MP4分块、参数集、写入还是解码器兼容；不作根因结论，也不把“保存成功”当作可播放通过。原录屏设计audio:false，纯视频没有音轨符合旧实现，不是本轮带Tab音频实验失败。

后续任务应固定两份样本，核对capturePage.html的MediaRecorder分块和fileWriter字节序/参数集，增加其他播放器和独立直录对照。当前只记录，没有顺手修改src；整个升级回归和插件前置仍不能标记全部通过。

## 2026-11-10独立修复与复验

用户授权修复后，1倍缩放999像素源宽稳定损坏，1000像素不发生；原始Blob拼接与落盘哈希相同。生产采集页读取真实视频尺寸并固定偶数宽高后通过，preload的saveChunk返回真实Promise，主进程增加顶层senderFrame核验。六项生产采集回归（奇偶尺寸、resize、关闭目标、提前停止、拒绝权限）见recording-1794288972587/results.json。真实UI产物native-fixed/native-recording.mp4为15.3913秒，QuickTime打开并播放。

严格解码使用`ffmpeg -v error -xerror -i <文件> -enc_time_base demux -fps_mode passthrough -f null -`，退出0且stderr为空。源461个包时间戳严格递增；先前null输出的重复DTS是默认输出时基舍入，不是文件倒退。旧39/42坏样本仍保留，原文描述的是修复前状态。

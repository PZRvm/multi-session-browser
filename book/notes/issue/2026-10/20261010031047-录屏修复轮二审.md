## 中（3 项）

### 中-1 受理即广播后、recorder 建立前到达的 pause/resume 被采集页丢弃，「暂停期间不落帧」契约破

- 位置：`src/main/browser/recording/capturePage.html:20-37`（onCommand：仅 stop 排队，`if (!recorder) return` 直接丢 pause/resume）；`src/renderer/src/components/browser/Toolbar.tsx:316-340`（recState 一变 recording 即渲染暂停钮）；`src/main/browser/recording/index.ts:348`（受理即广播——中招窗口的来源）
- 问题：上轮低-6 修复让胶囊与暂停钮在 begin 受理时即刻出现，而采集页 MediaRecorder 要等采集页加载 + getDisplayMedia 握手完成（实测 1-8s）。此窗口内点暂停：主进程 machine.pause 成功、UI 冻结时长，但 `sendCommand('pause')` 到达采集页时 `recorder` 尚未建立——pause 被静默丢弃，随后 `recorder.start(500)` 照常落帧。结果：UI 显示已暂停（时长冻结），文件却持续增长——直接违背 PRD 3.10.2/4.13「暂停期间不落帧、不计时长」。resume 同理被丢（后果较轻：UI 恢复与实际录态恰好归于一致，但中间「暂停段」已落帧）。stop 有 pendingStop 排队防线（高-2①），pause/resume 无对称处理。
- 证据：capturePage.html onCommand 全文（仅 `cmd === 'stop' && !recorder` 走 pendingStop）；index.ts:354-363 pause handler 不校验 collectorReady 即 machine.pause + sendCommand。
- 建议方向：采集页对称排队（pendingPause，recorder 建立后立即执行）；或主进程在 `collectorReady === false` 时拒绝 pause（返回当前态，UI 不变更）；或广播载荷携带 ready 位让 renderer 延迟启用暂停钮。三者取一即可闭合。

### 中-2 录制中进出 HTML 全屏使时长显示永久冻结（ticker 单例随 Toolbar 卸载被杀、重挂不复原）

- 位置：`src/renderer/src/components/browser/Toolbar.tsx` 卸载链 + `src/renderer/src/stores/capture.ts:23-47`（attach cleanup 无条件 `syncTicker('idle')`；attach 本身不按现态恢复 ticker）；`src/renderer/src/components/BrowserFrame.tsx:29` 与 `IndependentWindowFrame.tsx`（`{!htmlFullscreen && <Toolbar />}`——全屏期间 Toolbar 卸载）
- 问题：录制中用户对被录页面点全屏（录视频页面是现实动作）：Toolbar 卸载 → attach 的 cleanup 执行 `syncTicker('idle')` → 模块级单例 ticker 被清；退出全屏 Toolbar 重挂 → `attach()` 只注册监听、**不按 store 现态重启 ticker**，而录制期间不会再有状态推送 → `now` 冻结在全屏前的最后一次 tick，胶囊时长停走（红点脉动依赖 CSS 仍动，更具迷惑性）。PRD 验收 37 明文「红点＋累计时长」。该缺陷早于低-3 修复即存在，但低-3 改造的正是这套 ticker/now 机制，属本轮审查面内。
- 证据：syncTicker 全文（`shouldRun = status === 'recording'`，仅由 push 回调与 detach 调用）；attach 全文（无 `syncTicker(useCaptureStore.getState().state.status)` 类复原）。
- 建议方向：attach 时按当前 store 状态调一次 syncTicker；或 ticker 生命周期与组件订阅解耦（status 变化驱动启停，卸载只退订不整表）。附带收紧：双窗各自 renderer 进程各持一份 store/ticker，互不影响——同窗内修复即闭合。

### 中-3 采集器 URL 判定的 'media' 放行面过宽：file:// 可达，伪造同名页可静默拿到摄像头/麦克风权限

- 位置：`src/main/browser/permissions.ts:330-338`（`isRecordingCollectorUrl(webContents.getURL())` → `finish(true)`，且位于 `isPureVideoRequest` 检查**之前**——音视频一起要也放行）；`permissions.ts:70-76`（判定 = file:// + 文件名 capturePage 前缀 .html）；`src/main/browser/url.ts:6`（`ALLOWED_SCHEMES` 含 `file:`）
- 问题：file: 在地址栏 scheme 白名单内，任何会话都可导航到本地任意文件。构造一个名为 `capturePage.html` 的本地 HTML 让用户（或测试流程）打开后，其 `getUserMedia({audio:true, video:true})` 会命中该分支被**免对话框放行**——绕过 PRD 摄像头授权对话框（会话名 + origin 告知用户）的应用层同意；macOS/Windows TCC 仍在，但应用已获 TCC 授权的机器上即为静默取流。代码注释声称「零越权由该层承担（setDisplayMediaRequestHandler）」——该论断只覆盖**屏幕流**（核为属实：handler 只认采集器 frame，采集页外一律 callback({})，录制外未注册 handler 默认拒绝），不覆盖**摄像头/麦克风权限本身**的越权放行。触发条件需用户打开攻击者命名的本地文件，概率低但路径真实存在。
- 证据：url.ts 白名单含 file:；permissions.ts request handler 分支顺序（display-capture → isCurrent/media → isRecordingCollectorUrl → isPureVideoRequest → origin 询问链）。
- 建议方向：身份判定从「URL 形状」升级为「实例身份」——录制域暴露 `isCollectorWebContents(wc)`（采集器持有自身 webContents 引用，经 deps 注入 broker 或经共享注册表查询），伪造页即失效；最低限度也应把该放行收窄到 `isPureVideoRequest` 之后并比对 `webContents.getURL()` 与装配点注入的 collectorPagePath 精确相等。

### 低-5 begin 的 getSessionName await 窗口内插入生命周期事件：录制「无状态机伴随」启动，靠 1.5s 兜底才收

- 位置：`src/main/browser/recording/index.ts:279-292`（generation 递增 → **await** getSessionName → 建 writer/collector）；`:202-220`（requestStop 兜底）
- 问题：中-2 修复把 getSessionName 留在 begin 的 async 段。该 await（读盘，毫秒级）期间事件循环可处理 registry 生命周期 emit：若此刻被录 Tab 关闭/切走，handleTabGone 等触发 requestStop——当时 collector 尚为 null，sendCommand('stop') 落空，machine 已 idle；await 返回后 begin 继续建 writer/collector，录制在「状态机 idle、UI 全程 idle」下真实运行，直到 requestStop 预约的 STOP_FALLBACK 定时器（generation 未变 + collector 非空 → 命中）在 1.5s 强制 settle——以「tab-closed」文案（碰巧正确）落一个小文件或因零块弹「开始录制失败」。结果有界、无泄漏、无卡死，仅体验困惑。
- 证据：requestStop 内 `collector?.sendCommand` 在 collector === null 时为 no-op；begin 后续不再复查 machine 现态。
- 建议方向：await 返回后复查 `machine.getState().status === 'idle'` 即整体回滚（回收 writer/collector 直接 return），不等兜底。

### 低-6 启动期 .part 清扫无单实例锁护栏，双实例并发时可截断在录文件

- 位置：`src/main/browser/recording/index.ts:95-114`（清扫）；`src/main/index.ts` 全文无 `requestSingleInstanceLock`
- 问题：应用未做单实例锁，同一 userData 可被两个实例并发使用。实例 B 启动时实例 A 正在录制：B 的清扫会 unlink A 的在写 `.webm.part`；A 的后续 appendFile（'a' flag）会重建同名文件继续写——最终产物**头部缺失**（webm 无 header，大概率不可播）且无任何告警。概率低（需恰好在他人录制时启动第二实例），但后果是静默数据损坏，与「绝不产出损坏文件」的产品意图相悖。
- 建议方向：加 `app.requestSingleInstanceLock()`（标准做法，顺带解决 userData 并发写的一揽子问题）；或清扫前探测锁。二选一即可。

## 边界观察（不计入问题数）

- **webContents 无 emit 销毁路径**：页面自调用 window.close() 或渲染进程崩溃时，Tab 消失不经 registry.closeTab，五路生命周期不触发。推测会自愈（源 frame 销毁 → 捕获 track ended → MediaRecorder 自动 onstop → reportStopped → settle 落盘），但未实测。属录屏五路设计时已有的盲区（非本轮修复引入），建议后续以 `wc.once('destroyed')` 挂 handleTabGone 收口并实测验证自愈假设。
- **collapseRectFor 多显示器疑虑排除**：`x = -width - 64` 是 WebContentsView 的窗口内容坐标，view 越界部分被宿主窗口剪裁，不存在「在左侧显示器可见」的问题；恢复路径核实可靠（overlayDepth 归零 → useRectObserver 重连并立即 rAF 上报非零矩形 → 悬挂解除），上报语义与修复前完全一致，无新增「永久屏外」风险。
- **HTML 全屏 × 移出屏幕优先级**：currentRect 中悬挂优先于全屏（既有语义）；录制窗全屏期间弹原生框，view 按全屏前缓存尺寸移出屏幕，捕获保持全帧无缩小段，可接受。
- **createCollector 半构造泄漏**：ipcMain.handle 冲突已由 begin 幂等清场防住，其余建窗异常抛出时理论上有已建窗口泄漏，现无现实触发路径（防御性备注）。

## 八项必查逐项结论

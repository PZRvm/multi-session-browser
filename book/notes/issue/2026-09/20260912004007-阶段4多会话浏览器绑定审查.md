## 1. 审查摘要

阶段 4 主体架构质量高：分区拼装收敛在 registry 单点、挂摘保活与清除时序有冒烟实证、store v2 迁移未破坏既有坏数据矩阵、preload 暴露面严格 +2、typecheck/lint 全绿。但 renderer 会话编排层有两处与主进程编排不对等的缺口构成高严重度问题：**新建会话从不触发主进程激活**（叠加 selectSession 的 prev===id 早退，新会话单击无法激活，首次安装场景右侧永久空态，且验收文档把计划用例 F 的该验收项删掉了）；**删除激活会话时级联切换的快照推送必被 renderer 守卫丢弃**（removeSession 非乐观更新 activeId，推送先于 invoke 回复到达），browser store 残留已删会话镜像。主进程侧 destroySession 的有界重扫存在**超轮后无告警的复生路径**（window.open → newTab 在 clearStorageData/fs.rm 之后复生该分区 webContents，泄漏 + 数据回写），需要 dispose 标志。

### 2.3 竞态条件

结论：发现 8 个问题（H1、H2、M1、L1、L2、L3、L9、L11）。

- [x] **[高]** [已修复 2026-09-12] H1：新建会话不触发主进程激活，新会话成为「死会话」——单击永远无法激活，首次安装场景右侧永久卡在空态
  - 位置：`src/renderer/src/stores/sessions.ts:66-74`（addSession 仅本地 set activeId）、`src/renderer/src/stores/sessions.ts:105-108`（selectSession `prev === id` 早退）、`src/main/sessions.ts:76-104`（create handler 不改 activeId、不调 deps.onActiveChanged）
  - 描述：addSession 创建后只在 renderer 本地置 `activeId = item.id`，从不调用 `setActive`。主进程侧 `sessions.json` 的 activeId 与 registry 的 activeSessionId 均维持旧值：右侧浏览器不切换到新会话，且 browser store 的守卫（browser.ts:37）从此刻起把仍真实激活的旧会话全部推送判为过期丢弃（旧会话 tab 栏冻结）。用户点击新会话行自救时，`selectSession` 因 `prev === id`（activeId 已是新会话）直接 return——唯一出路是先点别的会话再点回来。**首次安装（零会话）新建第一个会话后右侧仍是「尚无会话」空态，没有任何可点的其他会话，必须再建第二个会话或重启**。
  - 证据：addSession 全文无 `window.api.sessions.setActive` 调用；`selectSession` 首行 `if (prev === id) return`；主进程 create handler（sessions.ts:84-102）只 push 会话不动 activeId；开发计划步骤 7 用例 F 明确要求「新会话创建即激活且右侧出现新标签页」，而验收文档 `book/notes/summary/20260911191316-.../20260912003809-阶段验收.md` 用例 F（第 72 行起）共 5 条，把该验收项删除了——计划与验收文档不一致，缺陷被掩盖。
  - 建议方向：addSession 成功后追加 `await window.api.sessions.setActive({ id: item.id })`（复用既有乐观/回滚框架），由主进程 onActiveChanged 级联切换浏览器；或主进程 create 后按「落盘 activeId 为 null 时自动选中新会话」规则写入并在 create handler 内调 deps.onActiveChanged。修复后把该验收项补回验收文档实测。
- [x] **[高]** [已修复 2026-09-12] H2：destroySession 复生路径无 dispose 标志——重扫超轮后 in-flight 的 window.open→newTab 可在 clearStorageData/fs.rm 之后复生该分区 webContents（泄漏 + 数据覆写回盘）
  - 位置：`src/main/browser/registry.ts:251-297`（destroySession，重扫循环 276-282）、`src/main/browser/manager.ts:258-261`（setWindowOpenHandler → `newTab(openUrl)`）、`src/main/browser/manager.ts:153-271`（newTab 无任何「已废弃」守卫，activate→attachView 128-133 会把复生 view 挂回 contentView）
  - 描述：managers.delete(id) 后 manager 闭包仍被其 webContents 的事件接线引用而存活。closeGracefully 的 close() 走页面 unload，期间页面 JS 调 `window.open` 命中 manager 的 setWindowOpenHandler → 同分区 newTab（新 WebContentsView + loadURL + 挂入窗口）。重扫循环 3 轮内扫到的会被补杀；**最后一轮扫描之后到 rm 完成之间复生的 wc 无人再杀**：其 in-memory session 会把新写入的 cookie/存储回刷落盘（分区目录在 rm 后复现，违背「永久删除、不可恢复」承诺），view 与 manager 闭包泄漏至应用退出。概率评估：普通页面偶发（unload 期 window.open 属恶意/弹窗类行为）低概率，但蓄意页面（beforeunload 内循环 window.open）可确定性逃过 3 轮；缓解因素：标准删除流经确认弹层，期间 manager 处 suspended 态，复生视图以零矩形挂入（不可见、不遮挡），但泄漏与数据回写不因不可见而消失。
  - 证据：`wc.setWindowOpenHandler(({ url: openUrl }) => { if (openUrl && isOpenableUrl(openUrl)) newTab(openUrl); return { action: 'deny' } })`（manager.ts:258-261）对已从注册表摘除的 manager 照常生效；重扫循环 `for (let round = 0; round < DESTROY_RESCAN_ROUNDS; round += 1)`（registry.ts:276-282）结束后无任何存活检查或告警，直接进入 clearStorageData → rm。
  - 建议方向：给 TabManager 增加 `dispose()`/`disposed` 标志，destroySession 摘引用后立即置位；newTab（含 setWindowOpenHandler 转换路径与 before-input-event 的 Cmd+T 路径）在 disposed 时一律 no-op、window.open 直接 deny 不建 Tab。这是对用户专审问题 1 的肯定回答：需要 dispose 标志。
- [x] **[中]** [已修复 2026-09-12] M1：删除激活会话时，级联切换的快照推送必被 renderer 守卫丢弃，browser store 残留已删会话镜像
  - 位置：`src/renderer/src/stores/sessions.ts:77-88`（removeSession 非乐观更新 activeId，set 在 await 之后）、`src/renderer/src/stores/browser.ts:33-40`（守卫）、`src/main/sessions.ts:135-146`（onDeleted 在 handler 返回前同步触发 switchSession → 推送）
  - 描述：删除激活会话 S1（级联到 S2）时，主进程在 delete handler 返回前就同步完成 switchSession(S2) 并推送 S2 快照（webContents.send 先于 invoke 回复到达 renderer）。此刻 renderer 的 sessions.activeId 仍是 S1（removeSession 的 set 在 await resolve 之后才执行），守卫把 S2 快照整体丢弃。随后 activeId 更新为 S2，但 browser store 仍镜像 S1（已删会话）的 tabs/activeTabId/地址栏：右侧原生视图是 S2 的页面、chrome 框体却显示 S1 的 tab 列表，点 S1 的 tab 报「标签页不存在」，直至 S2 的 manager 自行 emit 任意快照事件才自愈（静态页可能长期不自愈）。删除最后一个会话的场景由 destroySession 尾部 `if (wasActive) notifySnapshot()`（registry.ts:296）的空态推送兜底恢复，但延迟到销毁链完成（closeGracefully 卡住时最长 3s+），期间同样显示已删会话的 tab 列表。
  - 证据：时序链——sessions.ts:145 `deps.onDeleted(id, nextActiveId)` → index.ts:163-168 `switchSession(nextActiveId)` + `destroySession(id)` → registry.notifySnapshot → ipc.ts:37-39 推送；renderer 收到推送时 `useSessionsStore.getState().activeId` 仍为 S1（removeSession 的 set 在 ipc.ts 回复之后）。selectSession 有乐观更新（sessions.ts:108）所以正常切换无此问题，removeSession 没有。
  - 建议方向：removeSession 在 await 前乐观更新 activeId（与 selectSession 同法：先按主进程级联规则本地算出 next，失败回滚）；或在 delete/setActive 返回后由 store 主动补拉一次 `browser.getState()` 对账。
- [x] **[低]** [已修复 2026-09-12 修复轮] L1：init 读盘窗口内激活会话，lastUrls 缓存未填，恢复成空白页而非上次打开页
  - 位置：`src/main/browser/registry.ts:299-315`（init 的 storeReady 异步缓存）、`src/main/browser/registry.ts:224-228`（ensureManager 读 lastUrls.get(id)，undefined 即 newTab(undefined)）
  - 描述：init 的 lastUrls 缓存由异步 loadSnapshot 填充；若用户在缓存填充完成前点击某会话，switchSession → ensureManager 读到 undefined，该会话懒创建 Tab 走 about:blank，丢失 PRD 3.1.4 的「上次打开页」恢复（且 initHandled 置位后不再补做）。窗口为数毫秒级（小文件读盘 vs renderer 加载+用户点击），概率极低。
  - 证据：`const lastUrl = lastUrls.get(id); manager.newTab(lastUrl && isOpenableUrl(lastUrl) ? lastUrl : undefined)`（registry.ts:226-227）。
  - 建议方向：ensureManager 对未命中缓存的 id 现读一次 store（loadSnapshot 已是回退安全的只读调用），或 switchSession 对「缓存未就绪」的首次激活做一次异步补读。
- [x] **[低]** [已修复 2026-09-12 修复轮] L2：销毁宽限期内 setStatus 幽灵回填已删会话的状态条目
  - 位置：`src/main/browser/registry.ts:207-217`（manager 快照接线 setStatus 无会话存活判断）、`src/main/browser/registry.ts:258`（destroySession 开头 deleteStatus）
  - 描述：deleteStatus(id) 之后、webContents 真正死透之前，垂死 manager 的快照事件（did-stop-loading、复生 newTab 的 emit 等）仍会触发 setStatus(id, ...) 把已删会话重新写回 statuses map 并推送，后续 getStatuses 永远带着幽灵 key（id 含时间戳不会复用，无法自然清除）。renderer 侧 applyStatuses 按已知会话 map，幽灵 key 无害，仅主进程状态面失真。

  - 建议方向：statuses 维护引入「已注销」判断（如 destroySession 置位后再收到该 id 快照直接忽略），或 setStatus 前校验 managers.has(id)。
- [x] **[低]** [已修复 2026-09-12 修复轮；复审 F1 指出首轮移入 fn 仍会在 saveSnapshot 失败时前移，已补正为 resolve 后置更新（见修复轮复审清单）] L3：flushReport 先更新 reported 缓存后落盘，写盘失败后去抖判据失真

  - 建议方向：把 reported.set 移入 mutateSnapshot 的成功路径（fn 内或 then 内）。
- [x] **[低]** [已修复 2026-09-12] L9：main.tsx init 链未加 .catch（用户点名复核项）

- [x] **[低]** [已修复 2026-09-12 修复轮] L11：应用退出不冲去抖定时器，最近 500ms 内导航的 lastUrl/pageTitle 丢失

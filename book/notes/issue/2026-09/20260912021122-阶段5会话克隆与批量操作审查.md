## 2. 专审清单逐项结论

### 2.1 close-then-copy 一致性

- [x] 销毁等待与 cp 时序：closeSession 内 `await killPartitionWebContents(...)` 完整等待（3s 宽限 × 3 轮重扫，最坏 ~9s+）后才进入 stat/cp；closeGracefully 的宽限超时分支发出强制 close 后同步 resolve（wc 可能未死透），该残余由 survivors 告警如实呈现，与 destroySession 同一接受度，未发现新的时序破坏。
- [x] killPartitionWebContents 抽取的逐行为等价：对照 9ed9bc5 原内联实现，循环边界（DESTROY_RESCAN_ROUNDS=3）、扫描谓词（`!wc.isDestroyed() && wc.session === target`）、survivors 复查与告警结构完全一致，仅文案参数化（nextLabel='清除' 时输出与原文逐字相同）；destroySession 的清存储/删目录步骤保持在共享函数之外，无语义漂移。
- [x] lastUrls 保留 vs 删除的分叉：destroySession 删（元数据已移除）、closeSession 保留（元数据仍在，切回按 lastUrl 重载）——分叉点与各自的元数据存续状态处处对齐；closeSession 关前冲刷（reportTimers 清理 + flushReport 在 managers.delete 之前调用，满足 flushReport 的注册表存在性判据）与随后的元数据 mutateSnapshot 排队顺序（flush 先入串行队列、克隆元数据后入）保证克隆取到冲刷后的最新值。flushReport 的 `.then` 回写 lastUrls 不检查 managers——对 closeSession 后的源会话恰好是期望行为（缓存续存）。
- 发现的问题：H1（见 3.1，激活侧 lastUrls 缓存缺口）、M1/M2（见 3.2/3.3）。

### 2.2 cp 细节

- [x] basename 排除误伤评估：Chromium 分区目录内名为 Cache / GPUCache / Code Cache / DawnGraphiteCache / DawnWebGPUCache 的目录均为纯可再生缓存；站点数据目录名（Cookies、Local Storage、Session Storage、IndexedDB、databases、File System、WebStorage、Service Worker/CacheStorage、Service Worker/ScriptCache 等）与排除集无交集，未发现误伤路径。filter 同时作用于文件，分区顶层不存在这些名字的文件，无实际影响。
- [x] 并发两次 clone 同一源：第二次 closeSession 对已关闭的源 no-op；两次 cp 各写各的独立目标目录、同读一个静止源，互相无干扰（各自的元数据 mutateSnapshot 经串行队列先后落盘）。
- [x] cp 失败残留清理：失败（含 dst 就位复核失败）先 `rm(dstDir, {recursive, force})` 再上抛，清理自身失败与复制失败均中文告警，链路闭合。缺口见 L1（元数据写盘失败分支的 dst 残留）。
- [x] 目标 id 撞目录：newId 出自单调 seq + 当期时间戳，本运行期内必不重复；既往落盘 id 已在生成时避开。仅理论缺口：跨运行期时钟回拨 + 与孤儿残留目录（此前克隆清理失败遗留）同 id 才可能撞，不可达量级，不立案。
- [x] 源目录不存在（从未激活过）：stat ENOENT → 跳过复制，产物空白环境；非目录（文件占用路径）显式拒绝并提示疑似数据损坏。isENOENT 判据单源，实现正确。

### 2.3 openUrlInSessions

- [x] newTab→detach 时序：manager.newTab 同步完成（view 创建 + activate 挂入 contentView + setBounds + loadURL 发起），同步返回后立即 detachActiveView——同一次主进程事件循环轮次内完成，无合成器绘制窗口，无视觉闪烁。
- [x] detach 精确性：detachActiveView 按 manager.getActiveWebContents() 的 webContents 身份在窗口子视图反查，同一时刻每个 manager 至多一个激活 view 挂在窗口上，且 webContents 不能跨 manager 共享——不会摘掉别的会话的 view。后台 manager 挂入瞬间应用 currentRect()（悬挂态正确传递），摘除后激活会话的 view 不受影响。
- [x] 对当前激活会话的重复调用：每次调用新增一个 Tab 并激活之（既有 Tab 保活），符合「各新建一个 Tab」语义。叠加瑕疵见 L2（从未激活会话多出一个空白初始 Tab）。
- [x] URL 已在 handler 层过 normalizeInput（scheme 白名单 http/https/file/about + 缺省补 https://），失败整单拒绝。

### 2.4 三 handler 守卫完备性

- [x] clone 的 id 注入面：校验时点（loadSnapshot）与落盘时点（mutateSnapshot）之间，源可能被改名（mutateSnapshot 重读盘取到最新值，正确）、被删除（`?? src` 回退校验时点快照值，分区副本已完整，注释已声明）、并发 create/clone 新增 id（均出自同一单调 seq，必不与 newId 相同；mutateSnapshot 串行队列无旁路）——推演成立。newId 在 mutateSnapshot 内不做二次查重的论证（单调 seq + 既往 id 已避开）成立。
- [x] deleteAll 空列表：`ids.length === 0` 提前返回 `{ok:true}` 不触发编排；与并发单删交错：无论先后，快照收敛到空、onAllDeleted 对已删 id 的 destroySession 幂等（manager 缺失时跳过杀 webContents，clearStorageData/rm 容忍不存在）；deleteAll 与并发 clone 交错时 cp 因源目录被 rm 失败 → 清残留 → 抛错 → 无孤儿元数据（失败路径干净）。
- [x] batchOpenUrl 整单校验：payload 形状（record + 非空 string[] + string url）、逐 id 存在性、normalizeInput 三道守卫齐全，任一不满足整单拒绝。校验与执行的 ms 级窗口为注释显式声明接受项；其最坏后果（孤儿 manager：后台 webContents 永久保活 + 已删分区目录被 fromPartition 惰性复活）记入 5 遗留观察，不重复立案。

## 3. 问题详情

### 3.1 高

- [x] **[高]** [已修复 2026-09-12，方案②] H1 克隆完成后激活新会话打开空白页，而非克隆的 lastUrl——「页面状态随行」确定性落空
  - 位置：`src/main/browser/registry.ts:344-345`（ensureManager 只从 lastUrls 内存缓存取初始 Tab 地址）、`src/main/browser/registry.ts:348-361`（补载仅在 `!lastUrlsLoaded` 的启动毫秒级窗口内生效）、`src/main/sessions.ts:212-225`（clone 的元数据 mutateSnapshot 落盘 lastUrl，但不通知 registry 刷新 lastUrls 缓存）
  - 描述：克隆链路为「clonePartition 复制分区 → mutateSnapshot 落元数据（lastUrl 已随行复制）→ 返回 renderer → setActive → switchSession(新 id) → ensureManager(新 id)」。ensureManager 的初始 Tab 地址取 `lastUrls.get(id)`——该缓存只在启动 preloadLastUrls 与 flushReport 回写时填充，**运行期新增的克隆 id 从不在缓存中**，且 `lastUrlsLoaded` 此刻必为 true（补载块不进入）→ `manager.newTab(undefined)` → about:blank。结果：克隆会话激活后显示「新标签页」，行内 pageTitle 却显示源的页面标题；要看到「上次打开页」只能重启应用（重启后 preloadLastUrls 从落盘读到克隆的 lastUrl，恢复正常）。与源会话形成不对称：源会话 closeSession 后 lastUrls 保留，切回即按 lastUrl 重载（设计目标），克隆自身反而空白。
  - 证据：registry.ts:344-345 `const lastUrl = lastUrls.get(id)` / `manager.newTab(lastUrl && isOpenableUrl(lastUrl) ? lastUrl : undefined)`；lastUrls 的全部写入点仅 registry.ts:119（preloadLastUrls）与 registry.ts:282（flushReport 的 then），均不可能包含运行期克隆 id；验收文档 book/notes/summary/20260912013740-*/20260912020317-阶段验收.md 用例 A2 明确期望「右侧为其浏览器并**自动加载 S1 的上次打开页**」；计划 2.3 数据原则「'页面状态'落在 lastUrl 单值恢复语义上」。
  - 复现路径（确定性）：任一会话导航至某页 → 行菜单「克隆会话」→ 数秒后克隆行入列并激活 → 右侧为新标签页（about:blank），非源会话上次打开页。
  - 建议方向：任选其一——① clone handler 落元数据后经新增 dep 回调通知 registry `lastUrls.set(newId, cloned.lastUrl)`（保持 sessions.ts 不 import registry 的分层）；② ensureManager 对缓存未命中且 lastUrlsLoaded 的 id 异步补读一次落盘（把现有补载块的触发条件从「未就绪」放宽为「缓存未命中」）；③ 克隆激活路径改由 registry 在 clonePartition 成功后顺带预热目标会话缓存。修复后用例 A2 应通过。

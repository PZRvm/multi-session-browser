## 2. 八项必查结论

### 2.1 重复代码

结论：发现 3 个问题（L1—L3）

- [ ] **[低]** L1：tmp+rename 原子写模式与 store.ts 重复
  - 位置：`src/main/browser/history.ts:171-186`（writeSession）；对照 `src/main/store.ts:141-154`（saveSnapshot）
  - 描述：`临时文件名 = target.${Date.now()}-${random}.tmp → writeFile → rename → 失败 unlink 清理` 的原子写序列在两处各写一份（第三处 persistence 经 store.ts 间接复用）。当前仅两处、域不同（sessions.json vs history/*.json），漂移风险低。
  - 证据：`history.ts:179-180` 与 `store.ts:147-148` 逐行同构；临时名生成、mkdir、清理 catch 结构一致。
  - 建议方向：出现第三个落盘文件时抽 `src/main/fs-utils.ts`（atomicWriteJson(target, data)）单源；本轮两处可接受。
- [ ] **[低]** L2：文件名安全正则与会话 id 正则双源
  - 位置：`src/main/browser/history.ts:61`（`SESSION_ID_FILE_RE = /^[A-Za-z0-9_-]+$/`）；对照 `src/shared/sessions.ts:36`（`SESSION_ID_RE = /^sess-[a-z0-9-]+$/`）
  - 描述：历史文件名校验自拟了更宽的正则而非复用 SESSION_ID_RE。语义上有差异（历史模块刻意不要求 `sess-` 前缀、允许 `_`），但两套规则并存，未来会话 id 字符集变化时可能单边漂移。
  - 证据：grep 确认两处定义；`history.ts:92-95` 用自拟正则拒绝拼接。
  - 建议方向：在 shared/sessions.ts 注释互指，或让文件名校验显式复用 SESSION_ID_RE 加 `_` 扩展并注明差异原因（当前注释已部分说明）。
- [ ] **[低]** L3：Toolbar 命中加粗渲染三重复制
  - 位置：`src/renderer/src/components/browser/Toolbar.tsx:300-337`（标题/网址/无标题网址三段各一份 splitByQuery().map() 渲染）
  - 描述：同一段「切分 → hit 加粗」JSX 复制三份，仅外层 span 类名不同。
  - 证据：三段 map 体逐字符相同（`part.hit ? <b className="chrome-omnibox-suggest-hit">…` ）。
  - 建议方向：抽一个 `HighlightedText({ text, query, className })` 小组件收敛。

### 2.2 权限漏洞

结论：已查，未发现问题

- getHistory 按 `event.sender` 作用域解析（`src/main/browser/ipc.ts:330-336`），renderer 不传 sessionId，无越权读他窗会话历史的通道；preload 仅白名单暴露两方法（`src/preload/index.ts`），未引入原始 ipcRenderer。
- 路径穿越：文件名经 `SESSION_ID_FILE_RE` 拒绝 `.`/`/`（`history.ts:92-95`），会话 id 来源为 registry 内部（落盘侧已有 SESSION_ID_RE 前置校验）。
- 无 SQL、无秘密、无新增依赖（package.json 的 diff 为用户既有 Windows x64 脚本改动，非本专项）。
- 附带观察（不构成漏洞）：历史条目 faviconUrl 为页面可控 URL，renderer 以 `<img src>` 渲染——与 TabStrip 同一先例；CSP `img-src https:` 会拦截 `file://` 图标（见 2.6 L6）。

### 2.3 竞态条件

结论：发现 1 个问题（L4）

- [ ] **[低]** L4：dropHistory 与在途懒加载的复活窗口
  - 位置：`src/main/browser/history.ts:246-256`（dropHistory）与 `:96-121`（loadSession/ensureLoaded）
  - 描述：会话删除时若该会话历史懒加载仍在途（读盘未返回），loadSession 完成后 `sessions.set` 会向已删除的会话复活一个内存 map（若读盘发生在 rm 之前，含陈旧条目）。后续无写入方（manager 已 dispose、无定时器）、无读取方（getEntries 不会再被调用），flushAll 只遍历 timers——复活数据滞留内存至进程退出，不回写磁盘、不外泄。
  - 证据：dropHistory 删除 `sessions`/`loads` 键后未使在途 promise 失效；loadSession 尾部无条件 `sessions.set(sessionId, …)`。
  - 建议方向：ensureLoaded 链内回填前比对 `loads.get(sessionId) === 本次 promise`（drop 后不相等即弃置），与 renderer refreshHistory 的 token 判据同构。
- 其余已查无问题：recordVisit 沿 ensureLoaded 单飞行链串行合并（防读盘竞态丢条目）；refreshHistory token + 会话双校验（`stores/browser.ts:102-119`）；applyHistoryChanged 与快照守卫同构双校验（`:128-145`）；overlay effect cleanup 杜绝计数泄漏（`Toolbar.tsx:82-87`）；init 失败路径退订 onHistoryChanged；克隆窗口期 cloningIds 守卫覆盖 destroy 路径。

### 2.6 边界遗漏（入参范围 / 空值 / 极值）

结论：发现 2 个问题（L5、L6）

- [ ] **[低]** L5：favicon 加载失败无 onError 回退，留 16px 空位
  - 位置：`src/renderer/src/components/browser/Toolbar.tsx:288-295`（`<img className="chrome-omnibox-suggest-favicon">`）
  - 描述：faviconUrl 为 `file://` 时被 CSP `img-src https:` 拦截、https 图标 404 时 `<img>` 加载失败——无 onError 处理，渲染为 16×16 空白框而非灰阶圆点占位（TabStrip 同款已知行为，先例一致但下拉行更窄、空位更可感）。
  - 证据：组件无 onError 属性；CSP 规则见 DESIGN.md「Chrome 框架」条目（img-src https:）。
  - 建议方向：onError 时切换到 favicon-dot 占位（受控 state 或 CSS 隐藏 img 显 dot）。
- [ ] **[低]** L6：超上限落盘文件（手工编辑）读入后未即时写回裁剪结果
  - 位置：`src/main/browser/history.ts:126-152`（parseStored/trimToLimit）
  - 描述：读盘时按 2000 条裁剪与去重仅作用于内存返回值，落盘文件保持原样，直到下一次 recordVisit 去抖写盘才收敛。功能正确（内存不变量成立），仅磁盘瞬时态偏大。
  - 证据：`loadSession` 只 `sessions.set`，不回写。
  - 建议方向：可接受现状（写放大不值得）；若要收敛，在 trim 生效时 scheduleWrite 一次。
- 其余已查：空串/纯空白输入规范化后低于阈值返回空（`omniboxSuggest.ts:57`）；visitCount/lastVisitedAt 的整数与有限性校验（`history.ts:46-58`）；重复 url 按 lastVisitedAt 取新（`:141-146`）；URL 长度恰为 2000 的边界放行、2001 拒绝（recordVisit 严格大于判断）。

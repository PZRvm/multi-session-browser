### L1：preloadLastUrls 共享 promise + ensureManager 异步补载 —— 成立，附 1 低

- [x] 核验通过项：
  - **共享 promise 语义**：`lastUrlsPreload` 缓存的 promise 经 `.catch` 转 `null` 恒不 reject；补载消费端 `if (!snapshot) return`，二次调用无副作用；catch 内 `lastUrlsLoaded = true` 防永久未就绪（registry.ts:89-105）。loadSnapshot 设计上不 reject，该 catch 属纯兜底，语义正确。
  - **init 交互**：init 与 ensureManager 复用同一 in-flight；`initHandled` 由显式 switchSession 置位后 init 的恢复跳过、补载照常执行——补载本身就是该次显式激活的恢复语义，二者不冲突也不双载（缓存已填时 `lastUrlsLoaded` 必为 true，补载块不进入；manager 已存在时 ensureManager 早退，无重复补载）。
  - **补载时序对「切走」安全**：补载回调对已转后台的 manager 在保活 wc 上 loadURL 属期望行为（切回即见页面），快照推送经 `sessionId === activeSessionId` 过滤、setStatus 经 managers.has 守卫（L2），无串台。

  - **补载对「已死 wc」安全**：`buildSnapshot` 跳过 destroyed wc（manager.ts:102），activeTab 缺失即 return；`wc && !wc.isDestroyed()` 双保险。
- [x] **[低]** [已修复 2026-09-12 阶段5修复轮] F2：补载回调缺「会话已注销」守卫——销毁竞态下会对垂死 wc 发起 loadURL（回调首行补 managers.has(id) 守卫；阶段 5 H1 修复已将该回调重写为 ensureManager 内联现读，守卫落在新位置）

### L3：lastUrls/reported 移入 mutateSnapshot 临界区 —— **未达修复声明（中）**

- [x] **[中]** [已修复 2026-09-12] F1：写盘失败时判据仍然前移，「失败不前移可重试」的注释承诺与实现不符——原 L3 缺陷在 saveSnapshot 失败路径原样存在
  - 位置：`src/main/browser/registry.ts:212-223`（flushReport）、`src/main/store.ts:104-116`（mutateSnapshot 的 fn/save 顺序）
  - 描述：mutateSnapshot 的实现是 `loadSnapshot → fn → saveSnapshot`——**fn 在 saveSnapshot 之前执行**。把 `lastUrls.set`/`reported.set` 移入 fn 只是把写入点从 flushReport 同步时刻推迟到临界区 load 完成后，saveSnapshot reject（唯一真实失败模式，loadSnapshot 设计上不 reject）时两者**已经执行**。注释「写盘失败（reject）时两者不前移，下次快照仍判‘有变化’会重试，判据与磁盘不脱节」描述了不存在的运行时行为：写盘失败后判据照旧前移、同值快照不再调度、磁盘停留旧值——正是原 L3 要修的缺陷。修复实际达成的只有两点：target 不存在（删除竞态）分支不前移（该场景 destroySession 本会 reported.delete，原行为也无害）；lastUrls 缓存值与磁盘截断值一致。
  - 证据：store.ts:105-109 `const snapshot = await loadSnapshot(); const result = await fn(snapshot); await saveSnapshot(snapshot)`；registry.ts:217-218 注释原文；旧清单 L3 建议方向原为「把 reported.set 移入 mutateSnapshot 的成功路径（fn 内或 then 内）」——then 内才成立，fn 内不成立。
  - 建议方向：fn 返回 target 是否存在的标志，在 `mutateSnapshot(...).then((found) => { if (found) { lastUrls.set(...); reported.set(...) } })` 中落缓存（reject 路径不进 then，天然满足「失败不前移」）；或给 mutateSnapshot 增加写后回调。修复后应把旧清单 L3 的勾销改为部分完成再重新勾销。
  - 附带观察（不单列）：reported.set 推迟到 fn 执行点后，flushReport 调用到 fn 执行的排队间隙内到来的快照事件会按旧 reported 重复 scheduleReport——幂等写、无害，但属行为微变。

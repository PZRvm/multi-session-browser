## 2. 八项必查结论

### 2.1 重复代码

结论：发现 1 个问题（低）。

- [ ] **[低]** 中点换位判定逻辑存在两处同源实现
  - 位置：`src/renderer/src/components/browser/useTabReorder.ts:63-79`（move 的相邻单步判定）与 `src/renderer/src/components/browser/TabStrip.tsx` 悬停插入指示器 effect（按 dragCursorX 对全量 Tab 中点循环定位 index）
  - 描述：两处都是"光标 clientX 对各 Tab 中点判定插入意图"，但形态不同——hook 是相邻单步换位（一次 move 至多一位）、指示器是全量 index 定位（可一次跳任意位）。目前无注释互指来源，后来者易把两处当独立算法各自演化。
  - 证据：两段代码均取 `getBoundingClientRect().left + width / 2` 与光标比较。
  - 建议方向：两处补一行注释互指（"中点判定语义与 X 处同源，差异为单步/全量"）；若未来指示器也要单步化再考虑提取公共函数，当前不强制。

其余核对：useTabReorder 与 useSessionDragReorder 结构对称但引擎不同（指针捕获 vs HTML5 DnD），属 steps 文档冻结的设计对称而非复制；applyTabOrder 提取后 moveTabToWindow 内嵌循环已删除，无双份。

### 2.2 权限漏洞

结论：已查，未发现问题。

- 新通道 `browser:reorder-tabs` 命令口径完整：`requireScope`（主窗零会话拒绝）+ 结构守卫（ids 非空数组、每项 string、量级按该窗快照 2 倍封顶）+ manager 全序整单校验（长度一致 + 无重复 + 每项为本作用域 Tab——未知 id 与越权 id 一并拒绝，抛字典文案）。
- 页面 webContents 无 preload 不可触达；重排为纯内存序变更，无落盘、无路径拼接、分区无关。
- preload 暴露面仅增 `reorderTabs` 一方法，`index.d.ts` 同步，无越权能力。

### 2.3 竞态条件

结论：已查，未发现问题。

- **applyTabOrder 共用改造的行为等价性**（重点核查项）：moveTabToWindow 旧实现只 delete/set「本 Tab + 插入位之后」的键，新实现按全序 delete/set 含插入位之前的键——全局 Map 迭代序确实会变（其他窗口键与作用域键的交错位置不同），但唯一消费方 `buildSnapshot` 按 windowId 过滤输出，**作用域内相对序两实现完全一致**（前段→本 Tab→后段），其他窗口键彼此相对序未被触碰——对全部快照输出、邻位补位取序、persistence 归并序均无影响，等价成立。
- **升级 tear-off 两段提交**：commitIfMoved await IPC 后才 engageDrag；renderer→main 的 dragStart 在重排 IPC 之后到达，主进程按序处理，tear-off 起点必为新序。
- **pointerup 与隐式失捕的顺序安全**：松手时 pointerup 先派发（mode 复位 idle），React 提交移动 DOM 触发的隐式失捕事件后到时 mode 已 idle，`onLostPointerCapture` 走无操作分支——不会对已收尾手势二次 finishReorder。
- **重捕获循环**：向右连续换位时每次 DOM 移动各触发一轮失捕→`setPointerCapture` 重捕获，事件流无缝恢复；重捕获抛错（指针失效）兜底 finishReorder。
- 多触点：pointerId 校验挡掉第二触点；拖拽中快照推送由 `applySnapshot` 既有守卫消化。

### 2.4 事务边界（落盘原子性与级联一致性）

结论：已查，未发现问题。

- 本专项零落盘（Tab 列表不持久化口径不变）；重排为纯内存 Map 序变更，失败不落半态（整单拒绝时 Map 未动）。
- applyTabOrder 对不存在键跳过、作用域外键零触碰——与 closeTab/tearOff/destroyTabsInWindow 的级联清理无交错。

### 2.5 通知遗漏

结论：发现 1 个问题（低）。

- [ ] **[低]** 重排提交失败无用户可见反馈
  - 位置：`src/renderer/src/components/browser/useTabReorder.ts:110-118`（commit 的 catch 返回 false，调用方 finishReorder `void` 不消费）
  - 描述：整单拒绝（拖动中 Tab 被关等竞态）或 IPC 失败时，store 只 console.error，UI 表现为"顺序没变"——靠回滚本身隐式表达。会话列表重排先例有 `onReorderFailed` 回调做显式反馈，本实现未对齐。
  - 证据：finishReorder 对 `reorderApi.commit()` 的 Promise 结果不读取；失败路径无 message/动画反馈。
  - 建议方向：正常路径不会失败，竞态失败概率低且"回滚原位"即自然结果——可接受现状并注释冻结；若要对齐先例，commit 返回 false 时给一次性轻反馈（如源 Tab 短暂 shake 或不 Feedback 仅留注释），任选其一。

其余核对：store 失败 console.error 留痕；成功路径快照全序覆盖推送，UI 无脱节。

### 2.6 边界遗漏（入参范围 / 空值 / 枚举）

- i18n 键 zh/en 双语落库、typecheck 完备性通过。

### 2.7 复杂度是否增加

结论：发现 1 个问题（低）。

- [ ] **[低]** onPointerMove 分流分支内嵌 Esc 监听定义与挂载
  - 位置：`src/renderer/src/components/browser/TabStrip.tsx` onPointerMove 的 reordering 分支（JSX 属性回调内定义 `onReorderEsc` 并 `addEventListener`，约 20 行）
  - 描述：意图分流的核心判定（水平主导 + 栏矩形）与 Esc 挂载细节混在同一内联块， JSX 回调嵌套函数定义，阅读成本偏高；同文件 finishDrag/engageDrag 已有"逻辑提取为组件方法"的惯例。
  - 证据：engageDrag（tear-off 路径）的 Esc 挂载在组件方法 engageDrag 内，两态风格不一致。
  - 建议方向：提取 `beginReorder(e)` 组件方法（begin + setDragOffsetX + Esc 挂载），onPointerMove 分流分支一行调用，与 engageDrag 对称。

其余核对：manager 净变化为提取共用函数 + 一个校验前置的原语，复杂度下降；TabItem 四态状态机各态收尾路径齐全（up/cancel/lostcapture/Esc），注释完整；分层未破坏（事实源主进程、renderer 纯镜像 + 本地瞬态）。

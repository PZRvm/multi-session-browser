## 1. 审查摘要

本专项为 Electron 内建 findInPage 引擎的三进程接线（4 条 IPC 通道 + 键位解禁 + renderer 查找瞬态 + 停靠式 FindBar），并含两项执行期加固（0 命中自动重搜、find-request 推送前主进程归还 shell 焦点）。整体质量良好：作用域守卫复用既有 resolveSenderScope 链路、越权面为零、竞态防护（关栏后迟到回执守卫、重试的 query 比对、tick 幂等）到位、契约三处对齐、文档同步完整。最需要关注的一项：manager.activate / registry.detachActiveView 对被摘 webContents **无条件** stopFindInPage('clearSelection')，按 API 文档语义会清除页面选区——若页面本无 find 会话，可能误清用户手动选择的文本（切 Tab/切会话后选区丢失），需实测确认并考虑按 find 会话标记门控。

  - 描述：ipc.ts 两处推送桥现为同构的「windowForId → focus() → send()」五行块；registry.ts ensureManager 内 focusAddress / findRequest / findResult 三段订阅各自重复计算同一 `bound` 会话归属守卫（三连同款三元表达式）。

### 2.2 权限漏洞

结论：已查，未发现问题。

- 4 条新通道全部经 `requireScope`/`resolveScope` 按 event.sender 作用域路由（ipc.ts:366 findStart、:384 findStop），与既有命令同规，无越权旁路。
- findStart 入参运行时守卫齐全：isRecord + text string + 非空 + ≤ FIND_TEXT_MAX（ipc.ts:373-374）；forward/findNext 以 `=== true` 严格归一（ipc.ts:375-376），垃圾值落 false 安全缺省。
- findStop 的 action 白名单收敛为两枚举（ipc.ts:387-388），其余一律 clearSelection。
- find-request 只可能由真实键盘事件触发（before-input-event 是浏览器层事件，页面脚本无法伪造），registry 侧再过会话归属守卫，定向推送不可被页面滥用为弹栏攻击面。
- preload 无新增白名单外暴露（findStart/findStop/onFindRequest/onFindResult 四方法均为窄签名）；无依赖变更、无路径拼接、无秘密输出。

### 2.3 竞态条件

结论：已查，未发现问题。

- 关栏后迟到的 found-in-page 回执被 `if (!get().findOpen) return` 拦截（stores/browser.ts:325-326），不复活旧态。
- 0 命中自动重搜的时序闭合：捕获期与触发期双重比对 `findRetryQuery !== get().findQuery` / `findRetryQuery === query`（stores/browser.ts:333-341），150ms 窗口内用户继续输入即作废；query 变化在 searchFind/openFind 重置预算（:524-527、:504），无跨会话残留（模块级变量仅存 query 字符串，无回调句柄）。
- 快照失效守卫（applySnapshot 内 findInvalidated/findNavigated）在 set 的同一原子更新里关栏/复位，与推送到达顺序无关；高亮清理由主进程摘 view 源头保证（manager.activate:316-318、registry.detachActiveView:295-297），renderer 不依赖 IPC 时序。
- 监听器生命周期：found-in-page 每 Tab 挂一次随 webContents 销毁；ipc 层两桥随 registerBrowserIpc 单次注册；FindBar 的 setTimeout 在闭包内自守卫（findOpen/query 复验），窗口关闭随 renderer 消亡，无泄漏路径。
- findRequestTick 单调递增计数信号，重复推送幂等（效果只是再聚焦全选一次）。

### 2.6 边界遗漏（入参范围 / 空值 / 极值）

结论：发现 3 个问题（L5、L6、L7）。

- [ ] **[低] L5：renderer 侧无 FIND_TEXT_MAX 预防，超长输入静默死路**
  - 位置：`src/renderer/src/stores/browser.ts:528-529`（searchFind 直发）与 `src/shared/browser.ts:178`
  - 描述：FIND_TEXT_MAX=200 只在主进程守卫（ipc.ts:374 超长抛 invalidParams）；renderer 未引用该常量。用户粘贴 >200 字符进查找框时：UI 如常显示文本，findStart 被拒且 `.catch(() => {})` 静默，计数永远 0/0 红显且无任何解释——看起来像功能坏了。
  - 证据：`grep -rn "FIND_TEXT_MAX" src/` 仅命中 shared/browser.ts 与 main/browser/ipc.ts，renderer 零引用。
  - 建议方向：searchFind 发送前对 query 做 `query.slice(0, FIND_TEXT_MAX)` 截断（shared 常量 renderer 可直接 import），或超长时行内提示；两者取其一即可闭环。
- [ ] **[低] L6：0/0 红显在首个回执到达前闪烁**
  - 位置：`src/renderer/src/components/browser/FindBar.tsx:35、65-68`
  - 描述：`noMatch = findQuery.length > 0 && findMatches === 0` 在 searchFind 复位计数后、found-in-page 首个回执前即为真——每次按键到回执的间隙（约 50-200ms）计数区闪一帧红 0/0，连续输入时红闪频繁。Chrome 的 0/0 红显只在结果确认后出现。
  - 证据：searchFind 立即 set findOrdinal/findMatches 归零（stores/browser.ts:527），渲染同步变红；回执到达才转真值。
  - 建议方向：store 增一个「结果已到达」标志（searchFind 置 false、onFindResult 置 true），noMatch 判定加该标志；或暂存 finalUpdate 态。改动面约 4 行。
- [ ] **[低] L7：查找输入框定宽 180px，长关键词可视截断且无提示**
  - 位置：`src/renderer/src/assets/app.css:1159`（`.chrome-find-input { width: 180px }`）
  - 描述：固定宽度下长关键词在框内滚动显示，光标外内容不可见，也无 title/任何提示；测试人员粘贴长报错串定位时体验受损（Chrome 的 find 框随内容与窗口弹性）。
  - 证据：app.css:1159 `width: 180px`（无 max-width、无弹性）；FindBar.tsx 输入框未设 title。
  - 建议方向：改 `width: 240px; max-width: 40vw` 一类弹性度量（impeccable token 口径内），或至少输入框悬停 title 全文兜底。

结论：发现 1 项观察（不列为待办）+ 1 个中危跨面问题（M1，见下）。

- [ ] **[中] M1：摘 view 前无条件 stopFindInPage('clearSelection') 可能清除用户手动选区**
  - 位置：`src/main/browser/manager.ts:316-318`（activate 切 Tab）；`src/main/browser/registry.ts:295-297`（detachActiveView 切会话/后台化）
  - 描述：两处对被摘 webContents 无条件调用 `stopFindInPage('clearSelection')`。按 Electron 文档，clearSelection 语义是「清除页面选区」——若该 Tab 从未进行过查找，页面无 find 会话，此调用是否为无操作未经实测；若它同样清除用户手动选择的文本，则「切 Tab/切会话丢失文本选区」是对既有卖点（页面状态保留，PRD 3.6.1/4.2）的回归。
  - 证据：manager.ts:317 `if (!prev.view.webContents.isDestroyed()) { prev.view.webContents.stopFindInPage('clearSelection') }`——无 find 会话标记门控，每次激活切换必调；registry.ts:297 同款。Electron webContents 文档 stopFindPage(action)：'clearSelection' - Clear the selection in the page。
  - 建议方向：TabEntry 增 `findActive` 标记（found-in-page 事件置 true——该事件仅 findInPage 触发，是最廉价的信号源），activate/detachActiveView 仅在标记为真时 stopFindInPage 并复位；同时顺带解决「无谓调用」本身。修复前先做一次隔离实例实测（切 Tab 后回切，手动选区是否丢失）确认影响等级。

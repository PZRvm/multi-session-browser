### 2.3 竞态条件

结论：发现 3 个问题（均低危，其中 2 项为既有模式的延续）

- [ ] **[低]** flushReport 的 .then 在会话销毁竞态下回填缓存，留下死条目
  - 位置：`src/main/browser/registry.ts:313-319`（restoreSets.set / reported.set 的成功回调）
  - 描述：destroySession 同步删除 restoreSets/reported 条目后，在途 mutateSnapshot 的成功回调仍会 `restoreSets.set(id, ...)` 重新写入。id 含时间戳不复用，条目成为永不清除的死数据（内存级，非功能错误）
  - 证据：v2 的 `lastUrls.set(id, saved)` 同模式（registry.ts 旧代码），本阶段将该模式扩展到了 restoreSets 与 reported
  - 建议方向：.then 内先判 `managers.has(id)` 再回填（与 flushReport 入口的判据对齐）
- [ ] **[低]** 补载径 loadURL 未完成即退出的毫秒窗口会把首 Tab 落盘回退为 about:blank
  - 位置：`src/main/browser/registry.ts:214-219`（applyRestore 的 hasLiveBlankTab 分支）
  - 描述：loadURL 是异步导航，did-navigate 前 quit 会以快照 url=about:blank 冲刷落盘，下次重启首 Tab 退化为空白页（其余 Tab 不受影响）
  - 证据：manager 的 url 字段仅在 did-navigate/did-navigate-in-page 后更新（manager.ts:194-203）
  - 建议方向：属"URL 级恢复尽力而为"口径内的既有类别（v2 lastUrl 同窗口）；若要收敛，可在恢复完成前抑制该会话的上报落盘（armed 标志），或在 flushReport 判"恢复进行中"跳过
- [ ] **[低]** 批量打开"从未激活过的克隆会话"会整体丢弃其恢复集
  - 位置：`src/main/browser/registry.ts` openUrlInSessions 复用分支（约 :640-660）与 pendingBackfill 资格撤销的联动
  - 描述：克隆产物落盘有 tabs 但无缓存条目，批量打开先经 ensureManager 建一个空白 Tab，复用路径 loadURL(批量地址) 并撤销补载资格——源的 Tab 列表从此不再恢复。与 v2"lastUrl 被批量地址覆盖"行为一致，但 v3 下"有恢复集却被静默清空"语义变重了（v2 只丢一页，v3 丢整组）
  - 证据：R1 定案的撤销机制原注释（registry.ts:239-243）；v3 恢复集走 applyRestore 多开，被撤销后无其他恢复路径
  - 建议方向：语义裁决项——复用分支对"落盘有 tabs 的会话"跳过复用（先恢复再叠加新 Tab），或维持现状并在 DESIGN.md「克隆语义边界」注明；建议前者

### 2.6 边界遗漏（入参范围 / 空值 / 极值）

结论：发现 2 个问题

- [ ] **[低]** tabs 空但 lastUrl 非空的不一致落盘数据被静默接受
  - 位置：`src/main/store.ts` restoreTabs（约 :59-105）
  - 描述：v3 元素 tabs 为合法空数组时直接接受（不回退 lastUrl 派生、不告警）。写侧恒出"tabs 非空 ⇔ lastUrl 非空"（live manager ≥1 Tab），出现该组合只可能来自手工编辑/损坏，静默接受会让用户误以为恢复集丢了
  - 证据：`tabs = []` 通过 `every(isStoredTab)` 空真判定，restoreTabs 返回空列表；applyRestore 走空白 Tab 分支，lastUrl 被无视且无日志
  - 建议方向：restoreTabs 对"version≥3 且 tabs 为空数组且 lastUrl 非空"告警一次（是否回退派生可再裁决）
- [ ] **[低]** tabsKeyOf 以 '\n' 连接 URL 存在指纹歧义
  - 位置：`src/main/browser/registry.ts:157-159`
  - 描述：URL 列表 join('\n') 作变化指纹，构造数据（URL 含原始换行）可产生跨列表碰撞，理论上让去抖判据漏判一次落盘；实际 URL 经 Chromium 规范化不含换行，仅磁盘被手工构造时可触发
  - 证据：`['https://a/\nb']` 与 `['https://a/', 'b']` 的 tabsKey 同为 `"0:https://a/\nb"`
  - 建议方向：改用 `JSON.stringify(tabs)` 或长度前缀拼接，消除歧义

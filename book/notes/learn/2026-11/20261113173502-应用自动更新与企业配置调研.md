> 需求来源：启动检查 GitHub 新版本，左上角和设置页提供可配置的更新入口；应用内下载、确认后重启安装，配置由开发/构建统一控制。

## 1. 需求理解

### 1.1 功能目标与功能点

测试人员启动应用后即可知道是否有新版本，在应用内下载，由本人决定何时重启安装。正式发布只构建公开版；公司使用场景只在本地调试打包时验证隐藏入口等配置，不维护独立的公司发行版。普通用户不能从设置中修改入口配置。

| 编号 | 功能点 | 已确认的行为 |
| --- | --- | --- |
| F1 | 启动检查 | 每次启动应用时检查新版本 |
| F2 | GitHub 更新来源 | 从 GitHub Releases 获取应用发布版本和更新文件 |
| F3 | 左上角更新提示 | 主窗口和独立窗口都增加入口；Windows 放在左上角功能区右侧，macOS 无需这一 Windows 专门处理 |
| F4 | 应用内下载 | 从更新入口发起下载，在应用内完成 |
| F5 | 确认重启安装 | 下载完成后，由用户确认，再重启并安装 |
| F6 | 设置页更新入口 | 设置页提供更新按钮；建议承载手动检查、下载和重启安装 |
| F7 | 两处入口可配置 | 左上角入口、设置页入口分别提供显隐配置；两处均隐藏时，不检查、不下载、不安装更新 |
| F8 | 配置与发布方式 | 配置由开发/构建统一控制；本地可打包测试隐藏态，GitHub 正式发布只打公开版 |
| F9 | macOS 正式签名 | 用户已选择签名；继续从 GitHub 分发，不要求上架 App Store |

已确认的首期范围：Windows x64、macOS arm64/x64 稳定版；不定时轮询、不自动后台下载、不降级、不更新插件。左上角入口只在存在可更新版本时显示；发现新版本后点击下载，下载完成由用户确认重启安装。

配套行为如下；其中“稍后安装、普通退出不安装”已获用户确认，其余实现细节在开发计划中展开：

- 启动检查在后台执行，不阻塞窗口和会话恢复；每个应用进程启动检查一次，重开窗口不重复检查。
- 只自动检查；点击“更新”才下载。展示下载进度、失败重试和“重启安装”，不强制退出。
- “稍后”之后，普通退出也不自动安装，保留用户确认安装的语义。
- 根据两处显隐配置推导更新能力，双隐藏时不发更新联网请求，不另加用户可操作的总开关。

调研阶段只产出文档；功能实施按 **L**：涉及共享 IPC 契约、sender 权限和退出生命周期，命中[始终按 L 的规则](../../../guidelines/task-tiers.md)。用户已确认需求并要求编写 Step 0 与开发计划，本轮停在规划阶段。

### 1.2 未知点清单

- [x] 如何隐藏入口且让普通用户无法从设置恢复？使用构建期策略，主进程执行限制，见 3。

### 1.3 拆分判断

拆成三个单元：更新引擎与发布链、分发配置、界面与 IPC。前两个可独立确定；界面与 IPC 依赖引擎状态和策略结果。更新只处理应用程序包，保持现有会话 partition、WebContentsView 和 DevTools 归属规则。

## 2. 调研单元：更新引擎与 GitHub 发布链

### 2.1 该部分要做什么

检查版本、下载对应系统和架构的应用包、校验下载内容、准备安装；让现有 GitHub Release 同时发布更新器需要的附件。保留现有 `dev → main` 发布入口和草稿校验流程。

### 2.3 候选方案

**方案 A：electron-updater + electron-builder GitHub provider，推荐。**

库负责版本比较、平台选择、下载、校验和安装；主进程控制检查和安装时机。当前依赖和 NSIS 安装包可复用。依据：[v26 自动更新文档](https://www.electron.build/v26/docs/features/auto-update/)、[GitHub provider 配置](https://www.electron.build/v26/docs/publish/#github)。

**方案 B：Electron 内置 autoUpdater + update-electron-app。**

Electron 官方提供更新服务和封装，适合按其约定发布的公开 GitHub 应用。它基于 Electron 原生更新器；Windows Squirrel 路径与本项目已有 NSIS 不匹配，默认后台下载、周期检查的流程也需改造。依据：[Electron 更新教程](https://www.electronjs.org/docs/latest/tutorial/updates)、[autoUpdater 平台说明](https://www.electronjs.org/docs/latest/api/auto-updater/)、[update-electron-app](https://github.com/electron/update-electron-app)。

**方案 C：GitHub Releases API 检查，手写下载及替换程序。**

API 能读取版本和附件，但完整需求还需要自研跨平台安装、权限、签名验证、失败恢复及重启处理。仅“提示新版本并跳发布页”适合这条轻量路径；用户已确认应用内安装，不选。依据：[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)。

### 2.4 可行性分析

| 维度 | A：electron-updater | B：原生更新器与封装 | C：自行实现 |
| --- | --- | --- | --- |
| 技术匹配 | 已有依赖；NSIS 可沿用；macOS 需 ZIP 和稳定签名 | 需适配更新服务与 Windows 产物，签名限制仍在 | 检查可行，安装部分维护面大 |
| 规则冲突 | 主进程接入，不触碰会话分区 | 可遵守分层，但需改变打包约定 | 能遵守分层，仍需独立处理程序替换安全性 |
| 成本 | MIT，现有安装体积中已含库；主要工作是接线及发布附件 | 官方项目、MIT；增加依赖和打包调整 | 省更新库的收益有限，跨平台安装全部自担 |

### 2.5 结论与实施建议

**结论：采用现成方案，复用锁定的 electron-updater 6.8.9。** 本需求不要求升级库，也不需要额外更新服务器。

引擎建议：

1. 主进程新增 `src/main/updates.ts`，持有唯一更新器实例。启动只调用 `checkForUpdates()`；不采用同时发系统通知的便捷调用。
2. 明确设 `autoDownload=false`、`autoInstallOnAppQuit=false`、`allowPrerelease=false`、`allowDowngrade=false`。用户点击后才 `downloadUpdate()`，确认后才 `quitAndInstall()`。这些能力已核对本机 6.8.9 的 `AppUpdater.d.ts`、`BaseUpdater.js` 和 `MacUpdater.js`；macOS 下载事件后还有原生更新器交接阶段，不能把“下载完成”当成“安装已成功”。
3. 生产启动由 `src/main/index.ts` 在窗口可用后安排检查，失败不阻断启动；开发态默认不检查真实源。更新器使用独立的更新网络上下文，不借用任一 `persist:sess-<id>` 的 Cookie 或代理。

发布链必须同时调整：

| 文件/环节 | 建议改动 |
| --- | --- |
| `electron-builder.yml` | 将 publish 改成 GitHub，明确 `owner: PZRvm`、`repo: multi-session-browser`；保留 appId；macOS 显式构建 DMG + ZIP，ZIP 文件名包含版本和架构 |
| `.github/workflows/release.yml` | 收集安装包、更新用 ZIP、`latest.yml`、`latest-mac.yml` 及所生成的 blockmap；继续由汇总发布任务统一上传，构建任务保留 `--publish never` |
| 多架构汇总 | 两个 macOS job 都可能生成同名 `latest-mac.yml`。先按架构分目录下载，校验版本一致，再合并 `files`；上传单一清单，保留兼容字段并校验每个 URL、大小和 SHA-512，不使用同名覆盖后的结果 |
| `scripts/release.mjs` | 扩展精确附件名单；新附件也纳入现有 SHA-256 对账；公开前验证清单引用的文件齐全、架构齐全，不接受仅上传 YAML 而缺实际 ZIP |
| `.github/workflows/extensions-release.yml` | CRX 发布显式 `--latest=false`；应用发布保留 `make_latest=true`。现存 Latest 也须在实施/发布阶段校正，本轮未修改远端 |
| `.github/RELEASING.md` | 补充更新附件、签名配置、首个带更新器版本及失败处理步骤 |

多架构清单结论来自本机 `app-builder-lib/out/publish/updateInfoBuilder.js`：macOS 清单名不按架构区分，内部汇总按 `files` 合并；`electron-updater/out/MacUpdater.js` 按文件名中的 `arm64` 识别架构。`PublishManager.js` 显示禁止上传与生成更新信息是分开的，所以无需为生成清单取消 `--publish never`。这些是源码核对结果，仍需打包验证。

Latest 问题直接影响推荐方案：6.8.9 的 `GitHubProvider.js` 在稳定版模式读取 GitHub Latest，再读取该 Release 的更新清单；它不会自动从 CRX 发布回退到最近的应用发布。[GitHub CLI](https://cli.github.com/manual/gh_release_create)支持显式禁止插件成为 Latest。若将来无法保证这条发布约定，再考虑独立的应用更新仓库；首期不增加仓库或自定义 provider。

**已确认决策：macOS 采用正式签名，继续通过 GitHub Releases 分发，无需上架 App Store。** 实施按 Developer ID Application 签名路径设计。[Apple Developer ID 文档](https://developer.apple.com/developer-id/)明确面向 Mac App Store 之外的软件分发；获取该证书需要 Apple Developer Program 账号。签名证明发布者身份，公证是 Apple 对站外分发包的安全检查，上架 App Store 是另一个分发渠道，三者不可混同。

macOS 自动安装的签名要求来自 [Electron autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater/#macos)；[Squirrel.Mac 验签实现](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/SQRLCodeSignature.m)会用当前应用的 designated requirement 验证新包。**根据这一机制推断，当前 ad-hoc 签名不能仅凭完整性检查就承诺跨版本可更新。** 正式发布保持稳定签名身份，并按[Electron 签名说明](https://www.electronjs.org/docs/latest/tutorial/code-signing)和[electron-builder 签名与公证文档](https://www.electron.build/v26/docs/features/code-signing/)准备发布配置；公证的具体接入在实施设计阶段确定。证书、私钥和密码仅在实施时通过安全渠道及 CI Secrets 配置，本轮不收集、不写入仓库。

本次签名决定针对上述 macOS 自动安装前置条件；Windows 是否接入正式代码签名单列设计，不据此视为已经确认。Windows NSIS 可先验证现有未签名链，但不能据此宣称具备发布者身份验证。

## 3. 调研单元：企业分发配置

### 3.1 该部分要做什么

统一控制更新能力和两个入口。配置属于开发/构建策略，界面只读；主进程检查策略，不能只在 React 中隐藏按钮。双入口均隐藏时彻底停止更新。

### 3.2 项目现状

- [settings.ts](../../../../src/main/settings.ts)把主页、语言、截图/录屏显隐写入 `userData/settings.json`；[设置契约](../../../../src/shared/settings.ts)及[PaneBrowsing](../../../../src/renderer/src/components/settings/PaneBrowsing.tsx)允许用户修改。这套写接口不适合本次配置控制权要求。
- [electron.vite.config.ts](../../../../electron.vite.config.ts)统一构建 main/preload/renderer；[electron-builder.yml](../../../../electron-builder.yml)负责分发，尚无企业更新策略。
- [electron-vite 5 官方文档](https://electron-vite.org/guide/env-and-mode)支持主进程专属构建变量和 mode；更新策略不必通过 renderer 环境变量分散维护。

### 3.3 候选方案

**方案 A：构建期策略，推荐。** 在 `build/update-policy.json` 定义公开版默认策略，主进程构建时读入并固定；本地调试打包可用主进程构建变量覆盖显隐值。正式 CI 显式使用公开版配置，不增加公司版构建矩阵、独立包名或发布附件。普通设置页不提供修改口。依据：[electron-vite 环境变量与 mode](https://electron-vite.org/guide/env-and-mode)。

**方案 B：部署期受管配置文件。** 使用同一个安装包，由管理员在系统受管目录部署策略，主进程启动读取。需要确定 Windows/macOS 路径、文件权限及优先级。electron-builder 的 [extraResources](https://www.electron.build/v26/docs/contents/#extraresources)可随包附带默认配置，但 macOS 安装后修改已签名应用包内的文件可能破坏签名；真正的部署覆盖文件应放在包外。

### 3.4 可行性分析

| 维度 | A：构建期策略 | B：部署期受管文件 |
| --- | --- | --- |
| 技术匹配 | 适合本地测试隐藏态、正式只发公开版；不增加运行期读盘机制 | 适合同一包在部署后改变策略，当前不需要 |
| 规则冲突 | 无用户写接口，主进程执行，与当前分层一致 | 必须避开用户可写设置文件和已签名应用包 |
| 成本 | 无新依赖，随构建审查和验证 | 无需专用库，但增加权限、损坏配置及升级保留规则 |

### 3.5 结论与实施建议

**结论：借鉴思路手写，以构建期策略作为首期配置。** 暂不引入通用企业策略框架。

用户已确认“双入口隐藏即不更新”，配置可以收敛为两个布尔项：

| 配置项（拟定名） | 公开包建议值 | 语义 |
| --- | --- | --- |
| `showHeaderEntry` | `true` | 是否允许主窗口及独立窗口左上角显示更新状态 |
| `showSettingsEntry` | `true` | 是否显示设置页更新行及按钮 |

只要至少一个入口允许显示，每次应用启动检查一次；两项都为 `false` 时，不初始化联网更新流程，检查/下载/安装命令均拒绝执行。无需另设 `enabled` 和 `checkOnStartup` 配置，避免出现“入口全隐藏仍在更新”的组合。配置非法时构建失败，不能悄悄恢复为公开版默认值。

公开版两项默认 `true`；本地需要验证公司使用场景时，打包覆盖为所需隐藏态。测试覆盖值不得改变上传后的正式发布配置；GitHub CI 只构建和发布公开版，不新增公司版发布流程。

新增 `src/main/updatePolicy.ts` 统一计算有效策略；新增 `build/update-policy.json` 保存构建输入。renderer 只收到入口能力，不接触可写策略。更新源继续以 `electron-builder.yml.publish` 为单源，由其生成 `app-update.yml`；首期可配置 GitHub owner/repo，不在设置页提供地址输入，也不另抄一份仓库配置。

构建期方案满足普通用户无法通过产品配置修改；它不承诺抵抗对程序本体的逆向篡改。部署期受管文件方案仅保留为调研对比，本期不采用。

## 4. 调研单元：入口、IPC 与重启交接

### 4.1 该部分要做什么

主窗口及独立窗口的左上角入口，与设置页共用同一更新状态，发出检查、下载、安装意图；原生确认后完成会话保存，再交给更新器重启。Windows 入口排在左上角功能区右侧，macOS 不套用这一 Windows 专门处理。

### 4.2 项目现状

- 主窗口左上角板头在 [SessionPanel](../../../../src/renderer/src/components/SessionPanel.tsx)，独立窗口由 [IndependentWindowFrame](../../../../src/renderer/src/components/IndependentWindowFrame.tsx)承载，没有主窗口的左侧面板；不能只在右侧 [Toolbar](../../../../src/renderer/src/components/browser/Toolbar.tsx)加一次入口就视为满足新位置。入口应抽成共用组件，在两类窗口分别选择左上角挂载位置。
- [main/index.ts](../../../../src/main/index.ts)的 Windows 主窗使用隐藏标题栏和右侧原生窗口控制 overlay，macOS 主窗使用原生三灯及占位；[独立窗](../../../../src/main/browser/windows.ts)当前保留原生标题栏。实现需按用户要求处理 Windows 左上角功能区右侧的位置，不改动这些窗口控制机制；精确锚点在 impeccable 设计阶段核对。
- [PaneAbout](../../../../src/renderer/src/components/settings/PaneAbout.tsx)已展示真实应用版本；[settingsWindow.ts](../../../../src/main/settingsWindow.ts)使用 `app.getVersion()`，可复用“关于”承载更新，无需新增设置分类。
- [preload](../../../../src/preload/index.ts)已有窄接口及返回退订函数的订阅；[settings store](../../../../src/renderer/src/stores/settings.ts)已有快照镜像；[插件管理](../../../../src/main/extensions/management.ts)也使用“变更通知后重取”模式。
- [main/index.ts](../../../../src/main/index.ts)退出前等待 `registry.flushPendingReports()`，封笔后关独立窗，再调用 `app.quit()`；普通退出目前有 1 秒上限和吞掉失败的容错。安装交接不能直接照搬这条成功判定。
- [录屏控制器](../../../../src/main/browser/recording/index.ts)退出仅尽力收尾，不保证全部录制内容保存；主动重启前应检查录制忙碌，不能把安装当作普通退出强行推进。
- [PRD](../../../docs/requirements/PRD.md) 4.9—4.11 和 [AGENTS.md](../../../../AGENTS.md)要求全局设置与会话数据隔离、确认与结果反馈使用原生界面；[语言注册表](../../../../src/shared/i18n/index.ts)当前有简中、繁中、英文三种，新增文案须三语同步。

### 4.3 候选方案

**方案 A：主进程推完整更新快照，推荐。** renderer 启动先订阅，再拉取快照；后续由主进程推送状态，Zustand 只做镜像。契合当前设置域模式，下载进度不必每次再发 IPC 请求。依据：[Electron IPC 模式](https://www.electronjs.org/docs/latest/tutorial/ipc)和本项目 settings 代码。

**方案 B：主进程只通知变更，renderer 重取快照。** 沿用插件管理模式，消费者总从查询接口拿最新数据；下载进度会产生额外请求，需要节流并处理回包乱序。同样遵守主进程所有权，可作为低频状态通知的替代。

### 4.4 可行性分析

| 维度 | A：完整快照推送 | B：通知后重取 |
| --- | --- | --- |
| 技术匹配 | 状态和进度一起到达，适合两个入口实时同步 | 低频变更简单，连续进度多一次往返 |
| 规则冲突 | 无；只向已登记的应用壳窗口发送 | 无；查询和命令同样校验来源 |
| 成本 | 复用现有 Zustand，无新依赖；需快照序号 | 无新依赖；需节流与回包顺序处理 |

### 4.5 结论与实施建议

**结论：借鉴思路手写，使用主进程快照和现有 IPC/Zustand 模式。** 不引入渲染层更新 SDK。

建议接口与文件：

| 拟改文件 | 职责 |
| --- | --- |
| 新增 `src/shared/updates.ts` | 更新状态、能力、进度、版本信息及通道常量；不暴露下载文件路径或执行命令 |
| 新增 `src/main/updates.ts` | 单例状态与命令；`updates:get-state`、`updates:check`、`updates:download`、`updates:install`、`updates:changed` |
| `src/main/index.ts` | 启动装配、主窗口/独立窗口/设置窗口身份引用、安装前保存与退出交接 |
| `src/preload/index.ts`、`index.d.ts` | 暴露 `window.api.updates` 的固定方法和可退订订阅，不暴露原始 IPC |
| 新增 `src/renderer/src/stores/updates.ts` | 只读镜像与调用意图；快照带递增序号，防止初次拉取覆盖更晚的推送 |
| `src/renderer/src/main.tsx` | 在主窗、独立窗、设置窗角色初始化更新镜像，浮层和被测页面不初始化 |
| 新增共用更新入口组件；`SessionPanel.tsx`、`IndependentWindowFrame.tsx`、`PaneAbout.tsx`、`app.css` | 左上角入口、设置行和必要状态样式；Windows 放功能区右侧，macOS 常规左上布局；具体挂载位置由 impeccable 设计核对 |
| `src/shared/i18n/locales/` | 简中、繁中、英文同步补按钮、进度、确认和错误文案 |

建议状态与入口行为：

| 状态 | 左上角（主窗及独立窗） | 设置“关于” |
| --- | --- | --- |
| 未检查 / 检查中 | 不显示更新入口 | “检查更新” / 检查中，防重复提交 |
| 当前已最新 | 不显示 | 当前版本及最新状态，可再次检查 |
| 有新版本 | “更新” | 显示新版本，可下载 |
| 下载中 | 显示进度，重复点击不新建下载 | 同步进度 |
| 下载完成 | “重启安装” | 同一版本的“重启安装” |
| 失败 | 已发现新版本时保留重试入口 | 明确失败，允许重试；失败不等同于已最新 |
| 策略关闭 | 不渲染、不预留空位 | 不渲染更新行；当前版本信息保留 |

入口隐藏必须由能力过滤表格行为；两处都隐藏时完全停止更新。主进程再次检查有效策略、主窗/已登记独立窗/设置窗的允许来源和当前状态；检查/下载去重，安装确认全应用最多一个。`install` 接口不接受 renderer 传入 URL、文件路径或“已确认”布尔值。依据：[Electron IPC sender 校验要求](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages)。

重启顺序建议：用户点击 → 主进程原生确认（“稍后 / 重启安装”，稍后为默认）→ 重新检查版本、下载就绪及忙碌状态 → 等待会话保存并封笔 → 调用更新器安装。任何保存失败或超时均中止安装；不能照普通退出路径吞掉错误后继续。录屏中建议拒绝重启，提示结束录屏后重试；保存期间也不能再接收改变恢复集的新操作。安装与普通退出的交接标记要统一，避免现有保存回调再次 `app.quit()` 打断 updater。

特别是 macOS，Electron [autoUpdater 文档](https://www.electronjs.org/docs/latest/api/auto-updater/#autoupdaterquitandinstall)说明其关窗与 `before-quit` 顺序不同；因此保存必须主动发生在 `quitAndInstall()` 前，不能仅增加一个退出监听。取消确认不退出、不清数据；普通退出不安装未获确认的更新。

实现界面时先走 **impeccable 的 scoped polish 流程**，结合 [PRODUCT.md](../../../../PRODUCT.md)、[DESIGN.md](../../../../DESIGN.md)确定主窗/独立窗左上角位置、Windows 功能区避让、亮暗主题与窄窗行为；不用渲染层 Modal、message 或 notification，更新进度采用按钮/设置行内状态。

## 5. 风险与开放问题

1. **macOS 正式签名已确认，尚未接入。** 需要准备 Developer ID 证书及发布配置，在 arm64/x64 上完成两版应用的真实更新，不能仅凭下载完成或 `codesign --verify` 报交付。已有 ad-hoc 用户切换到正式签名版的首跳也须验证；失败时需手动覆盖安装一次新基线。无需上架 App Store；账号、证书和公证接入在后续实施阶段处理。
2. **GitHub Latest 已被插件占用。** 必须修正发布标记并防止重现；本轮只读核实，没有修改插件 Release 或工作流。
3. **双架构清单不能覆盖上传。** YAML 引用的 ZIP、架构、版本及 SHA-512 都要一致；`SHA256SUMS.txt` 不能替代 updater 使用的清单。
4. **更新会中断正在进行的测试。** 安装确认与会话保存必须覆盖独立窗；录屏忙碌处理及截图编辑未保存提示需在设计阶段定稿。页面运行态仍按现有产品约定不恢复，不能把 URL 级恢复宣传为保留未提交表单。
5. **GitHub 网络失败是正常错误路径。** 检查不依赖某个被测会话的代理；超时、下载断网、空间不足、校验失败、权限不足均保留当前应用并允许重试。下载缓存和恢复行为需实测，不额外承诺断点续传。
6. **现有 1.1.0 没有更新入口。** 首个带本功能的版本需要用户先下载安装；后续才能自动检测下一版。本轮没有构建、安装或发布任何版本。

实施验证至少包括：本地打包覆盖两个入口的独立显隐，双隐藏时零更新请求且 IPC 拒绝；正式 CI 仅产公开版且两处入口默认开启；主窗和独立窗左上入口及 Windows 功能区右侧位置；最新/低版本/预发布与 CRX Latest；并发检查和下载；下载失败重试；确认取消及普通退出不安装；保存失败中止；Mac 双架构和 Windows 已安装包从低版本更新到高版本，重启后核对 `app.getVersion()`、会话 URL/顺序及登录态。本地隐藏态测试可沿用现有调试签名；macOS 真实自动安装必须用正式签名包验证。开发界面验证按项目规则使用 `npm run dev:agent`；真实安装必须使用隔离数据的打包应用。typecheck、lint、build 通过不能替代安装实测。

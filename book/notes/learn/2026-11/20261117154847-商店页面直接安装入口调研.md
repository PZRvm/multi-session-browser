# 商店页面直接安装入口功能调研报告

> 创建时间：2026-11-17 15:48:47（Asia/Shanghai）
> 需求来源：打开Chrome商店后，插件详情的“添加至Chrome”不可点击，希望直接从商品页安装。
> 调研单元：1个
> 状态：2026-11-17用户选定方案C同页自有按钮，已确认全局安装，实施见[计划](../../../plans/2026-11-17-商店详情页安装按钮.md)。下文保留候选比较。
> 分级：本轮S级只读调研与文档；后续实施触及网站特权桥、IPC身份和会话生命周期，必须按L级推进。

## 1. 需求理解

### 1.1 功能目标

用户继续在官方商店搜索和查看插件，在详情页点击安装，经过应用原生确认后交给现有安装管理器。完成后插件出现在应用设置与工具栏，并按现有规则供所有会话使用，无需复制ID或另装一个伴随插件。

[PRD3.11](../../../docs/requirements/PRD.md)已明确要求商品页安装，ID/链接只能作为备用。因此这是现有需求的入口缺口；此前任务中的“商店安装已实现”主要对应ID下载安装链，不能据此宣称商品页点击已经完成。

### 1.2 未知点清单

- [x] 是否因为不是Google Chrome而完全无法安装？不是：本项目已有独立下载与验签事务，Electron的加载能力和商店网页的安装入口是两层能力，见2.2。
- [x] 已有库能否恢复商店按钮？库已有webstorePrivate适配；能否直接适配当前线上商店仍需最小实测，见2.3。
- [x] 能否直接启用库？会引入其安装目录、状态查询、更新和加载流程，不能无条件照搬，见2.4。
- [x] 最合适接入哪里？受限商店preload→专用主进程桥→项目统一安装服务，见2.5。

### 1.3 拆分判断

整体作为一个调研单元：页面按钮只是同一安装事务的新入口，分开调研容易遗漏页面状态与安装结果的对应关系。

## 2. 调研单元：商店网页安装入口

### 2.1 该部分要做什么

让商店详情页具备可用安装操作，覆盖安装中、已安装、取消和失败；保留现有CRX/ID入口。第一期不做后台自动升级、另一个商店目录、商店搜索克隆或全浏览器身份伪装。

### 2.2 项目现状

| 事实 | 代码依据 |
| --- | --- |
| 打开商店仅导航当前会话到官方域名，没有启用商店网页桥。 | `src/main/extensions/management.ts`的openStore；src全文没有installChromeWebStore调用 |
| 设置页支持32位a—p字符ID安装，页面直接安装入口仍为TODO。 | `src/renderer/src/components/settings/PaneExtensions.tsx` |
| 已有允许列表、原生确认、Google更新服务下载、CRX验签解包、manifest登记。 | `src/main/extensions/install/store.ts`、`install/crx.ts` |
| 安装后通过remountAll向各会话挂载并广播设置刷新。 | `src/main/extensions/management.ts`的installStore |
| electron-chrome-web-store 0.13.0已在依赖中，MIT；Electron45.3.0。 | package.json与本机依赖package.json/README/dist |
| 默认UA已经去掉应用名并保留Chrome形态；不能把修改UA当成缺失桥接的解决方案。 | `src/main/browser/userAgent.ts`、`src/main/index.ts` |
| 现有扩展preload被限定到chrome-extension来源，普通商店页不会得到该扩展桥。 | `src/main/extensions/runtime/preload-guard.ts` |

现有ID处理器只接收ID并进入安装链，不能直接把整个window.api开放给商店网页。商店是远程内容，新入口须单独限定来源主frame和注册表中的真实目标页面。

用户报告disabled，本轮静态核查确认“没有商店网页桥”这一接线缺口。尚未观察用户那一页的实际API检测分支、DOM与控制台，不能断言禁用只由某一个字段导致，也不能写成已通过线上修复实测。

### 2.3 候选方案

**方案A：直接启用electron-chrome-web-store全套能力**

库提供installChromeWebStore，可向指定Session注册preload，适配商店调用的webstorePrivate，并负责安装、加载与更新。集成表面最少，但项目已有自己的安装事实源。即使关闭autoUpdate/loadExtensions，网页beginInstall仍调用库的installExtension，不会自然切换为项目事务；beforeInstall是批准/拒绝钩子，并非可替换安装器的接口。

来源：[库README](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/README.md)、[入口源码](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/src/browser/index.ts)、[API源码](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/src/browser/api.ts)。本机0.13.0的dist也已核对，线上master仅作参考，不视为固定版本承诺。

**方案B：借鉴库的商店协议适配，安装仍由项目管理（推荐）**

仅在官方商店顶层页面提供必要的状态查询与安装调用，使原按钮能驱动项目事务。先以现有库列出的getExtensionStatus、getFullChromeVersion、beginInstallWithManifest3/completeInstall等调用为线索，观察当前线上页面实际需要的最小集合，再确定实现；不是预先实现全部Chrome私有API。

来源：[上游商店preload](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/src/renderer/chrome-web-store.preload.ts)。这证明已有同类实现路径，但私有API不属于稳定网页标准，当前商店、Electron45和项目preload组合仍要验证。

**方案C：自有安装按钮，不依赖原按钮**

在商店详情页放置应用自己的“添加至多会话测试浏览器”按钮，从当前官方详情URL解析ID后走统一事务；可用受限preload注入独立DOM控件。若采用应用工具栏入口，可进一步减少对商店DOM结构的依赖，但用户需要离开商店按钮位置，体验有差异。它是B失败后的可行替代，不默认同时做两套入口。

来源：[Electron preload机制](https://www.electronjs.org/docs/latest/tutorial/tutorial-preload)、[Session受限preload注册](https://www.electronjs.org/docs/latest/api/session#sesregisterpreloadscriptscript)；安装能力直接复用项目store.ts。该方案是基于这些能力提出的项目设计，不是官方提供的商店按钮组件。

### 2.4 可行性分析

| 维度 | A全套库 | B最小商店适配 | C自有按钮 |
| --- | --- | --- | --- |
| 页面体验 | 原商店按钮，有参考实现 | 原商店按钮，最贴近用户要求 | 同页独立入口，原按钮可能仍禁用 |
| 安装事实源 | 与现有清单/分区挂载重复，需要深改 | 完全复用项目事务和广播 | 同样复用项目事务 |
| 权限与隔离 | 上游注册范围及来源判断需重审 | 专用主frame、精确origin与页面身份校验 | 页内按钮仍需受限桥；工具栏可复用可信壳 |
| 维护成本 | 初接少，双安装器整合成本高 | 中等；维护最小私有协议兼容 | 中等；页内DOM需适应SPA，工具栏需新增界面 |
| 依赖与许可 | 已有依赖，MIT | 不增加包；借用源码须保留MIT版权声明 | 不增加包，自研控件与桥 |

单纯移除disabled属性只改变外观，不能补安装能力，不列为可交付方案。全局改UA也不能建立事务桥；上游preload的硬编码Mac UA、宽泛前缀来源匹配与额外management操作不宜照搬。依据为本机0.13.0 preload与API源码。

### 2.5 结论与实施建议

结论：**借鉴思路手写，采用B。** 已有成熟协议适配可参考，但项目需要自己的安装事务、精确权限与会话生命周期；无需先安装一个普通Chrome伴随插件。

建议用户路径：官方商店搜索→进入详情→点击安装→应用原生确认→下载并验签→全局登记及各会话挂载→页面显示真实结果。网页文案尽量说明安装到本应用；只修改相关按钮，不泛改页面中所有Chrome文字。安装成功与部分会话加载失败要分开反馈，不假报全部成功。

实施顺序：

1. **最小可行性门禁**：在隔离profile的真实Electron45应用观察当前商店需要的API与禁用原因；先验证按钮可用和取消路径，不访问真实用户数据、不实际安装。若缺口可控，再冻结最小协议。若需要大片伪装或当前商店无法兼容，报告证据，改选C，不持续追逐私有API。
2. **统一事务服务**：从`src/main/extensions/management.ts`抽出当前ID安装后续动作供设置页与商店共用；`install/store.ts`保留验签与manifest事实源。设置与多个商店页并发点同ID时要全流程单飞，不能把manifest写锁误认为下载/确认/挂载都已串行。卸载、升级与删除Session的交错列入设计。
3. **新增专用商店桥**：建议`src/main/extensions/store-page.ts`与`src/preload/storePreload.ts`，注册时限制官方HTTPS商店来源，仅顶层文档；handler复核精确origin、主frame、真实Tab/Session身份、详情页ID及在途请求。拒绝同名前缀域、iframe、离站后旧请求及任意下载URL。导航后不得重新把已销毁会话登记为活动会话。
4. **接线与打包**：在会话初始化接缝注册独立preload，不放宽现有扩展preload过滤；`electron.vite.config.ts`增加专用入口。`src/shared/extensions/management.ts`可定义最小商店通道/状态类型，主`window.api`不扩大到远程页面。安装确认绑定发起窗口，而不是安装结束时恰好聚焦的另一窗口；原生确认及结果反馈复用现有机制，文案走三语字典。
5. **验证与写回**：真实商店搜索→详情SPA导航→安装/已安装/取消/失败；两窗口同ID并发、安装中离站/关页/删会话、设置页同步、重启、新会话、伪造来源和iframe拒绝、正式包preload加载。至少一款已验证兼容的原版插件贯穿完整链；安装入口通过不代替全部插件运行兼容验收。UI改动按impeccable流程，L级计划及Step0先于实现。

## 3. 风险与开放问题

- 原按钮依赖私有商店协议和当前站点实现，尚未实测，B的可行性门禁不能省略。方案C保留为明确替代方向。
- [Electron官方](https://www.electronjs.org/docs/latest/api/extensions)明确只支持部分扩展API。页面能安装不意味着任意插件都能运行；此功能沿用项目现有兼容边界。
- 当前store.ts使用Node全局fetch，而非来源Session请求；商店网页能通过会话代理访问，不代表CRX下载也走同一出口。需单独验证并明确下载网络策略，不能默默绕过用户代理，也不应为入口改造顺带调整所有下载网络。
- 商店网页提供的名称、manifest或图标不是最终可信安装信息；不得接收任意下载地址，最终包身份仍由现有验签和固定下载源确认。安装确认信息的获取与展示顺序需在设计中确定。
- 仅注册一个宽泛网页桥会重现项目曾遇到的注入范围问题；使用官方受限注册并进行主进程二次授权，不假设页面声明了域名或ID就可信。

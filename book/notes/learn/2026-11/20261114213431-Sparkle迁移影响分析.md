# Sparkle 迁移影响分析功能调研报告

> 创建时间：2026-11-14 21:34:31（Asia/Shanghai）
> 需求来源：个人开源项目暂不购买 Apple Developer 证书，改用 Sparkle，先判断影响哪些代码。
> 调研单元：2 个；以下保留调研时分析。当前 Sparkle 已接入并发布，完整平台验收仍待补。
> 当前入口：[Sparkle 迁移计划](../../../plans/2026-11-14-macOS更新迁移Sparkle.md)与[1.1.2 发布记录](../../../plans/2026-11-15-1.1.2审查与正式发布.md)。不要将下方当时的“尚未实施”视为当前状态。

## 1. 需求理解

### 1.1 功能目标

macOS 更新引擎从 electron-updater / Squirrel.Mac 迁移至 Sparkle；Windows 继续使用 electron-updater。保留右上角主题圆钮、popover、原生版本日志窗口、用户确认才下载、下载完成询问是否重启，以及安装前录制检查和严格保存。用户选择稍后或普通退出时，不应擅自安装。

Sparkle 的 EdDSA 更新签名可自行生成密钥，不依赖付费 Apple 开发者账号；这和 macOS 的应用身份签名、公证是不同机制。未公证应用的首次安装限制仍存在，不能承诺迁移后系统不再提示。[Sparkle 安装与签名说明](https://sparkle-project.org/documentation/)、[Electron 桥接项目的 ad-hoc 分发说明](https://github.com/biw/electron-sparkle)

### 1.2 未知点清单

- [x] 现有代码能否局部替换：主进程已有更新引擎接口，UI 和 IPC 多数可复用，见 2.2。
- [x] 是否存在 Electron 桥接：找到两个候选，但各有行为冲突，不能直接替换，见 2.3。
- [x] 日志如何绑定版本：继续沿用版本 Markdown 单源，macOS 增加 appcast 分发，见 3.5。
- [ ] 原生桥接能否完整保留“稍后不安装、普通退出不安装、保存失败阻止安装”：必须用真实双版本应用验证，不能以文档分析标记通过。
- [ ] Electron 45.3.0 下 arm64 / x64 的加载、安装、重启和缓存恢复：待原型与构建验证。

### 1.3 拆分判断

分为运行时桥接、打包发布两个单元。运行时先确定所需原生接口与取消语义，发布工具随后围绕同一 Sparkle 版本与密钥契约落地。正式迁移涉及原生依赖、更新信任和发布链，建议按 L 级执行；本轮仅调研，没有进入实现阶段。

## 2. 调研单元：macOS 原生更新桥接

### 2.1 该部分要做什么

让主进程调用 Sparkle 并将事件映射回既有状态机。下载、解包、验签、安装交给 Sparkle；用户决策、保存事务、窗口和可信 IPC 继续由本项目控制。

### 2.2 项目现状

| 文件 | 现有职责 | 迁移影响 |
| --- | --- | --- |
| `src/main/updates.ts` | 创建 electron-updater，连接 Squirrel.Mac，下载后主动确认安装 | 必改：按平台选择引擎，Mac 移除 Squirrel 事件和交接超时，接入 Sparkle 事件及失败反馈；Windows 保留 |
| `src/main/updateController.ts` | check / download / install 接口、状态与并发锁，安装前确认、录制检查、保存 | 复用核心事务；核对下载结束、原生取消和退出事件的语义，必要时小幅扩展接口 |
| `src/main/updatePreparation.ts` | 写入锁、严格保存、失败后恢复 | 复用，原生层必须允许保存失败后中止安装 |
| `src/main/index.ts` | 注册更新及退出、保存依赖 | 核对 Sparkle 请求退出的时机与既有退出门禁，防止跳过保存 |
| `src/main/updateReleaseNotes.ts` | 日志长度限制、版本匹配与安全文本归一化 | 复用归一化，增加 Sparkle 日志来源适配 |
| `src/shared/updates.ts`、`src/preload/index.ts`、`src/preload/index.d.ts` | 快照、IPC 和窄 API | 尽量保持契约；仅在原生能力确有差异时调整类型与错误映射 |
| `UpdateEntry.tsx`、`UpdateDetailsSheet.tsx`、`stores/updates.ts` | 圆钮、popover、日志与操作、状态镜像 | 预期复用；以上组件位于 `src/renderer/src/` 下，不需因换引擎重做视觉 |
| `src/main/workspacePickerWindow.ts` | 原生日志窗口、动作来源与版本校验 | 保留原生窗口和校验规则 |

当前 `package.json` 使用 Electron 45.3.0，已有 electron-updater；`electron-builder.yml` 关闭 npmRebuild，现有构建不会自动解决新增原生模块的 Electron 编译和打包。项目当前没有 Sparkle 运行时或 appcast。

### 2.3 候选方案

**方案 A：electron-sparkle-updater，调研时 npm 版本 0.5.3。**

N-API 桥接、静默 user driver 和发布工具较接近现有自定义界面。但源码在发现更新后直接回复 Install，开始下载；并未暴露独立 download 方法。`showUpdateReleaseNotesWithDownloadData` 也未向 JS 转发数据。直接使用会破坏先看日志、确认才下载的流程。macOS 需按 Electron 与架构显式构建原生模块；主入口为 ESM，需要与现有主进程打包方式适配。

来源：[项目与接入说明](https://github.com/Innei/electron-sparkle-updater)、[本次核对的原生桥接源码](https://github.com/Innei/electron-sparkle-updater/blob/364b41afc8ee42f47ceb6af4e723bb1315d3e55b/native/src/sparkle_bridge.mm)。

**方案 B：electron-sparkle，调研时 npm 版本 0.2.0。**

Swift 桥接，支持 Electron Builder / Forge，声明 Electron >=42，默认使用 Sparkle 原生界面。其 `setBeforeRelaunchHandler` 可以等待异步准备，但当前源码在 handler 拒绝后仍调用 `continueRelaunch`，不满足本项目保存失败必须阻止安装的规则。版本范围包含 Electron 45 不等于已在本项目验证兼容。

来源：[项目与 API 说明](https://github.com/biw/electron-sparkle)、[运行时实现](https://github.com/biw/electron-sparkle/blob/main/src/runtime/updater.ts)。

**方案 C：官方 Sparkle + 项目可控的原生桥接。**

使用官方 `SPUUpdater` 与自定义 `SPUUserDriver`，参考方案 A 的 N-API 接缝，保留下载决策、日志事件和安装许可控制；不自行实现更新引擎。官方协议支持自定义 UI，但准备安装之后普通退出也可能触发安装，不能把 Dismiss 简单映射成本项目的“稍后”。

来源：[自定义 UI](https://sparkle-project.org/documentation/custom-user-interfaces/)、[SPUUserDriver 协议](https://sparkle-project.org/documentation/api-reference/Protocols/SPUUserDriver.html)。

### 2.4 可行性分析

| 维度 | A：直接接现有 N-API 库 | B：直接接现有 Swift 库 | C：官方引擎 + 定制桥接 |
| --- | --- | --- | --- |
| 技术匹配 | 事件较合适，但缺少显式下载与日志转发 | 默认 UI 与现有流程不同 | 接口可围绕现有事务设计，需原型验证 |
| 规则冲突 | 发现即下载；安装后段退出语义需处理 | 准备失败仍继续重启 | 能主动控制，但普通退出取消能力尚未证实 |
| 成本 | 初装省事，之后仍需补原生行为 | 仍需改桥接与 UI 控制 | 原生维护成本最高，控制边界最清楚 |
| 许可与维护 | MIT，固定版本并保留许可 | MIT，固定版本并保留许可 | Sparkle 及借鉴桥接代码分别保留许可，原生构建由项目维护 |

### 2.5 结论与实施建议

**借鉴思路手写，选择 C。** 使用官方 Sparkle，不直接照搬候选桥接的自动下载或失败后继续重启行为。参考 A 的 N-API 实现，只做项目所需桥接；优先使用官方框架，首轮采用完整更新包，避免额外引入桥接项目的定制差分框架。

建议新增 Mac 专用适配模块（如 `src/main/updates/macSparkle.ts`）及独立原生源码、构建脚本，按平台由 `updates.ts` 注入现有控制器。桥接需要显式检查、开始下载、安装许可、取消、日志与进度事件；缺模块、错架构或配置缺失应给出明确失败，不回退到当前必然签名失败的 Squirrel 路径。

先做两个版本的原型，证明：检查不下载；确认后下载；稍后与普通退出不安装；录制中与保存失败阻止安装；确认后能替换并重启；重启后数据保留。尤其需要验证取消已准备安装的更新后能否保留缓存，不能先承诺与当前 ready 状态完全等价。未通过前不替换现有完整链路。若需要调整视觉，实施时使用 impeccable。

## 3. 调研单元：打包、签名、发布和版本日志

### 3.1 该部分要做什么

把 Sparkle 框架及桥接打进 Mac 包，用自行生成的 EdDSA 密钥签署更新归档，并发布 appcast；继续通过 GitHub Releases 分发。Windows 的 NSIS / latest.yml 链路保持现有职责。

### 3.2 项目现状

| 文件 | 迁移影响 |
| --- | --- |
| `package.json`、`package-lock.json`、`electron.vite.config.ts` | 增加或构建原生桥接，配置主进程外置依赖；electron-updater 仍供 Windows 使用 |
| `electron-builder.yml` | 加入 Sparkle.framework、原生 `.node`、asar 解包及 Info.plist 的 feed / 公钥配置，检查 rpath 与嵌套 helper |
| `scripts/patch-mac-display-names.js` | 当前 afterPack 改 LC_UUID、本地化并临时签名；必须组合钩子，保留这些行为，所有嵌入完成后再最终签名 |
| `scripts/electron-builder-release.cjs` | 当前强制 Apple 证书与公证凭据；增加 ad-hoc + EdDSA 路径及相应完整性门禁，不能只删除校验 |
| `.github/workflows/release.yml` | Mac 两架构构建原生桥接，加入 Sparkle 私钥 secret 和签名、appcast 步骤；调整强制 Developer ID / stapler 检查，Windows 门禁保留 |
| `scripts/update-assets.mjs` | 当前围绕 latest-mac.yml / latest.yml 合并与校验；新增 Mac appcast、架构、版本、URL、签名及资源白名单校验 |
| `scripts/release.mjs` | 上传 XML 和日志资源，完整校验后发布 draft；更新输入变更识别，防止漏掉原生源码与构建脚本 |
| `scripts/release-notes.cjs` | 保留唯一版本 Markdown 校验，增加 Mac feed 日志输出的复用入口 |
| `scripts/update-test.mjs`、`scripts/electron-builder-update-test.cjs`、`tools/update-test/` | Mac 双版本样本改为 Sparkle + 测试密钥 + appcast；补原生安装、错误签名、取消和退出验证，Windows 样本保留 |

### 3.3 候选方案

**方案 A：官方 generate_keys / generate_appcast + 项目发布脚本。** 保留现有发布事务，用官方工具生成更新签名和 feed，再由现有脚本做版本、资源与日志校验。来源：[Sparkle 发布说明](https://sparkle-project.org/documentation/)、[发布更新指南](https://sparkle-project.org/documentation/publishing/)。

**方案 B：桥接库提供的发布 CLI / GitHub Action。** 能减少配置，但需要适配现有三平台资源合并、draft 校验和版本 Markdown；不能直接覆盖本项目 release 工作流。来源：[electron-sparkle-updater 的工具链](https://github.com/Innei/electron-sparkle-updater)。

### 3.4 可行性分析

| 维度 | A：官方工具 + 现有发布编排 | B：替换为库的工具链 |
| --- | --- | --- |
| 技术匹配 | 与运行时同版本工具配套，可控制两架构 feed | 需核对工具链自带框架版本及差分行为 |
| 规则冲突 | 可以保留版本绑定、资源白名单和发布前校验 | 现有发布流程仍需额外桥接 |
| 成本 | 多维护一层薄适配，改动边界可见 | 初期配置较少，绑定第三方工具行为更多 |

### 3.5 结论与实施建议

**采用现成方案，选择 A 的官方工具，保留项目发布编排。** 密钥只生成一次，公钥打进应用，私钥进入发布 secrets 并另行安全备份；禁止每次发布重新生成。免费 EdDSA 解决更新包来源校验，不替代应用首次分发的 Apple 信任。

建议 arm64 / x64 分别生成 feed，避免错误架构被选中；具体文件名在实施计划中固定。应用查稳定的最新 feed，enclosure 指向对应 `vX.Y.Z` Release 的确定资源，不使用可能随版本改变内容的安装包 URL。

版本日志继续执行既有单源链：

`package.json.version` → 唯一 `book/changelogs/YYYY-MM/release-notes-vX.Y.Z.md` → `vX.Y.Z` 标签 / GitHub Release 正文 + Mac appcast 日志 + Windows latest.yml 日志。

Mac 采用 appcast 内嵌日志或由相同 Markdown 生成的版本专属日志资源；原生桥接需把正文和版本送给当前安全文本归一化。选择侧文件时，日志读取失败不得卡住更新，且不得回退展示其他版本日志。官方较新工具支持 Markdown，但桥接固定的框架版本和工具必须配套验证，不能据最新文档推定任意版本都支持。

实施后同步 `book/docs/architecture/项目骨架.md`、PRD 4.16、ADR-004、`DESIGN.md`、`AGENTS.md`、`.github/RELEASING.md` 及计划 / summary。当前文档仍描述现状，本次不提前把未实现的 Sparkle 写成已生效规范。无需恢复已删除的独立“应用更新验收”文档。

## 4. 风险与开放问题

1. **“稍后”语义是首个验证门槛。** Sparkle 准备安装后，Dismiss 仍可能在普通退出时安装；官方 Skip 在该阶段可以取消且不会永久跳过版本，但缓存保留、恢复与本项目 ready 状态如何对应仍需实测。[官方协议](https://sparkle-project.org/documentation/api-reference/Protocols/SPUUserDriver.html)
2. **免费路线仍有系统限制。** ad-hoc 签名与 EdDSA 不能消除 Gatekeeper 的首次安装限制。Hardened Runtime 的 Library Validation 也可能阻止加载异签名框架，需在打包阶段明确处理和验证。[框架嵌入与 Library Validation](https://sparkle-project.org/documentation/)
3. **首次迁移需要手动安装。** 当前未正式签名的 Squirrel 版本已无法安装更新，不能依靠它把用户自动迁移到 Sparkle；之后的两个 Sparkle 版本才用于验收真实自动更新。
4. **原生分发增加维护面。** arm64 / x64、Electron 版本、asar、框架符号链接和签名顺序都需验证；不能以 TypeScript 检查代替真实替换与重启测试。
5. **不顺带修复既有审阅问题。** 当前保存事务恢复时序的 R1 仍按原记录追踪，迁移不能将它写成已解决。

## 5. 待确认假设

无阻塞本轮影响分析的产品假设。Sparkle 方向和暂不购买 Apple 证书来自用户；保留当前交互来自已确认需求。双架构独立 feed、首轮全量包和定制桥接是本报告的实施建议，尚未落代码，技术可行性按前述原型门槛判定。

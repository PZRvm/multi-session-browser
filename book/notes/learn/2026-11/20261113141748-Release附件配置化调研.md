# Release 附件配置化调研：CRX 随安装包发布

> 2026-11-13 · 应用户要求先调研不实现。目标：自研插件 CRX（截图/录屏）随版本发布流程自动上传到 GitHub Release，机制做成**配置文件声明式**——列进配置的文件与三平台安装包同批发布。

## 1. 现状与约束

| 事实 | 影响 |
| --- | --- |
| 发布链：`release.yml` 三平台矩阵构建 → `upload-artifact`（`installer-*`）→ publish 任务下载 → `scripts/release.mjs` `collectAssets()` 校验上传 | 附件名单**硬编码**三个安装包名 + SHA256SUMS.txt；目录里多任何文件直接抛「发布目录包含意外文件」——配置化的核心改动点就在这里 |
| CRX 与 PEM **均不在版本库**（`.gitignore` 显式排除 `recorder.crx/screenshot.crx/*.pem`，注释「自研插件构建产物」） | publish 任务 checkout 拿不到 CRX——设计必须先回答「CRX 从哪来」 |
| PEM 是插件私钥（CRX 签名与稳定 ID 的根） | 绝不入库、绝不上传 Release；CI 打包只能走 GitHub Secrets |
| CRX 体量极小：recorder 20K + screenshot 512K ≈ 540K | 「入库」方案的二进制成本可忽略 |
| CRX 构建输入全在库：插件源码（`extensions/`）+ `extensions/build.mjs`（截图编辑器 esbuild bundle，录屏纯静态）；重打包先例 = Chrome `--pack-extension` + 固定 pem（同 pem → 同 ID，确定性） | CI 现场重打包可行；macOS/Windows GitHub runner 均预装 Chrome |
| 附件已有校验链：SHA256SUMS.txt 覆盖全部附件、上传后逐个 digest 对账 | CRX 并入同一链路即可，零新机制 |
| GitHub Release 附件上限 2GiB/文件，发布后可随时补传（`gh release upload`，草稿/已发布均可，同名 `--clobber` 覆盖仅草稿安全） | 体量与补传无障碍 |

## 2. 「CRX 从哪来」三源 + 一条 stopgap

### 方案 A：CRX 入库（构建产物进 git）

- 做法：`.gitignore` 移除两条 `*.crx` 排除（`*.pem` 保持排除），重打包后提交 `extensions/dist/*.crx`；配置文件列 glob，publish 直接从 checkout 读取。
- 优点：机制最简（零新构建步骤、零 secrets、零 artifact 通道），发布即所得。
- 缺点：**推翻既有「构建产物不入库」决策**；每次插件改动产生 ~0.5MB 二进制 diff；本地重打包与库内副本可能漂移（漂移时发布的不是最新——需配「入库即真相」纪律）。

### 方案 B：CI 现场打包（推荐）

- 做法：新增一个小型构建 job（或并入某个平台 build job 的后置步）：
  1. `node extensions/build.mjs`（截图编辑器 bundle；录屏纯静态无需构建）
  2. runner 预装 Chrome 执行 `--pack-extension=<源码目录> --pack-extension-key=<pem>`（或用 `tools/extension-preflight/crx.mjs` 的 CRX3 签包能力，纯 Node 无浏览器依赖，跨平台一致性更好）
  3. pem 从 GitHub Secrets 注入（base64 环境变量落临时文件，步末清理）
  4. `upload-artifact: extra-assets` → publish 任务并入下载
- 优点：无二进制入库（尊重既有决策）；产物与源码同 commit 严格对应（发布的就是这份源码打的包）；pem 只活在 Secrets 与本地。
- 缺点：CI 新增构建步与 secrets 配置（一次性）；签包工具选型要定（Chrome CLI vs crx.mjs 自签）。

### 方案 C：独立产物工作流（不推荐）

- 手动触发的「插件发布」工作流先产 CRX 存 artifact / 进库，版本发布再取——两段式时序耦合、产物版本对齐靠人，复杂度不成比例。

### Stopgap：v1.1.0 人工补传（一条命令，随时可做）

```bash
gh release upload v1.1.0 extensions/dist/recorder.crx extensions/dist/screenshot.crx
```

已发布版本可随时补传附件；本次 v1.1.0 若要立刻带上 CRX，用这条即可，不必等机制。

## 3. 配置文件形态（两方案通用）

位置建议 `build/release-assets.json`（与 electron-builder.yml 同域，主题聚合）：

```json
{
  "include": ["extensions/dist/*.crx"]
}
```

`collectAssets()` 改造语义（与方案解耦）：

1. 安装包三件套仍硬编码（平台矩阵产出），配置只管**附加附件**
2. glob 相对仓库根展开（publish 已 checkout merge commit；方案 B 时目录换成 artifact 下载目录）
3. **安全栏**：命中 `*.pem` 直接 fail（私钥硬保护）；单文件 >100MiB fail（防误配大文件）；glob 零命中 fail（防配错路径静默丢附件）；「意外文件」检查名单 = 安装包 + 展开结果（保持防夹带语义）
4. 附加附件并入 SHA256SUMS.txt 与上传后 digest 对账（现有校验链零改动地覆盖）
5. 文件名原样上传（`recorder.crx`）——Release 下载 URL 跨版本稳定可引用

## 4. 改动面清单（实现时）

| 文件 | 改动 |
| --- | --- |
| `build/release-assets.json` | 新增配置 |
| `scripts/release.mjs` | collectAssets 读配置 + glob 展开 + 安全栏 + 并入校验链 |
| `.github/workflows/release.yml` | 方案 B：新打包 job + extra-assets artifact + publish 下载 |
| GitHub Secrets | 方案 B：`RECORDER_PEM_B64` / `SCREENSHOT_PEM_B64` |
| `.github/RELEASING.md` | 文档补「附加附件」一节 |
| `book/changelogs` 发布说明模板 | 提及插件包附件 |

体量评估：S 级（配置 + 脚本改造 ~60 行；方案 B 加一个 CI job ~30 行 + secrets 配置）。

## 5. 推荐结论

- **机制选型：方案 B（CI 现场打包 + Secrets pem + 配置声明）**——无二进制入库、产物-源码强对应、尊重既有 gitignore 决策；签包建议用 crx.mjs 的纯 Node 路径避开 runner Chrome 依赖。
- 若追求当期最小成本，方案 A 也可接受（540K 体量实害小），但需明确推翻 gitignore 决策并接受 diff 噪音。
- **v1.1.0 的当下需求走 stopgap 人工补传**（用户确认后一条命令完成）。
- 版本语义：CRX 自身版本（0.1.1）与应用版本解耦，附件名不带应用版本号；发布说明里口头注明插件版本即可。

## 落地记录（2026-11-13）

定稿执行方案 B 变体：**CI 现场打包 + 独立工作流发布**（用户裁决：CRX 与应用版本解耦，不是每次应用发版都带 CRX）。实现 = `.github/workflows/extensions-release.yml`（workflow_dispatch 手动触发）+ `tools/extension-preflight/pack-release.mjs`（CRX2 签名复用 crx.mjs 单源；pem 经 repo Secrets 注入；脚本落 tools/ 不进应用版本门打包输入哈希）+ 非草稿直发 + 字节对账。PEM Secrets 已配置（RECORDER_PEM_B64 / SCREENSHOT_PEM_B64）。

首跑全链实证：三平台……修正——CRX 工作流首跑即绿（dispatch → 打包双插件 → Release crx-202611130857 → 下载产物 SHA256SUMS 逐行核对 OK → 已发布 CRX 装入隔离实例：双插件导入/挂载/popup 打开全通过）。教训补记：① `workflow_dispatch` 要求工作流文件先存在于默认分支——dev 先行时需先走 PR 合入 main 才可触发；② scripts/ 在应用版本门打包输入哈希内，插件工具脚本落 tools/ 可避免锁死应用版本号；③ 合并 PR 前检查等待的 jq 过滤要覆盖 FAILED 态（本轮靠 gh pr checks 复核兜住）。

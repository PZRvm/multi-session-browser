# 地址栏行内补全与 Tab 搜索功能调研报告

> 创建时间：2026-11-06 16:28:48（Asia/Shanghai）
> 需求来源：参照两张 Chrome 截图增加历史行内补全、搜索引擎 Tab 搜索，普通 Tab 留在输入框插入制表符。
> 调研单元：3 个
> 状态：已确认（2026-11-06 用户逐项批复，第 3 项修订 Tab 补全规则；核心实现已落地，待审查修复与平台验收）
> 本轮为 S 级文档调研：核对代码与公开资料、记录方案，以索引生成和文档检查验证；后续功能预计 M，若扩展共享 IPC/类型契约则升级 L，实施前重新定级并补 Step 0 与完整阶段流程。

三个功能都能实现。推荐**借鉴思路手写**：沿用会话历史镜像和原生建议子窗，在现有受控输入框上补编辑状态机；搜索使用内置引擎表生成结果页 URL，经既有导航通道在当前会话打开；普通 Tab 插入 U+0009。无需新增第三方依赖，也不需要搜索 API 密钥。网络可达性和真实桌面输入体验仍需实施时验收。

## 1. 需求理解

### 1.1 功能目标

测试人员输入访问过的网址前缀时，输入框直接显示可接受的补全部分，如输入 `bai` 后显示 `bai[du.com]`，方括号表示自动选中的后缀。保留已有历史下拉供选择其他结果。

输入已支持的搜索引擎域名后按 Tab，地址栏进入“搜索 百度”等模式，继续输入关键词、回车后在当前 Tab 打开该引擎结果页。其他情况下按普通 Tab，焦点仍在输入框，并在选区或光标处插入一个真实制表符。用户批复后按此优先级执行：Tab 优先用原始输入精确判断引擎，命中即进入搜索模式；未命中引擎时才接受当前行内补全；其余插入制表符。搜索模式内 Enter 直接搜索，普通 URL 的 Enter 保持访问语义，不增加默认引擎自动搜索。

### 1.2 未知点清单

- [x] 历史数据是否已有？已有按会话隔离的主进程存储与 renderer 镜像，不必重建，见 §2。
- [x] 截图一是否已有？现有代码只有下拉建议，没有行内后缀选区，需扩展编辑状态，见 §2。
- [x] Electron 是否能直接接入 Chrome 地址栏？WebContentsView 提供页面承载，Chrome 的关键词模式属于其浏览器 UI；本项目继续实现自己的地址栏，见 §3。
- [x] 是否支持三个以上引擎？可使用九种候选引擎的 GET URL 模板，见 §3.3；本轮核对模板来源，未逐一验证在线搜索成功。
- [x] Tab 能否不切焦点并插入字符？可以在输入框处理键盘、选区与受控值；需特别处理 URL 对制表符的忽略行为，见 §4。
- [x] 会话隔离、原生下拉、中文输入法如何兼容？复用原作用域与导航链，组合输入期间暂停补全与搜索切换，实施时做双平台手验，见 §5。

### 1.3 拆分判断

分为历史行内补全、引擎搜索模式、Tab 编辑行为三个单元。数据源与引擎表可独立梳理；最终键盘优先级必须统一，避免各自监听 Tab 造成冲突。本报告沿用 research-feature 模板，按仓库 BoCode 约定落入 `book/notes/learn/2026-11/`，不建立旧 `notes/think-report/`。

## 2. 调研单元一：历史行内补全

### 2.1 该部分要做什么

从当前会话历史中选择前缀候选，在输入框选中自动追加的后缀。仅命中标题或 URL 中段的记录仍留在下拉，不能强塞进输入文本。

### 2.2 项目现状

- [Toolbar.tsx](../../../../src/renderer/src/components/browser/Toolbar.tsx)：普通 `input type="text"`，`autoComplete="off"`；显示值为 `draft ?? pendingShown ?? mainUrl`。已有选中建议、Esc 分层、输入法 Enter 守卫，没有行内补全或 Tab 分支。
- [omniboxSuggest.ts](../../../../src/renderer/src/components/browser/omniboxSuggest.ts)：按域名前缀、URL 前缀、URL 子串、标题子串分级；同级按新近度与频次排序。匹配会小写化并去 scheme/www，原 URL 和 query 保留。
- [shared/history.ts](../../../../src/shared/history.ts)：每会话最多 2000 条历史，输入至少 2 字符时给出最多 8 条建议，包含完整 URL、标题、图标、访问次数与时间。
- [history.ts](../../../../src/main/browser/history.ts)、[browser store](../../../../src/renderer/src/stores/browser.ts)：主进程持有并落盘，renderer 拉全量和接增量；切会话清空镜像并丢弃过期回复。[ipc.ts](../../../../src/main/browser/ipc.ts) 的 history-get 从 sender 解析会话，不接受前端指定任意 sessionId。
- [useOmniboxSuggestWindow.ts](../../../../src/renderer/src/components/browser/useOmniboxSuggestWindow.ts) 与 [main/omniboxSuggest.ts](../../../../src/main/browser/omniboxSuggest.ts)：下拉由不夺焦的原生子窗承载，保留实际呈现回执与旧回执失效机制。
- [PRD §3.2.1](../../../docs/requirements/PRD.md)、[PRODUCT.md](../../../../PRODUCT.md)、[DESIGN.md](../../../../DESIGN.md)：输入瞬态必须归属窗口、会话和 Tab；下拉与地址栏连续融合。旧[历史补全调研](../2026-09/20260914111602-地址栏历史补全.md)提供背景，本轮现状以实际源码为准。

### 2.3 候选方案

**A：保留现有 input，自行维护补全选区（推荐）。** 借鉴 Chromium 的行内补全概念，用 DOM 文本选区 API 选中追加后缀；用户继续输入时自然替换后缀。来源：[Chromium 输入法协调设计](https://new.chromium.org/developers/design-documents/omnibox-ime-coordination/)明确区分行内补全和下拉，并说明组合输入期间禁用行内补全；[HTML 文本选区 API](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#textFieldSelection)定义选区控制。适配 React 19 的受控输入，不依赖 Electron 私有接口。

**B：改为 HTML datalist。** 浏览器提供候选列表，但不能满足指定的行内后缀、搜索标签和既有原生子窗融合外观。[datalist 文档](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/datalist)还说明了样式和无障碍限制。适合简单表单，本地址栏无需替换成它。

### 2.4 可行性分析

| 维度 | A：自控选区 | B：datalist |
| --- | --- | --- |
| 技术匹配 | 保留现有匹配与下拉，可处理编辑和 IME | 能给列表，不能完整覆盖两张截图 |
| 规则冲突 | 复用会话镜像、原生子窗，不碰隔离契约 | 替代现有下拉，融合与按键行为难以统一 |
| 成本 | 零新增依赖，主要成本是编辑状态与手验 | 接入少，定制与回归成本高 |

### 2.5 结论与实施建议

结论：**借鉴思路手写**，使用 A。

在 `Toolbar.tsx` 区分“用户原始输入”“展示补全”“真实提交目标”。匹配始终基于原始输入，不能让自动追加的后缀反过来过滤列表。新增 renderer 本地纯函数，返回 `{ displayText, selectionStart, selectionEnd, targetUrl }`，不改变历史持久化或 IPC 结构。

推荐规则如下，实施前作为交互契约确认：

- 首期只对 http/https 的连续前缀做行内补全；完整历史 URL 为提交目标。去 scheme/www 只用于查找，不能用规范化串索引直接切原 URL。保持路径大小写与 query，不解码 `%2F` 等内容。
- 只有光标在末尾、没有用户主动选区、非粘贴/删除/组合输入时才自动追加。候选从既有排序中取第一个可安全映射的前缀结果。
- 继续打字替换后缀；Backspace/Delete 先去掉自动后缀并抑制立即补回；中间编辑或移动光标取消自动选区。Tab 或右方向键在补全选区上接受补全，接受时不导航、不插制表符。
- Enter 有可见的明确高亮行时按现有规则选择该行；否则有行内候选就访问其完整目标，最后才提交原始输入；在引擎模式内 Enter 直接搜索关键词。历史更新不得在用户确认后偷偷改写目标。
- Esc 首次取消补全、关闭下拉并保留原始输入，再按回归当前 URL；保持现有两层退出体验。切会话/Tab、失焦时清掉补全及删除抑制状态。
- 若保留当前 2 字符阈值，则单个 `b` 不补全、`ba` 开始候选。截图中的站点图标可复用历史 `faviconUrl`，加载失败回退既有通用图标；是否放入输入框交由 impeccable 决定，不引入新的图标抓取链。

布局、输入框标签与补全选区视觉实施时使用 **impeccable scoped 流程**。保持原生下拉和融合几何，缩窄窗口时不能挤掉实际输入区域。

## 3. 调研单元二：搜索引擎 Tab 模式

### 3.1 该部分要做什么

识别已支持的引擎域名或明确别名，以 Tab 切换到特定引擎搜索，显示独立标签并提交关键词。普通 URL 仍按原逻辑导航。自动发现任意网站搜索、默认搜索引擎设置和联网关键词预测属于额外能力，本轮只比较可行性。

### 3.2 项目现状

[package.json](../../../../package.json) 声明 Electron `^39.2.6`、React `^19.2.1`、antd `^6.6.3`、zustand `^5.0.15`。本轮读取依赖声明，未升级依赖。

`Toolbar.tsx` 的 submitDraft 只 trim 后提交 URL；[main/url.ts](../../../../src/main/browser/url.ts) 给无已识别协议的输入补 https，并用 `new URL()` 检查。它没有引擎选择或搜索词解析，不能把中文单词被解析成域名当成搜索支持。

既有 `navigate(url)` 经 preload 到主进程，作用于来源窗口当前会话的当前 Tab。可直接传构造好的 HTTPS 搜索 URL；无需让 renderer 访问 Node、共享 Cookie 或另开全局网络请求。[Electron WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view)提供页面承载；[Chromium 关键词模式说明](https://chromium.googlesource.com/chromium/src/+/main/docs/site_search_explainer.md)将模式标签、匹配器、引擎模板服务列为 Chrome 自己的浏览器逻辑。这支持本项目继续扩展壳层地址栏的选择。

### 3.3 候选方案

**A：内置引擎配置表 + 自有模式状态（推荐）。** [Chrome 快捷键帮助](https://support.google.com/chrome/answer/157179?hl=en)列出输入引擎名称后按 Tab 的入口；[Chrome 搜索设置帮助](https://support.google.com/chrome/answer/95426?hl=en)使用名称、快捷词和 URL 占位符描述搜索引擎。借鉴数据驱动方式，自行实现小型表，不照搬 Chromium 服务架构。

以下九个候选的核心参数来自 [Chromium 126 固定版本引擎表](https://chromium.googlesource.com/chromium/src/+/refs/tags/126.0.6478.266/components/search_engines/prepopulated_engines.json)。这是历史代码参考，**不是当前网络可用性保证**；下表是去掉 Chrome 分发参数后的拟用模板，Google 固定使用 google.com，百度采用源表中列出的 `/s` 形式。DuckDuckGo 的 `q` 参数另有[官方参数文档](https://duckduckgo.com/duckduckgo-help-pages/settings/params)，Ecosia 提供[官方浏览器接入说明](https://support.ecosia.org/article/657-installing-ecosia-on-your-desktop-device)。`{query}` 为本报告占位，提交时只编码参数值一次。

| 引擎 | 拟支持的域名 | 拟用结果页模板 |
| --- | --- | --- |
| 百度 | baidu.com / www.baidu.com | `https://www.baidu.com/s?ie=utf-8&wd={query}` |
| 必应 | bing.com / www.bing.com / cn.bing.com | `https://www.bing.com/search?q={query}` |
| Google | google.com / www.google.com | `https://www.google.com/search?q={query}` |
| DuckDuckGo | duckduckgo.com / www.duckduckgo.com | `https://duckduckgo.com/?q={query}` |
| Brave Search | search.brave.com | `https://search.brave.com/search?q={query}` |
| Ecosia | ecosia.org / www.ecosia.org | `https://www.ecosia.org/search?q={query}` |
| Yahoo | yahoo.com / www.yahoo.com / search.yahoo.com | `https://search.yahoo.com/search?p={query}` |
| 搜狗 | sogou.com / www.sogou.com | `https://www.sogou.com/web?ie=utf8&query={query}` |
| 360 搜索 | so.com / www.so.com | `https://www.so.com/s?ie=utf-8&q={query}` |

别名是项目拟定交互，不是 Chrome 行为保证：建议至少支持 `百度/baidu`、`必应/bing`、`谷歌/google`、`duckduckgo`、`brave`、`ecosia`、`yahoo`、`搜狗/sogou`、`360`。不启用 `b/g` 等单字母别名，避免与测试域名冲突。地区域名逐项登记，不用 `google.*` 或字符串包含匹配。

**B：OpenSearch 自动发现。** [OpenSearch 描述格式](https://developer.mozilla.org/en-US/docs/Web/XML/Guides/OpenSearch)可声明带 `{searchTerms}` 的 URL，网页可通过描述文件供浏览器发现。可扩展站点覆盖，但需要本项目自己做发现、下载、解析、模板校验、存储和用户管理；不是所有网站都声明，也不能由“曾经访问过”推导搜索能力。

### 3.4 可行性分析

| 维度 | A：内置表 | B：OpenSearch |
| --- | --- | --- |
| 技术匹配 | 九种候选可用统一 GET 模板表达，接既有 navigate | 仅覆盖提供合适描述文件的站点，需自行集成 |
| 规则冲突 | 不改变 IPC、会话分区或持久化 | 若引入用户配置或共享类型，按 L 级流程设计契约；请求必须遵守会话边界 |
| 成本 | 零新增依赖，维护域名和模板；只借鉴结构，复制第三方源码需保留许可 | 多出网络、解析、数据迁移和管理界面，本次范围明显扩大 |

### 3.5 结论与实施建议

结论：**借鉴思路手写**，先用 A；B 留作后续独立需求。不依赖 Chrome 扩展，Electron 的[扩展支持](https://www.electronjs.org/docs/latest/api/extensions)也只承诺部分 API。

建议新增 `src/renderer/src/components/browser/searchEngines.ts`，只存 renderer 本地的 id、域名/别名、显示名称映射和 URL 构造规则，不导出新的跨进程契约。`Toolbar.tsx` 增加 `engineId`、关键词与进入前草稿；标签放在 input 外的同一地址栏容器中，input 里只放关键词，标签不混入复制文本。新增文案同步 `src/shared/i18n/locales/{zh-CN,en-US,zh-TW}/browser.ts`，当前仓库实际有三种语言。

建议交互：

1. 输入完整支持域名、根 URL 或明确别名，按普通 Tab 进入模式；完整输入引擎域名时，即使历史自动追加路径，Tab 也优先进入搜索；只输入部分前缀时先 Tab 接受补全，之后再判断引擎入口。只输入 `b` 而没有明确补全目标时，不猜百度或必应。
2. URL 按 hostname 精确匹配，允许根路径 `/`，拒绝带凭据、非默认端口及非空 path/query/hash 的触发。`baidu.com.evil.test`、`example.test/?next=baidu.com` 和搜索结果页 URL 都不能误触发。
3. 进入模式后显示“搜索 百度”等标签，清空关键词并保留焦点，不立刻导航。关键词非空 Enter 构造 HTTPS URL，复用 submitUrl 和待导航锁定；空关键词 Enter 保持模式，不产生导航。
4. 搜索模式内暂不展示普通 URL 历史建议，防止 Enter 打开旧地址；不调用外部联想接口。Backspace 在关键词为空时退出并恢复进入前草稿；Esc 先退出模式，再按现有规则还原 URL。
5. 失焦或切换会话/Tab 时退出模式，清空其瞬态。导航结果自然由既有历史采集链记录，搜索结果仍使用当前会话 partition 与代理。

提交前用 URL/URLSearchParams 或等价编码处理中文、空格、`&`、`+`、`#`、百分号，避免双重编码与参数注入；不要把整段模板连同查询值一起编码。九个引擎需分别核验 ASCII、中文、特殊字符与地区重定向。无需搜索服务 API key，但访问失败、验证码、登录和地区限制仍可能来自网站。

## 4. 调研单元三：普通 Tab 插入制表符

### 4.1 该部分要做什么

焦点在地址栏时，普通 Tab 不移动到其他组件。除接受行内补全或触发引擎模式外，Tab 替换当前用户选区或在光标处插入 U+0009，光标落在其后；连续 Tab 可连续插入。本要求是项目定制行为，不能称为完整复刻 Chrome。

### 4.2 项目现状

`Toolbar.tsx` 的 onKeyDown 没有处理 Tab，目前会执行默认焦点导航；onBlur 清草稿。input 是 React 受控输入，直接改 DOM 而不更新 draft 会在下次渲染丢失。`submitDraft()` 与 `normalizeInput()` 都 trim 输入，但中间制表符仍会交给 URL 解析器。

### 4.3 候选方案

**A：保留 input，在键盘入口统一更新草稿和选区（推荐）。** [HTML 文本控件选择 API](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#textFieldSelection)支持选择范围和替换选区；[React input 文档](https://react.dev/reference/react-dom/components/input)要求受控值与输入更新同步。使用 selectionStart/selectionEnd 计算新文本，更新 draft，提交 DOM 后恢复光标；不能只调用 setRangeText 而漏掉 React 状态。

**B：改为 contenteditable 编辑器。** [HTML 编辑规范](https://html.spec.whatwg.org/multipage/interaction.html#contenteditable)支持可编辑内容，可做更复杂 token。但必须处理 DOM Range、粘贴清洗、IME 与无障碍，且 Tab 仍需自行拦截。一个标签和单行输入不值得更换编辑器。

### 4.4 可行性分析

| 维度 | A：input 与选区 | B：contenteditable |
| --- | --- | --- |
| 技术匹配 | 能保留真实制表符和单行编辑，复用现有 ref | 能实现，但增加编辑语义 |
| 规则冲突 | 仅限地址栏按键，不接管其他组件或网页 | 容易扩大现有 combobox 的重写范围 |
| 成本 | 零新增依赖，需核验撤销、组合输入和选区 | 自行维护粘贴、选区、读屏，回归面更大 |

### 4.5 结论与实施建议

结论：**借鉴思路手写**，使用 A，与搜索模式共享一个键盘入口。仅处理没有 Ctrl/Meta/Alt 修饰的 Tab，保留 Ctrl+Tab 等已有快捷键。建议 Shift+Tab 保持反向焦点退出通道，详见待确认假设。

| 普通 Tab 时的状态 | 建议结果 |
| --- | --- |
| 正在组合输入 | 不改写组合文本、不切搜索模式；需在目标平台核验 Tab 是否由 IME 消费，并避免落入壳层默认焦点跳转 |
| 导航编辑，原始输入精确命中引擎（即使存在后缀） | 优先进入引擎模式，不插字符 |
| 导航编辑，原始输入未命中引擎且有待接受的行内补全后缀 | 接受补全并把光标放到末尾，不导航、不插字符 |
| 导航编辑，其余状态 | 阻止焦点跳转，在选区/光标处插入一个 U+0009 |
| 已在引擎搜索模式 | 在关键词选区/光标处插入一个 U+0009，不切换引擎 |

自动补全后缀与用户主动选区分开记录：Tab 优先按原始输入判断引擎，未命中才接受自动补全后缀；只有用户主动选区且没有可触发的引擎模式时，才用制表符替换选区。接受补全后不立即重复生成同一后缀，下一次 Tab 才继续判断引擎入口或字符插入。

制表符在值中保留，但显示宽度需真机核验；不要把几个空格冒充制表符。插入后仍走输入变化的建议清理、无效提示清除和光标恢复链；必须核验 Ctrl/Cmd+Z 是否能撤销一次 Tab 插入，React 值更新不能视为浏览器撤销栈已自动正确。

**提交边界需要明确。** [WHATWG URL 解析算法](https://url.spec.whatwg.org/#concept-basic-url-parser)会移除 ASCII tab/newline。本轮 Node 只读验证得到：

- `https://exa\tmple.com` 经 `new URL()` 变成 `https://example.com/`。
- `https://example.com/a\tb` 变成 `https://example.com/ab`。
- 查询里已编码的 `%09` 则保持为 `%09`。

以上 `\t` 表示实际制表符，不是反斜杠和字母 t。建议沿用首尾 trim；普通导航输入中间仍含制表符时，以既有地址栏行内无效状态阻止导航，不静默拼接；搜索模式则将其作为查询值编码后交由引擎解释。若业务要访问包含制表符的路径，用户可明确输入 `%09`。首期可在 Toolbar 的地址栏提交路径检查，避免改动通用 normalizeInput 对其他调用者的行为；是否扩展主进程校验须另核对所有调用点。

## 5. 风险与开放问题

- **最高风险是编辑状态相互覆盖。** 原始输入、补全展示、候选目标、搜索关键词与 pending 不应共用同一个字符串含义。切会话/Tab 时都要纳入现有 `(sessionId, activeTabId)` 清理，异步导航回执沿用作用域守卫。
- **输入法与撤销没有完成桌面验证。** 现有 Enter 的 isComposing 守卫不等于新增补全、Tab、Backspace 已兼容；实施时核验 compositionstart/end、中文候选确认、粘贴、中间编辑、撤销和连续 Tab。不能全局拦截 Tab，更不能影响网页表单。
- **现有下拉存在原生层边界。** 保留不夺焦子窗、实际呈现回执、移动/缩放与屏幕底部空间不足处理，不使用 renderer 弹层覆盖 WebContentsView，不为面板收起网页。
- **搜索模板核对不等于线上验收。** 固定版本 Chromium 模板仅为参考；本轮未验证九家站点在当前网络、地区或代理下均成功。上线前每家实际打开结果页，失效者移出首发名单或修订模板，不承诺所有地区可达。
- **视觉与可访问性。** 搜索标签应可读、窄窗不遮输入；普通 Tab 不跳焦点后需保留明确退出路径。impeccable 实施时检查亮暗主题、主题表面色、主窗/独立窗与屏幕阅读语义。原生子窗与输入框跨文档，不在本次顺手重构其 ARIA 关系。
- **验收建议。** 用 A 会话历史验证补全，用 B 空历史验证无泄漏；同名 tab-1 跨会话、导航在途切会话、独立窗都要覆盖。按九家引擎验证域名/别名进入、空词不提交、中文和特殊字符；非引擎域名及伪装域名不触发搜索；有历史补全时先接受，否则插入 Tab。检查真实 U+0009、选区替换、光标恢复、退格和撤销。改完必跑 typecheck、lint，并用 npm run dev 在 macOS 与 Windows 手验；本轮只改报告，不宣称这些验收已完成。
- **后续流程。** 用户确认本报告后再立实施任务、Step 0 与分阶段计划，修订 PRD 的新增交互，再按 impeccable 做 scoped 设计。推荐先固定纯函数规则，再接输入状态与键盘，最后真机验证和书写回；不触碰历史存储、Cookie、代理和跨窗口转移实现。

## 6. 用户确认结果

2026-11-06 用户逐项确认第 1、2、4、5 项；第 3 项修订为“Tab 也能够补全，Enter 直接搜索”。结合第 1 项不增加默认搜索的确认，Enter 搜索指已进入引擎模式；普通 URL 保持回车访问。后续新增反馈要求完整引擎输入优先于历史补全；正文与以下规则已同步至该最新裁决。

- [x] 搜索引擎首次内置表采用上述九家，域名和明确中英文别名均可触发；不自动学习任意站点、不新增引擎管理设置、不提供联网关键词预测，也不增加普通文字自动走默认引擎搜索。
- [x] 普通 Tab 按最新反馈执行原始输入精确引擎入口优先、其次补全、否则插真实制表符；Shift+Tab 保留反向退出焦点；组合输入期间以不破坏 IME 为准，具体平台行为由技术验证定案。

- [x] 普通 URL 首尾 Tab 沿用 trim，中间 Tab 阻止提交并使用既有行内无效提示；搜索词中的 Tab 编码为查询参数，不在本地偷偷删除或换成空格。

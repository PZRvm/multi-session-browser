# 扩展删除回收与代理兼容都需要修复

## 范围与实测环境

用户要求先运行项目验证两项是否需要做，需要时新建分支并先写计划，不进入功能实现。验证基线 dev@6e47219，macOS、Electron 45.3.0 / Chromium 156.0.8078.96；前两轮均以 `npm run dev:agent` 启动真实项目，使用 `/tmp/msb-backlog-20261115-first`、`/tmp/msb-backlog-20261115-second` 两个新 profile，端口 6173/CDP 9337。所有窗口隐藏，focusedWindows=0；未读写日常 profile。

复用现有开发自检入口，临时接入仓库外探针后恢复工具原文，确认 git diff 为空。测试未修改 src/、package 或构建配置。探针和原始 JSON 归档到 `tools/extension-backlog/`。本轮只有 macOS 证据，不等同 Windows/完整插件 UI 验收。

补充复跑：第三个新 profile `/tmp/msb-backlog-20261115-third-fixed` 使用归档探针，删除后只纯计算预期 ID，不调用可能建立扩展副本的 resolveLoadedId；两项仍复现。第三次接线首次因相对路径错误在探针启动前失败，修正后用全新 profile 完成，此为诊断接线错误，不是产品失败。

## 1. 会话删掉后，被新安装重新触达

通过真实 preload IPC 创建 A/B、激活、导入官方 SwitchyOmega；记录 A 的 Session、挂载登记与引擎。随后调用真实 `window.api.sessions.delete` 删除 A，等待元数据消失及其 Partitions 目录实际删除，再从产品导入路径安装 Cookie-Editor。

三轮相同结果：

| 检查点 | 实际结果 |
| --- | --- |
| A 删除后的会话元数据 | 已不存在 |
| A 删除后的分区目录 | 确实消失 |
| A 的 mounted 与 engine | 均仍存在，旧插件仍在该 Session 加载 |
| 再安装 Cookie-Editor | 产品返回安装成功；新插件被加载到已删 A 的 Session |
| 再看 A 分区目录 | 重新出现；A 元数据仍不存在 |

这已从静态风险变为真实复现：删除后的 Session 仍被管理层 remountAll 枚举，触发加载与目录重建。没有测试跨用户数据泄漏，不作该宣称。入口在 `extensions/management.ts` 的 mountedSessions/remountAll，登记在 dev-entry.ts 与 runtime/index.ts，删除在 browser/registry.ts。

## 2. 代理 API 存在，回调成功却没生效

固定官方 SwitchyOmega 2.5.20，安装 ID `padekgcemlokbadohgkifijomclgjgif`，SHA-256 `0b7b185ef8bd0dc45287d8bbc487e33a759f8e9a4556bdf072945185c50b0c1b`。真实加载并打开其 options.html，在该扩展页调用自身依赖的 `chrome.proxy.settings.set`。使用本地源站、代理两个独立 HTTP 服务，目标为开发测试域 `msb-fixture.test`，避免 localhost 的隐式旁路干扰。

三轮相同结果：chrome.proxy 是 object、settings.set 是 function；回调不带 lastError，但 Session.resolveProxy 仍返回 DIRECT，真实 session.fetch 收到源站标记。主进程日志出现 `Unknown Extension API - types.ChromeSetting.set`，另有 clear 未支持日志。

正向对照：在同一 A 通过应用已有 sessions.setProxy 设置相同代理，resolveProxy 变为 PROXY，真实请求收到代理标记；B 保持 DIRECT。因而不能以“代理 API 不存在”描述此缺口，也不能将回调不报错当作兼容成功。前两轮 options 页采样偏早仍有模板占位，第三轮已渲染设置项，不能据此认定 UI 损坏；完整页面/后台主要操作仍需在计划中逐项跑通。

## 可行路线与依据

- 回收：借鉴宿主生命周期协议手写封锁/排空/卸载。公开 removeExtension 可用于卸载，但固定库 4.10.0 没有完整 dispose，不能承诺删掉宿主 Map 就释放其全部 WeakMap/observer；设计阶段需枚举资源，必要时扩展固定依赖补丁。仅过滤 remountAll 不足以处理在途 mount 和资源退出。
- 代理：采用 Electron Session.setProxy 作为底层，宿主按原生扩展身份补 ChromeSetting 的 set/get/clear/onChange。当前内置代理已证明底层有效。只换 Electron 版本或只测试对象存在都不足以证明兼容；不采用“给插件回调假成功”的路径。
- 两项独立，先处理回收再做代理，避免代理卸载/删除清理继续依赖已知失效生命周期。内置代理与插件控制的优先权、PAC 及完整 SwitchyOmega UI 边界需在代理计划设计门禁落定。

官方参考：[Electron 扩展仅支持 API 子集](https://www.electronjs.org/docs/latest/api/extensions)、[Session.setProxy](https://www.electronjs.org/docs/latest/api/session#sessetproxyconfig)、[Chrome proxy](https://developer.chrome.com/docs/extensions/reference/api/proxy)、[ChromeSetting 生命周期/控制权](https://developer.chrome.com/docs/extensions/reference/api/types#type-ChromeSetting)。固定样本来自[SwitchyOmega 官方 v2.5.20](https://github.com/FelisCatus/SwitchyOmega/releases/tag/v2.5.20)。

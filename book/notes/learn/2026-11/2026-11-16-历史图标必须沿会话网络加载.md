# 历史图标必须沿会话网络加载

地址栏建议由独立 BrowserWindow 承载。它未指定 partition，使用默认 Session；直接 img src 加载历史 favicon URL 不会继承被测网页的会话 Cookie 和代理。存储 URL 也不等于保存图片。

2026-11-16 在隔离 dev:agent 中，用同一图标 URL 按 Cookie 返回不同的 A/B 图标。主进程的对应 Session.fetch 携带 owner=a/b，弹窗分别显示 A/B；子窗图片请求只有 data URL，没有远程图标请求。停掉夹具服务并重启应用后，已缓存的图标仍能显示。

实施时保留子窗默认分区，图片在主进程按可信 sender 会话获取，再传图片数据；不要为继承登录态把整个应用界面切入网页分区。只保存 favicon URL 的旧历史和 Chrome 导入记录可在显示时尝试站点 /favicon.ico。网络和图片解码均可能失败，展示层必须独立保留搜索图标兜底，并在 src 改变时清除失败状态。

## 真实站点补验：下载上限也会阻止缓存

用户反馈 SCRM 登录页反复搜索仍无图标。2026-11-16 直接读取该页的 link rel=icon，指向 `/xingqun-gravity-icon.png`：HTTP 200、PNG、512×512、96,024 字节。`historyIcons.ts` 的下载上限是 65,536 字节，在写缓存前即拒绝。站点 `/favicon.ico` 则返回与登录页相同的 3,220 字节 HTML（同 SHA-256），HTTP 200 不表示图标有效。

将真实响应字节输入当前图标模块复现：有图标地址时原图因超限拒绝、根路径因 HTML 拒绝；无图标地址的旧历史只走根路径。两种情况连续 resolve 两次均返回 null、缓存文件为零；第二次受 60 秒失败冷却而不重复请求。该证据说明是候选图片未取得，不是原子写盘失效。查阅本地相关历史也能看到 null 和实际图标 URL，两类都存在。

不要把缓存单图上限直接当作网络原图上限。后续应分别限制下载体积和落盘体积，允许获取常见大尺寸 favicon 后缩小；旧历史的根图标路径失败时，还需考虑读取页面声明的图标。问题见 [SCRM 站点图标无法缓存](../../issue/2026-11/2026-11-16-SCRM站点图标无法缓存.md)。本次仅排查，未修改产品代码。

同日用户随后选择仅提高上限：下载和缓存同步放宽到 256 KiB，未增加缩图或页面发现。真实 96,024 字节响应已验证可落盘、重复读取和重建服务读盘命中；当前实现以该选择为准，以上分离与缩图只是后续方向。

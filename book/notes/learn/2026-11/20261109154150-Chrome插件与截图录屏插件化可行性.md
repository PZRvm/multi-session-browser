# Chrome 插件与截图、录屏插件化调研报告

> 创建时间：2026-11-09 15:41:50（Asia/Shanghai）
> 需求来源：添加一次插件后所有会话可用；另做截图、录屏两个插件，原有功能暂时保留。
> 用户补充：两个插件也要能安装在普通 Chrome 中独立使用；CRX 与 Chrome 商店下载安装同一期交付。
> 调研单元：4 个；状态：调研完成，待用户确认，未实施。
> 范围修订：2026-11-09，用户将 CRX 与商店安装纳入本期；原“只加载目录”的建议由本文当前方案取代。
> 定级：本轮为 S 级文档调研，通过官方资料、代码核对、临时隔离实验和 book 索引检查验证结论；后续实现触及会话生命周期、权限和共享契约，预计按 L 级重新定级，补 Step 0 与完整流程。

## 1. 需求理解

### 1.1 功能目标

测试人员添加一次插件后，现有会话和后来创建的会话都能使用。安装入口包括本地 CRX 和 Chrome 商店下载安装，保留已解压目录入口供调试。安装清单全局统一，先不提供按会话安装、禁用或选择插件的能力。网页本身的 Cookie、缓存、登录态与代理仍按会话隔离。

另外交付两个独立的 Manifest V3 扩展包：截图插件、录屏插件。它们既能在本项目运行，也能在普通 Chrome 中独立运行；本项目已有截图与录屏入口、编辑器和行为暂时保留。

“不需要插件隔离”目前能确定的是不需要按会话配置插件。Electron 会让各分区中的插件存储、后台实例自然分开；若还要求插件自己的设置、历史和后台任务跨会话实时共用，需要另外建设全局状态服务，不属于最小加载方案。

### 1.2 未知点清单

- [x] Electron 能否加载 Chrome 插件？能加载已解压扩展，但只支持部分 API，不能承诺任意商店插件。见 §2。
- [x] 能否所有会话共用？能共用安装包和安装清单，逐分区加载；不能只加载到 defaultSession。见 §2。
- [x] MV3 是否一定不可用？本机 39.8.10 的后台消息实验成功；仍须按具体 API 验证。见 §2.2。
- [x] 截图插件能否直接复用 Chrome API？Chrome 可以；本机 Electron 缺少 captureVisibleTab，需要宿主适配。见 §3。
- [x] 录屏插件能否直接搬现有代码？MediaRecorder 思路可复用，采集、文件保存和生命周期要双端适配。见 §4。
- [x] 只做一个加载入口是否足够？不足以支持依赖工具栏 action、弹出页或缺失 API 的插件。见 §2.5。
- [x] CRX 与商店是否需要另外开发？需要，可共用下载/验包/安装流水线并借用现成库；本期一并纳入。见 §5。

### 1.3 拆分判断

1. 全局扩展安装与分区加载：截图、录屏插件在本项目运行的基础。
2. 截图插件：依赖加载器与受控扩展页桥接；Chrome 端可独立开发验证。
3. 录屏插件：同样依赖加载器，另需持续采集、后台控制与输出收尾；建议在截图适配验证后推进。
4. CRX 与 Chrome 商店安装：和扩展运行兼容分别建设，安装完成后共同接入单元一的全局加载。

## 2. 调研单元一：全会话 Chrome 扩展支持

### 2.1 该部分要做什么

支持 Chrome 扩展的全局安装、工具栏入口、弹出页、基础 Tab/窗口交互与重启恢复；安装来源包含 CRX、Chrome 商店和已解压目录。账号同步、定时自动更新与逐会话开关仍待需求确定。适用范围应写成“支持经验证的 Chrome 扩展”，不能承诺所有 Chrome 扩展无差别可用。

### 2.2 项目现状

- [package.json](../../../../package.json) 声明 Electron `^39.2.6`；本机安装为 **39.8.10 / Chromium 142.0.7444.265**，由隔离进程的 process.versions 验证。未安装扩展兼容库。
- [registry.ts](../../../../src/main/browser/registry.ts) 的 partitionFor 是分区单源，ensureManager 懒建会话并安装权限处理；[manager.ts](../../../../src/main/browser/manager.ts) 的 newTab 创建 WebContentsView，网页没有应用 preload。没有扩展加载或管理模块。
- ensureManager 和 newTab 当前均有同步调用链。loadExtension 是异步的，后续设计必须明确首个导航前的初始化屏障，不能随手启动 Promise 后立即导航，导致首屏内容脚本漏注入。
- [架构规则](../../../guidelines/architecture.md)、[PRD](../../../docs/requirements/PRD.md) §4.1 要求网页环境独立；[PRODUCT.md](../../../../PRODUCT.md) 要求效率优先。[DESIGN.md](../../../../DESIGN.md) 和项目规则要求选择/确认使用原生界面，不能新增渲染层模态或结果 toast。
- [electron-builder.yml](../../../../electron-builder.yml) 使用 ASAR。内置扩展将来应放真实资源目录，例如 extraResources；用户扩展复制到 userData 下的应用管理目录，不依赖用户下载目录长期存在。

**隔离实验，2026-11-09，macOS，本机 Electron 39.8.10：**

使用临时 userData 和两个全新 `persist:a`、`persist:b` 分区；同一路径加载同一个最小 MV3 扩展。扩展声明 service_worker、storage、tabCapture、offscreen、downloads、activeTab；在同分区隐藏的扩展页检查 API、写 storage.local，并向 worker 发消息。

| 检查 | a / b 结果 | 能说明什么 |
| --- | --- | --- |
| loadExtension | 均成功，返回相同扩展 ID | 同包可在多个持久分区加载 |
| runtime.sendMessage → worker | 均返回 `{worker: true}` | 此版本最小 MV3 后台通信可运行 |
| storage.local 首次读 marker | a、b 均为空，a 已先写入 | 同 ID 的扩展存储仍按分区分开 |
| tabs.captureVisibleTab | undefined / undefined | 不能直接使用 Chrome 截图调用 |
| chrome.tabCapture | undefined / undefined | 不能直接使用 Chrome 标签页录制调用 |
| chrome.downloads、chrome.action | 均 undefined | 下载与工具栏动作需适配 |
| offscreen.createDocument | function / function | 接口存在；未验证实际创建与媒体采集 |

加载还输出 `Permission 'tabCapture' is unknown` 与 `Permission 'downloads' is unknown`。初轮脚本因销毁最后一个窗口触发应用退出，第二分区页面加载失败；保留进程生命周期后重跑，两分区均完成上表检查。这里只把完整重跑作为结果。

实验没有读取应用真实分区或 Chrome profile，没有修改 src、安装依赖、加载第三方插件。没有验证 WebContentsView 内容脚本首屏、真实工具栏 action、插件热安装、Windows 或打包环境；不据此声称已完成产品兼容验证。

### 2.3 候选方案

**A：Electron 原生 Extensions API + 薄加载器。**

全局登记扩展清单，各会话惰性初始化时调用 `ses.extensions.loadExtension`；在运行中的分区补加载，在下次启动时重新加载。官方仅支持已解压目录和持久 session，加载状态不会跨应用退出自动恢复。[39.8.10 Extensions API](https://raw.githubusercontent.com/electron/electron/v39.8.10/docs/api/extensions-api.md)

**B：electron-chrome-extensions 兼容层。**

它补充 action、popup、tabs、windows 等概念，宿主通过 addTab/selectTab 和窗口回调对接自身模型。源码 README 明确把 captureVisibleTab 列为未实现；没有承诺 tabCapture 或 downloads，所以装库不能直接解决两款工具插件的底层能力。[上游能力与接入文档](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-extensions/README.md)

本轮读取的源码包版本为 4.10.0，MIT，生产依赖为 debug；开发 Electron 为 ^44.1.0。这里是所读源码版本，未核验 npm dist-tag，也没有实测其与本项目 Electron 39 的组合。[包声明](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-extensions/package.json)

### 2.4 可行性分析

| 维度 | A：原生加载 | B：兼容库 |
| --- | --- | --- |
| 技术匹配 | 本机已验证同包多分区加载；适合内容脚本、DevTools 和受控自研扩展 | 更适合需要标准工具栏 action/popup、tabs/windows 的第三方扩展；仍有 API 缺口 |
| 规则冲突 | 保留所有网页分区，符合隔离规则 | 同样须每分区对接；Tab 与窗口映射必须服从 registry，不能接管其所有权 |
| 成本 | 零新增第三方依赖；宿主自行提供最小入口和受控桥 | 除包本身，还要接线 Tab 创建/选择/删除、主窗与独立窗、切会话、打包 preload |

不能以“插件不隔离”为由把所有网页改用同一个 Session。Electron 的[版本化支持文档](https://raw.githubusercontent.com/electron/electron/v39.8.10/docs/api/extensions.md)明确扩展按 session 安装，且不追求完整 Chrome 兼容；latest 文档与 39 的支持表已有差异，实施应锁定实际版本。

### 2.5 结论与实施建议

结论：**采用现成方案**，按修订范围以 B 的运行兼容层为候选，底层仍使用 A 加载扩展；结合 §5 的安装流水线。用户要使用普通 Chrome 插件，action/popup 与基础 tabs/windows 应列入本期，不能只做目录加载。候选库须先通过 Electron 39 兼容实验，不能把 README 的支持清单当成本项目已验收结果。

本期运行支持建议：

1. 新增 `src/main/browser/extensions/`，负责 manifest 校验、托管目录复制、全局清单、逐分区加载 Promise 缓存和失败状态。安装记录独立于 sessions.json；重复安装、扩展 ID/版本冲突须明确处理。
2. `registry.ts` 在每个会话首次建页前等待扩展准备完成；现有会话安装后补加载。已加载页面上的内容脚本不保证追补，首期明确重新加载网页后生效，避免静默刷新正在测试的表单。
3. 新建、恢复、克隆后首开、关闭后重开都走同一准备入口；会话删除时释放分区运行态，保留全局安装包。卸载至少支持全局移除并卸载已初始化分区；原生选择目录、原生错误反馈。
4. 新增 `src/shared/extensions.ts` 与 preload 窄桥；renderer 只显示扩展名、安装状态和移除入口，不直接访问 Session。补简中、繁中、英文现有字典，界面实施使用 impeccable。
5. 本期接入标准 action/popup 入口，并将所有页面 Tab 的创建、选中、关闭和跨窗归属变化同步给兼容层；不同会话使用各自运行上下文。扩展 popup 要由原生视图/窗口承载，不能用 renderer 浮层盖在 WebContentsView 上。自研插件的专用工具页桥仍保留；只用宿主菜单打开自研页面的旧最小建议已不足以覆盖本期目标。
6. 受控工具页由主进程在所属 Session 的 BrowserWindow 承载，仅这些已登记的内置扩展页获得专用 preload。manifest 的标准 action 入口留给 Chrome；本项目端另用启动约定打开同一工具页。不得给普通网页或任意外部扩展开放截图、录屏特权。

安装包、清单全局共享，扩展实例仍每会话一份。若后续要求扩展自身设置全局一致，另做明确的设置协议；直接合并插件数据库或共享网页 Session 都不适合本项目。

## 3. 调研单元二：独立截图插件

### 3.1 该部分要做什么

交付独立扩展 ID 和 manifest 的截图插件，首期覆盖当前网页可视区、复制、PNG 下载；截图编辑可作为后续增量复用。整页滚动拼接、区域取景、桌面截图不默认加入本次范围。原有截图功能继续可用。

### 3.2 项目现状

[capture.ts](../../../../src/main/browser/capture.ts) 已有当前窗口/会话/Tab 解析、webContents.capturePage、空图重试、PNG、原生剪贴板、下载命名和缓存版本校验。[captureEditorWindow.ts](../../../../src/main/browser/captureEditorWindow.ts) 管理独立编辑窗，[captureEditor/](../../../../src/renderer/src/components/browser/captureEditor/) 使用 React/Konva。

现有截图 IPC 只接受 registry 认可的应用窗口，不能直接让扩展伪装应用 renderer 调用。共享类型在 [src/shared/capture.ts](../../../../src/shared/capture.ts)，现行行为在 PRD §3.10.1；[既有编辑器调研](../2026-10/20261014130059-截图编辑器.md)可提供选型背景，但当前实现的多窗口快照语义应以代码和最新 PRD 为准。

### 3.3 候选方案

**A：全部使用标准 Chrome 扩展 API。**

通过用户点击获得 activeTab 权限，调用 tabs.captureVisibleTab 获取 PNG；用独立扩展页承载预览/编辑、Clipboard API 复制、downloads.download 下载。captureVisibleTab 截取窗口当前活动 Tab，需 activeTab 或相应授权；采集需在编辑页激活前完成，否则会截到编辑页。[Chrome tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-captureVisibleTab)、[downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads)

**B：共用插件业务与编辑界面，设置 Chrome / MSB 两个适配器。**

Chrome 使用 A；本项目工具页经专用桥调用 capturePage、剪贴板和下载能力。复用现有底层处理，但桥接身份与版本账本独立设计，不能直接放开原 IPC。[Electron webContents.capturePage](https://www.electronjs.org/docs/latest/api/web-contents#contentscapturepagerect-opts)

另查过 html2canvas：它从 DOM 重绘，不是真实截图，存在 CSS 和跨域图像限制，不适合测试取证的画面保真要求。[官方限制说明](https://html2canvas.hertzen.com/documentation/)

### 3.4 可行性分析

| 维度 | A：仅 Chrome API | B：双端适配 |
| --- | --- | --- |
| 技术匹配 | 可在 Chrome 独立工作，本机 Electron 缺少采集/下载 API | 覆盖两端，可共用图像编辑代码 |
| 规则冲突 | 无网页分区冲突，但不能满足本项目运行目标 | 必须核验扩展页 sender、分区和固定目标，不扩大普通网页权限 |
| 成本 | Chrome 端较低；为 Electron 补齐通用标准 API 成本会上升 | 增加少量专用桥与构建入口；可复用 React/Konva 依赖和现有原生服务 |

### 3.5 结论与实施建议

结论：**借鉴思路手写**，采用 B。做标准 MV3 插件，同时提供 MSB 适配；Chrome 独立运行不依赖本项目、Native Messaging 或本地 HTTP 服务。

- 建议新增 `extensions/screenshot/`（独立构建入口、manifest、后台、工具页）和 `extensions/shared/`（仅两款插件确实共用的适配接口与字典生成）。这是建议目录，不是本轮新增源码。
- 能力接口控制在 `captureViewport`、`copyImage`、`saveImage`；Chrome 接 chrome.* 与 Web API，本项目接受控 preload。宿主选择适配器以桥握手和能力版本为准，不用浏览器 UA 猜测。
- `src/main/browser/extensions/bridge.ts` 将“宿主点击时的窗口、会话、Tab、webContents”绑定到这次动作；验证 e.sender、senderFrame URL、扩展 ID、Session 与记录的窗口身份。不可相信扩展传来的 sessionId 或任意文件路径。
- 在 capture.ts 中将必需的底层动作抽成可供旧入口和新桥调用的服务，保留旧 IPC 与 UI。避免顺便重构整套截图域；若范围只做最小截图，可先保留现有编辑器，新插件暂不上全部编辑工具。
- Chrome 没有本项目会话名，默认文件名用页面标题或插件名加时间；本项目可沿用会话名。剪贴板操作放在有 DOM 的扩展页，并验证 clipboardWrite、焦点和用户操作条件；不承诺后台 worker 能直接写图片剪贴板。
- 若编辑器首版要迁移全部工具，拆开纯图像/标注逻辑与 window.api、Electron 窗口控制依赖。两端使用扩展页承载编辑，打包本地脚本，遵守 MV3 CSP。界面工作使用 impeccable。

## 4. 调研单元三：独立录屏插件

### 4.1 该部分要做什么

交付另一个扩展 ID 的录屏插件。建议最小范围为当前 Tab 视频、不含音频，支持开始、暂停、继续、停止与 MP4 下载；既有原生录屏继续保留。同 Tab 导航可继续录制，不能把录制管线放在随页面导航销毁的 content script 或随失焦关闭的 action popup 中。

### 4.2 项目现状

- [recording/index.ts](../../../../src/main/browser/recording/index.ts) 持有全局单飞状态、IPC、目标 Tab、生命周期和落盘反馈。当前工具栏切 Tab/切会话、被录 Tab 关闭或跨窗转移会停止保存，见 PRD §3.10.2—3.10.3。
- [captureView.ts](../../../../src/main/browser/recording/captureView.ts) 创建同会话分区的隐藏 BrowserWindow，setDisplayMediaRequestHandler 只给可信采集器授予目标 WebFrameMain。
- [permissions.ts](../../../../src/main/browser/permissions.ts) 与 collectorGate 只放行已登记采集器；不允许任意网页借机获取捕获流。不能为了插件录屏把这层改成普遍批准。
- [capturePage.html](../../../../src/main/browser/recording/capturePage.html) 使用 getDisplayMedia（audio:false）与 `video/mp4;codecs=avc1` 的 MediaRecorder，等待分块链排空后上报 stopped；[fileWriter.ts](../../../../src/main/browser/recording/fileWriter.ts) 串行写临时文件并收尾。媒体录制过程在页面环境，文件写入依赖 Node，不能原样拷入 Chrome 扩展。

### 4.3 候选方案

**A：标准 MV3 tabCapture + offscreen + MediaRecorder。**

Chrome 中由 action 用户操作触发，service worker 调用 tabCapture.getMediaStreamId，offscreen 文档通过 getUserMedia 获取流并持有 MediaRecorder；worker 只管命令与状态路由。Chrome 116 起支持 worker 取流 ID 并交给 offscreen；关闭 popup 不结束录制。[Chrome 官方采集方案](https://developer.chrome.com/docs/extensions/how-to/web-platform/screen-capture)、[tabCapture](https://developer.chrome.com/docs/extensions/reference/api/tabCapture)、[offscreen](https://developer.chrome.com/docs/extensions/reference/api/offscreen)

**B：插件控制界面共用，Chrome 采用 A，MSB 调用现有录屏服务。**

在本项目中，插件负责操作与显示，宿主继续采集、编码、写文件；Chrome 中插件自己完成全部录制与下载。底层路线不同，对用户提供相同的开始/暂停/继续/停止操作。[Electron Session API](https://www.electronjs.org/docs/latest/api/session#sessetdisplaymediarequesthandlerhandler-opts)支持宿主裁定捕获目标，项目已有真实接线。

不推荐用 getDisplayMedia 的“选择桌面/窗口”流程替代当前 Tab 一键录制：它会改变目标选择和交互，而且现有 Electron 权限门明确拒绝未经登记的请求。也不采用逐帧截图拼视频：性能、时间戳和清晰度成本都高于现有媒体管线。

### 4.4 可行性分析

| 维度 | A：纯标准路线 | B：双端适配 |
| --- | --- | --- |
| 技术匹配 | Chrome 的成熟官方路线；本机 Electron tabCapture 不存在，offscreen 方法存在也不能补足流来源 | Chrome 独立运行，MSB 复用既有同分区捕获与 MP4 输出 |
| 规则冲突 | 全量搬进 Electron 仍要处理授予门、窗口作用域和单飞 | 旧/新入口共用一个原生状态机，符合全应用单飞与原有权限边界 |
| 成本 | 标准插件中等；补成通用 Electron tabCapture 兼容层较大 | 专用控制桥和 Chrome 录制管线，改动可限定在录屏域 |

### 4.5 结论与实施建议

结论：**借鉴思路手写**，采用 B。参考 Chrome 官方示例自研插件，不引入转码框架或大型第三方录屏产品。

1. 建议新增 `extensions/recorder/`，独立 manifest、service worker、offscreen 页面和控制页；权限按需使用 tabCapture、offscreen、storage、downloads。Chrome 最低版本至少 116，但最低可发布版本还须通过 MP4 编码能力实测确定。
2. Chrome 端：action 点击锚定 targetTabId；先取得流 ID，再创建/激活控制界面。offscreen 负责媒体流、暂停/继续、累计时长和资源清理；跨页面导航保持；worker 重启后向 offscreen 查询真实状态，不能只依赖 worker 内存布尔值。
3. 编码前检测 `MediaRecorder.isTypeSupported('video/mp4;codecs=avc1')`。本项目已有支持不代表所有 Chrome/OS 都支持。沿用 MP4 要求时，不支持就明确失败；WebM 回退必须另行确认，不能把 WebM 数据改后缀当 MP4。
4. Chrome 端 Blob URL 在 offscreen 等有 DOM 的长生命周期页创建，经消息交给 worker 调 downloads；offscreen 只支持 runtime 扩展 API，不能直接调用 downloads。下载完成/失败后再回收 URL 与文档。首版设置明确时长/体积边界；长录制需评估 IndexedDB 分块和编码器 stop 时才刷块的内存压力，不能声称 timeslice 保证恒定内存。
5. MSB 端不直接给插件媒体流，也不另装 setDisplayMediaRequestHandler，避免覆盖当前分区唯一的授予处理器。由受控插件页桥调用录屏服务的 start/pause/resume/stop/status，复用现有采集器、文件 writer 和生命周期订阅。
6. 原生入口和插件入口共享同一个单飞仲裁：旧入口开始后插件能显示状态并控制，反向同样成立；第二次开始仍拒绝。需要明确控制授权，而不是给任何扩展开放旧 pause/stop 通道。全局录屏运行态不需要合并各会话 chrome.storage。
7. 普通 Chrome 没有“会话切换”，需用 tabs.onActivated/onRemoved 和目标窗口状态制定对应停止规则。控制页自身的打开/聚焦必须豁免，防止插件为了展示控制台而立刻把自己的录制停止；该行为与本项目现有切 Tab 停止规则的差异须写入插件需求。

## 5. 调研单元四：本地 CRX 与 Chrome 商店安装

### 5.1 该部分要做什么

用户已要求同一期完成两种入口：选择本地 `.crx` 安装，以及在本项目打开 Chrome Web Store、从商品页安装。安装一次，所有会话可用；下载和验包只执行一次，不按会话重复下载。

三个概念分别验收：安装来源（CRX/商店/目录）、运行兼容（插件依赖的浏览器 API）、自研插件发布（把我们自己的插件提交商店）。前两项是本期范围，最后一项尚未被明确要求。CRX 是分发格式，解包后仍走同一个 Electron 加载器，不会自动补上缺失的 API。

### 5.2 项目现状

本项目没有 CRX 解析、Chrome 商店下载或安装桥，现有 Chrome 数据导入也不包含扩展，不能复用为扩展安装器。Electron 39 的 loadExtension 本身不接受 CRX，见 §2 引用的版本文档。

2026-11-09 在本机做了只读网络探测：Dark Reader 的 Chrome 商店详情页返回 HTTP 200；按候选库构造、携带本机 Chromium 142 版本的更新下载地址，Range 请求返回 HTTP 206，类型为 `application/x-chrome-extension`，前 8 字节为 `Cr24` 与版本 3。仅读取 16 字节后关闭，没有下载完整包或安装插件。这证明本次网络环境能访问该样本的商店与 CRX 下载入口，不代表完整安装和运行通过。

### 5.3 候选方案

**A：采用 electron-chrome-web-store，适配全局安装事务。**

库提供商店页面安装桥、按扩展 ID 安装、目录加载和更新功能，可挂到指定 Electron Session。所读源码包为 0.13.0、MIT，依赖 adm-zip、pbf、debug 与 @types/chrome；未核验 npm 当前发布版本。运行兼容仍需 §2 的另一套能力层。[README](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/README.md)、[包声明](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/package.json)

源码 installer.ts 使用 Google 更新下载端点，解析 CRX、提取 ZIP、向 manifest 写入公钥以稳定 ID，然后调用 loadExtension。本地文件读取/解析函数未作为顶层公共 API 导出；所以“本地 CRX 导入”仍要加受控适配，不能声称安装 npm 包即全部完成。[安装器源码](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/src/browser/installer.ts)

**B：借鉴上游协议，自建下载与 CRX 安装模块。**

保留统一商店入口，自研 CRX 解析、签名验证、解包、清单管理与下载协调；商店网页桥可有选择地借鉴上游。CRX3 的头部、公钥、签名和 ZIP 结构有 Chromium 一手定义。[CRX3 格式](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/crx_file/crx3.proto)

### 5.4 可行性分析

| 维度 | A：现成库加适配 | B：自建安装模块 |
| --- | --- | --- |
| 技术匹配 | 商店网页桥与下载协议已有实现；需验证 Electron 39 和当前商店页面 | 本地 CRX 和全局事务可完全按本项目设计；网页桥与协议维护工作更多 |
| 规则冲突 | 默认操作指定单个 Session，需改为全局一次安装、逐分区加载 | 可直接服从 registry 与全局清单；仍须维护商店来源校验 |
| 成本 | 安装来源部分中等，另有来源校验、验包和多会话接线 | 中等至较高，长期维护商店页面变化的负担更大 |

查阅源码发现两项必须核实的接入条件，不据此修改上游：installer.ts 的所读路径匹配了公钥与扩展 ID，但未见对 CRX 包签名的密码学验证；api.ts 对商店来源使用 startsWith 判断，不能替代精确 origin 判断。采用前应补全或替换相关路径，再做畸形包、错误签名、错误来源测试。[商店桥源码](https://github.com/samuelmaddock/electron-browser-shell/blob/master/packages/electron-chrome-web-store/src/browser/api.ts)

### 5.5 结论与实施建议

结论：**借鉴思路手写**。优先复用候选 A 的商店交互和下载思路，对安装事务、CRX 验证及全局分发做受控适配；不直接调用默认安装/自动更新路径替代本项目的全局协调。若锁定的依赖版本能提供所需受控入口，可减少自研代码；先做兼容实验再决定是否保留小型 fork。

统一流水线：

```text
本地 CRX ────┐
商店下载 CRX ─┼→ 临时目录 → 验包/读取实际权限 → 原生安装确认
已解压目录 ──┘       → 全局托管目录与安装清单 → 各会话加载
```

- **CRX 入口**：原生文件选择器选 `.crx`，校验格式版本、签名、ID、实际 manifest 与宿主最低版本；解压限制目录逃逸、符号链接和异常体积。CRX3 是当前主目标，CRX2 要明确支持或给出不支持反馈，不能当普通 ZIP 静默处理。原文件由用户保存，应用只管理自己的副本。
- **商店入口**：通过专门的商店窗口/页面打开 Chrome Web Store，接入标准商品页安装动作；本期还可提供粘贴商品 URL/ID 的备用入口，但备用入口不替代商品页安装。页面桥只授予精确的 HTTPS 商店 origin 与已登记 webContents，导航后失效；普通测试网页不能调用商店安装通道。
- **全局协调**：新增 extensions/installService.ts、crxInstaller.ts、webStore.ts、store.ts 等职责模块；所有入口按扩展 ID 串行、下载一次、版本目录暂存、成功后提交清单。商店窗口 Session 仅负责商店界面，不承载所有测试网页；提交后再向业务分区分发。
- **升级/卸载**：同一 ID 不重复安装；不同版本明确升级或拒绝降级，更新失败保留旧版本；卸载先从所有已初始化分区移除，再清理包目录。不得每个会话各跑一个库内 updater，共写同一安装目录；默认自动更新应先关闭，由宿主统一协调。定时更新是否本期开放另定。
- **确认与反馈**：以实际下载包中的权限为准，不能仅相信网页传来的描述；使用原生安装确认与原生结果框。跨分区部分加载失败必须可辨识、可重试，不能单个分区安装成功就返回“全部成功”。界面设计使用 impeccable。
- **验收**：至少覆盖一个真实商店插件的商品页安装、同包本地 CRX 安装、全会话使用、重启恢复、主/独立窗口 action 和 popup；另测损坏包、断网、取消、重复安装、覆盖升级、卸载。运行验收样本由用户常用插件补齐。

额外成本分别来自：CRX 的验包与导入、商店的网页桥与下载、两者共用的安装事务；运行兼容还有独立成本。它们可以同一期分步完成，但目前没有完成完整插件实验，不给出未经验证的人日承诺，也不承诺全商店插件百分之百可用。

## 6. 风险与开放问题

| 问题 | 实施前怎么收敛 |
| --- | --- |
| 加载成功不代表插件可用 | 用计划安装的具体插件核对 manifest/API；内容脚本、DevTools、action、网络修改分开验收 |
| 扩展默认 storage/后台仍分区 | 首期只统一安装，不额外做插件数据共享；若要求共享设置，另定协议 |
| 新增后台会影响关闭/克隆 | registry 目前会关闭该分区全部 webContents；验证扩展后台重生、关闭后重开、克隆快照和卸载清理，不能只测主窗 |
| 动作在途时切会话或删除 | 宿主按点击时目标和生命周期校验，不在结果返回时重新获取当前活动 Tab；删除后不得重建分区 |
| 插件页面导航到普通网页 | 专用桥按每次 IPC 的 frame URL、身份、Session 校验，失效即拒绝；不把应用完整 window.api 传给插件 |
| 第三方权限兼容 | 不给所有插件开放本项目专用桥；先做实际插件清单，原生安装反馈显示不支持项 |
| 安装目录与扩展 ID | 托管复制路径须稳定，自研插件用固定 manifest key 稳定 ID；跨平台、更新、移除、重装均验证 |
| 页面首屏与运行中安装 | 首开等待 loadExtension；现有网页需要重新加载后验证，不能宣称热安装自动覆盖已打开页面 |
| 两端输出行为不同 | Chrome 会受浏览器下载设置和剪贴板条件影响，不能承诺和 Electron 一样无条件静默落盘；Chrome 标准浏览器界面与 MSB 原生反馈分别适配 |
| 跨平台与打包 | 本轮仅 macOS 最小实验；Windows、打包后资源路径、真实网站、音视频编码与长录制尚未验证 |

建议的推进顺序与退出条件：

1. **运行基础设施**：内容脚本、工具栏 action/popup 和基础 Tab API 在两会话、未来新会话、重启、克隆、主/独立窗口中生效；登录态仍互不影响。补测真实 WebContentsView 首屏和卸载；失败不能伪报全局成功。
2. **最小截图插件**：Chrome 与 MSB 均完成可视区采集、复制和 PNG 下载，和原入口并存；切会话竞态不截错页。编辑器是否首版迁移单独确定。
3. **录屏插件**：两端均完成跨导航录制、暂停/继续、MP4 可播放、关闭目标收尾；MSB 新旧入口互斥一致；验证 1 分钟、10 分钟与设定上限附近的内存/尾块完整性。
4. **本期完成安装来源**：CRX 与商店页面安装共用验包、全局清单和加载器；验证断网/取消/重复安装/覆盖升级/卸载。实施可在运行基础设施之后、工具插件之前接入，这里的序号不表示延期。定时自动更新的范围另定。

这份报告提供研究结论与建议边界，不替代 L 级实施计划。实施前同步唯一 PRD 的新扩展范围与插件双端行为；原生截图/录屏的删除留待用户另行决定。

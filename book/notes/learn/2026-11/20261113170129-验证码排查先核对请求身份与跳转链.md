# 验证码排查要比较实际请求，不能只看 navigator.userAgent

用户明确本次症状是频繁要求证明“我是真人”，Cookie 正常。调查目标是人机风控触发频率，不是登录态丢失；Cookie 探针仅作排除性记录，不能用存储正常推导人机验证正常，也不应建议清 Cookie 来验证此问题。

2026-11-13 排查飞书进入豆包频繁验证码，隔离实例复现：主文档和 JS UA 含中文应用名，页面 fetch 的 UA 同一位置却变为 `??????`；主文档与 fetch 的 Client Hints 也不同。只查看网页 UA 会漏掉这类差异。探针直接接收请求头；Node 将非 ASCII 头按 latin1 读取，展示时需要正确解码，避免制造日志乱码的假证据。

应用把 window.open 转为新 WebContentsView，只传 URL 时会丢掉来源。本地同源 target=_blank 链接打开后，新页 document.referrer 为空，但仍能读到同一 partition 的诊断 Cookie/localStorage。排查时应把跳转语义和会话切换分开验证。

用户提供 URL 后，安装版现场确认验证码位于飞书内嵌豆包 iframe 的聊天界面，不走新标签创建链，因此应将上述来源问题移出这次主因排序。独立豆包首页的区域限制也不能代替实际嵌入路径。

继续比较页面、iframe、Dedicated Worker、Service Worker，发现前三者没有宿主桥，但普通网站 Service Worker 可见 `electron` 与 `__msbShimBridge` 对象。原因是扩展 preload 对全部 Service Worker 放行，没有先限定扩展来源。检查页面隔离不能只验证 window；跨进程、跨上下文逐一验证才可能发现这类误注入。

本地只将 UA 中中文应用名换成 ASCII 名称、保留 Electron 和真实引擎版本后，页面与 fetch UA 恢复一致；favicon 仍可能走默认 UA。标签级覆盖的实验不能直接当作应用级修复，所有请求和上下文仍须复验。

以上差异不等于网站因此弹验证码。要确认原因，仍需同账号、同出口、同路径逐项对照。Chrome headless 新 profile 可做接口和字段对照，不能代表用户日常 Chrome 的风控结果。本次两种引擎访问豆包公开页都遇到区域限制，没有复现用户的登录现场验证码。

实测参数、代码入口和待验证项见[完整排查记录](../../issue/2026-11/20261113170129-网站频繁验证码与浏览器身份排查.md)。

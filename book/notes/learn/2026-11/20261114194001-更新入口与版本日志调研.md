# 更新入口与版本日志功能调研报告

> 创建时间：2026-11-14 19:40:01（Asia/Shanghai）
> 需求来源：主窗右上角主题圆形更新钮，Windows避让系统功能区，点击先看本次日志再下载。
> 调研单元：1个；状态：方案已确认，进入实施。

## 1. 需求理解

### 1.1 功能目标

用户更新前先了解本次变化。入口在整个主窗右上角、搜索区上方；Windows位于系统窗口控制组左侧。采用每版本Markdown日志和原生窗口，用户已确认。关于页检查入口保留，独立窗沿用同一右端入口。

### 1.2 未知点清单

- [x] 日志来源：electron-updater 6.8.9的UpdateInfo.releaseNotes已支持字符串或版本数组；元数据显式带notes时GitHubProvider不会替换为feed正文。
- [x] 日志展示：复用现有workspacePickerWindow原生模态子窗口，扩内部app-update场景，保持网页可见。
- [x] 发布单源：版本Markdown同时写入更新清单和GitHub Release，测试版本带固定示例日志。

### 1.3 拆分判断

整体一个调研单元；日志来源、展示和入口共同决定用户下载前的操作。

## 2. 调研单元：更新入口与日志

### 2.1 该部分要做什么

调整位置、圆钮和主题色，新增候选版本日志读取、展示与发布机制；不修改安装事务、隔离或已有R1/R2处理状态。

### 2.2 项目现状

UpdateEntry直接下载，SessionPanel/IndependentWindowFrame分别挂载。TabStrip已有40px顶栏与Windows WCO避让。updates单例及可信IPC已具备；workspacePickerWindow和WorkspacePickerWindow承载原生sheet。release.mjs当前只拼发布说明，没有本次产品变更；update-assets.mjs合并各平台清单。

### 2.3 候选方案

A：每版本Markdown进更新清单，复用原生sheet。库getReleaseInfo会读取releaseInfo.releaseNotesFile并把正文放到latest清单；已有GitHubProvider优先采用清单notes。本地和线上同源，无额外网络请求。

B：只读取GitHub Release正文。少一份本地日志管理，但已有正文含源码和签名说明，用户日志与发布元信息混杂；本地generic源也需要另一条路径。

C：自建日志服务。可管理多语言，但增加服务器、网络失败及授权面，本期没有需要。

来源：[electron-builder更新文档](https://www.electron.build/v26/docs/features/auto-update/)、[Electron父子及模态窗口](https://www.electronjs.org/docs/latest/api/browser-window#modal-windows)、本机app-builder-lib/out/publish/updateInfoBuilder.js与electron-updater/out/providers/GitHubProvider.js。

### 2.4 可行性分析

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 技术匹配 | 已锁定库支持，同一清单覆盖本地和线上 | 线上可用，本地需补路径 | 需新增服务 |
| 规则冲突 | 原生sheet，主进程数据所有权不变 | 需处理HTML正文，不能直接注入 | 扩大外部依赖 |
| 成本 | 不增依赖，复用窗口机制 | 需HTML净化及额外规则 | 维护成本高 |

### 2.5 结论与实施建议

借鉴思路手写，采用A。新增版本日志读取工具和安全规范化，扩UpdateSnapshot与showDetails窄桥；app-update sheet只返回当前版本对应的下载/安装意图，主进程再验版本和来源。入口走impeccable shape/polish，使用现有主题色。发布前缺日志明确失败，不虚构历史变更。

## 3. 风险与开放问题

Markdown/HTML不作为可执行内容；限制长度，版本数组仅选当前候选。日志为空明确显示缺省说明。原生窗口关闭零下载；迟到动作不得切换版本或绕过构建策略。WCO、窄窗和多Tab需要检查。

## 4. 待确认假设

无阻塞假设。用户已确认主窗右上角、Windows功能区左侧以及版本日志+原生窗口。

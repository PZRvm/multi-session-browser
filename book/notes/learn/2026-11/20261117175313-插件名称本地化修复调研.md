# 插件名称本地化修复功能调研报告

> 创建时间：2026-11-17 17:53:13（Asia/Shanghai）
> 需求来源：修复插件列表显示占位符的问题，适配 i18n，先调研
> 调研单元：1 个
> 状态：调研完成，待用户确认（未实施）

## 1. 需求理解

### 1.1 功能目标

使使用 `__MSG_…__` 名称的扩展显示真实名称，覆盖商店安装、本地 CRX 和已安装记录。名称随应用简体中文、繁体中文、英文切换，翻译缺失时有明确回退；旧插件无需重装。

本轮为 S 级只读调研与文档返写，核对代码、官方规范和已验签样本，不修改产品代码。

### 1.2 未知点清单

- [x] 占位符能否还原？能。真实样本已有 `_locales` 消息，缺口在宿主读取链，见 2.2。
- [x] 如何适配应用 i18n？复用主进程语言态，按完整 locale、基础语言、扩展默认语言逐条找消息，见 2.5。
- [x] 是否能直接用 Electron 名称？API 有 name，但没有承诺随本项目语言态动态更新，且依赖扩展已加载，见 2.3。
- [x] 旧记录是否需要迁移？推荐显示时重新解析，跳过旧占位符，不改持久化 schema，见 2.5。

### 1.3 拆分判断

整体作为一个调研单元：统一解决宿主名称元数据的解析与刷新。插件自身页面的语言运行时不在此次范围。

## 2. 调研单元：宿主插件名称解析

### 2.1 该部分要做什么

统一提供可展示名称，供设置列表、插件面板和固定图标提示使用；不修改扩展包、会话分区或插件加载权限。

### 2.2 项目现状

- [问题记录](../../issue/2026-11/2026-11-17-扩展本地化名称占位符直接显示.md)保存真实 CRX 的验签、摘要和字段证据。样本 1.0.6 的 name 是 `__MSG_extName__`，default_locale 为 en；简体消息为“暗色主题 - 网络暗色阅读器”，英文为“Dark Theme - Dark Reader for Web”，没有 zh_TW 消息。
- `src/main/extensions/install/crx.ts`直接返回原始 manifest.name；`install/store.ts`与`install/service.ts`将其保存。`src/main/extensions/management.ts`再次原样读取，list 优先使用记录里的 r.name，只有 name 缺失时才回填。只修改安装步骤无法修好现存记录。
- `src/main/i18n.ts`提供 getCurrentLanguage 与 onMainLanguageChanged；`src/shared/i18n/index.ts`注册 zh-CN、zh-TW、en-US。扩展翻译来自扩展自己的 messages.json，不应抄进应用字典；新增宿主文案仍须进入三语言字典。
- `PaneExtensions.tsx`和`Toolbar.tsx`订阅 extensions.onChanged 重取 list。`useExtensionsPanelWindow.ts`开面板时获取 list，但没有订阅此广播；已展开面板需要补刷新。管理模块已有全窗 broadcastExtensionsChanged，可复用通道，不新增 IPC 契约。
- package.json 固定 Electron 45.3.0。主进程负责文件读取，renderer 只消费现有 ExtensionListItem.name，符合分层约束。

### 2.3 候选方案

**方案 A：使用 Electron 已加载 Extension.name**

从会话已加载扩展获取名称。[Extension 对象](https://www.electronjs.org/docs/latest/api/structures/extension)具有 name，[加载说明](https://www.electronjs.org/docs/latest/api/extensions)表明扩展按 session 加载。可复用加载结果，但未加载或加载失败的安装项无法覆盖。官方未承诺 name 随本项目语言设置变化，因此不能作为统一来源。

**方案 B：安装时解析并保存一个翻译名称**

按 [Chrome i18n 规则](https://developer.chrome.com/docs/extensions/reference/api/i18n)读取消息，在现有安装入口写入翻译。能修正新安装初始显示，但单一 name 字段无法同时代表三种语言，切换语言会陈旧；旧记录仍需额外处理。为每种语言增加持久化字段又引入迁移成本。

**方案 C：展示时按应用语言解析（推荐）**

主进程 list 读取原始名称与消息，每次按当前应用语言求值，避免旧 r.name 占位符遮蔽结果。参考 [Chrome 消息格式](https://developer.chrome.com/docs/extensions/how-to/ui/localization-message-formats)实现大小写不敏感的消息键及静态占位内容处理；输出仍为现有 name 字符串。

### 2.4 可行性分析

| 维度 | A：运行时名称 | B：安装时保存 | C：展示时解析 |
| --- | --- | --- | --- |
| 技术匹配 | 依赖已加载会话，语言更新无保证 | 首次显示可用，旧记录和切换不完整 | 新旧记录、未加载项和语言切换均可覆盖 |
| 规则冲突 | 不应为取名称额外加载插件 | 若增加语言字段涉及持久化迁移 | 文件读取留在主进程，可保持现有契约 |
| 成本 | 代码少，运行态耦合高 | 多入口修改，容易保存过期名称 | 无新依赖，增加小型解析器及边界验证 |

### 2.5 结论与实施建议

结论：**借鉴思路手写**。借鉴 Chrome 的消息查找规则，在主进程实现限定于宿主显示名称的解析器。

1. 新增 `src/main/extensions/localizedName.ts`，输入包目录、manifest 原始字段和明确的应用语言，输出名称或无有效结果。普通名称保留；含消息引用的名称解析所有引用，未解析完整时转回退，不把半截占位符当成功结果。
2. locale 映射与顺序：zh-CN → zh_CN → zh → default_locale；zh-TW → zh_TW → zh → default_locale；en-US → en_US → en → default_locale。去重，并在“文件存在但目标键缺失”时继续回退。样本在简体显示中文，英文和繁体显示默认英文；不自行进行繁简转换。
3. 消息键按大小写不敏感查找，支持静态 `$NAME$` 内容和美元符号转义；无调用参数的动态替换、不合法类型、空白结果、残留引用均须定义降级，避免声称实现完整 chrome.i18n 运行时。无法取得有效包名称时，优先保留旧记录中可用的普通名称，最后使用扩展 ID；不把原始 `__MSG_…__` 作为兜底展示。
4. 修改 `management.ts` 的 readManifestExtra 与 list 名称优先级：有效包解析名称优先，再取有效旧名称、ID。既有占位符记录由下次 list 自动修复显示，无需重装或落盘迁移。原安装记录及 `.package.json`可继续保留原始元数据，不保存当前语言的派生值；本轮不必修改 crx/store/service 的安装语义。
5. 在管理模块注册语言变化回调，复用 extensions.changed 广播；`useExtensionsPanelWindow.ts`为打开的面板补重取。列表请求捕获当次语言，消费者丢弃旧请求结果，避免快速切换时慢回包覆盖新名称；固定图标拖拽结束后补齐被暂时抑制的刷新。
6. locale 字段不可信：限制合法代码，固定 `_locales/<locale>/messages.json` 结构，检查实际路径仍在包内并拒绝符号链接越界，限制文件字节数；读取、解析异常按当前候选失败处理，不能让单个插件拖垮全列表。缓存如需增加，应同时包含包版本与语言，更新和卸载时失效；首版可先不缓存。

建议实施按 M 级单功能缺陷走 Step 0 与完整流程，维持 IPC、schema 与生命周期契约不变；若实施发现必须修改这些边界，升级 L。没有布局或样式变化。

验收应覆盖：真实样本三语言、无需重装的旧占位符记录、普通名称、大小写键、局部翻译缺键、静态占位符、文件缺失/坏 JSON/超限/路径越界、快速切换语言，以及设置列表/打开的面板/固定图标提示同步。运行 typecheck、lint，并在隔离 dev:agent 数据中验证；本轮未执行产品验收。

## 3. 风险与开放问题

宿主名称随应用语言变化，不代表插件内部网页也能热切换语言；这是不同的运行时范围。自研解析器必须明确支持边界，不能只对 extName 特判。已有“缺名回填”逻辑应避免将当前语言派生名称永久写回。

包文件损坏时可能只能显示 ID，这是保证列表仍可操作的最终回退。具体字节上限与占位符边界应在实施设计和样本验证中固定。

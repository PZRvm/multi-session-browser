# 自研插件 CRX 失效三因排查（2026-11-12）

## 现象与定性

store 插件在应用内正常，自研截图/录屏插件 CRX 导入后图标不渲染、功能不可用。定性为三个独立原因，另有一个次要 bug：

1. **CRX 过时**：icon 缺失的唯一原因，screenshot.crx 还内含已删除的 PiP 时代代码。
2. **shim 注入机制缺陷**：页面上下文扩展 API 缺失，功能不可用的主技术根因。
3. **popup-less 插件点击缺口**：截图插件在应用内点不动，与 CRX 新旧无关。
4. 次要：清单 name 字段读写往返剥离（应用内有自愈，非用户可见）。

## 一、CRX 过时（icon 缺失的直接原因）

- dist 两个 CRX 内没有 icons/ 目录，manifest 里也没有 icons/default_icon 字段。面板图标读取链断在第一环：readManifestExtra（management.ts）从解包目录读 manifest 的图标字段（≤48px）并转 dataURL，字段与文件全缺则 icon=undefined，面板渲染占位。
- screenshot.crx 含已删除的 PiP 时代文件（pip-lifecycle.js、editor-bridge.js，6946ad3 加入、bbfdda6 删除），background.js 与当前源码不一致；recorder 代码与当前一致，但 manifest 与 icons 同样是旧树态。
- CRX 文件 mtime（Nov 12 01:33:46）晚于图标提交 5034a60（Nov 11 18:29），但内容对应更早的树态 → 打包自一个陈旧副本目录（副本已清理，未找到原处），需用当前源码目录加原 pem 重打包。
- 解包加载本身成功（loadExtension 成功，仅 `Permission 'downloads'/'tabCapture' is unknown` 警告——Electron 清单校验的未知权限警告，非错误）；「无法引入」不是加载失败。
- dist 已替换为新包（同 pem → 同 ID），端到端复测 icon 渲染恢复。重打包用正式 Chrome 同样可用：`--pack-extension=<源码目录> --pack-extension-key=extensions/dist/<名>.pem --no-first-run --user-data-dir=/tmp/临时profile`（--user-data-dir 隔离，不触碰日常 Chrome profile）。

## 二、shim 只落在 preload 隔离上下文（功能失效的主技术根因）

- 库 4.10 的 preload 在 contextIsolation 下经 contextBridge.executeInMainWorld 把 chrome API 注入主世界，并执行 Object.freeze(chrome)。
- preload-guard.ts 生成的守卫 preload 把 shim（captureVisibleTab、downloads.download 实装、tabCapture.getMediaStreamId、offscreen.createDocument、runtime.getContexts、getUserMedia tab 源改写）赋值在 preload 隔离上下文的 globalThis.chrome 上。扩展页面（popup/editor/offscreen 页）主世界里的 chrome 是库冻结的对象——shim 对页面脚本不可见，赋值也被冻结态静默吞掉。
- SW 上下文无 contextIsolation，shim 落在唯一上下文上有效（机制推演，未直接实测）。
- 实测（隔离 userData + --remote-debugging-port + CDP Runtime.evaluate）：录屏 popup 主世界 tabCapture=undefined、captureVisibleTab=undefined、downloads.download 仍是库 noop 桩（invoke 返回 id:undefined）、getUserMedia 无 shim 标记；chrome 对象 Object.isFrozen=true，试探性赋值不可写；runtime.getContexts 是 Electron 原生实现（无参调用报 No matching signature），不是宿主 shim。
- 应用日志实证：录屏 popup 点「开始录制」在 popup.js:60 抛 Cannot read properties of undefined (reading 'getMediaStreamId')（一次会话内连续 6 次点击 6 次同错）。
- 影响：录屏启动链第一步即死；截图编辑器「下载」是库 noop 静默无效；M2 offscreen 链依赖的 getUserMedia tab 源改写同样失效。

## 三、popup-less 插件点击缺口

- 工具栏面板点击自研截图插件（manifest 有 action 无 default_popup）→ openPopup → readPopupPath 无 popup → 直接返回 NO_POPUP，没有派发 chrome.action.onClicked。截图插件在应用内点不动，与 CRX 新旧无关（换新包也一样）。electron-chrome-extensions 引擎本身有 onClicked 派发路径（activateBrowserAction 无 popup 时 sendEvent browserAction.onClicked），宿主自建 popup 链路没有走到它。

## 四、次要 bug：清单 name 字段往返剥离

- manifest-store.ts 的 validateInstallRecord 校验返回对象不含 name 字段——每次读盘校验都把 name 剥掉（隔离复测稳定复现）。应用内 list 有「名称自愈」从解包 manifest 回填，面板显示不受影响，但清单数据持续丢字段，upgrade 幂等判断等依赖完整记录的场景要留意。

## 复核方法与修复方向

- 复核环境：MSB_USER_DATA 隔离数据目录 + --remote-debugging-port + CDP 驱动（Runtime.evaluate 调 window.api.extensions.list / openPopup，popup 上下文做 typeof 检查）；CRX 内容用 adm-zip 截 CRX3 头后直接列 zip 条目比对源码树。
- CRX 重打包已替用户完成（dist 内新包已验证 icon 渲染恢复）；shim 与点击缺口是宿主侧修复项，方向：shim 改经 contextBridge.executeInMainWorld 注入主世界（冻结前完成或在库注入后补挂）、popup-less 点击派发 onClicked、validateInstallRecord 补 name 字段。

## 修复轮新增的平台事实（2026-11-12 下午，端到端全绿后固化）

- **库把 chrome 注入主世界后 Object.freeze(chrome)**：一切宿主 shim 想被页面脚本看见，必须在库 freeze 前进入主世界。可行路径 = preload 里先 contextBridge.exposeInMainWorld('桥')，再把消费点字符串补丁进库 mainWorldScript 的 Object.freeze(chrome) 之前（锚点唯一出现，带形状断言）。SW 的 mainWorldScript 直接调用（无隔离时）与页面 executeInMainWorld 共用同一份补丁文本。
- **Electron35+ 扩展 SW 的 invoke 不进 ipcMain.handle**——每个 SW 实例有独立注册表，必须监听 session.serviceWorkers 的 running-status-changed，'starting' 时 getWorkerFromVersionID 拿 ServiceWorkerMain 后逐实例 sw.ipc.handle 注册（库 crx-msg 同款模式）。SW 空闲终止后重启会再发 'starting' 且 ipc 注册表随实例重置，**必须重挂，不能做版本去重**。
- **SW 隔离 preload 世界里 chrome.runtime.id 不可得**（库注入只进主世界）——SW 路的扩展 ID 用 sw.scope（chrome-extension://<id>/）平台权威派生并注入 payload，不能靠调用方自报。
- **Electron45 原生 chrome.offscreen.createDocument 存在**但建的是无 preload 的原生采集文档（getUserMedia 'tab' 源在其内不可用，报 Error starting tab capture）——必须强制覆盖为宿主采集窗 shim（判断「原生缺函数才覆盖」会被原生实现绕过）。
- **库 windows.create 依赖宿主 impl.createWindow**（构造器把多余选项全部当 store impl；缺省抛 createWindow is not implemented，仅 console 静默）——自研截图编辑器窗依赖此链，宿主按扩展 ID 反查挂载会话建窗。
- **sandbox:false 会让会话级 preload 里的 contextBridge 抛「contextIsolation is enabled」**（采集窗曾因此拿不到任何注入）；采集窗/编辑器窗统一用默认 sandbox + contextIsolation: true。
- **capturePage 抖动**：合成器未就绪报 display surface/UnknownVizError，窗口遮挡时持续失败——用 stayHidden/stayAwake 参数（Electron45 签名 capturePage(rect?, opts?)）+ 三次轻量重试。
- **getUserMedia 'tab' 源改写后产物无音轨**：宿主音频如实降级（audio:false）会让「请求了音频」的调用方在建 AudioContext.createMediaStreamSource 时抛 InvalidStateError——插件侧按「音轨在才保活」守卫（纯视频录制照常）。
- 调试基建：MSB_USER_DATA 隔离 + --remote-debugging-port + CDP Runtime.evaluate 驱动真机全链路（列表/点击/openPopup/popup 内点击/下载落盘核对），本轮十余次重启迭代全靠它。

## 分区隔离修复轮（2026-11-12 晚，多分区交叉+重启恢复全绿后固化）

- **Electron 扩展运行时按扩展 ID 全局路由**：runtime 消息（chrome.runtime.sendMessage）、storage、事件都不按 session 分区隔离。多分区挂同一扩展 → 消息投给"当前存活"的那个分区 SW、storage 读写跨分区错位——复现：A 会话截图，编辑器消息跑到 B 分区 SW 读 B 的 storage →「截图不存在」；录屏 start 投错分区 → 状态污染 → 点了没反应。**这不是"旧会话不兼容"，是任意多会话场景的分区串扰**（哪个分区"赢"取决于谁的 SW 活着）。
- **修复 = 分区副本目录（路径即身份）**：`packages/<installId>.partitions/<sha256(partition)前16>`，cp 安装目录剔除 .package.json，manifest.json 删除 key → ID 从「CRX 公钥」切换为「路径哈希」（extensionIdFromPath，Chromium id_util GenerateIdForPath 同构）。分区稳定跨重启一致、分区间不同、升级不改路径（目录名不含版本）。native 隔离天然成立，顺带实现会话级插件数据隔离（截图/录屏产物分分区）。
- **映射与迁移**：面板/清单继续用安装 ID 记账，openPopup/卸载经 runtime.resolveLoadedId（确定性路径派生，无需状态表）重映射；挂载时对「已按安装 ID 加载」的历史实例做迁移清理（removeExtension）。卸载清理 `<id>.partitions/`。
- **恢复场景兜底**：扩展随分区持久化、SW 可能早于本轮接线启动——registerSessionShimIpc 接线时先枚举 `serviceWorkers.getAllRunning()` 对存活 SW 补挂 handler，再挂 running-status-changed 事件路。
- **编辑器空白真相**：编辑器入口第一步 `chrome.runtime.sendMessage('screenshot.load')` 失败即整页空（root 不挂载）；单分区下本就正常，多分区串扰时必现。图3 的空白 = 跨分区读到空 storage 的报错渲染。
- 驱动注意：openPopup 依赖 list() 先刷新 manifestCache（真实用户流程先开面板天然满足；脚本直调必须补 list），否则 popup-less 派发误判。

## 正式环境验收轮（2026-11-12 晚，真实旧会话全绿后固化）

- **「算出标记却从未落盘」缺陷**：partition-copy.ts 的 ensurePartitionExtensionCopy 读取标记比对，但写入代码从未存在——每次会话重激活/remountAll 都 rm+cp 整个副本目录，**把运行中扩展的加载目录删了重建**；加载器又因「已加载」跳过重载，坏一次永久坏。用户正式环境「旧会话所有插件失效、新会话正常」的直接根因（旧会话=被反复重激活的会话）。
- **为什么此前的隔离环境测试没抓到**：驱动每次运行每会话只挂载一次；重激活同会话（切走再切回）才触发 rm+cp-under-live——正式用户的真实使用路径。教训：**回归用例必须覆盖「同进程内二次挂载同一分区」**。
- 修复三件套：标记真正落盘（staging 内写好随目录换装）；staging→rename 安全换装（rm 副本目录只发生在换装瞬间）；换装发生在已加载实例之下时自愈重载（removeExtension + loadExtension 新目录）。正式环境验证：两个旧会话 + 切回重激活共三轮截图/录屏全绿，标记文件 16 个落盘，22 个会话数据零变动。
- **真机操作纪律**：正式 userData 上绝不能双实例并发（LevelDB 锁冲突）；打包版占用时要先优雅退出（quit 走退出冲刷）再启动修复版；测试只做会话切换/截图/取消录制这类只读或零落盘动作。

## 录屏产物损坏轮（2026-11-13 凌晨，ffprobe 可播放验证后固化）

- **dataURL 分隔符陷阱（本次产物全坏的直接根因）**：录屏产物 dataURL 形如 `data:video/mp4;codecs=avc1,mp4a.40.2;base64,<body>`——MIME 的 codecs 参数自带逗号。下载 shim 用 `indexOf(',')` 取 base64 主体，取到的是 `'mp4a.40.2;base64,'+body`：解码器静默跳过 `.`/`;` 等无效字符后按错位对齐解码，**整个文件从第 0 字节起全坏**。签名特征：落盘大小 = 源 + 十几字节、文件无任何容器魔数、多次录制坏文件头部字节完全相同（确定性变换）。修法：永远以 `';base64,'` 标记截取。
- **FileReader.readAsDataURL 会在「扩展页 + executeJavaScript」上下文挂死**：onloadstart 触发后 onload 永不投递（9KB blob 多轮实测，关节流/可见性改造均无效）。绕开：`blob.arrayBuffer()`（同上下文实测正常）+ 32KB 分块 `String.fromCharCode` + btoa。顺带修掉隐藏扩展页的页面冻结/后台降级：采集窗改「可见 + 屏幕外坐标」+ backgroundThrottling:false + 应用级 disable-renderer-backgrounding/disable-backgrounding-occluded-windows。
- **录制状态机楔死机制**：收尾链挂起 → 状态持久化在 finalizing → SW 存储视图陈旧 + startRecording 要求 idle / cancel 不收 finalizing → 后续 start/cancel 全被静默忽略；popup render() 对 rec=null 早返回，界面永远显示陈旧状态。修法：stop 路径 15s 收尾看门狗解楔 + popup rec=null 时重置空闲 UI。**教训：跨上下文持久化状态机必须带看门狗**。
- 持久化会话的 SW 早启于本轮 preload 注册（第二/三次启动实例必现）→ 首挂载强制 removeExtension+loadExtension 重载（同进程后续重激活跳过，保护录制中会话）。
- 残留小账：重名落盘 shim 会自动加序号（recording-2-1.mp4），但回传扩展的 filename 仍是原名，popup 显示名可能与实际文件名不同（低危）。
- 坏文件不可恢复：错位 base64 解码不可逆（原始 base64 串已丢），旧录制文件只能删除重录。
- **采集窗可见化的回退（2026-11-13）**：为绕 FileReader 挂死曾把采集窗改「可见+屏幕外坐标 x:-2400」——多显示器布局下负坐标落在左侧实屏上，录制时用户屏幕出现白块。arrayBuffer+btoa 绕开后可见化前提不再成立，已恢复 show:false 隐藏形态（两轮真机：首装+持久化恢复路径均正常落盘 ftyp isom）。教训：**涉及屏幕坐标的绕行方案必须考虑多显示器负坐标区**，用户不可见的判断要用 `screen.getAllDisplays()` 并集核算而不是拍负数。

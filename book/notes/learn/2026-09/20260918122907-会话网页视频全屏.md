# 会话网页视频全屏 功能调研报告

> 创建时间：2026-09-18 12:29（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户原话要点（"现在这个浏览器看视频无法全屏功能，帮我调研一下我这个项目能否加上这个功能"）
> 调研单元：1 个（根因单一链路：权限 → 窗口事件 → bounds/UI，跨层但同一能力点，不拆）
> 状态：调研完成，待用户确认（未实施）

## 1. 需求理解

### 1.1 功能目标

在会话浏览区（WebContentsView 内嵌网页）中观看视频时，点击网页自带的全屏按钮（bilibili / YouTube 等的 HTML5 Fullscreen API 路径）应当像 Chrome 一样进入全屏：窗口进入操作系统原生全屏、视频铺满整屏、应用壳（左侧会话面板 / Tab 栏 / 工具栏）暂时不可见；按 ESC 或网页全屏按钮退出后恢复原布局。当前现象是点击全屏按钮完全无反应。用户是专业测试人员，看视频是测试场景的组成部分（如验证页面视频功能），行为对齐 Chrome 惯例即可，不需要引导式设计。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 未知点 1：Electron 里 WebContentsView 的 HTML5 全屏默认行为是什么、为什么不生效？——**两层根因**：本项目的权限 broker 拒绝 `fullscreen` 权限（见 2.3/2.4）；且 Electron 默认只把宿主窗口置为 OS 全屏、不调整 view bounds（见 2.3 方案 A 原理）。详见第 2 节。
- [x] 未知点 2：有没有官方 API / 成熟方案支撑？——有：BrowserWindow 与 webContents 均有 `enter-html-full-screen` / `leave-html-full-screen` 事件；开源 Electron 浏览器 browser-base 用同款事件驱动接管 view bounds（见 2.3）。
- [x] 未知点 3：全屏时 bounds 与现有"renderer 锚点上报"数据流是否冲突？——不冲突，反而天然契合：renderer 全屏态隐藏壳 UI 后锚点自然扩满窗口，ResizeObserver 沿现有 IPC 通道上报整窗矩形，主进程零新增布局代码（见 2.5）。
- [x] 未知点 4：切 Tab / 切会话 / 悬挂弹层 / DevTools 等边界是否可解？——大部分由 Chromium 与现有架构自然承担，个别点需实现时处理与实测（见第 3 节风险）。

### 1.3 拆分判断

结论：整体 1 个调研单元。虽然改动会落在 main / preload 通道语义 / renderer 三层，但它们是同一条因果链（权限放行 → 全屏事件接管 bounds → renderer 壳层响应）上的一个能力点，"现状 + 方案"可在单节内说清，强行拆单元只会重复引用同一批文件。

## 2. 调研单元：会话网页 HTML5 视频全屏

### 2.1 该部分要做什么

负责：让会话浏览区内的网页（含独立窗口 tear-off 的 Tab）通过 HTML5 Fullscreen API 进入 / 退出全屏，视觉与交互对齐 Chrome（进 OS 全屏、壳 UI 隐藏、ESC 退出恢复）。

不负责：F11 / Cmd+Ctrl+F 的"窗口全屏"快捷键（OS 级窗口全屏是另一个能力点，见"待确认假设"）；网页内播放器自绘的"网页铺满"伪全屏（站点自身行为，不需要我们做任何事）；画中画（站点/Chromium 自带）。

### 2.2 项目现状

**版本事实**（`package.json`）：Electron ^39.2.6、React ^19.2.1、antd ^6.6.3、zustand ^5.0.15。本报告引用的 Electron 官方文档为 latest（覆盖 39），源码引自主分支同名实现。

**视图与布局链路**（与全屏直接相关，均已打开核实）：

- `src/main/browser/manager.ts`——每会话一个 `createTabManager`，持有全部 `WebContentsView`（每 Tab 一个 view，`TabEntry.view`）。**bounds 单向数据流**：renderer 锚点矩形经 IPC `browser:set-bounds` → `setBounds()`（627 行起）作用于该窗口激活 view；`boundsByWindow` 按窗口缓存最后有效矩形，`suspendedByWindow`（200 行）是"按窗口分槽的全局态覆盖 bounds"的现成先例——全屏态可完全复用这个模式。**当前没有任何 `enter-html-full-screen` 相关处理**。
- `src/renderer/src/components/browser/BrowserContentAnchor.tsx` + `useBrowserBounds.ts`——锚点 `.chrome-content`（`app.css` 2323 行，flex:1 占满剩余空间），ResizeObserver + rAF 节流上报视口矩形；弹层悬挂（`overlayDepth > 0`）上报零矩形收起原生层。**全屏若表现为"锚点自然扩满窗口"，这条数据流无需任何改动即可跟随窗口 resize**。
- `src/renderer/src/components/BrowserFrame.tsx`（主窗口）/ `IndependentWindowFrame.tsx`（独立窗口）——壳层结构：TabStrip + Toolbar + chrome-body（内含锚点）；主窗口外层还有左侧会话面板。两 Frame 共用同一锚点组件，全屏壳层隐藏需两处同步。
- `src/main/browser/ipc.ts` + `src/shared/browser.ts`——浏览器域命令与状态推送通道；快照 `BrowserSnapshot` 已带 `windowId` 作用域语义，全屏态并入快照推送有现成模式可循。

**根因一（权限拒绝）**：`src/main/browser/permissions.ts` 的 broker 为每个会话分区注册 `setPermissionRequestHandler` 与 `setPermissionCheckHandler`（277 / 261 行），白名单只有 `clipboard-sanitized-write` 与 `media`（纯视频），**其余权限一律 `finish(false)` 拒绝**。Electron 的 HTML 全屏请求恰好走权限路由：webContents `EnterFullscreenModeForTab` → `RequestFullscreenPermission` → session 权限 handler（permission 字符串 `'fullscreen'`，见 2.3 出处）。因此本项目里点视频全屏按钮，请求在权限层就被拒绝——这是"完全没反应"的第一层原因。

**根因二（view bounds / 壳 UI 无响应）**：Electron 默认（`disableHtmlFullscreenWindowResize: false`）在 HTML 全屏获批后把**宿主窗口** `SetFullScreen(true)`（macOS 原生全屏），但**不会调整 WebContentsView 的 bounds**，renderer 壳 UI 也不会隐藏——即使权限放行，看到的也会是"窗口进了全屏、视频仍嵌在原内容区"的破相布局。

**PRD 与设计事实**：

- `book/docs/requirements/PRD.md` 219 行（3.7.3）："HTML 全屏期间查找栏不可达（与 Chrome 行为一致）"——PRD 在查找栏专项已**预设 HTML 全屏是既有能力**，但通篇没有全屏的验收条目；本次属于把隐含预期补成显式能力。
- `book/plans/20260914162746-会话网页内查找开发计划.md` 39 行与 `book/docs/requirements/stages/feature-会话网页内查找.md` 同口径（HTML 全屏期间查找不可用，接受）。
- `PRODUCT.md` 设计原则：Chrome 交互惯例、界面纯中文——全屏行为对齐 Chrome 是产品原则内的决策。
- 红线对照：方案只动权限白名单与 view bounds/壳层显隐，不碰 `persist:sess-<id>` 分区、不引入 BrowserView、不动 DevTools 挂载关系，无冲突。

### 2.3 候选方案

**方案 A：权限放行 + 事件驱动接管 bounds 与壳层（Chrome 式 OS 全屏）**——推荐

- 原理：① 权限 broker 白名单放行 `fullscreen`（浏览器语义权限，与 clipboard-sanitized-write 同类处理）；② 利用 Electron 默认行为（HTML 全屏获批 → 自动 `SetFullScreen` 宿主窗口，无需自己调、也规避了 macOS `setFullScreen` 异步时序坑）；③ manager 给每个 Tab 的 webContents 挂 `enter-html-full-screen` / `leave-html-full-screen` 监听，enter 时该窗口激活 view 的 bounds 立即扩为整窗内容区并广播全屏态，leave 时恢复 `boundsByWindow` 缓存；④ renderer 收到全屏态后隐藏壳层（TabStrip / Toolbar / 左栏），锚点自然扩满窗口，后续窗口 resize 由现有 ResizeObserver 数据流自动跟随。
- 来源：
  - 事件 API：[BrowserWindow 文档](https://electronjs.org/docs/latest/api/browser-window)（Event: 'enter-html-full-screen' / 'leave-html-full-screen'；`disableHtmlFullscreenWindowResize` 选项，默认 false）、[webContents 文档](https://electronjs.org/docs/latest/api/web-contents)（webContents 级同名事件，天然携带 Tab 归属，是本项目更优的监听点）。
  - 默认窗口全屏行为（源码实证）：[electron_api_web_contents.cc 的 `SetHtmlApiFullscreen`](https://github.com/electron/electron/blob/main/shell/browser/api/electron_api_web_contents.cc)（5519—5546 行：默认 `owner_window_->SetFullScreen(enter_fullscreen)`；窗口本来就在 OS 全屏时只记 `native_fullscreen_` 不动窗口，退出时也不误撤用户自己的全屏——边界已被上游处理）。
  - 成熟实现：[wexond/browser-base](https://github.com/wexond/browser-base)（Electron 浏览器底座，WebContentsView 架构与本项目同族）：[windows/app.ts 178—186 行](https://github.com/wexond/browser-base/blob/master/src/main/windows/app.ts) 监听窗口事件置 viewManager.fullscreen 并 `send('html-fullscreen', bool)` 通知 renderer；[view-manager.ts](https://github.com/wexond/browser-base/blob/master/src/main/view-manager.ts)（19—32 行 fullscreen setter 触发 fixBounds；212—226 行全屏时 bounds 取 `{x:0, y:0, width, height}` 整窗）。与本方案的结构一一对应。
- 与本项目的适配点：manager 按 wc 监听（Tab 粒度）、全屏态按窗口分槽（`suspendedByWindow` 先例）、壳层隐藏挂在两个 Frame 组件上；全屏期间锚点扩满窗口沿用零新增布局机制（FindBar 压缩锚点是同款先例，`BrowserFrame.tsx` 34 行注释）。

**方案 B：`disableHtmlFullscreenWindowResize: true` + 纯窗口内全屏**

- 原理：建窗时 webPreferences 关掉"HTML 全屏自动置窗口全屏"的默认行为，全屏表现为视频占满**应用窗口**但窗口不进 OS 全屏；权限放行与 bounds/壳层处理与方案 A 相同。
- 来源：[BrowserWindow 文档](https://electronjs.org/docs/latest/api/browser-window) `disableHtmlFullscreenWindowResize` 选项（"Whether to prevent the window from resizing when entering HTML Fullscreen. Default is false"）。
- 与本项目的适配点：改动面与 A 几乎相同，仅差"谁驱动窗口全屏"——B 需自己决定是否/何时调 `setFullScreen`（macOS 异步动画、文档明确提示依赖 enter/leave-full-screen 事件收尾），或干脆不进 OS 全屏。
- 看过、倾向不选：不进 OS 全屏偏离 Chrome 惯例（用户已开小窗时"全屏"只是铺满小窗，观感欺骗）；要 OS 全屏则与 A 殊途同归但多自己扛 setFullScreen 时序。

**方案 C：向页面注入 JS/CSS 模拟全屏——看过，不选**

- 原理：拦截全屏按钮、用 `executeJavaScript` 把 video 元素放大铺满 view。
- 不选理由：网页内容不可信（manager.ts 353 行注释明确"网页内容不可信"，只设分区不设注入面）；站点播放器结构千差万别（shadow DOM、iframe 嵌套如 YouTube），兼容性无底；且根因一二修复后 Fullscreen API 原生路径已通，注入纯多余。

**辅助事实（支撑方案 A 的可行性判断）**：

- WebContentsView 挂入窗口时 Electron 自动 `SetOwnerWindow`（[electron_api_web_contents_view.cc 137—152 行](https://github.com/electron/electron/blob/main/shell/browser/api/electron_api_web_contents_view.cc)）——全屏链路的前置条件 `owner_window()` 在本项目"view 挂入 contentView"用法下天然成立。
- `fullscreen` 是 session 权限 handler 的合法字符串（[session 文档](https://electronjs.org/docs/latest/api/session)："fullscreen - Request control of the app's fullscreen state via the Fullscreen API"），本项目 `permissions.ts` 放行它即可。
- 权限路由实证：`EnterFullscreenModeForTab` → `permission_helper->RequestFullscreenPermission` → `RequestPermissionWithDetails`（[web_contents_permission_helper.cc 253—286 行](https://github.com/electron/electron/blob/main/shell/browser/web_contents_permission_helper.cc)）——即"权限被本项目 handler 拒绝 → 全屏请求静默失败"这条链路成立。
- 相关上游 bug：[issue #41941](https://github.com/electron/electron/issues/41941)（"Fullscreen permission handling doesn't work for WebContentsView"，Electron 30 报告、已修复关闭）——说明 39 上权限 handler 对 WebContentsView 生效，也提醒实现时要在 39 实测验证拒绝/放行行为。

### 2.4 可行性分析

| 维度 | 方案 A（默认窗口全屏 + 事件接管） | 方案 B（禁用默认 + 窗口内全屏） |
| --- | --- | --- |
| 技术匹配（项目版本 / 需求覆盖与边界情况） | 全部为 Electron 39 现存官方 API（事件、权限、禁用开关均有文档）；Chrome 式完整覆盖（OS 全屏 + 壳隐藏 + ESC 退出）；多窗口按 windowId 分槽天然支持；边界（用户已在 OS 全屏、macOS 异步）上游源码已处理 | API 同样现存；但"全屏不进 OS 全屏"观感打折，或需自管 setFullScreen 异步时序（文档明确提示 macOS 动画期间状态不可同步查询） |
| 规则冲突（领域红线 / PRD / 分层规则） | 无：不碰分区、不用 BrowserView、不动 DevTools；PRD 219 行预设了 HTML 全屏语境；Chrome 惯例符合 PRODUCT 设计原则 | 同 A |
| 成本（依赖体积 / 维护活跃度 / 许可证 / 耦合） | 零新依赖；改动集中在 permissions.ts 白名单、manager 事件监听与窗口分槽、快照字段、两个 Frame 的壳层显隐；与 browser-base 已验证模式同构 | 与 A 基本同量，额外自扛窗口态时序（耦合面反而略大） |

### 2.5 结论与实施建议

- 结论：**借鉴思路手写**——借鉴 browser-base 的"窗口事件 → 全屏态标志接管 view bounds → 推送 renderer 隐藏壳层"模式，适配本项目"renderer 锚点单一数据流 + 按窗口分槽"架构；不引入任何依赖，权限白名单是本项目特有的前置修复（browser-base 没有 per-session 权限 broker，这一层是本项目根因，方案库不会替你解决）。
- 落地路径（粒度到文件与接口，按依赖顺序）：
  1. `src/main/browser/permissions.ts`：request 与 check 两个 handler 白名单放行 `'fullscreen'`（浏览器语义、无条件放行，同 clipboard-sanitized-write 处理法）。
  2. `src/main/browser/manager.ts`：`newTab` 内给 wc 挂 `enter-html-full-screen` / `leave-html-full-screen` 监听；新增按窗口分槽的 `htmlFullscreenByWindow`（仿 `suspendedByWindow`）：enter 时该窗口激活 view bounds 立即设为整窗内容区（`win.getContentSize()`，防止 renderer 壳层隐藏完成前的空窗期）、置槽位并 `emitChange`；leave 时清槽位、view 恢复 `boundsByWindow` 缓存并 `emitChange`。
  3. `src/shared/browser.ts`：`BrowserSnapshot` 增 `htmlFullscreen: boolean`（该窗口激活 Tab 的 HTML 全屏态）——走既有快照推送通道，不加新 IPC 通道。
  4. renderer：`stores/browser.ts` 存快照字段；`BrowserFrame.tsx` 与 `IndependentWindowFrame.tsx` 在全屏态隐藏 TabStrip / Toolbar（主窗口 `App.tsx` 层同时隐藏左栏与拖拽分隔条），锚点随壳层消失自然扩满窗口、ResizeObserver 自动上报整窗矩形；离开全屏恢复。壳层显隐动画与否属视觉决策，实现时走 impeccable 技能定稿。
  5. 边界收口（manager / renderer 内小改）：全屏态下页面侧 `find` 吞键放行（PRD 219：全屏期间查找栏不可达）；`switchTab` / registry 切会话时若原全屏 view 被 detach，窗口全屏态保持（Chrome 同款"切 Tab 不退全屏"），实测后定是否需要主动 `exitFullscreen`。
  6. `book/docs/requirements/PRD.md`：在浏览区章节补一条全屏验收标准（进 OS 全屏、壳隐藏、ESC 恢复、独立窗口同规则），消除"PRD 预设了全屏却没有验收条目"的空档。
- 验证：`npm run typecheck` + `npm run dev` 手动验证（bilibili / YouTube 全屏进出、切 Tab、切会话、独立窗口、弹层期间、DevTools 开启时）。

## 3. 风险与开放问题

- **切 Tab / 切会话的全屏保持行为需实测**：Chrome 语义是全屏挂窗口、切 Tab 不退出；Electron 中 detach view 后页面 DOM 全屏状态是否保留（`document.fullscreenElement` 是否还在）没有文档承诺，实测若出现"窗口全屏但页面已退出全屏 DOM 态"的破相，兜底是切换时对原 view 主动触发退出（manager 内可拿到 wc）。
- **issue #41941 的修复版行为**：权限 handler 对 WebContentsView 的 fullscreen 请求在 39 上是否稳定生效需实测（若仍直接默认放行，说明权限拒绝并非根因、改动 1 无害但非必要——两层修复互为保险，不冲突）。
- **macOS 全屏动画期间锚点跟随**：enter-html-full-screen 触发在窗口 resize 动画中途，锚点矩形会连续变化上报——数据流本身适配（rAF 节流 + 逐帧 setBounds），但首帧 bounds 闪动需实测；必要时 manager 在 enter 时先设一次整窗 bounds（实施建议 2 已含）。
- **全屏期间触发弹层（悬挂态）的相斥**：全屏时壳层隐藏、弹层入口（左栏/板头按钮）不可达，但键盘路径（如 Cmd+F 唤起的 FindBar 挂载会压缩锚点）需在实现中显式封死（实施建议 5），否则会出现"全屏视频被收起露壳"的怪象。
- **DevTools 开启时进全屏**：原生 DevTools 停靠会改变 wc 内部布局，全屏表现需验收实测；不符预期再定"进全屏前自动关 DevTools"之类的规则（另行小专项，不在本报告拍板）。
- **Windows / Linux 差异**：`SetFullScreen` 在 Windows 无原生动画（直接全屏态），行为一致性需打包验证（AGENTS.md 常规要求）。

## 4. 待确认假设

- [ ] 假设 1：全屏形态采用 **Chrome 惯例（方案 A）**——点视频全屏按钮后窗口进入 OS 原生全屏（macOS 含菜单栏/Dock 隐藏），ESC 退出恢复原窗口尺寸。若你更想要"窗口不进 OS 全屏、只是视频铺满应用窗口"（方案 B），结论方向不变但实施建议 2/4 有差。
- [ ] 假设 2：本次**不做** F11 / Cmd+Ctrl+F 的窗口全屏快捷键与菜单项（那是独立的"窗口全屏"能力点，可另起调研）；窗口手动全屏走系统绿色按钮，天然可用（建窗未设 `fullscreenable: false`）。

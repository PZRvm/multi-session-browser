# 会话网页摄像头访问 功能调研报告

> 创建时间：2026-09-14 11:07（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户希望被测项目在多会话浏览器中可调用本机真实摄像头，用于网页摄像头扫码测试
> 调研单元：2 个
> 状态：调研完成，待用户确认（未实施）

## 1. 需求理解

### 1.1 功能目标

测试人员在会话页面中打开需要二维码扫描、实名校验或拍照的被测网站时，网站应能通过标准 `navigator.mediaDevices.getUserMedia({ video: true })` 拿到本机真实摄像头画面。授权必须与发起请求的会话和站点 origin 绑定，不能因为某一个会话允许而让其他会话默认获得摄像头权限。本功能只打通被测网页的摄像头输入；扫码解码逻辑仍由被测项目自己承担，本项目不内置二维码识别库。

预期效果是：合法的 HTTPS/localhost 站点发起纯视频请求时，用户能看清是哪个站点在申请、手动允许或拒绝；允许后再完成操作系统级授权，页面可以显示实时画面并扫码。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 未知点 1：`WebContentsView` 里的普通网页能否使用真实摄像头？——能，网页继续使用标准 `getUserMedia`，`WebContentsView` 不是障碍；需求属于 Electron `media` 权限（见单元 1）。
- [x] 未知点 2：是否需要第三方摄像头/扫码库？——不需要，Electron/Chromium 已提供媒体设备通道；本项目只需实现权限裁决与平台配置。
- [x] 未知点 3：多会话下权限能否隔离？——能，权限 handler 挂在每个 `persist:sess-<id>` 的 Electron `Session` 上，站点决策按“会话 + origin + 媒体类型”存取（见 2.5）。
- [x] 未知点 4：Electron 需要处理哪些权限 API？——要同时实现 `setPermissionRequestHandler` 和 `setPermissionCheckHandler`；官方文档明示只实现其一不是完整权限处理（见 2.3）。
- [x] 未知点 5：macOS/Windows 是否还有应用级权限？——有。macOS 需要 `Info.plist` 用途文案、camera entitlement 和系统授权；Windows 受“允许桌面应用访问摄像头”系统开关控制（见单元 2）。
- [x] 未知点 6：当前代码为什么可能不能用？——已发现三个直接风险：无站点权限 handler；macOS `extendInfo` 写成数组导致自定义用途文案未正确合并；当前签名权限不含 camera entitlement（见 3.2）。此外，被测页面如使用非 localhost 的 HTTP，网页平台会直接禁用 `getUserMedia`（见第 4 节）。

### 1.3 拆分判断

拆为 2 个有依赖顺序的调研单元：

| 单元 | 内容 | 依赖 |
| --- | --- | --- |
| 单元 1 | 被测站点的 Electron 会话级摄像头授权 | 独立，决定哪个会话/站点可以用 |
| 单元 2 | Windows/macOS 应用级授权与 macOS 打包配置 | 在单元 1 允许站点后执行，决定操作系统是否放行硬件 |

拆分原因：站点权限是每个 Electron `Session` 内的浏览器安全策略，系统权限是整个应用的操作系统/签名能力；两者缺一都会失败，但隔离粒度和落地文件不同。

## 2. 调研单元 1：Electron 会话级摄像头授权

### 2.1 该部分要做什么

负责识别发起摄像头请求的会话、顶层页/子框架 origin 及媒体类型，向用户展示明确授权询问，然后向 Chromium 返回允许或拒绝。本单元不负责操作系统级的 macOS/Windows 隐私开关，也不负责解码二维码。

### 2.2 项目现状

- 页面宿主已符合需求：`src/main/browser/manager.ts` 的 `newTab()` 为每个 Tab 创建 `WebContentsView`，`webPreferences.partition` 取注册表传入的会话分区；没有为远程页面配置 preload/Node 能力，可直接继续使用 Chromium 的 Web Media API。
- 会话隔离接缝已存在：`src/main/browser/registry.ts` 的 `partitionFor()` 固定返回 `persist:sess-<id>`，`ensureManager()` 每会话创建一个 manager。Electron 的 permission handler 本身就是挂在 `Session` 上，因此可直接继承一会话一分区，无需全局共享授权表。
- 当前没有权限裁决代码：全仓检索只发现 `session.fromPartition()` 用于分区清理/关闭，没有 `setPermissionRequestHandler` / `setPermissionCheckHandler` / `systemPreferences`。Electron 安全文档说明，未设置自定义 handler 时 Electron 默认自动批准权限请求；对会加载任意远程网页的浏览器工具，这是必须收口的隐私风险：<https://www.electronjs.org/docs/latest/tutorial/security#5-handle-session-permission-requests-from-remote-content>。
- 版本匹配：`package.json` 是 Electron `^39.2.6`，当前安装版为 39.8.10。本地 `node_modules/electron/electron.d.ts` 已核实 39.8.10 具备两个 permission handler，`MediaAccessPermissionRequest.mediaTypes` 可区分 `video` / `audio`，check handler 的 details 可取 `securityOrigin` / `mediaType` / `requestingUrl` / `isMainFrame`。官方 Session 文档也明确说明 `media` 就是摄像头、麦克风等媒体设备，且要同时实现 request/check handler：<https://www.electronjs.org/docs/latest/api/session#sessetpermissionrequesthandlerhandler>。
- 页面跨窗口迁移不会丢权限：`manager.ts` 保留原 `webContents`，而权限属于其 `Session`；符合 `book/docs/requirements/PRD.md` 4.1 会话隔离和 4.5 Tab 迁移不改变会话的约束。
- 界面原则：`PRODUCT.md` 要求 Chrome 交互惯例、效率优先、纯中文。Electron 没有自动生成 Chrome 地址栏权限气泡，需由应用决定是静默批准、白名单或自建询问界面。

### 2.3 候选方案

**方案 A：沿用 Electron 默认自动批准**

- 原理：不注册权限 handler，让 Electron 对 `media` 请求使用默认行为；网页发起 `getUserMedia` 后直接进入系统权限层。
- 来源：Electron 安全文档明说未配置自定义 handler 时权限请求默认自动批准，同时把“所有加载远程内容的 session 都使用 `setPermissionRequestHandler`”列为安全清单：<https://www.electronjs.org/docs/latest/tutorial/security#5-handle-session-permission-requests-from-remote-content>。
- 与本项目的适配点：零代码，但任意打开的站点都可尝试访问摄像头，没有站点级用户确认，与“浏览器加载任意远程网页”的产品形态不匹配。

**方案 B：固定测试域名白名单**

- 原理：为每个分区注册 request/check handler，仅当请求是 `media` + `video` 且 origin 命中配置白名单时返回允许，其余拒绝。
- 来源：Electron Session API：<https://www.electronjs.org/docs/latest/api/session#sessetpermissioncheckhandlerhandler>；请求结构可用 `securityOrigin` 和 `mediaTypes` 区分真实请求方与摄像头/麦克风：<https://www.electronjs.org/docs/latest/api/structures/media-access-permission-request>。
- 与本项目的适配点：安全、代码少，适合只有一两个固定内部域名的专用工具；但本产品是通用测试浏览器，新项目/临时环境会频繁变域名，白名单会成为配置负担。

**方案 C：每会话、每 origin 的运行期授权询问（推荐）**

- 原理：为每个 `persist:sess-<id>` 分区同时安装 request/check handler。首次收到 HTTPS/localhost 的纯 `video` 请求时，根据 `details.securityOrigin` / `details.requestingUrl` 展示中文系统对话框，明示站点 origin 和所属会话；结果按“会话 + origin + video”缓存到本次应用运行结束，其他会话仍需单独询问。官方对话框支持绑定宿主窗口和异步返回：<https://www.electronjs.org/docs/latest/api/dialog#dialogshowmessageboxwindow-options>。
- 来源：Electron Session API 的 request/check handler：<https://www.electronjs.org/docs/latest/api/session#sessetpermissionrequesthandlerhandler>；Electron 官方权限请求结构：<https://www.electronjs.org/docs/latest/api/structures/permission-request>、<https://www.electronjs.org/docs/latest/api/structures/media-access-permission-request>。
- 与本项目的适配点：兼容任意被测项目，又不把摄像头全局放开。使用 Electron 原生对话框可不改 renderer/preload，很适合先做摄像头能力的最小完整版。

### 2.4 可行性分析

| 维度 | 方案 A（默认自动批准） | 方案 B（固定白名单） | 方案 C（会话/origin 询问） |
| --- | --- | --- | --- |
| 技术匹配 | Electron 39 当前就是此行为，但没有站点授权交互 | Electron 39 官方 API 完全支持，但不适合频繁变更测试环境 | Electron 39 官方 API 完全支持；需自己管理询问、并发去重和运行期决策缓存 |
| 规则冲突 | 不破坏分区，但与隐私安全和 Chrome 明示授权惯例冲突 | 不破坏分区；固定配置降低通用性 | 不破坏分区；决策天然与会话绑定，符合 PRD 4.1 和 PRODUCT “会话是第一公民” |
| 成本 | 零开发成本，高安全代价 | 一个 handler + 白名单，但后续维护域名 | 零新依赖；新增一个主进程权限模块和少量窗口定位/并发处理 |

### 2.5 结论与实施建议

- 结论：**借鉴思路手写**——底层完全使用 Electron 39 现成的 `Session` permission API 和原生 `dialog`，但 Electron 不提供可直接复用的 Chrome 站点权限气泡或会话级决策存储，因此由本项目手写一层很薄的权限 broker。不引入 npm 摄像头/扫码库。
- 落地路径（粒度到文件与接口，不写实现代码）：
  1. 新增 `src/main/browser/permissions.ts`：提供“为指定会话分区安装媒体权限策略”的单一入口；同时设置 request/check handler，默认拒绝非 `media` 和本功能不支持的权限，对 `media` 仅放行 `video`，对包含 `audio` 的联合请求明确拒绝。
  2. 权限模块严格使用 `details.securityOrigin` / `details.requestingUrl` 判断请求框架，不只看顶层 `webContents.getURL()`；只接受 HTTPS 和安全 localhost origin，解析失败即拒绝。
  3. `src/main/browser/manager.ts`：在每个 manager 存活期内只安装一次对应 `Session` 的 handler；利用内部 `TabEntry.windowId` 将请求的 `webContents` 映射回主窗口/独立窗口，让原生对话框绑定真实宿主。如希望 registry 统一创建权限模块，则在 `src/main/browser/registry.ts` 的 `ensureManager()` 中以 `session.fromPartition(partitionFor(id))` 注入。
  4. 对话框使用中文文案，至少显示会话名和 origin，按钮为“允许”/“拒绝”。决策仅缓存到应用退出，同一会话/origin 不重复弹窗；不在没有“查看/撤销站点权限”入口时持久化摄像头允许。
  5. 同一 origin 的并发请求要合并为一次询问；对话框等待期间页面导航、Tab 关闭或会话销毁时统一回调 `false`，不留悬空 callback。
  6. 这一最小方案不改 `src/preload/` 和 `src/renderer/`；如后续增加地址栏权限图标、持久授权管理或摄像头活动指示，届时再扩展 shared/IPC/preload/renderer，界面实施前必须走 impeccable 技能。

## 3. 调研单元 2：操作系统授权与 macOS 打包配置

### 3.1 该部分要做什么

负责在站点授权通过后，确保 Windows/macOS 把真实摄像头交给 Electron 应用。其中 macOS 同时要修正打包产物的 `Info.plist` 用途文案和签名 entitlement。本单元不处理站点是否值得信任，该决策已由单元 1 完成。

### 3.2 项目现状

- `electron-builder.yml` 已准备 `NSCameraUsageDescription` 和 `NSMicrophoneUsageDescription`，但 `mac.extendInfo` 当前是 YAML 数组（每项一个单键对象），而 electron-builder 的定义是“要合并进 `Info.plist` 的额外条目对象”：本地 `node_modules/app-builder-lib/out/options/macOptions.d.ts` 和 `node_modules/app-builder-lib/out/macPackager.js` 已核实 `extendInfo` 会被直接 `deepAssign(appPlist, extendInfo)`。
- 这不只是静态推测：当前 `dist/mac-arm64/multi-session-browser.app/Contents/Info.plist` 里真实出现了键 `0` / `1` / `2` / `3` / `length`，项目写入的英文摄像头文案被放在数字键下，没有成为正常的顶层 Info.plist 属性。产物中顶层 `NSCameraUsageDescription` 之所以仍存在，是 Electron 基础包自带的通用英文默认值 `This app needs access to the camera`，不是本项目配置成功。
- `build/entitlements.mac.plist` 及当前打包产物的 `codesign` 权限只含 JIT/未签名可执行内存/dyld 三项，不含 `com.apple.security.device.camera`。Apple 官方要求 macOS 应用在访问摄像头前同时具有 `NSCameraUsageDescription` 和 Camera entitlement：<https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media>。
- 项目已在 `electron-builder.yml` 中将 `build/entitlements.mac.plist` 用作 `entitlementsInherit`，而该文件又是 electron-builder 会自动识别的主 entitlement 默认路径；所以修正一个 plist 即可覆盖主应用和继承权限的辅助进程，但必须以打包后 `codesign` 实际输出复核。
- Electron 39.8.10 的本地类型和官方文档已核实：`systemPreferences.getMediaAccessStatus('camera')` 支持 Windows/macOS，`askForMediaAccess('camera')` 仅支持 macOS；macOS 已拒绝后不会再弹系统询问，用户需到系统设置修改并重启应用：<https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesaskformediaaccessmediatype-macos>。
- Windows 将本项目视为桌面应用。Microsoft 说明摄像头访问受“Camera access”和“Let desktop apps access your camera”开关控制，而且桌面应用通常不能按单个应用切换：<https://support.microsoft.com/en-us/windows/privacy/manage-app-permissions-for-a-camera-in-windows>。
- 开发态与打包态是两个 macOS 应用身份：本地 `node_modules/electron/dist/Electron.app` 是 `com.github.Electron`，打包产物是 `com.electron.app`。Apple 会按应用记住用户回答，因此在 `npm run dev` 授权不代表打包后的应用已授权：<https://developer.apple.com/documentation/bundleresources/requesting-authorization-for-media-capture-on-macos>。

### 3.3 候选方案

**方案 A：仅修正打包配置，让网页首次取流时自然触发系统询问**

- 原理：配好 Info.plist 与 entitlement，不显式调用 `systemPreferences`；Chromium 真正开始获取设备时由 macOS/Windows 决定是否弹窗/拒绝。
- 来源：Apple 说明首次创建需授权的捕获输入会自动显示询问：<https://developer.apple.com/documentation/bundleresources/requesting-authorization-for-media-capture-on-macos>。
- 与本项目的适配点：开发量最小，但站点 handler 不容易将“站点拒绝”和“系统拒绝”分开，错误时缺少面向测试人员的可诊断结果。

**方案 B：应用启动时主动申请 macOS 摄像头权限**

- 原理：`app.whenReady()` 后立即调用 `systemPreferences.askForMediaAccess('camera')`，在任何网页使用前就拿到系统决策。
- 来源：Electron systemPreferences API：<https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesaskformediaaccessmediatype-macos>。
- 与本项目的适配点：技术上可行，但摄像头不是应用主启动功能；启动即弹系统隐私询问缺少站点上下文，不符合 Apple “只在用户调用相关功能时请求”的建议。

**方案 C：站点授权通过后懒触发并检查系统权限（推荐）**

- 原理：单元 1 的站点询问点击“允许”后，先用 `getMediaAccessStatus('camera')` 取系统状态；macOS `not-determined` 时调 `askForMediaAccess('camera')`，`denied/restricted` 则拒绝并给出系统设置路径；Windows 以状态检查和错误指引为主，不调用 macOS-only API。
- 来源：Electron systemPreferences API：<https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesgetmediaaccessstatusmediatype-windows-macos>；Apple 建议在实际需要摄像头时再检查/申请：<https://developer.apple.com/documentation/bundleresources/requesting-authorization-for-media-capture-on-macos>。
- 与本项目的适配点：站点和系统两层决策有清晰顺序，用户只在真正进入扫码流程时被询问，拒绝后也能告知是系统层问题。

### 3.4 可行性分析

| 维度 | 方案 A（网页自然触发） | 方案 B（启动申请） | 方案 C（首次真实使用懒申请） |
| --- | --- | --- | --- |
| 技术匹配 | 配置正确后可用；错误原因不够可观测 | macOS API 直接支持，Windows 不支持该 ask API | macOS/Windows 都可用 status API，macOS 再用 ask API；覆盖需求与失败诊断 |
| 规则冲突 | 无隔离冲突 | 无隔离冲突，但启动弹窗不符合效率/上下文原则 | 无；系统权限是应用级，站点决策仍保持每会话隔离 |
| 成本 | 只修打包配置 | 修配置 + 启动时一次 API | 修配置 + 权限 broker 内一段平台分支，仍为零依赖小改动 |

### 3.5 结论与实施建议

- 结论：**采用现成方案**——用 Electron 39 现成的 `systemPreferences` 在第一个站点请求通过后懒检查/申请系统权限，并按 Apple/electron-builder 规范修正打包元数据；不需要第三方库或原生扩展。
- 落地路径：
  1. `electron-builder.yml`：将 `mac.extendInfo` 从数组改成标准键值映射；摄像头用途改为明确中文，例如“用于被测网页的摄像头扫码与拍摄测试”。本需求不需要麦克风，不因摄像头扫码顺带开放音频。
  2. `build/entitlements.mac.plist`：新增 `com.apple.security.device.camera = true`；不新增 `audio-input`，除非后续需求明确支持麦克风。
  3. `src/main/browser/permissions.ts`：站点允许后执行平台分支；macOS 调用 status/ask，Windows 读取 status 并在被拒绝时展示“设置 > 隐私和安全性 > 摄像头 > 允许桌面应用访问摄像头”的中文诊断。
  4. 打包验证：`npm run build:mac` 后用 `plutil` 确认顶层 `NSCameraUsageDescription` 是项目中文文案且不再出现数字键，用 `codesign` 确认主应用/必要辅助进程实际携带 camera entitlement。
  5. 发布前把 `electron-builder.yml` 的通用 `appId: com.electron.app` 换成项目稳定的反域名标识，并保持签名身份稳定；具体 appId 需用户确认，不在报告中擅自命名。

## 4. 风险与开放问题

- **HTTPS/localhost 是硬前提**：`getUserMedia()` 仅在安全上下文可用；非 localhost 的纯 HTTP 页面中 `navigator.mediaDevices` 可能直接为 `undefined`，应用的 permission handler 无法把不安全页面变成安全上下文：<https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia#privacy_and_security>。内网/IP 测试环境如果是 HTTP，推荐为被测站点配 HTTPS，或在本机以 localhost 暴露；不建议关闭 `webSecurity` 或把所有 HTTP 当安全页面。
- **iframe 不一定可获授权**：如扫码组件在跨域 iframe 中，顶层页还需用 `Permissions-Policy` 和 iframe `allow="camera"` 显式委派；缺失时网页会在 Electron handler 之前就被拒绝：<https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy/camera>。
- **摄像头是应用/硬件全局资源**：站点决策可做到每会话隔离，但操作系统的摄像头授权属于整个应用，物理摄像头也无法按 session 切成多台。两个会话同时取流可能被系统/驱动复用，也可能因设备占用失败，必须列入冒烟测试。
- **后台 Tab 可能继续取流**：本项目切换 Tab/会话时只摘下 `WebContentsView`、不销毁 `webContents`，这是保持页面状态的核心设计；因此网页已开始的摄像头流不应被假设为“一切换就自动停止”。Electron 39 没有与 `getUserMedia` 活动一一对应的简单主进程事件；第一版至少要确认关闭 Tab 会停流，并决定是否把“正在使用摄像头”的可靠指示器单独立项调研。
- **站点请求摄像头 + 麦克风时无法在一个布尔回调中部分放行**：Electron permission callback 是对整个请求返回真/假。本需求建议仅允许 `mediaTypes` 只含 `video` 的请求；被测项目应使用 `{ video: true, audio: false }`。如后续要测语音/视频会议，再单独纳入麦克风权限。
- **多摄像头选择属于网页责任**：权限通过后，前后摄像头、外接 USB 摄像头的选择仍由被测页面的 `facingMode` / `deviceId` 约束决定；本项目不应代替页面强选设备。
- **macOS 权限调试要分开 dev 和打包态**：开发态的 Electron.app 与打包应用 bundle id/签名不同；必须两种形态各测一次，不能用 dev 通过代替打包验收。
- **安全作用域**：一旦注册 permission handler，它会收到该 Session 下的其他权限类型。本功能不应用“非 media 一律允许”重现 Electron 默认风险；建议未实现的权限默认拒绝。这可能让少数依赖通知/定位等权限的被测页变为不可用，后续应将通用站点权限中心作为独立需求，不在本次摄像头需求中无边界扩张。
- **手工验收页**：可用 WebRTC 官方样例页“Open camera”验证真实取流：<https://webrtc.github.io/samples/src/content/getusermedia/gum/>；同时还要用真实扫码项目验收 QR 解码链路。

## 5. 待确认假设

- [ ] 假设 1：本次只支持真实摄像头的视频输入，被测项目使用 `getUserMedia({ video: true, audio: false })`；不顺带开放麦克风。

- [ ] 假设 3：被测项目使用 HTTPS 或 localhost。如实际必须在 `http://192.168.x.x` 等非安全地址测试，需先单独确认环境和安全边界，不默认开不安全 Chromium 开关。
- [ ] 假设 4：站点授权按“每会话 + 每 origin”隔离，仅记住到本次应用运行结束；重启后重新询问，克隆会话不复制摄像头允许。

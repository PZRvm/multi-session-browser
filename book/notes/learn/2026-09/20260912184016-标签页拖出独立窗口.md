# 标签页拖出独立窗口 功能调研报告

> 创建时间：2026-09-12 18:40（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户原话"将 session 中的浏览器窗口单独拖动出去作为一个独立窗口"
> 调研单元：2 个（① 主进程 view 跨窗口迁移与独立窗口管理；② renderer 拖拽手势与功能入口）
> 状态：调研闭环——v2 方案全部定案（第 9 节），需求已写入 PRD（3.6/4.5/验收 12—17）；下一步可衔接 write-plan 转开发计划（未实施）

## 1. 需求理解

### 1.1 功能目标

测试人员在主窗口左侧会话列表 + 右侧浏览区的布局下工作时，有时需要把某个正在看的页面挪到独立窗口（拖到第二块屏幕、与主窗口并排比对）。本功能提供 Chrome 式"拖出标签页成独立窗口"（tab tear-off）能力：把某个会话的某个 Tab 拖出（或经入口命令）后，该 Tab 变成一个独立的 BrowserWindow，**页面状态（登录态、滚动位置、表单输入、会话分区）原样保留**，因为它仍是同一个 webContents。独立窗口仍属于原会话（同一 `persist:sess-<id>` 分区），关闭独立窗口后 Tab 销毁，与主窗口 Tab 管理互不串台。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] WebContentsView 能否在保留 webContents 状态的前提下从一个 BrowserWindow 迁到另一个？（→ 2.3 方案 A，官方 API 直接支持，项目内已有同机制先例）
- [x] 拖拽手势如何跨出窗口边界检测"拖到了窗口外"？（→ 3.3，HTML5 drag 的 dragend 屏幕坐标可用；稳妥入口是 Tab 右键菜单）
- [x] DevTools 是否随页面一起到新窗口？（→ 2.4，DevTools 挂在 webContents 上，天然跟随）
- [x] 现有 manager/registry 架构（单主窗口假设）如何承接多窗口？（→ 2.4/2.5，需引入"脱离窗口登记表"并调整 getWindow 语义）

### 1.3 拆分判断

拆为 2 个单元：①主进程的 view 迁移与独立窗口生命周期管理（核心机制，决定架构改动）；②renderer 的拖拽手势与功能入口（交互层，依赖 ① 提供的 IPC 通道）。两者跨进程层且 ② 依赖 ① 的通道设计，按序调研。

## 2. 调研单元：主进程 view 跨窗口迁移与独立窗口管理

### 2.1 该部分要做什么

提供主进程能力：把某会话某 Tab 的 `WebContentsView` 从主窗口摘下、挂到一个新建的独立 BrowserWindow 上，并管理该独立窗口的生命周期（关闭、应用退出、会话销毁/关闭/克隆时的级联处理）。不负责交互手势。

### 2.2 项目现状

- Tab 全部由主进程持有：`src/main/browser/manager.ts` 的 `tabs: Map<string, TabEntry>`，每个 Tab 一个 `WebContentsView`（分区 `persist:sess-<id>` 由 `src/main/browser/registry.ts:34` 注入）。
- **挂摘保活机制已存在且经过验证**：`attachView/detachView`（manager.ts:136-147）就是 `contentView.addChildView/removeChildView`，注释明确"脱离 contentView 但不销毁（页面状态保留）"；registry 的 `detachActiveView`（registry.ts:180-189）跨 manager 反查摘 view 也是同一手法。本项目换会话时已经这么干——**从主窗口摘 view 挂到另一个窗口，与摘下不挂，机制同源**。
- **单主窗口假设是主要阻碍**：manager 的 `getWindow()`（manager.ts:76-79）一律返回主窗口，view 只会挂回主窗口；快照推送（registry.ts:340-349）、focus-address 过滤（registry.ts:351-355）、lastUrl 上报（registry.ts:276-303）都以"激活会话 = 主窗口挂入"为前提。
- 生命周期红线相关：`destroySession`/`closeSession` 用 `killPartitionWebContents`（registry.ts:252-273）按 **session 身份**扫杀全部 webContents——独立窗口里的 view 与主窗口 view 同 session，现有扫描天然覆盖它，这是利好；但 `dispose()` 封死 newTab 的同时，独立窗口的 view 摘除需同步处理，否则窗口关闭时序复杂化。
- 版本事实：Electron ^39.2.6（package.json:38），WebContentsView 自 29 起为正式 API，39 完全可用。
- 通道面：`src/shared/browser.ts` 的 `BROWSER_CHANNELS`，命令一律作用于"当前激活会话"（registry 路由）。

### 2.3 候选方案

**方案 A：WebContentsView 跨窗口重挂（官方 API，保活迁移）**

- 原理：`new BrowserWindow()` 后 `win.contentView.addChildView(tab.view)`，webContents 与渲染进程原样保留（Chromium 的 view 树换父，页面进程不重启）。摘下用 `removeChildView`，与项目现有 detach 完全一致。
- 来源：<https://electronjs.org/docs/latest/api/web-contents-view>（View that displays a WebContents，`contentView.addChildView(view)`）；迁移总纲 <https://electronjs.org/blog/migrate-to-webcontentsview>
- 适配点：纯主进程改动，落在 `src/main/browser/`；无新依赖。

**方案 B：新窗口内新建 Tab 同分区加载同 URL（"伪迁移"）**

- 原理：独立窗口新建 WebContentsView（同 partition）`loadURL(当前 url)`，原 Tab 关闭。实现最简单，但页面状态（滚动、表单、SPA 内部态）丢失，只有登录态/Partition 数据因同分区而保留。
- 来源：electron-tabs issue 讨论 <https://github.com/brrd/electron-tabs/issues/75>（"copy contents to new window"即此路）
- 适配点：复用 newTab/loadURL 现有路径；体验是"重新打开"而非"拖走"，不符合测试人员比对场景的预期。

（看过不选的：原生 frameless + 自绘 Tab 条拖拽（Qt/Chrome 原生方案）——Electron 无窗口级原生 tab strip API，自己画成本远超收益。）

### 2.4 可行性分析

| 维度 | 方案 A（view 重挂） | 方案 B（同分区重开） |
| --- | --- | --- |
| 技术匹配 | Electron 39 原生支持；项目内 detach 保活已被冒烟验证（registry.ts:174 注释），挂到另一窗口是同一 API 的另一目标 | 完全匹配，零新 API |
| 需求覆盖 | 页面状态原样保留，符合"拖出去"语义；DevTools 挂在 webContents（manager.ts:335 `wc.openDevTools()`）天然随迁 | 状态丢失，语义降级为"在新窗口打开此网址" |
| 规则冲突 | 无：分区不变（仍 persist:sess-\<id\>）、仍 WebContentsView、DevTools 仍挂具体 webContents | 无 |
| 成本 | 中：需新增独立窗口登记表 + 改造 manager 的 getWindow 单窗口假设；无依赖 | 低，但达不到功能目标 |

方案 A 的主要技术风险点（调研确认均可解）：

1. **单 Tab 残留**：manager `closeTab` 有"最后留一"（manager.ts:285），拖出唯一 Tab 后主窗口该会话处于 0 Tab 状态，快照语义（activeTabId null）需要定义空态行为。
2. **快照/上报口径**：拖出的 Tab 应从主窗口快照消失（renderer Tab 条不再显示），但它的导航/加载事件仍走 manager 的 emitChange——需把 TabEntry 标记为"已脱离"并从 buildSnapshot 过滤，或迁移到独立登记表后由其自管。
3. **会话级联**：destroySession/closeSession/clonePartition 按 session 扫杀 webContents 已天然覆盖独立窗口的 view，但独立 BrowserWindow 本身要同步 close，避免留下空壳窗口。
4. **页面侧快捷键**：manager 的 before-input-event 接线（manager.ts:233）在 view 上，随 view 走，快捷键仍生效；但 toggle-devtools 作用于"激活 Tab"——脱离 Tab 不在激活位，需让脱离 Tab 的快捷键路由到它自己（接线已按 tab 闭包，多数分支无碍，仅 toggle 分支需注意）。

### 2.5 结论与实施建议

- 结论：**采用现成方案**（方案 A，Electron 原生 WebContentsView 重挂，无第三方库），理由：项目已有同机制的 detach 保活先例，跨窗口只是换挂载目标。
- 落地路径（粒度到文件与接口）：
  1. `src/main/browser/detached.ts`（新增）：脱离窗口登记表——`tearOff(sessionId, tabId): void`（建 BrowserWindow、摘 view 重挂、manager 侧摘除该 Tab）+ 窗口 closed 回调（销毁该 webContents）+ 按 sessionId 查询/级联关闭接口（供 destroySession/closeSession 调用）+ 应用退出冲刷。窗口本体建议带极简中文标题（会话名 - 页面标题，随 page-title-updated 更新）。
  2. `src/main/browser/manager.ts`：TabManager 增 `detachTab(id): { view, cleanup } | null`——从 tabs 摘除、若摘的是激活 Tab 则按 closeTab 的邻位规则激活下一个（可为 null 空态）、摘 view 不销毁 webContents；`buildSnapshot` 无需特殊处理（摘除即消失）。
  3. `src/main/browser/registry.ts`：destroySession/closeSession/clonePartition 收尾时调用 detached 级联关闭；快照/上报逻辑不变（脱离 Tab 不再进快照）。
  4. `src/shared/browser.ts` + `src/main/browser/ipc.ts` + `src/preload/`：新增 `browser:tear-off-tab` 命令通道（payload `{ id: string }`，作用于当前激活会话）与 `index.d.ts` 同步。
  5. `src/main/index.ts`：before-quit 时关闭全部脱离窗口（macOS 关主窗不退出的模板行为不受影响）。

## 3. 调研单元：renderer 拖拽手势与功能入口

### 3.1 该部分要做什么

提供用户触发 tear-off 的交互：①Tab 右键菜单/按钮入口（必做，稳妥）；②拖拽 Tab 到窗口外触发（Chrome 惯例，增强）。不负责主进程机制。

### 3.2 项目现状

- Tab 条在 renderer（React 19 + antd 6），Tab 数据是主进程推送的镜像（`src/shared/browser.ts` 注释：renderer 不得自造 tab id）。
- renderer 无 Electron API 访问权，一切经 `window.api` IPC；现有命令面即 `BROWSER_CHANNELS`。
- 键位/交互惯例对齐 Chrome（PRODUCT.md 设计原则）。

### 3.3 候选方案

**方案 A：Tab 右键菜单入口（antd Dropdown）+ 可选键盘**

- 原理：Tab 条项包 antd Dropdown，菜单含"移出到独立窗口"，点击发 `browser:tear-off-tab`。零手势难题，全平台可靠。
- 来源：<https://ant.design/components/dropdown-cn>（项目已用 antd 6）
- 适配点：纯 renderer 改动 + 既有 IPC 风格。

**方案 B：HTML5 dragstart/dragend 屏幕坐标判定拖出**

- 原理：Tab 设 `draggable`，dragstart 记起点；dragend 事件携带 `screenX/screenY`（Chromium 在拖出窗口外释放时也会派发 dragend，坐标为屏幕系）；与主窗口 `getContentBounds()` 比对，落点在窗口外即调 tear-off，并可用 `screen` 坐标作为新窗口初始位置。需配合 dragover 上临时 `event.preventDefault()` 才能让 dragend 正常触发。
- 来源：<https://stackoverflow.com/questions/50828059/electron-drag-tab-into-another-open-window>（同题讨论，正是 dragend + 屏幕坐标思路）；Chromium dragend 行为属平台实现细节，**建议实现期以 39 实测为准**。
- 适配点：renderer 内判定，判定结果仍走同一 IPC 通道；新窗口落点坐标可随 payload 传给主进程。

### 3.4 可行性分析

| 维度 | 方案 A（菜单入口） | 方案 B（拖拽手势） |
| --- | --- | --- |
| 技术匹配 | antd 6 现成组件，项目风格一致 | dragend 屏幕坐标跨平台行为需实测（macOS/Windows 差异是历史吐槽点） |
| 需求覆盖 | 覆盖功能，缺"拖动"的直觉性 | 完整对齐用户原话"拖动出去" |
| 规则冲突 | 无 | 无（不触碰红线，仅 renderer） |
| 成本 | 低 | 中：手势判定 + 落点计算 + 平台实测 |

### 3.5 结论与实施建议

- 结论：**只做方案 B（拖拽手势）**（用户定案 2026-09-12：触发方式只要拖拽，不做右键菜单入口）。方案 A 不实施，保留于 3.3 仅作记录。
- 落地路径：
  1. renderer Tab 条组件（`src/renderer/src` 下浏览器区组件）加 draggable 与 dragend 判定（dragstart 时对 document dragover preventDefault 保 dragend 触发；dragend 屏幕坐标经 IPC payload 传 `screenX/screenY`，主进程据此定位新窗口）。
  2. 拖拽中/落点在窗口外的 Tab 视觉反馈实现时走 **impeccable** 技能。
  3. 风险对冲：dragend 跨平台行为实测若在某平台不可靠，再与用户复议是否补菜单入口，不擅自加。

## 4. 风险与开放问题

- **PRD 超出**：`book/docs/requirements/PRD.md` 与 step-01~08 计划均无此功能（属一期 1-7 之外的新增能力）。实施前建议补一条 PRD 需求条目或在 notes 计划中立项，避免"事实源之外的功能"。
- **dragend 跨平台行为**：方案 B 在 macOS（本项目开发机）与 Windows（build:win 目标平台）上的拖出释放行为需实测；若 Windows 异常，可降级为菜单入口为主。
- **空会话态**：拖出会话唯一 Tab 后主窗口该会话 0 Tab，`BrowserSnapshot.activeTabId = null` 是新状态组合，renderer 空态展示需走 impeccable 一并设计。
- **多显示器/DPI**：新窗口初始位置用屏幕坐标直接定位，混合 DPI 下 Electron DIP 换算建议实现期验证。

## 6. 补充调研：拖回主窗口（2026-09-12 追加，用户追问"能不能拖拽回去"）

结论先行：**机制上完全可行且与拖出对称；手势上拖拽源不存在，需换触发方式**。

### 6.1 机制层（完全对称，复用单元 2 方案 A）

拖回 = 反向执行 tear-off：从独立窗口 `removeChildView(view)` → manager 重新登记该 TabEntry（view 与 webContents 未销毁，页面状态原样）→ 挂回主窗口 contentView 并激活。落点：

- `manager.ts` 增 `reattachTab(tab)`（与 `detachTab` 对称：重新入 tabs Map、激活、emitChange 推送快照——Tab 条自动重现）。
- `detached.ts` 增 `mergeBack(sessionId)`：关独立窗口、调 reattachTab；若该会话当前非激活会话，挂回逻辑退化为"摘下保活"（同 registry 后台会话既有语义，切回会话时重挂）。
- 边界：脱离期间主窗口该会话被销毁/关闭（killPartitionWebContents 已按 session 扫杀，独立窗口 view 已死）——mergeBack 前查 webContents.isDestroyed()，已死则只关空壳窗口；脱离期间主窗口同会话切走/克隆中（cloningIds 守卫）——mergeBack 入口套同一守卫。

### 6.2 手势层（拖拽源不存在，候选两路）

独立窗口内是任意网页内容（不可信、不可注入拖拽 UI），HTML5 drag 无从发起。候选：

**方案 A：窗口拖拽重叠判定（贴近"拖回去"直觉）**

- 原理：用户拖独立窗口标题栏，主进程经 BrowserWindow 的 `move`（Windows/Linux 拖动中连续触发）/`moved`（macOS 拖动结束触发）事件 + `screen.getCursorScreenPoint()` 判定独立窗口与主窗口浏览区重叠/鼠标落在主窗口内容区，落在则合并（可先给视觉提示，松手确认）。
- 来源：<https://electronjs.org/docs/latest/api/browser-window>（move/moved 事件）；<https://stackoverflow.com/questions/40579451/how-do-i-track-dragging-of-a-browserwindow-in-electron>
- 风险：判定是启发式（无"松手在窗口上"的原生事件，macOS 只有 moved 结束事件）；误触发需视觉反馈与撤销余地，实现成本高于拖出。

**方案 B：独立窗口加极简操作入口（推荐 MVP）**

- 原理：独立窗口顶部加一条极窄工具条（或标题栏菜单/快捷键，如 Cmd+Shift+W 语义另定），提供"合并回主窗口"按钮/菜单项，点击走 mergeBack。纯主进程 + 一个极简 UI，零手势判定。
- 适配点：与单元 2 中"独立窗口纯页面"的假设冲突——需把假设修订为"极简工具条"；工具条本身也是拖回功能的自然宿主（可顺带显示会话名/URL）。

### 6.3 结论

- 机制：**采用现成方案**（与单元 2 同一 API 的反向），reattachTab/mergeBack 接口已列 6.1。
- 手势：**只做方案 B（极简工具条）**（用户定案 2026-09-12：不做窗口拖拽重叠判定）。工具条视觉实现时走 impeccable。
- 独立窗口形态随之定案：顶部极简工具条（会话名/URL + 合并回主窗口按钮）+ 页面，不再是纯页面。

## 8. 方案修订调研（v2，2026-09-12 追加）：多 Tab 独立窗口与跨窗口 Tab 转移

> 用户修订需求：拖拽期间有拖拽状态反馈；拖出的独立窗口 title = 会话名称（Tab title 维持原样）；一个会话可拖出多个独立窗口；Tab 可拖入已存在的同会话独立窗口；独立窗口下的 Tab 也可再拖出；Tab 允许跨窗口互相转移，**但只允许转移到同一 session 的窗口**。本节为独立完整调研，结论取代第 2/3/6 节的"单 Tab 单窗口"形态（view 保活迁移的核心机制仍复用其结论）。

### 8.1 单元拆分

- 单元 C：多窗口浏览器宿主架构（主进程改造，本方案的主体）。
- 单元 D：跨窗口拖拽转移手势（拖出、拖入既有窗口、拖拽状态反馈）。依赖 C 的窗口宿主模型。

### 8.2 单元 C：多窗口浏览器宿主架构

**要做什么**：主进程支持"主窗口浏览区 + N 个同会话独立窗口"共存，每窗口有自己的 Tab 集与激活 Tab；独立窗口是带 Tab 栏的完整浏览器窗口（无侧栏、无地址栏，Tab 栏复用现有组件形态）；窗口 title 显会话名。

**项目现状**（接缝与阻碍）：

- 单窗口假设比 v1 更深：`manager.ts` 的 `activeId` 是**会话级唯一激活 Tab**（manager.ts:83），`setBounds` 只作用于激活 view（manager.ts:325-328），快照 `BrowserSnapshot` 也只有一组 tabs/activeTabId（shared/browser.ts:44-50）——多窗口下这些都要从"每会话一份"升为"每窗口一份"。
- 独立窗口需要 UI（Tab 栏），而 UI 在 renderer：主窗口加载入口 `src/main/index.ts:155-158`（dev 走 `ELECTRON_RENDERER_URL`，prod 走 `index.html`），同一入口可用 query 参数进入"独立窗口模式"（如 `?role=tab-window&session=<id>`），复用 `TabStrip.tsx` 只渲染 Tab 栏。多窗口 = 多个独立 renderer 实例，zustand store 各自独立（`stores/browser.ts` 按窗口快照各自镜像，天然不串台）。
- IPC 现按"命令作用于激活会话"路由（ipc.ts:20-29），推送盲发主窗口（ipc.ts:37-39）；多窗口下 `event.sender` 可识别来源窗口（`BrowserWindow.fromWebContents(event.sender)`），通道需窗口作用域化。
- 快照上报 lastUrl（registry.ts:276-303）取"激活会话激活 Tab"，多窗口后口径需定义（建议维持主窗口激活 Tab，独立窗口的 Tab 不上报）。

**候选方案**：

- **方案 C1：窗口宿主模型（Tab 位置从"激活位"升级为"归属窗口"字段）**——TabEntry 增 `windowId`，每窗口维护自己的 `activeTabId` 与内容区矩形；快照按窗口分发。纯主进程数据模型重构，无新依赖。来源：Electron WebContentsView 多窗口挂载（<https://electronjs.org/docs/latest/api/web-contents-view>）+ 多窗口多 renderer 实例（<https://electronjs.org/docs/latest/api/browser-window>，每 BrowserWindow 独立加载同一入口）。
- **方案 C2：每窗口一个独立 TabManager 实例（现结构平移）**——把现有 createTabManager 按"窗口"而不是"会话"实例化，会话只提供分区。改动看似小，但 Tab 跨窗口转移要在两个 manager 间搬 entry 且事件接线（导航/标题/快捷键，manager.ts:186-271）全部要迁移重挂，容易漏；且 registry 现有会话级编排（销毁/克隆/上报）全按 manager=会话假设写死。
- 看过不选的：单 renderer 多窗口（一个 renderer 渲染多个窗口）——Electron 无此模型，每 BrowserWindow 必有自己的 webContents。

**可行性**：

| 维度 | C1（windowId 字段模型） | C2（每窗口一 manager） |
| --- | --- | --- |
| 技术匹配 | Electron 39 全支持；Tab 转移 = 改字段 + 摘挂 view，事件接线不动 | 转移需搬 entry + 重接线，遗漏面大 |
| 规则冲突 | 无（分区不变、WebContentsView 不变、DevTools 随 wc） | 无 |
| 成本 | 数据模型一次改到位，registry 编排可沿用"会话级"职责 | 短期省、长期在每条转移路径上付利息 |

**结论与实施建议**：**借鉴思路手写**（无现成库，Electron API 全够，思路=Tab 树与窗口树解耦）。落地路径：

1. `src/main/browser/manager.ts`：TabEntry 增归属窗口；`activeId` 改为每窗口激活表；新增 `moveTabToWindow(tabId, targetWindowId | null)`（null = 新窗口）。
2. `src/main/browser/windows.ts`（新增，吸收 v1 设计的 detached.ts）：独立窗口登记表——创建（加载 renderer 独立窗口模式）、`setTitle(会话名)`、关闭时销毁其全部 Tab、按 session 级联（destroySession/closeSession/clonePartition 调用）、会话名变更时同步 title。
3. `src/shared/browser.ts` + `ipc.ts` + preload：快照与命令按窗口作用域化（payload/推送带 windowId 或经 sender 识别）；新增 `browser:move-tab`（拖拽落点结果）、`browser:drag-hover`（拖拽悬停高亮推送）类通道；`index.d.ts` 同步。
4. `src/main/index.ts`：独立窗口创建入口 + before-quit 级联关闭；macOS 关主窗不退出语义对独立窗口同样适用（模板行为，关主窗时独立窗口独立存活或随之关，见 9 假设 4）。
5. renderer：App 按 query 进入独立窗口模式（Tab 栏 + 导航工具栏——地址栏与导航按钮复用 `Toolbar.tsx` 形态——+ 内容区空槽，bounds 上报复用 `useBrowserBounds.ts`）。
6. 独立窗口生命周期规则（用户定案 2026-09-12）：最后一个 Tab 允许关闭（与主窗口"最后留一"分叉），关闭即销毁窗口；Tab 全部转移走后窗口自动销毁；独立窗口之间允许互转（限同 session，与主窗口同一套 D1 命中逻辑，目标集 = 全部同会话窗口含主窗口浏览区）。
7. 重启恢复（用户定案 2026-09-12）：不恢复独立窗口，退出时该会话全部 Tab（含独立窗口中的）都归到主窗口对应 session 下恢复。**落盘结构需扩展**：现 schema v2 每会话只存 `pageTitle` + `lastUrl` 单条（`src/shared/sessions.ts:50-51`），需升 v3 增每会话 Tab URL 列表（激活位 + 顺序），启动 `ensureManager` 懒创建时按列表多开 Tab（页面运行态不还原，URL 级恢复，与现有 lastUrl 恢复同口径）。

### 8.3 单元 D：跨窗口拖拽转移手势（含拖拽状态反馈）

**要做什么**：拖起 Tab 时进入全局"拖拽态"（源窗口 Tab 半透明、目标窗口高亮/插入指示）；释放在空白屏幕 → 新窗口；释放在同会话窗口 → 并入其 Tab 栏；释放在异会话窗口/主窗口其他会话 → 拒绝并回弹。

**关键事实（网络核实）**：Electron 中 HTML5 拖拽的 dragover/drop **不会**跨窗口送达另一个窗口的 DOM（各窗口是独立渲染树，Chromium 拖拽事件不出窗口）。跨窗口命中只能由主进程做：

- 方案 D1（推荐）：dragstart 经 IPC 通知主进程开启"拖拽会话"，主进程定时器轮询 `screen.getCursorScreenPoint()`（约 16ms，仅拖拽期间）+ 全部同会话窗口 bounds 命中，经 `browser:drag-hover` 通道让目标窗口 renderer 画高亮/插入指示（拖拽状态反馈由此实现）；源窗口 dragend 时上报落点屏幕坐标，主进程裁决目标（空白 → 新窗口 / 同会话窗口 → 并入 / 异会话 → 拒绝回弹）。
- 来源：<https://stackoverflow.com/questions/50828059/electron-drag-tab-into-another-open-window>（dragend 屏幕坐标判定）；<https://stackoverflow.com/questions/70626145/how-to-get-cursor-position-outside-of-a-window-in-electronjs>（窗口外取光标 = screen API 主进程轮询）；跨窗口 drop 不送达的社区佐证 <https://www.reddit.com/r/electronjs/comments/op2nbl/how_do_i_tell_which_window_i_dropped_my_elements_on/>；dragover+drop 注册技巧 <https://medium.com/@richard.stromer/how-to-get-drop-events-working-in-electron-a6f6173d9ae6>
- 方案 D2（看过不选）：原生模块接管拖拽（<https://www.fileside.app/blog/2019-04-22_fixing-drag-and-drop/>）——为省一个轮询引入原生依赖与签名/构建复杂度，不值。

**可行性**：D1 全部用 Electron 内建 API（screen/ipc/BrowserWindow.getBounds），无规则冲突；轮询只在拖拽期间存在，成本可忽略。风险同 v1：dragend 触发依赖 dragstart 时对 document 注册 dragover（已知技巧，见上源）；macOS/Windows 双平台行为需实测。

**结论与实施建议**：**借鉴思路手写**（dragend 坐标 + 主进程命中判定的社区通行做法）。落地路径含在上文 C 的通道清单中；拖拽态视觉（半透明、目标高亮、插入指示、拒绝回弹）实现时走 **impeccable**。

### 8.4 v2 总体结论

可行，无一条红线被触碰；体量上从 v1 的"增量为零的挂摘"升为**主进程浏览器层的中等重构**（manager 数据模型 + IPC 作用域化 + 新增窗口登记表 + renderer 多模式入口），建议确认后走 write-plan 拆步骤实施。

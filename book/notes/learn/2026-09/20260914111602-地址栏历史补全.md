# 地址栏历史补全 功能调研报告

> 创建时间：2026-09-14 11:16（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：访问过的网址下次还得重新输入/复制整个地址；希望像 Chrome 一样输入几个字母就弹出相关历史记录，且补全过程不能阻塞主进程
> 调研单元：2 个（①历史记录数据层·主进程；②地址栏补全交互·preload/renderer）
> 状态：已确认（2026-09-14 用户批复全部 6 条假设），转开发计划

## 1. 需求理解

### 1.1 功能目标

测试人员在会话里访问过的网址（测试环境域名、内网地址、带参数的 URL），下次在地址栏输入前几个字母时，地址栏下方**即时**弹出匹配的历史记录下拉，鼠标/键盘选择即完成导航，体验对齐 Chrome omnibox（PRODUCT.md 原则 3「Chrome 即标准」）。硬性约束：输入响应流畅，补全的检索计算不得拖慢主进程（主进程承担窗口管理与 Tab 快照推送）。本期只做「输入时的建议弹出」，不做历史管理页。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] Electron 有没有官方 API 读取 Chromium 内建浏览历史？→ **没有**。session 模块只有清除（clearHistory），无读取；且本地实证分区目录根本不落 History 库（见 2.3 方案 A），历史必须自建
- [x] 历史数据从哪里采集？→ `src/main/browser/manager.ts:292-301` 每 Tab 已挂 `did-navigate` / `did-navigate-in-page`（主 frame）钩子，采集点现成
- [x] 历史存哪、怎么落盘不拖慢主进程？→ 独立 JSON 文件（按会话分文件）+ 500ms 去抖 + 原子写，全部复用项目既有模式（见 2.2/2.5）
- [x] 击键时的匹配检索放在哪个进程？→ renderer 会话级镜像 + 本地同步过滤，编辑期间零 IPC、零主进程参与（见 3.3 方案 C 对比）
- [x] 下拉 UI 用 antd AutoComplete 还是自绘？→ 自绘。antd AutoComplete 在 antd 6 存在，但默认形态与 DESIGN.md「Chrome 灰阶语系 / 无阴影 / 禁止覆盖 .ant-\* 内部选择器」冲突（见 3.3 方案 A）
- [x] 与地址栏现有 draft/pending/Escape 状态机怎么整合？→ 键盘语义分层：Enter 优先高亮项、Esc 先关下拉再还原（见 3.5）
- [ ] 历史作用域按会话还是全局？克隆是否带历史？→ 推荐按会话 + 克隆携带，列为待确认假设（第 5 节）

### 1.3 拆分判断

拆 2 个单元：

1. **历史记录数据层（主进程）**：采集、内存持有、落盘、会话生命周期联动、IPC 通道
2. **地址栏补全交互（preload/renderer）**：历史镜像、匹配排序、下拉 UI、键盘整合

依赖顺序：单元二依赖单元一的通道与数据结构；单元一可独立先行。拆分依据：跨进程层各成块（main / preload+renderer），且「数据从哪来」与「建议怎么弹」是两个可独立定案的能力点。

## 2. 调研单元一：历史记录数据层（主进程）

### 2.1 该部分要做什么

每个 Tab 导航落地时记录/更新历史条目（url、title、faviconUrl、visitCount、lastVisitedAt）；主进程内存持有 + 去抖落盘，重启后保留；会话生命周期联动（删除清史、克隆携带）；对 renderer 暴露查询通道与变化推送。不负责：匹配排序与 UI（单元二）。

### 2.2 项目现状

- `src/main/browser/manager.ts:292-309`：每 Tab 已挂 `did-navigate` / `did-navigate-in-page`（主 frame 守卫）/ `page-title-updated` / `page-favicon-updated`，TabEntry 已维护 url/title/faviconUrl——**采集点现成，零新增事件监听**
- `src/main/browser/manager.ts:160-163`：`requestFocusAddress` 经 `focusListeners` 回调上抛、不含 IPC 的既有惯例——历史采集回调可完全仿此（manager 不碰持久化，registry 侧接线）
- `src/main/browser/url.ts:27`：`isOpenableUrl`（http/https/file/about 白名单）可直接复用为入史过滤
- `src/main/store.ts:141-178`：sessions.json 原子写（tmp + rename）与 `mutateSnapshot` 串行队列、`loadSnapshot` 坏数据回退——历史文件照抄此模式
- `src/main/browser/persistence.ts:22-23, 233`：500ms trailing 去抖落盘 + `flushAll` 封笔汇入 before-quit 优雅退出链的完整先例
- `book/docs/requirements/PRD.md` 4.4 与 DESIGN.md「会话元数据已持久化」条目：外观偏好与 sessions.json 分别存储、独立读写、任一侧损坏不连带——**历史独立文件有直接先例**
- `src/main/browser/registry.ts:132, 492`：destroySession 链（销毁 → clearStorageData → 删分区目录）与克隆的 close-then-copy 分区复制，是历史清理/复制两处接线点
- `src/shared/browser.ts:2-3`：**契约红线**——新增通道前必须先修订对应开发计划第 3 节（实现时随开发计划一起做，不改 shared 不算违规）

### 2.3 候选方案

**方案 A：复用 Chromium 内建历史库（读 partition 目录 History SQLite）**

- 原理：每个 `persist:sess-<id>` 分区目录下有 Chromium 自维护的 History SQLite，直接查询补全
- 来源：<https://electronjs.org/docs/latest/api/session>（无读取 API，仅清除）；社区讨论 <https://www.reddit.com/r/electronjs/comments/10etozc/access_chromium_history_db_from_electron/>
- 适配点：需引入 better-sqlite3 类原生依赖 + 复制文件绕开 Chromium 文件锁
- **看过、不选（本地实证，2026-09-14）**：遍历 dev 环境 `userData/Partitions/` 全部 24 个分区目录——每个分区确实各有一份 `Cookies` SQLite（Chromium 的 profile 数据本就是**每分区一份**，不存在全项目共用一个库的形态），但**没有任何一个分区存在 `History` 文件**：Electron 未给 session 分区接线 Chromium 的 HistoryService，历史根本不落盘。方案 A 不是"读起来勉强"，是**事实上无库可读**。自建 SQLite 库同理不值——每会话上限千条级，JSON 内存过滤足够

**方案 B：主进程自建历史 + 每次击键 IPC 查询（invoke）**

- 原理：主进程内存持有历史，renderer 每次输入（去抖后）invoke 查询，主进程过滤返回 top N
- 来源：<https://electronjs.org/docs/latest/api/ipc-main>（invoke/handle 异步模式）
- 适配点：`BROWSER_CHANNELS` 增一条 query 通道；需乱序响应防护（Min 的 placesPlugin 用时间戳丢弃过期响应）

**方案 C：主进程自建历史为唯一事实源 + renderer 会话级镜像 + 击键本地同步过滤（推荐）**

- 原理：主进程只做记录/落盘/推送，地址栏编辑期间零 IPC；renderer store 持当前会话历史副本，每次击键本地同步过滤排序（2000 条子串匹配 < 1ms）
- 来源：Min 浏览器 placesSearch.js 即在内存缓存上迭代打分而非发 SQL（<https://github.com/minbrowser/min/blob/master/js/places/placesSearch.js>）；Min 把 DB 查询放独立 worker 进程的「搜索不占主流程」思路同源；本项目 `BrowserSnapshot`「主进程事实源 + renderer 镜像」架构完全同构（`src/renderer/src/stores/browser.ts` 头注释）

### 2.4 可行性分析

| 维度 | 方案 A（Chromium History SQLite） | 方案 B（击键 IPC 查询） | 方案 C（renderer 镜像本地过滤） |
| --- | --- | --- | --- |
| 技术匹配 | Electron 39 无读取 API；文件布局非契约；需 SQLite 原生依赖 | 可行，覆盖需求；乱序/去抖自理 | 可行；每会话 2000 条 × ~200B ≈ 400KB 镜像无压力，同步过滤 < 1ms 无感 |
| 规则冲突 | 分区目录属 Chromium 管辖地盘（同 DESIGN.md「DevTools 停靠由 Chromium 管理」的边界感）；引入重依赖违背项目克制风格 | 无冲突；IPC 白名单扩一条 | 无冲突；与快照推送/守卫架构同构 |
| 成本 | better-sqlite3 + electron-rebuild 长期维护成本，收益为零 | 无依赖；每击键一跳主进程事件循环（微秒级但非零，与「不阻塞主进程」诉求相悖） | 无依赖；多一条拉取 + 一条推送通道；镜像内存几百 KB |

「不能阻塞主进程」在方案 C 下是结构性满足：击键路径上主进程根本不参与；方案 B 只是「阻塞量可忽略」。

### 2.5 结论与实施建议

- 结论：**完全手写**。Electron 无历史读取 API，方案 A 直接否决；无论查询放哪侧，数据层都必须自建——采集挂在既有导航钩子上，存储复用项目既有落盘模式，无任何新依赖。
- 落地路径（粒度到文件与接口）：
  1. 新增 `src/shared/history.ts`：`HistoryEntry`（url/title/faviconUrl/visitCount/lastVisitedAt）、`HISTORY_CHANNELS`（`browser:history-get` 命令 + `browser:history-changed` 推送）、落盘常量（schema 版本、每会话条数上限、URL 截断上限）
  2. 新增 `src/main/browser/history.ts`：内存 `Map<sessionId, Map<url, HistoryEntry>>`；`loadHistory`（坏数据回退，照 store.ts 模式）；`recordVisit`（upsert：同 URL 只更新 visitCount/lastVisitedAt/title/faviconUrl）；500ms trailing 去抖落盘 + `flushAll` 汇入既有 before-quit 退出链
  3. 落盘文件 `userData/history/<sessionId>.json`（按会话分文件：写盘只写变化的会话、删除=删文件、克隆=复制文件）；manager 仿 `focusListeners` 惯例增加 onVisit 回调上抛导航事实（manager 仍不碰持久化），registry 接线 history.recordVisit；入史过滤：`isOpenableUrl` 且排除 `about:blank`
  4. 生命周期接线：registry 的 destroySession / deleteAll 链删历史文件与内存；克隆链复制历史文件
  5. `src/main/browser/ipc.ts` 挂 get handler（按 `event.sender` 作用域解析会话——主窗来源 → 激活会话，独立窗来源 → 绑定会话，renderer 不传 sessionId 防越权读他窗会话历史）；条目变化时向该会话全部窗口定向推送（广播集合同 dragHover 惯例）
  6. `src/preload/index.ts` + `index.d.ts`：api 增 `history.get` / `onHistoryChanged`
  7. `src/shared/browser.ts` 头注释契约：新增通道前先修订开发计划第 3 节（IPC 通道 18 → 20）

## 3. 调研单元二：地址栏补全交互（preload/renderer）

### 3.1 该部分要做什么

地址栏聚焦编辑时按输入即时过滤当前会话历史，下拉展示 top N（建议 8 条）；匹配排序（规范化 + 前缀优先 + 新近度/频次加权）；键盘（↑↓ 选择、Enter 提交选中或原输入、Esc 分层关闭）与鼠标选择；亮暗双主题；主窗与独立窗口同享。不负责：历史采集与存储。

### 3.2 项目现状

- `src/renderer/src/components/browser/Toolbar.tsx`：地址栏原生 `<input>` + draft/pending/invalid 三态（提交锁定机制 36-45 行）、Enter 提交 / Esc 还原 / `isComposing` 守卫（101-109 行）——新键盘语义需与这套状态机共存；`autoComplete="off"` 关的是浏览器原生补全，与自绘建议层不冲突
- `src/renderer/src/components/IndependentWindowFrame.tsx:2` 与 `BrowserFrame.tsx:2` 均复用同一 Toolbar——**补全做进 Toolbar 自动覆盖独立窗口**；独立窗口 store 守卫按 windowId（`src/renderer/src/stores/browser.ts:100`）
- DESIGN.md Chrome 侧语系：chrome-surface/line/ink 灰阶、全应用 0 box-shadow（发丝线规则）、琥珀禁入右侧、**禁止覆盖 `.ant-*` 内部选择器**；TabStrip 的 favicon `<img>`（CSP 已放行 img-src https:、无图标灰阶圆点占位）是现成先例
- `src/renderer/src/assets/app.css`：chrome-\* token 体系齐备（DESIGN.md 颜色表亮暗成对）

### 3.3 候选方案

**方案 A：antd AutoComplete**

- 原理：官方输入建议组件，options 数据源 + 自定义 option 渲染
- 来源：<https://ant.design/components/auto-complete/>
- 适配点：antd 6.6.3 存在该组件；但默认形态（蓝色选中高亮、圆角浮层、自带间距）与 Chrome 灰阶语系冲突，对齐需深度 token 定制乃至覆盖 `.ant-*` 内部结构——DESIGN.md 明令禁止
- **看过、不选**：定制成本高于自绘；浏览器区 TabStrip/Toolbar 全自绘，混入 antd 浮层反成孤例

**方案 B：自绘下拉（推荐）**

- 原理：Toolbar 内绝对定位面板（omnibox 正下方），chrome-surface 底 + chrome-line 发丝线 + 灰阶选中行；键盘 ↑↓ 环形移动
- 来源：Chrome omnibox 交互形态（PRODUCT.md「Chrome 即标准」）；本项目 TabStrip 自绘先例

**匹配排序参考（两方案通用，借鉴 Min）**

- Min placesSearch.js：前缀命中 boost = min(2.5×词长, 10)，任意子串命中 0.4 + 0.075×词长；规范化 = 小写 + 去 `http(s)://` + 去 `www.`；模糊匹配仅对高热条目（visitCount>2 且一周内访问，或一天内访问过）启用
- 来源：<https://github.com/minbrowser/min/blob/master/js/places/placesSearch.js>、<https://github.com/minbrowser/min/blob/master/js/searchbar/placesPlugin.js>（结果条数、防乱序时间戳、删除键不自动补全等交互细节）

### 3.4 可行性分析

| 维度 | 方案 A（antd AutoComplete） | 方案 B（自绘下拉） |
| --- | --- | --- |
| 技术匹配 | 功能覆盖，但键盘细节、行形态、尺寸对齐 Chrome 需对抗组件默认行为 | 完全可控；双主题走既有 CSS 变量体系 |
| 规则冲突 | 与「禁止覆盖 .ant-\*」「无 box-shadow」「Chrome 灰阶」三条设计规则冲突风险高 | 零冲突（沿用 chrome-\* 语系与 TabStrip 惯例） |
| 成本 | antd 浮层主题定制的反复调参成本 | 一个小组件 + 若干 CSS token，无依赖 |

### 3.5 结论与实施建议

- 结论：**借鉴思路手写**——匹配排序借鉴 Min 的分级加权；UI 自绘对齐 Chrome 语系，不用 antd AutoComplete。
- 落地路径：
  1. renderer 历史镜像：并入 `src/renderer/src/stores/browser.ts`（新增 history 条目字段 + 订阅 `onHistoryChanged` + init 拉取），守卫与快照同规（主窗比对激活会话、独立窗比对绑定会话），切会话丢弃旧会话镜像——不跨会话串数据
  2. 新增 `src/renderer/src/components/browser/omniboxSuggest.ts` 纯函数模块：normalize + match + score + top N（无副作用）。排序建议：匹配等级（host 前缀 > URL/标题前缀 > 子串）为主序，同级按新近度（如 7 天指数衰减）+ log(visitCount)；输入 < 2 字符不触发；测试场景 URL 常带 query 参数区分环境，**不做** Min 的去 query 规范化
  3. `Toolbar.tsx` 整合：建议态（开合 + 高亮 index）；键盘插入现有 onKeyDown——Enter 有高亮先提交高亮项（走既有 navigate 与 pending 锁定，机制原样生效）、Esc 先关下拉再走现有还原、↑↓ 移动且 preventDefault 防 caret 跳动；建议行用 onMouseDown preventDefault 防点击前失焦
  4. 下拉面板组件：favicon `<img>`（复用 TabStrip 惯例）+ 标题 + URL；无匹配不弹面板（保持现状体验）
  5. **界面布局与视觉（行高、选中态、hover 蒙版、亮暗 token、开合动效是否为 120ms 灰阶过渡）实现时走 impeccable 技能**（新界面走 new-work 路径）
- 建议两步交付：第一步数据层 + 无样式打磨的最小下拉（功能可用）；第二步 impeccable 视觉定稿。

## 4. 风险与开放问题

- **IME 组合输入**：建议过滤挂在 onChange（组合期间值也在变），组合中列表实时变化属可接受行为；现有 `isComposing` 守卫已保证组合内 Enter 不误提交。实现时实测微调
- **两份落盘文件的边界**：history 与 sessions.json 互不读写（PRD 4.4「分别存储、独立读写」先例）；历史文件损坏按 store.ts 同款回退——丢历史不丢会话
- **性能兜底路径**：若未来历史上限量级远超预期，omniboxSuggest 是纯函数，可整体迁 Web Worker（调用方接口不变）——本期数据量不需要
- **推送形态开放**：增量条目推送（upsert 单条）与轻量信号 + 重拉两种形态，实现时按通道复杂度取简，不影响本架构结论

# 会话列表拖拽排序 功能调研报告

> 创建时间：2026-09-14 17:24（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户原话——"我希望左侧的会话列表，能够拖动更换会话列表的顺序"
> 调研单元：1 个（小功能）
> 状态：调研完成，用户已确认（2026-09-14，采用原生 HTML5 DnD 方案，假设逐条批复见第 4 节）；实现未开始

## 1. 需求理解

### 1.1 功能目标

左侧会话列表面板支持拖拽调整会话条目的排列顺序：测试人员按自己的工作习惯（如按测试计划顺序、按账号重要度）组织多个隔离会话，而不是被动接受"新建即追加末尾"的固定顺序。拖拽为纯视觉与元数据层面的重排——不触碰会话分区、不改变激活会话，右侧浏览区与登录态不受影响；排序结果持久化，重启后按用户排列的顺序恢复。与既有交互（点击激活、重命名、菜单、批量勾选）无冲突共存。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] React 19 生态有无成熟且活跃维护的拖拽排序库？→ 有三支主流：dnd-kit（维护趋缓）、@hello-pangea/dnd（活跃）、Atlassian pragmatic-drag-and-drop（活跃）；版本事实见 2.3
- [x] antd 6 有无现成的可拖拽 List 组件？→ 没有，官方仅 Table 拖拽排序示例且推荐引入 dnd-kit，见 2.3
- [x] 列表顺序要不要动落盘 schema？→ 不用：sessions.json 的 `sessions` 数组顺序本身就是顺序，原样读写，见 2.2
- [x] 需要新增 IPC 通道吗？→ 需要 1 条 `sessions:reorder`（全序数组、整单校验拒绝制，照 delete-batch 先例），见 2.5
- [x] 本项目 WebContentsView 架构对 renderer 内拖拽手势有何约束？→ 存在"右区原生层"边界问题，既有 overlay 机制可缓解，且存在一处平台未实测的不确定点（诚实记入第 3 节），见 2.2 / 2.4 / 3
- [x] 拖拽与行内既有交互（点击激活 / 重命名输入 / 操作菜单 / 批量勾选）如何共存？→ 见 2.4

### 1.3 拆分判断

单调研单元。界面手势、renderer store、主进程通道/落盘是一条功能的三个接缝，"现状 + 调研"在一屏内说得清，不拆。

## 2. 调研单元：会话列表拖拽排序

### 2.1 该部分要做什么

负责：主窗左栏会话列表（`ul.session-list` 的 `li.session-row`）的拖拽重排交互、排序结果经 IPC 落盘持久化、重启恢复顺序。不负责：跨面板拖拽（会话不能拖出列表/拖进右区）、批量模式下的排序行为（默认禁用，见假设 2）、会话分区与浏览器编排的任何变动。

### 2.2 项目现状

**顺序已经是落盘事实，持久化零 schema 变更：**

- 渲染顺序 = renderer store 数组顺序：`src/renderer/src/components/SessionPanel.tsx:355`（`ul.session-list` 内 `sessions.map` 按数组序渲染 `li.session-row`）。
- 主进程快照 `SessionsSnapshot.sessions: StoredSession[]`（`src/shared/sessions.ts:86`）数组顺序原样读写落盘 `userData/sessions.json`：`src/main/store.ts` 的 `parseSnapshot` 按 JSON 数组序重建（重复 id 去重保留首个，`store.ts:239-249`）、`mutateSnapshot` 串行读-改-写（`store.ts:159-171`）、原子写经 `src/main/fs-utils.ts`。**重排 = 数组换序，不动 version/字段结构。**
- 新建/克隆会话追加列表末尾：`src/renderer/src/stores/sessions.ts:81`、`src/renderer/src/stores/sessions.ts:101`（`sessions: [...state.sessions, item]`），与主进程 `snapshot.sessions.push`（`src/main/sessions.ts:145`、`263`）一致。

**IPC 接缝与既有先例：**

- 通道常量单源 `SESSIONS_CHANNELS`（`src/shared/sessions.ts:18-29`），现有 10 条（含 statusChanged 推送），`src/main/sessions.ts:342` 尾注释同步计数。新增通道须走同一常量，禁止手写字符串。
- **整单校验拒绝制先例**（新通道照抄的模板）：`sessions:delete-batch`（`src/main/sessions.ts:284-309`）——`parseNonEmptyStringIds`（非空数组逐项 string）+ 去重 + `SESSION_ID_RE` 格式前置校验 + `mutateSnapshot` 互斥期内存在性校验，任一不满足整单拒绝无部分执行。reorder 的校验形状几乎同构（全序数组 = 集合相等校验替代存在性校验）。
- preload 暴露面：`src/preload/index.ts:56-84`（`api.sessions.*`），同步维护 `src/preload/index.d.ts`。

**本项目特有的架构约束（候选方案取舍的核心）：**

- 右区被 `WebContentsView` 原生层覆盖：任何 DOM 内容延伸到右区会被遮挡，这就是 `ui store overlayDepth` 机制存在的原因（`src/renderer/src/stores/ui.ts:5-12`：BrowserFrame 据此让主进程按零矩形收起原生层，`src/renderer/src/components/BrowserFrame.tsx:13-16`）。对拖拽手势的含义：光标若越过面板进入右区，事件是否仍送达 renderer 未能从既有代码确证（见第 3 节风险 1），方案必须对此**天然免疫或可兜底**。
- **工程先例**：阶段 9 Tab 拖出/拖入手势为指针捕获自绘，且明确弃用了 HTML5 DnD（`DESIGN.md`「拖拽手势」条目）。弃用理由是**跨窗搬移时序**——原生拖放在窗外释放时系统先播"拖影飞回原位"动画、随后异步搬移才生效，叠成"先回原位再跳走"的两段视觉谎言。本功能不存在该问题：重排严格发生在列表内，列表外释放 = 不移动，"飞回原位"就是真实的最终态（诚实反馈）。适用边界差异在 2.4 逐条对照。
- 行内既有交互：点击/Enter/空格激活会话（`SessionPanel.tsx:108-123`）、行内重命名 `Input`（`SessionPanel.tsx:134-147`）、`Dropdown` 操作菜单（`SessionPanel.tsx:159-173`）、批量模式勾选（`SessionPanel.tsx:126-131`，行角色切换为 checkbox）。
- 领域红线不触碰声明：重排只动元数据数组顺序，不触碰会话分区（`persist:sess-<id>`）、不触碰 WebContentsView 结构、不引入 Playwright、界面文案中文。

### 2.3 候选方案

**方案 A：@dnd-kit/core + @dnd-kit/sortable（现成库）**

- 原理：React 拖拽工具链，`DndContext` + `SortableContext` + `useSortable`，指针传感器驱动，内置碰撞检测、拖影 overlay、键盘传感器（Space 拾取 + 方向键移动）、自动滚动。
- 来源：https://dndkit.com/ ；npm 事实（2026-09-14 查 registry）：`@dnd-kit/core` 最新 **6.3.1（2024-12-05）**，peer `react >=16.8.0`（React 19 兼容）；`@dnd-kit/sortable` 最新 **10.0.0（2024-12-04）**。
- 与本项目的适配点：纯 renderer 侧，不碰主进程；版本匹配 React 19。**但维护趋缓**：最后一次发版距今约 21 个月，2025-11 仍有用户公开追问维护状态（https://github.com/clauderic/dnd-kit/issues/1830）；新一代 `@dnd-kit/react` 尚未 1.0。
- antd 6 官方 Table 拖拽排序示例走的正是 dnd-kit（https://ant.design/components/table ），佐证其为 React 生态默认解——但 antd 无现成可拖 List 组件（讨论见 https://github.com/ant-design/ant-design/discussions/43569 ）。

**方案 B：@hello-pangea/dnd（现成库）**

- 原理：react-beautiful-dnd 的活跃维护分叉，声明式 `DragDropContext`/`Droppable`/`Draggable`，专注列表排序，键盘与读屏支持完善。
- 来源：npm 事实（2026-09-14 查 registry）：最新 **18.0.1（2025-02-09）**，peer `react ^18.0.0 || ^19.0.0`（React 19 兼容）；仓库 https://github.com/hello-pangea/dnd 。
- 与本项目的适配点：版本匹配；但 API 强约束 DOM 结构（render-prop 包裹每个列表项与整表），与现有 `li.session-row` 结构耦合改造面大；体积与运行时复杂度显著高于方案 A；传感器同为 mouse/pointer 事件驱动，方案 A 面对的"事件边界"问题它同样存在且无解法。

**方案 C：手写，基于浏览器原生 HTML5 Drag and Drop API（draggable + dragstart/dragover/drop/dragend）**

- 原理：`li` 设 `draggable`，`dragover` 在行上按光标相对行中点判定插入位并渲染指示线（纯视觉），`drop` 时提交一次新顺序（IPC reorder），`dragend` 清理全部临时态。**dragend 在源元素上无条件触发**（无论落在列表内、右区、窗外、Esc），拖拽会话不可能残留。自定义拖影经 `setDragImage` 渲染离屏行克隆；Chromium 对可滚动容器自带拖拽自动滚动；原生拖拽有位移阈值，与行点击天然消歧。
- 来源：MDN HTML Drag and Drop API（https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API ）；Chromium 拖拽自动滚动为浏览器内置行为。零 npm 依赖。
- 与本项目的适配点：纯 renderer 侧；手势逻辑集中在新组件/hook（预计 100—150 行），与 codebase 手写 UI 的既有风格（omnibox 建议面板、TabStrip 手势均为手写，项目当前零 DnD 依赖）一致。

**看过、不选：**

- **Atlassian pragmatic-drag-and-drop**（`@atlaskit/pragmatic-drag-and-drop` 3.1.0，2026-08-29，活跃，https://github.com/atlassian/pragmatic-drag-and-drop ）：底层正是对原生 HTML5 DnD 的封装与增强（hitbox/indicator/accessibility 拆成多个子包）。方向与方案 C 同路，但本项目只有一个平铺单列排序场景，用不上其多容器/树/性能增强面，引入 3—4 个 @atlaskit 包不成比例。若未来出现跨容器排序需求可回头评估。
- **主进程 16ms 光标轮询手势**（照 TabStrip 阶段 9 模式）：该模式的必要性来自跨窗命中裁决与窗外释放；本功能是单窗内列表排序，引入主进程拖拽会话 + IPC 面完全不成比例。

### 2.4 可行性分析

| 维度 | 方案 A（dnd-kit） | 方案 B（@hello-pangea/dnd） | 方案 C（手写 HTML5 DnD） |
| --- | --- | --- | --- |
| 技术匹配 | React 19 兼容（peer ≥16.8）；单列排序覆盖良好；**但指针传感器事件驱动的模型在本项目右区原生层边界下有"pointerup 丢失 → 拖拽态冻结"风险路径**（事件被原生层吞掉时文档收不到 pointerup，DragOverlay 卡住直到下一次按下），需自行打补丁 | React 19 兼容；单列排序最成熟；同样的事件驱动模型，同一风险路径；render-prop 结构与现有 li 行改造耦合大 | **dragend 恒达免疫边界问题**：无论光标落在右区/窗外/按 Esc，清理逻辑必然执行；插入指示只响应列表内 dragover，右区无指示器是天然合理语义（右区非落点）；Chromium 自带容器自动滚动；行点击/拖拽原生消歧 |
| 规则冲突 | 无红线冲突；引入两个新依赖与项目"手写手势、零 DnD 依赖"的既有风格相悖（非红线，风格层） | 无红线冲突；同上 | 与阶段 9"弃用 HTML5 DnD"决策**表面冲突**，逐条对照后不成立：该决策针对跨窗搬移的"回弹撒谎"时序问题，本功能列表外释放=真实不移动，回弹即诚实反馈；手势不跨窗、不需要窗外释放语义 |
| 成本 | +2 依赖（core 约 12KB gzip + sortable）；维护趋缓（末次发版 2024-12，#1830）；锁定面最大 | +1 依赖（约 100KB 级）；分叉维护活跃（2025-02 发版）；运行时复杂度高 | **零新增依赖**；手写约 100—150 行；键盘排序不纳入本次范围（假设 3 已批复裁掉，仅保留鼠标拖拽）；自定义拖影在 Chromium 桌面端表现可靠（本项目仅 Win/Mac 桌面 Chromium，无 Safari/移动端兼容负担） |

与行内既有交互的共存（三方案通用约束，实现时遵守）：行内重命名 `Input` 编辑态禁用拖拽（编辑态 `draggable=false`）；操作菜单按钮与批量勾选框在 dragstart 链路上天然不触发（按钮点击不构成拖拽起点，必要时 `draggable` 收窄到把手或 `onDragStart` 里按事件源过滤）；批量模式下整体禁用拖拽（行角色已切换为 checkbox，语义上不排序）；行文本让位拖拽需 `user-select: none`（视觉变化交由 impeccable 定稿）。

### 2.5 结论与实施建议

- 结论：**完全手写——基于浏览器原生 HTML5 Drag and Drop API**（方案 C）。理由：本功能是拖拽问题谱系中最简单的形态（单窗、单容器、平铺垂直列表），而本项目最硬的架构约束（WebContentsView 原生层边界）恰好是 HTML5 DnD"dragend 恒达"天然免疫、而两支事件驱动库都存在冻结风险路径的场景；零新增依赖且与 codebase 手写 UI 风格一致。dnd-kit（方案 A）虽是 React 生态默认解，但为这一个平铺列表引入两个维护趋缓的依赖、且不解决本项目特有的边界问题，不划算。

- 落地路径（粒度到文件与接口，分四步）：
  1. **契约层**：`src/shared/sessions.ts` 的 `SESSIONS_CHANNELS` 增 `reorder: 'sessions:reorder'`，新增 `ReorderSessionsPayload { ids: string[] }`（全序数组）；按仓库惯例修订 `shared/sessions.ts` 头注释契约与阶段 6 计划 2.4 节修订记录，`src/main/sessions.ts:342` 通道计数 10 → 11。
  2. **主进程**：`src/main/sessions.ts` 新增 handler，照 delete-batch 整单拒绝制——`parseNonEmptyStringIds` + 去重 + `SESSION_ID_RE` 前置校验 + `mutateSnapshot` 互斥期内「集合相等」校验（长度相等、无缺无余）→ 按入参顺序重排 `snapshot.sessions`；`activeId` 不动、无编排回调。`src/preload/index.ts` + `index.d.ts` 增 `sessions.reorder`。
  3. **renderer**：`src/renderer/src/stores/sessions.ts` 增 `reorderSessions(ids)`——乐观本地重排 + IPC 失败回滚（照 `selectSession` 模式，写盘为本地小文件，乐观体验优于 `renameSession` 的非乐观）。`SessionPanel.tsx` 增拖拽手势（draggable 行 + dragover 插入指示 + drop 提交 + dragend 清态；编辑态/批量态禁拖）。
  4. **视觉与文档**：拖拽态样式（拖影卡片、插入指示线、占位行）新增 `app.css` 条目——**实现时走 impeccable 技能**（含"整行拖 vs 拖拽把手"形态定稿）；`book/docs/requirements/PRD.md` 3.1 增拖拽排序条目、3.1.4 持久化补"列表顺序"；`DESIGN.md` 增对应设计条目。
  5. **验证路径**（沿用仓库惯例）：typecheck / lint / build + 隔离实例 CDP 真实 UI 链（拖拽换序、落盘 `sessions.json` 顺序一致、重启恢复、整单拒绝用例：拖拽瞬间另一窗删会话、批量模式禁拖、编辑态禁拖）。

## 3. 风险与开放问题

1. **右区事件边界未实测（对方案 C 无致命影响）**：光标按住左键从面板越过右区时，move/up 事件是否仍送达主窗 renderer，macOS（AppKit 将 mouseDragged 路由给 mouseDown 视图）与 Windows（按钮按下期间隐式捕获）按 OS 惯例通常仍送达，但 Electron WebContentsView 叠层下的实际行为未在本项目实测过——既有 overlay 机制注释只证实了"视觉遮挡"，未证实"事件吞没"。方案 C 下该问题最多表现为"越界后指示器不更新"（dragend 恒达保证不冻结、不错乱）；实施第一步建议先真机冒烟确认，据此决定是否需要在拖拽期间登记 ui overlay（代价是拖拽期间右区浏览内容被收起，视觉扰动大，非必要不做）。
2. **与阶段 9 弃用 HTML5 DnD 决策的表面冲突**：需在实现说明与 DESIGN.md 中写清适用边界差异（见 2.4 规则冲突行），避免后续开发者误读为决策反复。
3. **拖入网页页面的边缘行为**：原生拖拽会在 dataTransfer 携带被拖元素的默认文本数据，释放到右区网页理论上可能触发页面自身的 drop 处理。实现时用自定义 MIME 覆盖 setData、且仅列表内 dragover preventDefault 即可收敛，列入实现检查项。
4. 会话数量极大时依赖 Chromium 内置拖拽自动滚动，够用但不精细；如实测手感差，再评估补 `@atlaskit/pragmatic-drag-and-drop-auto-scroll` 同款思路的手写补齐（低优先级）。

## 4. 待确认假设（已于 2026-09-14 全部批复）

- [x] 假设 1（已确认）：排序持久化的语义为"顺序即列表数组顺序"，重启恢复；连带地，「删除会话后级联指向剩余首项」的"首项"（`src/main/sessions.ts:189`、`302`）将随用户排序而变——即用户把某会话拖到第一位后，删除激活会话时级联激活的就是它。
- [x] 假设 2（已确认）：批量模式（勾选态）下禁用拖拽排序，退出批量模式恢复。
- [x] 假设 3（已裁掉）：键盘排序不纳入本次范围——仅保留鼠标拖拽，不做方向键移动等键盘补充。
- [x] 假设 4（已确认）：新建/克隆会话仍追加列表末尾（现状不变，不因排序功能改变落位规则）。
- [x] 假设 5（已确认）：拖拽为纯重排——不切换激活会话、不触发右侧浏览区任何变化；拖拽中激活态高亮跟随原行（不是跟随被拖影）。

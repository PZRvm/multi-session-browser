# Chrome 登录态与站点存储导入可行性 功能调研报告

> 创建时间：2026-10-28 10:55:14（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户反馈导入 Chrome 后 mail.qq.com 等网站仍需登录，要求评估 Cookie、IndexedDB、sessionStorage 导入，并将第三条问题补进 steps。
> 调研单元：3 个（Cookie / IndexedDB / sessionStorage）
> 状态：用户已确认本期不做 Chrome 扩展、排除 sessionStorage、冲突可选数据来源；直接文件读取的技术验证待完成（未实施）
> 2026-10-28 反馈裁决：Chrome 扩展留待后续；sessionStorage 本期不做；冲突支持「以 Chrome 为准 / 以当前会话为准」。源 Cookie 加密与新增业务加密的区别见 2.3，明文源可以直接导入，已加密源仍需解密。

## 1. 需求理解

### 1.1 功能目标

让测试人员将 Chrome 中指定站点的登录凭据和站点数据带入指定的隔离会话，提高导入后登录状态延续的覆盖面。当前导入仅含历史与 localStorage，缺少 Cookie 是已确认的能力缺口；mail.qq.com 是用户提供的验收样本，尚未对用户账号的实际认证请求做验证。

初轮评估比较了“直接读取 Chrome 本地文件”与“Chrome 授权扩展导出、应用导入”。用户反馈后，本期仅推进直接文件读取的可行性验证，配套 Chrome 扩展留待后续；sessionStorage 移出本期范围。冲突允许用户选择以 Chrome 源数据或目标会话现有数据为准，本轮继续更新调研与需求记录。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] Cookie 能否进入目标分区？可以，Electron 官方 API 支持普通 Cookie，包括 HttpOnly；源侧读取存在平台差异。见第 2 节。
- [x] Windows 新版 Chrome 的加密是否意味着所有导入路线都不可行？不是；直接离线解密受限，授权扩展有官方 Cookie API。见 2.3。
- [x] IndexedDB 能否像 localStorage 一样逐条搬运原始 LevelDB 记录？不适合；数据库结构、内部编号、索引与外部对象使直接合并风险显著增大。见第 3 节。
- [x] sessionStorage 是否完全不落盘、因而无法导入？不是。Chromium 会为会话恢复保存部分数据；关键困难是标签页 namespace 的对应关系。见第 4 节。
- [x] 全部数据迁移是否等于网站一定免登录？不等于，设备绑定凭据等认证条件可能无法随存储迁移。见第 5 节。

### 1.3 拆分判断

初轮拆为三个单元，以下保留完整比较。本期有效范围为 Cookie 与 IndexedDB 的直接文件读取，优先验证 Cookie，再根据站点实际依赖扩 IndexedDB；扩展路线为后续备选，sessionStorage 单元仅留调研背景，不进入开发任务。

项目基线：`package.json` 声明 Electron `^39.2.6`，本机实际安装为 **39.8.10 / Chromium 142.0.7444.265**（本轮运行时实证）。`book/docs/requirements/PRD.md` 3.9.1 明确现行范围不含 Cookie；将来实施扩展需同步变更这份唯一 PRD。`PRODUCT.md` 的会话隔离、状态保留与效率原则继续适用；`DESIGN.md` 既有导入选择与结果反馈均为原生窗口/对话框，不新增渲染层模态或 toast。

## 2. 调研单元：Cookie

### 2.1 该部分要做什么

从用户选择的 Chrome profile 获取指定站点及相关认证域的 Cookie，保留作用域、过期时间与安全属性，导入单个目标会话。源侧可取得的会话 Cookie 也应纳入评估，不能简单按“没有过期时间”就判定不可导。

### 2.2 项目现状

- `src/shared/chromeImport.ts` 的内容闭集只有 `history`、`localStorage`，`src/main/browser/chromeImport/index.ts` 没有读取或写入 Cookie 的分支。
- `src/main/browser/registry.ts` 通过 `partitionFor` / `getPartitionDir` 管理单会话分区，`runImportQuiesced` 提供导入占用与页面收尾，可复用。
- 目标引擎具备官方 [cookies.get / set / flushStore](https://github.com/electron/electron/blob/v39.8.10/docs/api/cookies.md)；本轮临时分区实测 HttpOnly Cookie 写入成功，网页 `document.cookie` 无法读取它。因此普通网页 JS 导出 Cookie 会漏掉这一类凭据。

### 2.3 候选方案

**方案 A：直接读取 Chrome Cookies 数据库，按平台解密后写入目标分区。**

- “Mac 文件读取”指应用直接读取电脑上 Chrome profile 的 Cookies SQLite 数据库，不要求安装 Chrome 扩展，也不是另建一个 Mac 专用数据文件。
- “加密”指 Chrome 已经对磁盘中的 Cookie 值做的保护，并非本项目计划新增的业务加密。Chrome 源库如果提供有效明文 Cookie，可以直接调用 Electron `cookies.set`；如果实际值在 `encrypted_value` 中，仍须解密成原值，不能把密文作为 Cookie 值导入后当作原登录凭据。源库区分明文和密文的处理可核对 [Chromium Cookie 读取实现](https://github.com/chromium/chromium/blob/main/net/extras/sqlite/sqlite_persistent_cookie_store.cc)。
- 因此“项目不额外做加密”可与导入并存；“完全不做解密”只能覆盖源侧可用明文，无法解决已加密 Cookie 的迁移。导入将原值与属性交给 Electron Cookie API 管理，无需为此新增一套自定义加密格式，也不需要改写 Chrome 的加密设置。
- macOS：当前 Chromium 的 [Keychain provider](https://github.com/chromium/chromium/blob/main/components/os_crypt/async/browser/keychain_key_provider.mm) 和 [钥匙串命名实现](https://github.com/chromium/chromium/blob/main/components/os_crypt/common/keychain_password_mac.mm) 仍提供基于 Chrome Safe Storage 的路径。用户允许钥匙串访问、实际数据格式受支持时具有可行性；本轮没有获取真实密钥或验证用户 Cookie 解密。
- Windows：Chrome 127 起引入应用绑定加密，受保护的数据不能按旧 DPAPI 方案通用解密。应检测具体记录与加密类型；不能只按 Chrome 版本粗分，也不能把“Windows 直接离线读取受限”扩大成“Windows 完全不能导入”。[Google 官方说明](https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html)
- 直接复制加密 Cookies 文件不解决密钥差异。此方案最接近现有使用方式，但平台与格式维护成本高，读取不到的项目必须如实反馈。

**方案 B：Chrome 授权扩展通过官方 API 导出，应用接收本地导出包（用户裁决：后续再做）。**

- 扩展申请 Cookie 与对应站点权限，通过 [chrome.cookies](https://developer.chrome.com/docs/extensions/reference/api/cookies) 获取浏览器返回的 Cookie 数据，避免应用自行解开源数据库。适合 Mac/Windows 共用；可获取源浏览器当前仍持有的会话 Cookie。
- 应用主进程校验导出包，将支持的 Cookie 写入指定会话。导出包保留 profile/站点来源与属性，凭据值不写日志；文件导出导入足以作为第一版传输机制，无需先建设常驻同步或本地服务。
- 代价是需要额外安装并维护配套扩展、授权站点；用户已明确本期不支持，以下仅保留后续路线。关联登录域需要一并采集，不能只按地址栏主机过滤。

**方案 C：要求 Chrome 开启远程调试后读取。**

- Chrome 136 起，默认用户数据目录不再接受远程调试端口/管道开关，须使用非默认数据目录。不能把这一方案作为现有真实 profile 的通用导入路径。[官方变更](https://developer.chrome.com/blog/remote-debugging-port)
- 不推荐作为产品主路线；专用测试 profile 是另一个使用场景。

### 2.4 可行性分析

| 维度     | A：离线文件                              | B：授权扩展                                | C：远程调试                                |
| -------- | ---------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| 技术匹配 | Mac 有条件可行；Windows 应用绑定记录受限 | 普通 Cookie 跨平台可行；仍需目标端属性适配 | 默认 Chrome profile 不适用                 |
| 规则冲突 | 只写目标会话可满足隔离                   | 只写目标会话可满足隔离；新增显式源侧授权   | 需要改变用户启动方式，不能替代原有导入体验 |
| 成本     | 跨平台密钥访问、数据库格式和失败路径维护 | 配套扩展 + 导出包 + 主进程导入编排         | 运行态依赖强，支持成本高                   |

### 2.5 结论与实施建议

- 结论：**借鉴思路手写**。按用户裁决本期采用方案 A 的方向：明文记录直接读取，Mac 的已加密记录验证钥匙串授权与解密；Windows 按具体记录的支持情况降级，不能以跳过解密的方式承诺覆盖。方案 B 留待后续。
- 接缝：扩展 `src/shared/chromeImport.ts` 的支持能力与逐项失败结果；新增主进程 `cookieSource.ts` / `cookies.ts`，复用 `src/main/browser/chromeImport/index.ts` 编排及分区入口；同步 preload 两份桥定义与三语字典。本期不新增扩展模块或扩展导出包链路。
- 冲突选择可行：普通 Cookie 识别同一作用域的同名键，原值或受支持属性不一致时，由用户选择整条 Cookie 以 Chrome 或目标会话为准；目标没有的记录直接新增。localStorage 已实现相同的二选一方向，可复用原生冲突裁决机制。不能把“以 Chrome 为准”扩展为重置整个目标会话。
- Cookie 冲突应保留源属性，识别 host-only 与 domain Cookie；分区 Cookie（CHIPS）需额外处理。当前 [Electron 39.8.10 实现](https://github.com/electron/electron/blob/v39.8.10/shell/browser/api/electron_api_cookies.cc) 的 `cookies.set` 构造未携带 partition key，不能把 CHIPS 扁平化成普通 Cookie；需另验 CDP 等目标端路径或明确不支持。
- 先用受控 Cookie 样本验证读写、冲突、过期与隔离，再用 mail.qq.com 验证跳转和实际请求。完成反馈区分“数据导入成功”与“已确认登录可用”。涉及界面改动时走 impeccable scoped 流程。

## 3. 调研单元：IndexedDB

### 3.1 该部分要做什么

迁移站点数据库及其结构化数据；优先限定为用户选择的站点、可导出的数据类型和清晰的冲突语义，不默认对任意网站做无损数据库合并。

### 3.2 项目现状

- 当前 `siteData.ts` 只操作 localStorage 的记录格式，没有 IndexedDB 导入引擎。
- `registry.ts` 的会话克隆会复制包含 IndexedDB 的分区数据；这是同一 Electron 引擎内的整分区复制，不能据此推导 Chrome 不同版本间复制或已有库合并一定可靠。
- 当前 [Chromium IndexedDB 目录](https://chromium.googlesource.com/chromium/src/+/main/content/browser/indexed_db/instance/) 同时含 LevelDB 与 SQLite 实现。此事实不代表用户 Chrome 已使用某个后端，但足以说明不能把固定 LevelDB 文件布局当作长期接口。

### 3.3 候选方案

**方案 A：关闭 Chrome 后复制对应站点的完整存储快照。**

- 用户裁决不支持扩展后，本方案成为本期需要验证的方向，仍需兼容性实证，不能将“同为 Chromium”当作通过条件。
- 限定兼容的源/目标版本和数据布局，复制数据库及 Blob 等关联文件，写入前关闭目标页面并备份；优先用于空目标。已有库需要整体保留/替换语义，不做原始文件混合。
- [Chromium 存储说明](https://chromium.googlesource.com/chromium/src/+/main/content/browser/indexed_db/docs/README.md) 展示了数据库与外部 Blob 的关系。只复制 `.leveldb` 不足以覆盖该布局全部数据；Chrome 运行中对多文件逐一复制不能保证一致时点。
- 优点是沿用现有文件读取体验；缺点是版本兼容、storage bucket、关联文件和回滚验证工作较大。

**方案 B：源站点运行态逻辑导出，目标同源上下文逻辑导入（扩展采集路线留待后续）。**

- 通过授权扩展内容脚本访问用户选择页面的数据库，保留数据库名、版本、对象仓库、主键、索引和记录；主进程控制目标会话中的同源导入上下文。标准 API 的访问范围受 storage key 约束，不能在扩展自己的页面里直接读取所有站点。[IndexedDB 规范](https://w3c.github.io/IndexedDB/)
- 候选现成库 [dexie-export-import](https://dexie.org/docs/ExportImport/dexie-export-import) 支持非 Dexie 创建的数据库、分块处理及 Blob/Date/ArrayBuffer 等类型，但不支持 CryptoKey 导出。可减少自写序列化成本，不能据此承诺所有网站无损迁移。
- 已有数据库的 schema、版本或索引冲突需要独立策略；建议第一版只导入目标不存在的数据库，同名库明确跳过/替换，不把普通键冲突策略照搬到数据库结构冲突。

**方案 C：复用 classic-level，把源原始记录直接并入目标 IndexedDB。**

- 不采用。底层记录包含引擎内部的数据库编号、索引与外部对象引用，不是 localStorage 那种可逐键移植的简单业务键值；参考 [Chromium 编码文档](https://chromium.googlesource.com/chromium/src/+/main/content/browser/indexed_db/docs/leveldb_coding_scheme.md)。

### 3.4 可行性分析

| 维度     | A：文件快照                        | B：逻辑导出导入                             | C：原始记录合并                      |
| -------- | ---------------------------------- | ------------------------------------------- | ------------------------------------ |
| 技术匹配 | 有条件可行；要求格式兼容和完整快照 | 普通结构化数据可行；不覆盖所有凭据/对象类型 | 内部数据关联复杂，不适合作为通用合并 |
| 规则冲突 | 目标已有数据不能默默覆盖           | 可按目标会话、站点和数据库落实边界          | 难以兑现原有安全合并语义             |
| 成本     | 快照一致性与版本矩阵测试较重       | 增加页面侧库及同源采集/恢复编排             | 接近维护引擎存储实现，最高           |

### 3.5 结论与实施建议

- 结论：**借鉴思路手写**。用户排除扩展后，本期先验证方案 A 的完整快照路径，复用现有文件复制、会话静默、备份与还原机制；只有源/目标格式兼容且关联文件齐全时才执行。初轮建议的 Dexie 逻辑导出路线降为后续备选，本期不引入该依赖。
- 冲突可提供同一二选一交互，但文件快照不能直接实现任意行级合并。建议以独立的站点存储快照为裁决单位：无目标快照则新增；已有目标则选择整份保留或替换；同一底层库中的多个数据库不能靠拼文件分别合并。快照替换可能移除该单位内仅存在于目标侧的数据，提交前必须明确影响范围。这是技术粒度建议，用户已确认的是选择数据来源的能力。
- 后续备选库来源 [package.json](https://github.com/dexie/Dexie.js/blob/master/addons/dexie-export-import/package.json) 标记 Apache-2.0；本轮未安装。
- 接缝：新增主进程 IndexedDB 文件快照编排与兼容性检查，复用 `registry.ts` 分区入口、导入占用和逐类型反馈。当前 `manager.ts` 创建网页视图没有 preload；本期文件路径不为被测网站新增应用壳桥接能力。
- 验收覆盖普通/二进制数据、主键和索引、版本不兼容、同名数据库、失败回滚与双会话隔离。CryptoKey 等无法保真的项目须明确失败或跳过。

## 4. 调研单元：sessionStorage

> 用户 2026-10-28 裁决：本期不做。本节仅保留调研背景，以下候选与接缝均不进入本期实施范围。

### 4.1 该部分要做什么

把 Chrome 中某个仍打开标签页的临时字符串键值恢复到目标会话的对应标签页，而不是将同一域名的多个标签页混成一份数据。

### 4.2 项目现状

- `src/shared/sessions.ts` 的 `StoredTab` 仅保存 URL，`src/main/browser/persistence.ts` 按 URL 重建页面，没有源标签页 namespace、frame 或 sessionStorage 恢复数据。
- Chromium [DOM Storage 设计](https://chromium.googlesource.com/chromium/src/+/main/content/browser/dom_storage/README.md) 明确 sessionStorage 使用 storage key + namespace ID；Chrome 为会话恢复保存 namespace 关联，并清理不用的数据。因此旧报告“完全不落盘、无导可言”不准确。
- 本轮实测：在同一 Electron 分区、同源的两个独立 webContents 中，localStorage/IndexedDB 可共享，后建页面的 sessionStorage 为 null。这证明仅正确选择会话分区不足以恢复标签页临时状态。

### 4.3 候选方案

**方案 A：解析 Chrome 的 Session Storage 和标签页恢复文件，重建 namespace 对应关系。**

- 有研究路径，但不能只复制 Session Storage 目录。还要处理源 namespace、标签页和 frame 映射，以及目标引擎新建 namespace 的接入；现有项目没有这层恢复模型。
- 高度依赖 Chromium 内部格式与版本，不推荐作为第一版通用能力。[Chromium 生命周期说明](https://chromium.googlesource.com/chromium/src/+/main/content/browser/dom_storage/README.md)

**方案 B：授权扩展按标签页/frame 获取运行态快照，目标逐标签页恢复。**

- [Chrome scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting) 可按 tab/frame 执行；[存储说明](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies) 说明内容脚本访问的是宿主页面存储，而非扩展自有存储。扩展后台直接调用 sessionStorage 不可行，必须进入被授权页面上下文。
- 导出内容需保留源标签页标识、URL、origin/frame 与键值。目标创建对应标签页，在业务脚本读取前恢复；若在页面完成加载后才注入，可能已经发生未登录跳转，不能视为可靠恢复。
- 需要设计最早注入时机、重定向校验和失败重试；对消失且没有可恢复快照的源标签页，无法凭空重建。不能把快照变成所有新标签页默认注入的长期数据。

### 4.4 可行性分析

| 维度     | A：离线恢复文件                                            | B：按标签页运行态快照                              |
| -------- | ---------------------------------------------------------- | -------------------------------------------------- |
| 技术匹配 | 内部映射复杂；无稳定 Electron namespace 导入接口可直接复用 | 已打开且获授权的页面可采集，目标恢复需解决早期注入 |
| 规则冲突 | 不能把不同 Tab 的同源数据混合                              | 必须保持 Tab 级隔离和原本生命周期                  |
| 成本     | 内部文件解析与恢复模型扩展，最高                           | 键值本身简单，生命周期和 frame 对应成本中高        |

### 4.5 结论与实施建议

- 当前结论：按用户裁决**本期不实施**，不新增 Tab 状态导出、namespace 恢复或页面早期注入逻辑，也不扩展 `StoredTab` 持久化结构。
- 初轮技术分类为“借鉴思路手写”的方案 B，仅作为背景保留，不再形成当前待办或验收要求。

## 5. 风险与开放问题

1. **数据导入与认证通过分开验证。** 已启用设备绑定凭据的站点还需要原设备/浏览器持有密钥证明；复制 Cookie 未必能完成后续刷新。[Chrome DBSC 说明](https://developer.chrome.com/blog/dbsc-windows-announcement) 本轮没有证据表明 QQ 邮箱启用了此机制，不据此解释其具体失败。
2. **同一时点的数据。** 不论文件复制还是分别导出 Cookie/不同数据库，都不天然构成跨类型的原子快照。应控制采集期间页面写入，并在导入后验证对应站点。
3. **按已裁决范围推进。** 先验证普通 Cookie 与 QQ 邮箱所需认证域，再验证兼容版本的 IndexedDB 快照和整份冲突处置；本期不实现 Chrome 扩展与 sessionStorage。
4. **修订旧报告技术判断。** 20260930130104 报告关于 sessionStorage 不落盘、会话 Cookie 无法导入，以及 Mac“全量”支持的表述不作为本次依据；运行态可导范围和实际认证结果应分别验证。原 2026-09-30 的范围批复作为历史记录保留。
5. **本轮验证边界。** 已完成当前 Electron 的隔离分区实验和官方资料核对；没有读取真实 Chrome 密钥/凭据，没有安装扩展或 Dexie 依赖，没有验证跨版本 IndexedDB 文件复制，也没有验证 QQ 邮箱账号级完整迁移。

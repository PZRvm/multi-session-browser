## 1. Step 0：需求简报

### 背景

测试人员启动应用后，需要知道 GitHub 是否发布了新版本，并能在应用内下载，自行决定何时重启安装。公司使用场景需要能关闭更新；正式发布只产公开版，本地打包用于验证隐藏态。

### 范围与排除项

- 影响：应用启动、主窗与独立窗左上角、设置“关于”、共享更新 IPC、更新前保存、GitHub 发布附件、macOS 签名及公证接入。
- 不影响：会话 partition、Cookie/站点存储/代理隔离、WebContentsView 承载、DevTools 绑定、Tab 迁移本身的业务语义、产品名与 appId。
- 不做：公司版发布矩阵、App Store 上架、插件自动更新、预发布通道、版本降级、定时轮询、后台自动下载、静默安装、更新地址用户输入、整个设置域重构、依赖升级。
- 数据边界：应用程序包可替换，`userData` 及会话分区不清空；恢复仍为 URL、顺序、激活位等现有持久化数据，不承诺恢复未提交表单和页面内存。
- 平台：Windows x64、macOS arm64/x64 稳定版。开发态不连接真实更新源；真实安装验收使用独立测试数据和两个正式打包版本。

### 已确认的行为

| 编号 | 行为 |
| --- | --- |

| R2 | 更新来源为 GitHub Releases，复用现有 `electron-updater`；新版本才显示左上角入口，点击后在应用内下载 |

### 必须在实现中解决的风险

1. 直接 await 现有 flush 不能发现吞掉的写盘错误；失败后还可能永久停写，必须增加严格保存与恢复语义。
2. Mac 原生更新器的关窗顺序不同，不能仅靠 `before-quit` 保存；调用安装前就要完成恢复集保存。
3. 下载完成只表示更新包就绪，Mac 原生交接仍可能验签失败；在进程存活时必须恢复正常写入和入口状态。
4. 多窗口可重复触发检查、下载和确认；必须全局单飞，更新准备期间也不能继续接受改变恢复集的命令。
5. macOS arm64/x64 的 `latest-mac.yml` 不能由 artifact 合并步骤覆盖；缺一个架构不得公开 Release。
6. 既有 1.1.0 无更新入口；首个带该功能的版本需手动安装。ad-hoc 到正式签名的首跳单列实测，不作成功保证。

## 3. Phase 2：设计

### 3.1 状态与数据流

主进程是唯一事实源：构建策略 → 单例更新器 → 完整状态快照 → preload → 主窗/独立窗/关于页镜像。renderer 只发意图，不比较版本、不直接联网、不提供安装路径。

共享契约建议包含：

- `UpdatePolicy`：`showHeaderEntry`、`showSettingsEntry` 两个严格布尔值；更新能力为两项的逻辑或。
- `UpdateSnapshot`：递增 `revision`、当前应用版本、候选版本、已下载版本、能力、状态、下载进度、可重试的阶段及错误码。只传可序列化数据，不传 Error 实例、Token、磁盘路径和 HTML。
- 状态闭集：`disabled / idle / checking / up-to-date / available / downloading / ready / preparing / installing / error`。
- 进度含已传字节、总字节和百分比，未知总量时用不定进度；广播节流，状态跳转立即广播。
- 下载和就绪期间不重新 check，以免候选版本覆盖已下载版本；安装始终绑定已下载版本。启动后通过库校验缓存复用，不另建更新状态持久化文件。

`autoDownload=false`、`autoInstallOnAppQuit=false`、`allowPrerelease=false`、`allowDowngrade=false`。每次启动只安排一次检查，重开窗口只取快照。网络失败保持主应用可用，失败与“已最新”分别表示。

### 3.2 IPC、身份与并发

| 通道 | 方向与语义 |
| --- | --- |
| `updates:get-state` | 可信壳窗口读取完整快照；无参数 |
| `updates:check` | 手动检查；无 URL 参数，重复请求复用在途任务或现有忙碌快照 |
| `updates:download` | 为当前候选版本发起一次下载；不接受路径或任意版本 |
| `updates:install` | 请求主进程显示原生确认并执行安装；不接受“已经确认”布尔值 |
| `updates:changed` | 主进程向登记的可信窗口推送快照；preload 包装订阅并返回退订函数 |

全通道校验实际 `event.sender` 和顶层 `senderFrame`，须匹配主窗、当前登记独立窗或当前设置窗的 webContents；子 frame、被测网页、扩展页、建议窗、截图窗均不能调用。设置窗关闭后旧 sender 失效。每个命令还要检查策略与状态，不能以“桥没有按钮”代替授权。

单例分别管理检查、下载、安装确认/准备的在途锁；关闭发起窗等同取消未决确认。订阅先于初次拉取，镜像只接收不小于现有 revision 的状态，防旧回包覆盖新进度。失败只释放相应锁，保留有用的候选或已下载信息。

### 3.3 构建策略

新增 `build/update-policy.json` 保存公开版默认值，两项均为 true；`src/main/updatePolicy.ts` 在 main 构建期固定有效值。本地打包允许使用严格解析的 `MAIN_VITE_` 构建变量覆盖两项；非法字符串构建失败，不能用字符串真假值转换。

正式 CI 明确指定两个 true，不读本地调试覆盖；普通设置 JSON 不写这些键，恢复出厂也不能重新启用被禁用的能力。GitHub owner/repo 仅在打包 publish 配置中维护，由 builder 生成 `app-update.yml`，不另抄到 renderer。两个 false 时不创建更新器网络任务，所有执行命令返回禁用结果。

### 3.4 界面规划（impeccable shape）

沿用 [PRODUCT.md](../../PRODUCT.md) 的专业测试、效率优先和 [DESIGN.md](../../DESIGN.md) 的板面/Chrome 双套 token，模式为 Operate。已有对话已明确场景、状态和位置，本轮不新增界面问卷，不改全局设计世界。

> 2026-11-14用户调整：当前入口与版本日志以[更新入口与版本日志计划](2026-11-14-更新入口与版本日志.md)为准，下方原布局为设计历史。

- **主窗**：共用 `UpdateEntry` 挂左上角板头；Windows 排在已有左上功能区右侧。空间不足时标题优先截断，保留设置、现有功能和更新操作；不调整系统窗口控制。
- **macOS 主窗**：使用既有左上布局与三灯占位；不套用 Windows 专门排列，不覆盖三灯。
- **独立窗**：保留当前原生标题栏，在内容区顶部左侧放同一 UpdateEntry，避免把原生系统菜单当成 React 容器；与 Tab 区分组，按钮不混入 `role=tablist` 的 Tab 语义。
- **关于页**：在数据目录行下方增加更新行（2026-11-14用户调整）；提供检查、下载、重启安装及状态，当前版本始终保留。
- 顶部初始、检查中和已最新时隐藏更新入口；发现新版本显示“更新”，下载时显示进度，就绪时显示“重启安装”。失败保留可重试入口；策略隐藏或能力未加载时不渲染、不占空位。
- 确认由 `dialog.showMessageBox` 提供“稍后 / 重启安装”，稍后为默认和取消动作。进度与状态为行内反馈；启动检查失败不弹框；用户主动操作失败按现有规则使用原生信息框，不加 renderer Modal、message、notification 或系统推送通知。
- 简中/繁中/英文、键盘焦点、aria-label、亮暗主题、主窗左栏 220—420px 和独立窗最小宽度都要覆盖。HTML 全屏时随现有壳层隐藏，不挤压或收起被测页面。

本轮已运行 impeccable context 并阅读 shape；未加载仅用于实际 UI 编辑的 craft-floor，未运行 UI 或生成视觉验收证据。开工前通过局部 shape/polish 核对精确锚点，再更新本段；不把目前的结构方案记作像素验收通过。

### 3.5 更新前保存与安装交接

新增主进程内部更新准备协调器，只服务本次更新，不改现有普通退出的产品语义。禁止直接把现有 `flushPendingReports()` 当成严格保存。

1. 校验下载版本仍就绪，获取全局安装锁并向发起窗显示原生确认；取消释放锁。确认后再次校验 sender、策略、版本和录屏状态。
2. 从录屏模块提供明确的只读 busy 判定，覆盖准备、录制、暂停、收尾。若扩展录屏有独立宿主管线，也必须纳入可观察的 busy 判定；不能仅用有无录制窗口 ID 推断空闲。无法观测的扩展场景列为设计门禁，不宣称已保护。
3. 进入 `preparing`，通过主进程统一准备标记拒绝新增会话/Tab、导航、排序、跨窗转移、删除/克隆等会改变恢复集的命令，以及新录制、导入、恢复出厂等冲突操作；只读查询保持可用。已有写入先等落定，准备期间各壳显示同一忙碌状态。
4. 在 persistence/history 增加更新专用的 strict prepare/commit/resume 内部接口：记录在途写入，捕获所有存活会话的主窗+独立窗归并恢复集，等待队列，严格上抛失败。保留普通写入的既有日志容错；更新路径不得复用已经吞掉错误的 Promise。
5. 保存准备暂存 dirty/上报事件，不能先永久 sealed。成功后才提交封笔；写盘失败则恢复上报/dirty 与定时安排，释放准备标记，让应用能继续写入和重试。
6. 设置有限准备等待。超时取消安装，但不能假装已经取消底层文件写入；在途队列落定前保持准备/重试互斥，落定后恢复。不得用原有 `Promise.race(..., 1s)` 的完成直接当保存成功。
7. 明确保存成功后调用 `quitAndInstall()`；更新退出标记让普通 before-quit 不再另起冲刷和二次 `app.quit()`。库同步抛错或进程仍存活时发出异步错误，应恢复封笔与写入；进程已退出后的安装失败以真机结果判定，不显示虚假的成功消息。

封笔失败恢复、已开始写入的等待、多个窗口关闭和 Mac 原生交接是 Phase 2 必须复核的时序。需要触及 `browser/ipc.ts`、`sessions.ts` 等命令入口的改动仅限统一更新准备守卫，不顺便重构这些域。

首个提交动机必须记录 `L：共享更新 IPC、sender 权限与退出保存交接；本轮提交的范围及验证`，提交主题按中文 Clean Commit 校验。分步提交保持单一逻辑变更，不把应用开发和依赖升级混在一起。

## 5. 测试计划

不引入 Playwright 或新的项目级测试框架。关键策略/状态/发布清单可用 Node 内置测试和现有 TypeScript 工具作定向验证；界面通过项目 `dev:agent`/CDP，安装通过打包应用实测。验证工具不得只是复写实现逻辑。

| 编号 | 覆盖 | 通过标准 |
| --- | --- | --- |
| V1 | 显隐 00/01/10/11、首帧未知能力、非法配置、正式 CI 覆盖 | 00 无入口无请求无可执行命令；01/10 仅所配入口；非法构建失败，公开版双开启 |
| V2 | 启动/重开窗/新独立窗、手动检查、最新/更低/预发布、缺清单、CRX Latest | 每进程仅一次启动检查；版本结果准确；错误不装成已最新，不影响会话恢复 |
| V3 | 非可信 sender、子 frame、已销毁设置窗、伪 URL/路径、策略绕过 | 主进程拒绝，无下载、确认或安装副作用；新桥类型没有 any 漏洞 |
| V4 | 多窗并发检查/下载/安装、旧 revision 回包、窗关闭、重试 | 单任务、单确认、快照不倒退；失败可再操作，下载版本不串换 |
| V5 | 断网/超时/空间不足/哈希不符/权限不足、缓存失效 | 原应用可继续使用，不安装坏包，明确失败并可重试 |
| V6 | 准备/录制/暂停/收尾中的录屏，含宿主可观察的扩展录屏 | 重启被拒绝，录制保持正常；不可观测范围明确记录且未冒充通过 |
| V7 | 会话/历史写失败、延迟超时、已触发写、无待写 timer、失败后新导航/排序/再保存 | 严格错误可见、零安装；恢复后新操作仍写盘；不留下永久 sealed |
| V8 | 主窗/独立窗 URL 与 Tab 顺序、激活位，更新前后登录态 | 新版本启动，URL 级恢复与隔离仍正确，不清 userData/分区 |
| V9 | 稍后/Esc/关确认框、普通退出、安装交接失败 | 不退出安装；普通退出不自动安装；存活进程错误后恢复可操作状态 |
| V10 | Windows 左上功能区右侧、Mac 三灯、独立窗、关于页、三语、亮暗、220—420px 左栏、窄独立窗、HTML 全屏 | 入口可达、不遮挡功能和原生按钮、无页面露白或 Tab 角色污染 |
| V11 | Mac 两份同名清单、缺架构、错 URL/哈希、额外附件、CRX 发布 | 校验拒绝不完整产物；仅应用版本成为 Latest；所有引用都有附件 |
| V12 | Mac arm64/x64 正式签名与公证、两版升级、ad-hoc 首跳；Windows NSIS 已安装版本升级 | 签名身份有效，升级后 app.getVersion 正确；真机失败不得以静态全绿替代 |

必须运行 `npm run typecheck`、`npm run lint`、`npm run build`，以及新增的必要定向验证。Windows/Mac 某架构或证书条件缺失时记录“待测”，不把编译成功记作该平台已通过。

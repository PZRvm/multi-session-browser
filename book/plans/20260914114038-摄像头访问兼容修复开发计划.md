# 摄像头访问兼容修复开发计划

> 创建时间：2026-09-14 11:40:38（Asia/Shanghai）  
> 需求来源：`book/docs/requirements/stages/step-02-右侧浏览器基础功能.md`（完整网页渲染与原生交互）、`book/docs/requirements/stages/step-11-应用打包与发布.md`（Windows/Mac 安装与核心功能验证）；前置调研：`book/notes/learn/2026-09/20260914110740-会话网页摄像头访问.md`  
> 执行模式：直通  
> 实施范围：打通 HTTPS/localhost 被测网页对本机真实摄像头视频流的访问，补齐每会话/每站点授权、macOS 系统权限与打包能力；不实现扫码解码、麦克风、虚拟摄像头或权限管理界面  
> 目标结果：被测网页调用 `getUserMedia({ video: true, audio: false })` 时出现中文、可归属到会话和站点的授权询问；用户允许且系统权限正常后可看到实时非黑画面，不同会话互不继承站点授权；拒绝或环境不满足时给出可诊断结果  
> 当前进度：步骤 1 / 4 已完成，正在执行步骤 2

## 1. 当前基线

- `src/main/browser/manager.ts` 已用 `WebContentsView` 承载网页，创建时只注入 `registry.ts` 提供的 `persist:sess-<id>` 分区；网页未注入 Node/preload，标准 Web Media API 可直接工作，Tab 跨窗口迁移也不会改变其 Electron `Session`。
- `src/main/browser/registry.ts` 的 `ensureManager()` 是每会话懒创建浏览器实例的统一入口，但当前只把分区字符串传给 manager；全仓没有 `setPermissionRequestHandler`、`setPermissionCheckHandler` 或 `systemPreferences` 接线。摄像头黑屏不是 `WebContentsView` 不支持，而是站点授权与操作系统授权没有被完整管理。
- 本机已经识别到 MacBook Pro 摄像头和连续互通摄像头；macOS TCC 日志明确记录 `kTCCServiceCamera requires entitlement com.apple.security.device.camera but it is missing`。当前开发实例由 ZCode 启动，TCC 责任进程被归到 `dev.zcode.app`，因此该形态不能作为真实摄像头验收基准。
- `electron-builder.yml` 的 `mac.extendInfo` 被写成 YAML 数组。现有 `dist/mac-arm64/multi-session-browser.app/Contents/Info.plist` 因而出现 `0`、`1`、`2`、`3`、`length` 数字键；顶层摄像头用途说明仍是 Electron 自带英文默认值，不是项目配置。
- `build/entitlements.mac.plist` 与现有构建产物只包含 JIT、未签名可执行内存和 dyld 三项能力，主应用及 Helper 均没有 `com.apple.security.device.camera`；这与 TCC 拒绝日志相互印证。
- `src/shared/`、`src/preload/index.ts`、`src/preload/index.d.ts` 目前只承载 sessions/browser/appearance 契约。本轮采用主进程原生对话框，不增加 renderer API、共享类型或 IPC 通道。
- `package.json` 已有 `dev`、`typecheck`、`lint`、`build`、`build:unpack`、`build:mac` 脚本；仓库无自动测试框架，运行时验证必须使用 `MSB_USER_DATA` 临时目录。当前 `package.json` 的 Windows x64 脚本改动和未跟踪 `tmp/` 属用户现有工作，本计划执行时不得覆盖。
- `book/notes/summary/2026-11/legacy-process.md` 的“应用打包与发布”行仍指向已不存在的旧路径 `book/docs/requirements/stages/z-step-06-应用打包与发布.md`，而真实需求文件已是 `book/docs/requirements/stages/step-11-应用打包与发布.md`；收尾时一并校正。

## 2. 范围边界

### 2.1 本阶段必须完成

- 新增主进程摄像头权限 broker，并在每个 `persist:sess-<id>` 对应的 Electron `Session` 上幂等安装 `setPermissionRequestHandler` 与 `setPermissionCheckHandler`。
- 只处理 `permission === 'media'` 且 `mediaTypes` 明确为纯 `video` 的请求；按“会话 id + 请求 origin + video”询问和缓存，首次请求显示中文原生对话框，同会话同 origin 本次运行内复用决定。
- 请求 origin 取 `securityOrigin`/`requestingUrl` 并严格解析，只接受 HTTPS 与安全 localhost；解析失败、非安全 HTTP、未知媒体类型、音频或音视频联合请求均拒绝，禁止通过关闭 `webSecurity` 绕过网页安全模型。
- 用户允许站点后再懒检查系统摄像头权限：macOS 在 `not-determined` 时请求系统授权，`denied/restricted` 时说明系统设置路径；Windows 读取系统状态并说明“允许桌面应用访问摄像头”的设置路径。
- 修正 macOS `Info.plist` 合并结构与主应用/Helper 签名能力，确保摄像头用途说明和 camera entitlement 真正进入构建产物；不顺带声明或开放麦克风。
- 覆盖允许、拒绝、并发请求、导航/关 Tab 中断、跨会话隔离、克隆不继承、系统拒绝、非安全上下文、真实视频取流以及 macOS 打包产物检查。

### 2.2 本阶段明确不做

- 不实现二维码识别、扫码业务流程、多摄像头选择或 `facingMode/deviceId` 代选；这些仍由被测网页负责。
- 不支持麦克风、屏幕采集、通知、定位等其他站点权限；未纳入的权限默认拒绝，后续如需通用权限中心另立需求。
- 不做地址栏摄像头图标、摄像头使用中指示器、授权历史、撤销入口或持久授权；因此本轮不修改 renderer、preload、shared 和 `DESIGN.md`。
- 不支持将 `http://192.168.x.x` 等普通 HTTP 强制视为安全上下文，也不绕过跨域 iframe 所需的 `Permissions-Policy`/`allow="camera"`。
- 不做虚拟摄像头、预录视频注入、自动化扫码或 Linux 平台承诺；Windows 实机验收受当前环境限制时必须标记转人工，不能伪造通过。
- 不在本专项中擅自更换 `appId: com.electron.app`。稳定 appId/签名身份留 `step-11` 发布决策；一旦后续更换，macOS 会把它视为新应用并要求重新授权，验收记录必须注明。

### 2.3 本阶段数据原则

- 站点授权是“会话 + origin + video”级运行态，应用退出即清空；不同会话即使打开同一 origin 也要分别询问，克隆会话不复制允许记录。
- 操作系统摄像头授权属于整个应用身份，物理摄像头也属于全局硬件资源；不得把它描述为真正的 session 级系统隔离。多会话同时取流若受驱动占用限制，应如实呈现网页错误。
- 只有用户允许站点且系统层可用时才返回允许；用户拒绝、系统拒绝、请求过期或页面已销毁一律返回 `false`，每个 Electron callback 恰好完成一次。
- 同 key 并发请求合并为一次询问；会话删除时清理其运行态决定并封死在途请求，`closeSession` 的克隆临时收尾不清源会话决定，目标会话因 id 不同天然无继承。
- 摄像头真机验收全部使用 `MSB_USER_DATA` 临时目录；不得触碰真实 `sessions.json` 和真实会话分区。

## 3. 分步实施

### 步骤 1：修正 macOS 用途声明与签名能力

任务：

1. 修改 `electron-builder.yml`，把 `mac.extendInfo` 从数组改为标准键值映射；将 `NSCameraUsageDescription` 改成明确中文用途（被测网页摄像头扫码与拍摄测试），移除本轮无需求的 `NSMicrophoneUsageDescription`，保留文档/下载目录说明但确保它们也是顶层键。
2. 为 `mac` 显式指定 `entitlements` 与 `entitlementsInherit` 均使用 `build/entitlements.mac.plist`，避免主应用与 Helper 权限来源含糊。
3. 在 `build/entitlements.mac.plist` 增加 `com.apple.security.device.camera = true`，不增加 `com.apple.security.device.audio-input`。
4. 执行 macOS 目录构建，检查 `Info.plist` 顶层摄像头说明为项目中文文案且不再有数字键；检查主应用、Electron Helper 与 Electron Helper (Plugin) 的实际签名权限均含 camera entitlement。

验收：`npm run build:unpack` 成功；构建产物的 `Info.plist` 不存在 `0/1/2/3/length` 异常键，顶层 `NSCameraUsageDescription` 为项目中文文案；主应用及承担媒体请求的 Helper 签名权限均出现 `com.apple.security.device.camera = true`，且任何产物都没有 audio-input entitlement。

### 步骤 2：实现会话级摄像头权限 broker

任务：

1. 新增 `src/main/browser/permissions.ts`，提供 registry 生命周期内唯一的摄像头权限 broker：按 session 幂等安装两个 permission handler，维护运行期 allow/deny 决定、同 key 在途 Promise 与 session 失效代次。
2. 在 check handler 中只对已缓存允许的“安全 origin + video”返回 `true`，未知/拒绝返回 `false` 以进入 request/拒绝路径；request handler 对缓存命中直接完成，对未知请求只发起一次中文原生询问，未支持权限一律拒绝。
3. 中文询问至少展示当前会话名（读取失败回退会话 id）、请求 origin 和“仅摄像头、不含麦克风”；优先绑定发起页面所在主窗口/独立窗口，后台页面无法定位宿主时使用应用级对话框，不因定位失败自动允许。
4. 用户点击允许后执行平台权限分支：macOS 用 `getMediaAccessStatus('camera')`/`askForMediaAccess('camera')` 懒申请；Windows 只检查状态并在拒绝时显示系统设置说明；其他平台不调用这两个限定 API。
5. 对话框等待期间监听 webContents 销毁/主框架导航并在返回前复核 origin；会话删除时 broker 先切为拒绝态、清缓存并让所有在途回调安全落到 `false`，不得因 handler 被清空短暂恢复 Electron 默认自动批准。
6. 修改 `src/main/browser/registry.ts`：在 `ensureManager()` 中对 `session.fromPartition(partitionFor(id))` 安装 broker 后再创建 manager；`destroySession()` 接入失效清理，`closeSession()` 不清源会话运行期决定，保证克隆窗口期语义稳定。
7. 同步 `book/docs/architecture/项目骨架.md`：增加 `src/main/browser/permissions.ts` 文件与职责，补充 registry 的权限接线职责；核对 src 文件树和文件级表格一致。

验收：`npm run typecheck` 与 `npm run lint` 均为 0 错误；设置 `MSB_USER_DATA=<临时目录>` 后运行 `npm run dev`，HTTPS/localhost 纯视频请求出现一次中文询问，拒绝、音视频联合、普通 HTTP、未知权限均不放行；同会话同 origin 并发只弹一次，不同会话分别弹窗，克隆目标不继承，关 Tab/删会话期间无悬空回调或未处理 Promise。

### 步骤 3：完成真机取流与跨平台验收

任务：

1. macOS 真机验收使用步骤 1 的构建产物，通过 LaunchServices 启动并注入独立 `MSB_USER_DATA`；不把当前 ZCode 内启动的 `npm run dev` 结果当成硬件结论，避免 TCC 责任进程仍归属 `dev.zcode.app`。
2. 用 HTTPS/localhost WebRTC 摄像头页验证：允许后 `<video>` 获得非黑实时画面，`videoWidth/videoHeight > 0`、video track 为 `live`；再用真实扫码项目确认二维码识别成功，区分“取流成功”和“被测项目解码成功”。
3. 验证授权矩阵：首次允许/拒绝、同会话复用、不同会话隔离、重启后重新询问、克隆不继承、页面导航/关 Tab 时取消、后台 Tab 行为、两个会话同时取流以及系统拒绝后的中文诊断。
4. 验证网页前置条件：非 localhost HTTP 在进入应用 handler 前失败且不弹误导授权；跨域 iframe 缺少 `Permissions-Policy` 或 `allow="camera"` 时按网页安全模型失败，记录为被测页配置问题。
5. Windows 实机检查“摄像头访问”和“允许桌面应用访问摄像头”两级开关、允许/拒绝路径与真实画面；当前无 Windows 环境时保留明确人工项，不用 macOS 结果代替。

验收：`npm run build:unpack` 产物以自身应用身份启动后，macOS 系统设置能识别该应用并完成首次授权，WebRTC 页取到尺寸非零的实时画面且真实扫码成功；上述授权与安全上下文矩阵逐项有通过/预期拒绝证据，Windows 环境受限项被明确列为人工而非标为通过。

### 2.2 本阶段明确不做

不修改 `src/`、应用根 package.json/package-lock.json、正式 preload 或生产 Session 权限；不把验证程序装配进 `src/main/index.ts`。不实现完整插件管理界面、自动更新、全局安装事务产品化、完整编辑器迁移或完整录屏控制台，它们属于后续并行阶段。

按用户2026-11-10授权，Electron已锁定42.11.7，并独立维护React SVG修复版；原始商店包与原版解包样本仍不修改，不降低minimum_chrome_version，不伪造更高浏览器版本绕过约束。不为让测试通过关闭 sandbox、给被测网页加 Node 权限或普遍批准媒体请求。不引入 Playwright、生产服务端或新的通用测试框架；脚本断言和受控手动测试即可。

只允许在工具工程加入完成验证所需的小型适配。若必须补成整套浏览器 API 或大幅改候选库，记录缺口并暂停该选型，不能把前置阶段扩大成完整兼容层开发。

本阶段的三款主要功能验证不替代最终产品矩阵；完整编辑器所有工具、长时间压力与正式 UI 打包回归在后续验收中完成。前置阶段仍必须得到核心能力的真实结果，不能只做接口模拟。

### 2.3 本阶段数据原则

- 每次运行记录 runId、Git 基线、OS/架构、Electron/Chromium/Node/Chrome 版本、依赖版本、插件版本/ID、来源和哈希。原始日志、截图、媒体和自动断言结果关联同一 runId。
- 测试工具建议新增在 `tools/extension-preflight/`，包含独立 package.json/package-lock.json、启动器、Electron main/preload、局部测试站点和检查脚本；生产依赖与构建入口保持不变。工具里的检查命令必须实际实现并写入 README，不假称根 typecheck 已覆盖工具。
- 下载包、测试 profile、生成图像/视频和日志写在工具专属 `.artifacts/` 或本次 OS 临时目录；添加精确的忽略项，禁止把扩展包、node_modules 和 profile 提交入库。book 保存清单、步骤、结果及证据位置，证据目录应可交付且不只指向易失临时文件。
- 测试站点使用进程实际分配的 localhost 端口，两个分区访问同一 origin、同名虚构 Cookie 不同值，才能证明隔离。不得仅用不同域名证明“会话不串号”。
- macOS 和 Windows 单独记结果；环境不可用即“未执行/阻塞”，不把一个平台的结果推定给另一个平台。下载/人工安装受网络影响时区分环境阻塞与插件能力失败。
- 成功、失败、取消、超时、未执行分开记录；模拟返回不能计为真实插件或音视频成功。所有状态变化与清理结果都能反查证据。

### 2.4 契约核对与冻结范围

本阶段先在独立工具内验证候选协议，最后形成供后续开发使用的 v1 契约；不提前修改生产 src/shared 和 preload。

| 契约 | 需要确定的内容 | 本阶段验证 |
| --- | --- | --- |
| 安装与全局清单 | ID、版本、来源、已安装/分区加载结果、重复安装/升级/卸载、旧版保留和失败信息；全局事实由谁写入 | 模拟事务结果与真实下载/解包结果一致，不能以单分区成功代表全部完成 |
| 动作目标与权限 | 宿主创建的窗口/会话/Tab/扩展身份上下文或不可伪造令牌、请求编号、目标失效、授权范围 | 实际 IPC 校验 sender/frame/session，伪造目标、普通网页、未知扩展、关闭目标被拒绝 |
| 截图与编辑 | 图像载荷与像素尺寸、快照/版本、复制/下载结果、多个编辑目标 | PNG 往返与两个独立快照的模拟编辑结果不串；过期版本明确失败 |
| 录屏与音频 | start/pause/resume/stop/status、音频选项、就绪/收尾、状态订阅与取消订阅、一次只录一个视频 | 真实媒体结果配合状态机检查；busy、启动中停止、目标关闭和重复结束均有确定结果 |

所有接口共同规定：协议版本、能力握手、输入校验、错误码和载荷、超时、幂等、取消及晚到结果规则。业务错误码与三语展示分开；不向插件暴露任意文件路径读写或应用完整 window.api。未来生产 preload 类型和字典迁移清单一并列出。

接口文档落入 `book/docs/api/`；影响持久化所有权、特权桥等架构边界的决定，在实施阶段按 ADR 规则留档。冻结前只称“草案”，真实探测完成后才锁定；变更必须同步 mock、检查和下游使用说明。

## 3. 分步实施

### 步骤 1：建立隔离验证工程，固定样本与环境基线

1. 从最新 dev 创建功能分支，核对工作区；记录 Step 0、影响清单和工具设计完成情况后再编码。新增独立验证工程及实际可运行的启动/检查入口，锁定依赖来源与版本。候选 `electron-chrome-extensions`、`electron-chrome-web-store` 分别核查公开 API、preload 分发和 Electron 39 支持；不只按 README 宣传锁定。
2. 设置单独 userData，创建两个持久分区、两个 WebContentsView、主/独立测试窗口和 localhost 测试站点。测试页包含会话标识、可编辑表单、可辨色块/图案、React 组件和独立音频标记；验证错误进程、普通网页没有应用特权。
3. 固定以下三款插件的原版下载包、manifest、来源、版本、哈希和主要操作；以能在实际宿主版本合法运行的原版包为基线，不能悄悄换插件或改包。商店展示版本是本次计划核对结果，执行时重新确认并冻结实际下载版本。

5. 新增工具文件/职责时，同步 [项目骨架](../docs/architecture/项目骨架.md) 的相关目录说明，只修本阶段涉及结构，不趁机重写整份 legacy 文档。工具 README 写明依赖安装、启动、检查、清理命令及权限条件，并实际复跑；新脚本不能只有文档没有实现。

验收：工具按 README 在独立目录可重新安装和启动，生成环境/样本清单，两个同 origin 分区的虚构 Cookie 和页面输入不同且不互串；三款插件在普通 Chrome 的主要操作均有基准证据。CRX2/3 正向样本来源与包头可查，历史样本明确标为负向；依赖可复现，`npm run typecheck`、`npm run lint` 通过。任何版本不兼容、正向样本不足或平台资源缺失均记录，不伪称已完成本步骤。

### 步骤 2：实测第三方插件、两种包格式和商店安装

1. 在同一个隔离工程中，对照原生 Electron 基线和候选兼容层，实际注册 WebContentsView 与窗口/激活关系，打开 action/popup 和会话专属 DevTools；执行三款固定插件的主要操作，留下正常与失败日志。必要测试控制优先用原生菜单和候选库既有入口；若新增可见控制页，先走 impeccable 的 scoped 流程，不设计正式产品 UI。
2. 对两个分区、主/独立测试窗口、新增分区、同 Tab 导航、重启重载和卸载做最小代表性验证；三插件同时启用后复跑主要操作。Cookie-Editor 必须在同一 origin 上证明只修改来源分区。Dark Reader 的样本站点变化是用户使用插件产生的行为，不等于应用强制全站反色。
3. 分别解析并密码学验证 CRX2/CRX3，核对扩展 ID、公钥、包体和 manifest，安装合法正向样本；覆盖截断包、损坏签名、ID 不符、目录逃逸和过旧 manifest。CRX2/3 正确 ZIP 偏移分别计算；拒绝错误包不留下已安装状态或被覆盖的旧包。
4. 在隔离工具的受控商店页面实际点击商品页安装，完成下载、验包、确认与加载；精确限制商店 origin/sender/session。再测试本地 CRX 安装同一 ID 的去重和失败保留旧包。安装桥应拒绝其他网页与伪装来源；不能用“粘贴 ID 下载成功”代替商品页安装实证。
5. 形成依赖选择记录：确切版本/锁文件、Electron 39 适配、preload 路径、必要补丁、许可证及已知缺口。外部库仅解析 ID 而不验签的路径不能算通过；最低版本不符时先明确阻塞和备选，不自动升级应用。记录本阶段兼容适配的有限范围，避免把实验扩大成生产完整实现。

验收：三款原版插件在普通 Chrome 对照和 Electron 验证宿主内主要操作一致，action/popup/DevTools 可操作；两个分区不串 Cookie，新增分区与重启后仍可用。真实商店商品页安装与合法 CRX2/3 正向安装有完整记录，负向包与错误来源明确拒绝且无已安装残留。核心机制在 macOS、Windows 均有结果；脚本检查非零退出表示失败，不能靠日志中出现“loaded”判通过。尚不能完成的关键能力进入阻塞清单，禁止发布并行准入结论。

### 步骤 3：验证截图、编辑适配及带当前 Tab 音频的 MP4

1. 对同一测试图案，在普通 Chrome 最小 MV3 工具扩展中调用真实 captureVisibleTab，在隔离 Electron 中调用目标 webContents.capturePage。生成 PNG，检查尺寸非零、像素/DPR 与图案一致，且不含应用壳、DevTools 或另一分区画面。覆盖目标关闭、切换目标和过期结果，不截取结果返回时碰巧激活的新 Tab。
2. 在普通 Chrome 扩展页验证图片复制和 PNG 下载的真实条件；在 Electron 受控页验证专用桥请求/响应。用已有编辑器的图像输入/输出形态做最小适配：至少完成一次矩形标注、一次裁剪和两个快照交错返回的检查。仅复制出的原生编辑器窗口能用，不能证明普通 Chrome 可移植；本步骤不要求迁完全部工具，但需列出逐项迁移依赖和障碍，不删减后续完整工具范围。
3. 普通 Chrome 使用 tabCapture + offscreen + MediaRecorder；Electron 以同分区可信采集器获取目标 WebFrameMain 的视频和音频并保留本地播放。分别生成带声音 MP4，检测真实 MIME/codec 和音轨，不用纯视频 MIME 支持结果代替音频编码成功。记录未知扩展、普通网页、其他 Session 请求被拒绝的证据。
4. 测试页输出可辨识计时画面、节拍和目标音频，同时让另一个 Tab 播放不同音频。验证成品只有目标 Tab 声音、用户仍能听到目标播放、音画偏差不超过 250ms。包含总计约 12 秒、暂停 3 秒的测试，成片有效时长约 9 秒（容差 1 秒），暂停段不进入音画；再做同 Tab 导航、目标关闭、启动中停止与控制面板开关。
5. 两端各完成一次不少于 60 秒的带声音录制并在独立播放器打开；记录音画、尾块与结束清理。macOS/Windows 分别记录能否捕获目标音轨、MP4 音频编码与播放结果。编码不支持、只有静音轨或录入其他 Tab 声音时如实失败，不转成无声文件或系统混音伪通过。

验收：证据中有两端真实 PNG、图片复制/下载结果、最小编辑成品与交错快照检查；有可在独立播放器播放的带目标 Tab 声音 MP4、暂停时长/音画偏差和其他 Tab 声音排除证据。用户无须相信 console 的“录制成功”判断结果；页面仍可操作，目标失效和未授权请求按预期失败，媒体轨道、订阅和临时窗口被释放。上述关键能力未通过或平台未测不得进入最终冻结；全部编辑工具的产品验收仍留在后续阶段。

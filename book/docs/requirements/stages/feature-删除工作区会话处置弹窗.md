# 删除工作区会话处置弹窗专项

需求（2026-09-24 用户提出，用户口径「分组/对话」即产品术语「工作区/会话」）：删除一个工作区时，弹窗询问用户是否同时删除该工作区下的所有会话；选择不删除，则会话移入「未分组」。

现状：删除工作区固定走「必留会话」口径（PRD 4.8：其中会话全部移入未分组，会话数据不受影响），确认框只有「删除 / 取消」两键（`dialog:confirm-destructive` 的 workspace-delete kind）。用户想在删除工作区的同时清掉其下会话，只能先删工作区、再到未分组逐个删除残留会话，效率缺口明确。

- 交互定稿（右键工作区行「删除工作区」，入口唯一）：
  - 工作区含会话（n>0）：主进程原生对话框三键——「删除全部会话」（该工作区全部会话连同分区数据彻底删除，不可恢复）/「保留会话」（会话全部移入「未分组」，即原必留会话口径）/「取消」（零副作用）；「取消」为 cancelId 兼安全默认（Enter/Esc=取消，沿用用户裁决 2026-09-18 防误触不可逆删除）
  - 空工作区（n=0）：维持既有两键确认（删除 / 取消），交互零变化
- 弹框形态：仍在 dialog 域 `showMessageBox` 家族（PRD 4.10 扩三键选择形态，非 4.11 模态子窗口——无输入/选择列表诉求，原生对话框即可承载）；三键的屏幕视觉次序存在平台差异，语义以 defaultId/cancelId 为准绳（既有惯例）；弹框期间页面视图保持可见（不经 overlay 悬挂登记），主窗口输入被窗口模态阻塞
- 执行链路（确认与执行两段解耦，零新增执行通道）：「删除全部会话」→ renderer 于执行时从 store 现取该工作区会话 id 集 → 既有 sessions:delete-batch（整单拒绝制，分区销毁 / activeId 级联 / 悬空记忆清理 / 快照推送全复用）成功后再走既有 workspaces:delete；delete-batch 失败则中止（工作区不删）并按失败反馈惯例行内提示，可从入口再次发起。「保留会话」→ 既有 workspaces:delete（降级未分组，主进程语义零变化）
- 契约方向（通道与校验在开发计划定稿）：dialog 域新增一条 invoke 通道，载荷只带 name/count，返回三态结论（delete-all / keep-sessions / cancel）；旧 confirmDestructive 的 workspace-delete kind 退役（消费面唯一是 WorkspaceSwitcher，随迁新通道收窄白名单）
- 文案：新增键三语并行落字典（zh-CN 为源语言与类型来源，en-US / zh-TW 并行受类型完备性约束），主进程经 main/i18n 语言态取词、随界面语言；明暗随应用主题（既有 showMessageBox 链路）
- 范围外：删除会话、批量关闭选中两处确认不动（session-delete / sessions-batch-close 零变化）；workspaces:delete 主进程「降级未分组」语义保留（「保留会话」路径原样）；不做「不再询问」checkbox、自绘子窗口、按钮主题色注入（PRD 4.10 既有裁决）；独立窗口无工作区入口不涉及；批量模式不涉及

## 验收

- 删除含 n>0 会话的工作区弹原生框：标题「删除工作区」、正文含工作区名与会话数、三键「删除全部会话 / 保留会话 / 取消」，「取消」为默认（Enter/Esc=取消）；弹框期间右侧浏览器页面内容全程可见、不变白、不重载
- 「删除全部会话」：该工作区全部会话连同分区数据删除（重启后会话不复活）、工作区删除、视野与激活级联正常；「保留会话」：会话全部移入「未分组」、会话数据与登录态不受影响（与原口径一致）；「取消」/Esc/关框零变化
- 删除会话执行失败（delete-batch 整单拒绝）时工作区不删、有行内失败反馈、可从入口再次发起，不出现部分执行
- 空工作区维持两键删除确认；文案随界面语言（zh/en/zh-TW）；macOS 亮暗主题下弹框与应用主题一致

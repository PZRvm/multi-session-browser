# 地址栏下拉融合、新会话空输入与 Chrome 登录态导入

> 记录时间：2026-10-28（Asia/Shanghai）
> 来源：用户本轮反馈与 Chrome 地址栏参考截图
> 状态：开发计划七步已全部执行完毕（2026-10-28，波次 A-E；分支 feature/omnibox-chrome-site-import）：地址栏融合与输入隔离、四类型导入（含 Mac 授权解密与 IndexedDB 版本门禁）已交付并通过各波检查点；QQ 邮箱真实样本与钥匙串真实密钥正例为用户侧待操作项（见验收目录）；步骤 7 审查轮与验收文档随收尾落定。
> 开发计划：[地址栏交互与 Chrome 站点数据导入](../../../plans/20261028112040-地址栏交互与Chrome站点数据导入开发计划.md)

## 1. 地址栏与历史建议下拉框融合

- 历史建议展开时，输入框左下角、右下角取消圆角，下拉框紧贴输入框下沿，左右边缘对齐，整体呈现连续的一个面板。
- 接缝处不出现空隙、重复边框、独立圆角或分离的阴影；整体顶部保留输入框圆角，底部圆角由下拉框承担。
- 建议下拉框关闭后，输入框恢复四角圆角；空查询、无匹配、Esc 关闭、失焦等收起路径保持一致。
- 主窗口与独立窗口、亮暗主题采用同一交互；窗口移动、缩放与尺寸变化后仍保持贴合。
- 沿用现有原生建议子窗口机制，页面保持可见；保留鼠标选择、方向键、Enter、Esc 和中文输入法行为。

验收：输入有历史匹配的文字，确认输入框与下拉框无缝连接；逐条验证收起路径恢复圆角，并在主窗口、独立窗口与亮暗主题下复核。

实施入口：`src/renderer/src/components/browser/Toolbar.tsx`、`useOmniboxSuggestWindow.ts`、`src/main/browser/omniboxSuggest.ts`、`src/renderer/src/assets/app.css`。涉及视觉调整，实施前按仓库要求使用 impeccable 的 scoped 流程。

## 2. 新建会话时地址栏输入框为空

- 新建会话进入后，地址栏初始为空，不残留上一个会话的网址、搜索词、未提交草稿或其他输入文本。
- 新会话不沿用旧会话的历史建议、选中项、编辑状态或待导航文本；后续正常导航时，地址栏仍按当前会话的页面状态更新。
- 保留会话历史隔离：修复不能通过清除旧会话历史或其他会话数据实现。
- 实施时重点核对工具栏组件复用期间的本地 `draft`、`pending`、建议选择状态，以及新会话快照和历史镜像的更新时序。
- 契约核对：PRD 3.8.2 当前规定自定义主页用于新会话首个 Tab。实施时需明确“初始空输入”与主页加载后 URL 展示的时序，不通过删除或改写用户主页设置实现清空。

验收：在已有会话输入未提交文字后新建会话，再从已导航页面新建会话，确认两种情况下新会话均不残留旧输入；新会话输入匹配词不出现旧会话历史，切回旧会话后其页面与历史数据仍在。另核对已配置自定义主页的场景。

实施入口：`src/renderer/src/components/browser/Toolbar.tsx`、`src/renderer/src/stores/browser.ts` 与主进程新建会话、激活快照链路。

## 3. Chrome 导入后部分网站登录态缺失

- 用户反馈：从 Chrome 导入数据后，很多网站仍需登录；已提供站点样本 `mail.qq.com`。
- 已确认的能力缺口：当前只导入浏览历史与 localStorage，没有导入 Cookie、IndexedDB、sessionStorage；“导入完成”不表示已验证站点登录可用。当前 PRD 3.9.1 明确排除 Cookie，这是待扩展的现行范围，实施前需同步唯一 PRD。
- 目标：评估并补齐实际站点所需的登录凭据和站点数据迁移，只写用户选择的目标会话，保持会话隔离。
- Chrome 扩展：用户已明确本期不支持，留待后续；本期沿用应用直接读取本机 Chrome 文件的方向。
- Cookie：普通 Cookie 导入可行，包括 HttpOnly。有效明文源可直接导入；Chrome 已加密的源值需先解密，Mac 验证钥匙串授权与格式，Windows 应用绑定加密记录按支持情况明确反馈。“不新增加密功能”不等于能够跳过源数据解密；本轮不改写 Chrome 加密设置。分区 Cookie 与设备绑定认证单独识别，不承诺全部站点免登录。
- 冲突：用户可选「以 Chrome 为准 / 以当前会话为准」。“当前会话”指本应用目标会话现有数据，“Chrome”指选中的源 profile 数据；localStorage 现已实现对应二选一，Cookie 新增/冲突按记录处理。IndexedDB 文件路径建议按站点完整快照选择保留或替换，不按原始数据库记录拼接；整体替换的影响范围需在提交前说明，粒度在技术验证中定稿。
- IndexedDB：本期不依赖扩展，先验证源/目标格式兼容的完整文件快照，包含 Blob 等关联文件；源 Chrome 完整退出、目标会话静默、备份与失败还原为执行前提。不能将“同为 Chromium”视为兼容性已经验证。
- sessionStorage：用户已明确本期不做，不新增标签页快照、namespace 映射或早期注入；原调研仅保留背景。
- 推荐顺序：先用 Cookie 验证 QQ 邮箱等样本，再验证 IndexedDB 文件快照与冲突策略。

验收方向：使用用户选择的 Chrome profile 和登录站点，分别核对导入范围、关键 Cookie/存储属性、目标请求实际携带凭据与最终登录结果；失败或不支持的类型明确反馈；原有历史与 localStorage 导入、目标原数据回滚及其他会话隔离均需回归。本轮尚未对 QQ 邮箱账号级完整迁移作实测。

详细可行性、候选方案、官方来源、本机实验结果及本轮裁决见 [Chrome 登录态与站点存储导入可行性](../../../notes/learn/2026-10/20261028105514-Chrome登录态与站点存储导入可行性.md)。本条记录当前范围，不将已排除的候选能力转成实施任务。

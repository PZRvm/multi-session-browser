# 截图编辑多窗口修复开发计划

> 创建时间：2026-11-03 23:13:11（Asia/Shanghai）

> 执行模式：直通  
> 实施范围：截图编辑窗口由全局单例改为按截图复用的多窗口，补齐窗口绑定图片、产出与清理链路  
> 目标结果：截图 A 已开编辑窗后，截图 B 点击编辑新开 B 窗；A 的编辑状态保留，两窗各自复制、下载、续编

## 1. 当前基线

- `src/main/browser/captureEditorWindow.ts`：控制器仅持有一个 `win`。`open()` 发现旧窗未销毁即 `focus()` 并返回，不区分截图；因此第二次截图点编辑必定回到旧编辑窗。这是本次问题的直接原因。
- `src/main/browser/capture.ts`：`lastCapture` 是全应用最近截图单槽，包含 `captureId/png/sessionName`；每次截图整体替换。反馈条 `feedbackAction` 的 edit 分支和宿主 `openEditor` handler 都调用同一控制器，尺寸从当前单槽计算。
- `src/renderer/src/components/browser/captureEditor/EditorWindow.tsx`：挂载时只调用一次 `getEditImage()`，没有新截图订阅。标注、撤销栈、裁剪与工具状态保存在该窗口 React 实例内；单纯 focus 不会更新底图。
- `capture.ts` 的 `getEditImage` 读取当前单槽，编辑专属 IPC 白名单通过 `getEditorWindow()` 只承认一个窗口。即使只把建窗改为每次 new，也会产生旧窗被拒、开窗后取错最新图的问题。
- `editCopyCapture` / `editDownloadCapture` 以单槽 `captureId` 校验并回写新 ID；新截图会使旧窗导出报过期。下载的 await 完成后直接回写单槽，还可能覆盖等待期间的新截图。多窗口实现必须收拢这条数据链。
- `EditorWindow.tsx` 产出后通过 `refreshSlotAfterApply()` 重读全局单槽、重建编辑基准；仅以尺寸判断是否切图，同尺寸不同截图无法识别。多窗口下应只重读本窗成品。
- `src/shared/capture.ts` 已有 openEditor/getEditImage/editCopy/editDownload 四个通道；`src/preload/index.ts` 和 `index.d.ts` 已暴露对应 API。现有返回形状足以保留，需改变的是数据归属和注释契约。
- `src/main/index.ts` 在主窗 closed 和退出路径调用控制器 `dispose()`；目前只关闭单窗，多窗口后应关闭全部编辑窗并释放快照。
- `docs/PRD.md` 3.10.1 / 验收 39、`DESIGN.md`「截图编辑器」、`docs/项目骨架.md` 明确记录全局单例及单槽过期规则。本次用户要求改变旧行为，实施时必须同步这些契约。历史计划保留原状。
- `notes/steps/feature-快速截图与快速录屏.md` 是专项来源，尚未描述本次多窗规则；其中另有快捷键、WebM 等旧描述，本计划仅补本次截图编辑变更，不扩展整理历史漂移。
- 项目使用 Electron 39、React 19、react-konva 19.2；不需要新依赖。仓库无测试框架，验证使用 typecheck、lint、build 与 dev 手动验收。

## 2. 范围边界

### 2.1 本阶段必须完成

- 不同截图分别打开独立编辑窗；同一截图重复点击编辑聚焦原窗（最小化时先还原），不重置标注与撤销栈。
- **方案建议与推导边界**：用户明确要求第二张图新开编辑页；本计划同时建议让旧窗继续可用，避免仅新开窗口后旧窗立即报过期。此项属于配套行为调整，实施前随计划一并确认。
- 每个编辑窗固定绑定开窗时的 PNG 与会话命名源，新截图不替换其底图；各窗复制、下载、裁剪与产出后续编互不串图。
- 单窗关闭只释放自己的条目；主窗关闭和应用退出清理全部编辑窗；关闭后重新编辑当前截图可正常重建。
- 保留图像自适应尺寸、原像素导出、macOS 原生红绿灯与 Windows/Linux 系统框；保持既有工具与 inline 反馈。
- 同步 PRD、专项 steps、DESIGN、项目骨架；实施收尾更新 process 与手动验收文档。

### 2.2 本阶段明确不做

- 截图历史库、截图列表、后台历史保留、编辑草稿持久化与重启恢复。
- 每次点击同一张图都创建副本窗口；本次按“不同截图”区分窗口。
- 编辑器布局、配色、工具能力和窗体样式改造；不新增模态框、toast 或窗口管理入口。
- 修改录屏、会话分区、Tab 与 DevTools 行为；不引入新依赖或测试框架。
- 将反馈条改为每宿主独立截图仓库：本次两个开窗入口仍在主进程受理时解析当前最近截图，解析一次后立即固定快照。跨宿主旧反馈条归属另案处理。

### 2.3 本阶段数据原则

- 最近截图单槽继续服务反馈条下载；编辑窗持有自己的内存快照。只为实际打开的编辑窗保留额外快照，关闭释放，禁止无限累计截图历史。
- 区分两个身份：`sourceCaptureId` 为原始截图稳定身份（截图时生成，编辑产出不改变，用于窗口去重）；`captureId` 为当前 PNG 版本（每次成功产出更新，用于本窗版本校验）。最近槽和编辑条目都携带稳定身份，避免复制后 ID 改变又开出同一张图的第二个窗口。
- 打开时同步取得同一份槽对象，窗口去重键、PNG、尺寸和会话命名源都由这份快照派生；禁止创建窗口时读一次、挂载取图时再读全局单槽。
- 编辑输出先校验 sender 所属条目及其版本；A 窗携带 B 的 ID 必须拒绝。PNG 前缀、长度、非空及尺寸守卫全部保留。不能只因 sender 是任意编辑窗就允许读写所有条目。
- 保留“当前最近图的编辑成品回写最近槽”的兼容行为，但必须条件回写：仅最近槽仍等于本次输出前的截图身份与版本时更新；下载 await 后再次校验。旧窗输出可成功写剪贴板或文件，但不得覆盖新截图缓存。
- 下载复用现有 `serializeSave` / `writePngToDownloads`，同名不覆盖；会话命名源固定为该图拍摄时的值。队列开始执行时重新确认窗口条目仍存活且版本匹配；写盘中关窗不重建条目，已受理文件操作正常完成。
- 写剪贴板/下载失败不推进本窗版本、不修改最近槽；成功后刷新只读取本窗成品，不切换到其他截图。窗口关闭、加载失败或 renderer 崩溃后摘除索引和快照；允许 GC 回收数据。

### 2.4 契约核对

1. **需求文档先行**：PRD 3.10.1 与验收 39 中“单例 / 编辑期新截图导致旧窗过期 / 产出后切最新图”改为“每原始截图一窗 / 独立快照与版本 / 本窗成品续编”；专项 steps 增记本次用户反馈及配套方案。DESIGN 修改截图编辑器生命周期和并发语义，现有视觉规则保留。
2. **控制器内部接口**：`open()` 改为接收必需的截图快照（含稳定身份、版本、PNG、会话命名源与尺寸或可派生尺寸）；用按稳定身份索引的窗口条目替代 `win`。提供按 `WebContents` 解析条目的方法，替代单窗 `getEditorWindow()`；dispose 遍历全部条目。窗口及其快照生命周期由控制器统一管理，避免两处 Map 清理不同步。
3. **IPC 外形保持**：保留现有通道及 preload 方法签名，`getEditImage()` 按可信 sender 返回本窗快照；`CaptureEditImagePayload.captureId` / `CaptureEditApplyPayload.captureId` 改为本窗版本语义。稳定身份留在主进程内部，不让 renderer 通过自报 ID 选择其他窗口数据。更新 shared 与 preload 两文件的相关注释并核对类型。
4. **取图与续编**：两个开窗入口共用同一快照解析方法。无截图时拒绝打开、沿现有 IPC 错误链处理，不创建无绑定空窗；不新增反馈器件。产出成功后 `getEditImage()` 返回本窗刚提交的成品，保留现有烘焙标注后重置历史的行为，删除按尺寸猜测“切换最新截图”的分支；`slotSwitched` 如无剩余引用，三语字典同步删除。
5. **安全与清理**：编辑专属 handler 按 sender 找唯一存活条目；版本校验与更新围绕同条目执行。主窗关闭/退出 dispose 的装配点保留并升级为全量清理。职责从单窗升级为窗口池，必须同步 `docs/项目骨架.md` 的树与文件级职责。

完成标志：PRD 与 DESIGN 中本次冲突有明确修订；主进程身份、版本、sender 归属及条件回写规则有唯一实现；不新增 IPC 通道或 renderer 侧任意截图读取入口。

## 3. 分步实施

### 步骤 1：冻结契约并实现按截图绑定的编辑窗口池

任务：

1. 先按 2.4 更新 PRD、专项 steps、DESIGN，仅修改本次行为契约。
2. `capture.ts` 的截图槽引入稳定身份，每次新截图创建新身份；两个编辑入口同步解析并传递同一份完整快照。清除仅传图片尺寸、随后再读全局单槽的路径。
3. `captureEditorWindow.ts` 用窗口条目池替代单引用：按稳定身份去重、按 sender 反查；首次打开注册条目后加载页面，同图 restore/focus，异图建窗并分别计算尺寸。保留现有主题、语言和窗体参数。
4. 将 get-edit-image 与 sender 校验接到条目池；普通 shell、反馈条以及其他编辑窗不可越权读取。空槽不建窗，错误走既有链路。
5. 补齐 closed、页面加载失败、renderer 崩溃和 dispose 的条目清理；更新 index.ts 单例旧注释，并同步项目骨架的控制器与截图域职责。

验收：`npm run typecheck`、`npm run lint` 通过。`npm run dev`：A 截图开编辑并画矩形，B 截图点编辑出现第二个窗口且显示 B；A 窗矩形保留；连续两张同尺寸、内容不同的图仍分别正确。B 重复点编辑窗口数不增加，最小化 B 后点编辑能还原；快速重复触发在 ready-to-show 前也只能生成一个 B 窗。主窗与独立浏览器窗发起截图均适用。骨架文档与实际职责一致。

### 步骤 2：产出按窗口校验并隔离续编与最近槽回写

任务：

1. 修改 `capture.ts` 的 edit-copy/edit-download：先解析 sender 条目，再验证载荷版本；在该条目上提交新成品和新版本。保留输入守卫、下载串行化及命名规则。
2. 封装条件回写最近槽的共用逻辑：输出前捕获身份和版本，输出完成后仅在最近槽仍匹配时回写；下载等待中出现新截图不得覆盖。队列内重验存活与版本，关闭条目不可被异步完成回调复活。
3. `EditorWindow.tsx` 将 `refreshSlotAfterApply` 改为本窗成品刷新语义，保留 busy 防重入、成功反馈与历史重置，移除尺寸比较切图逻辑；更新模块头注及 shared/preload 注释。若删除 slotSwitched，清理 zh-CN/zh-TW/en-US 三语键。
4. 同步项目骨架对取图、版本对账、成品回写和续编的职责描述。

验收：`npm run typecheck`、`npm run lint` 通过。dev 中 A、B 两窗分别复制后下载、下载后复制、继续标注再产出，各自图片与命名源正确，无误报过期或跳图；A 输出后再次编辑最新 B 仍聚焦 B。下载等待期间截 C，完成后当前槽仍为 C；以同尺寸异内容图片验证。错误 sender 和跨窗版本请求均被拒且无剪贴板、文件、槽状态副作用；故障写盘不修改编辑基准。关闭等待中的编辑窗后无条目复活或未处理异常。

### 步骤 3：完整回归与验收记录

任务：

1. 运行 `npm run typecheck`、`npm run lint`、`npm run build`；运行 dev 完成以下矩阵并记录结果，不能把未实际验证的项目勾为通过。

## 1. 需求理解

### 1.1 功能目标

快速截图目前是「截 → 入剪贴板 → 反馈条确认 → 可选下载」。本功能补上「截 → **编辑标注** → 复制/下载」的中间环：测试人员截图后需要圈出报错区域、盖住敏感信息、裁掉无关部分、加文字说明或箭头指引时，不必离开应用去第三方工具——在反馈条点「编辑」进入独立编辑子窗，用微信式熟悉心智的六件工具（**矩形/椭圆/箭头**各三档粗细+换色、**马赛克**区域打码、**裁剪**暗遮罩+确认、**文本**换色+调字号）完成轻量标注，编辑窗内「复制到剪贴板」「下载」两 icon 直接产出成品。产品是专业测试工具，效率优先：入口就一个（反馈条），工具就六件，不做画板级编辑器。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 未知点 1：有没有现成开源项目/组件可直接用？——**有但均不可直接采用**：`react-screenshots`（MIT，可独立使用的 React 截图编辑组件）工具集与交互固定、视觉不可融；`tui.image-editor` 停更过重；Pintura/Syncfusion 商业许可。详见 §2.3/2.4。
- [x] 未知点 2：标注工具在 canvas 上技术是否全部可行？——**全部可行**：Rect/Ellipse/Text/Arrow 是 Konva 内建形状，裁剪 = 遮罩 + 导出裁切，马赛克 = Pixelate 滤镜 + 裁剪副本（含官方修复注记）。见 §2.3 方案 B 与 §3。
- [x] 未知点 3：编辑器放在哪一层、怎么拿到截图字节？——**独立编辑子窗（主进程 BrowserWindow，settings 窗先例）+ 主进程单槽直供**，不经宿主 shell 中转图像数据（用户 2026-10-14 批复独立子窗形态）。见 §2.5。
- [x] 未知点 4：编辑结果如何产出？——**编辑窗内「复制」/「下载」两 icon**（用户批复修订原「完成即覆盖」方案）：复制 = 写系统剪贴板；下载 = 直写系统下载目录（复用 downloadNaming 命名链）；两者均回写单槽。见 §2.5。
- [x] 未知点 5：与本项目 React 19.2 兼容吗？——`react-konva` 官方按 React 次版本对齐发版，19.2 线与本项目 `react ^19.2.1` 精确匹配。见 §2.3 方案 B。
- [x] 未知点 6（追加）：箭头与马赛克可行性？——箭头 = Konva.Arrow 内建形状零风险；马赛克 = Konva.Filters.Pixelate + 区域裁剪副本，唯一已知坑（DPR 缩放下像素漂移/暗边）有维护者官方修复 `cache({ pixelRatio: 1 })`，另有手写降采样兜底。见 §3。

### 1.3 拆分判断

结论：**2 个调研单元**。单元 1 = 编辑器主体（选型、承载形态、数据链、四件基础工具）——已完成并获批复；单元 2 = 箭头与马赛克（用户批复追加的两工具可行性）——依赖单元 1 的 react-konva 结论，独立成节补研。

## 2. 调研单元 1：截图编辑器主体（工具 + 承载 + 数据链）

### 2.1 该部分要做什么

- 边界内：反馈条新增「编辑」入口（「下载」钮左侧）；独立编辑子窗承载标注工具与「复制到剪贴板」「下载」两产出 icon；编辑产物回写主进程单槽（复制/下载均回写，保持「单槽 = 最近一次成品」不变量）；编辑期间与既有截图/下载链路的并发对账。
- 边界外：不做画笔/序号/高亮等其余微信工具（架构留扩展位）；不做多步撤销历史以外的图层管理；不改变截图触发与反馈条显隐既有行为。

### 2.2 项目现状

- **截图数据链单源在主进程**：`src/main/browser/capture.ts` 的 `lastCapture` 单槽缓存（captureId + PNG Buffer + sessionName；新截图整体覆盖、退出即失）；`save-last` 以 captureId 对账，不匹配报「截图已过期」——编辑产物的回写与过期判定复用此语义。落盘命名单源 `src/main/browser/downloadNaming.ts`（会话名清洗/时间戳/同名序号），编辑图下载直接复用。
- **反馈条**：`src/renderer/src/components/browser/CaptureFeedbackWindow.tsx`（宿主内 WebContentsView 纯展示子视图，kind 三态 copied/saved/danger）；按钮回程模式已打通——`feedback-action`（dismiss/download 两 action，sender 白名单校验）→ 主进程转发 → 宿主 shell 汇流（`src/renderer/src/stores/browser.ts`）。「编辑」入口 = 同模式加一个 action。
- **独立子窗先例**：设置窗 `src/main/settingsWindow.ts`（单例 BrowserWindow，主进程建窗/聚焦复用）；选择类模态 sheet `src/main/workspacePickerWindow.ts`。编辑器是全功能编辑面（非确认/输入模态），归独立子窗形态，不违反「模态一律原生」裁决（AGENTS.md 界面设计节）。
- **渲染端多角色分流**：`src/renderer/src/main.tsx` 已按 query role 分流（settings / omnibox-suggest / workspace-picker / capture-feedback），编辑窗加一个 role 即可，且懒加载分包有先例（out/assets 里 SettingsWindow 独立 chunk）。
- **红线与约束**：界面纯中文 + i18n 三语字典单源（`src/shared/i18n/`）；图标一律 @ant-design/icons 禁手写 SVG（DESIGN.md 图标统一条目）；界面视觉改动走 impeccable；会话隔离不受影响（编辑全程零分区触达，纯图像处理）。
- **版本事实**：Electron ^39.2.6 / React ^19.2.1 / antd ^6.6.3 / zustand ^5.0.15（package.json）。

### 2.3 候选方案

**方案 A：react-screenshots（nashaofu/screenshots monorepo 的 React UI 子包，直接嵌入）**

- 原理：现成的微信式截图编辑 React 组件——传入图像 url + 画布尺寸，自带「框选裁剪区（选区外暗遮罩）→ 底部工具条（矩形/椭圆/箭头/画笔/马赛克/文本 + 撤销重做 + 颜色/粗细选择）→ 确定/保存」完整交互，`onOk/onSave` 回调返回合成后的 Blob 与选区 bounds。
- 来源：<https://github.com/nashaofu/screenshots>（MIT，468 stars）；子包 README：<https://github.com/nashaofu/screenshots/blob/master/packages/react-screenshots/README.md>；npm `react-screenshots@0.6.1`（peer `react >=16.9.0`，零运行时依赖，unpacked ~456KB，devDeps 用 @types/react 19 现代工具链维护中）
- 与本项目的适配点：renderer 层直接 `import` 即用，Electron 39/React 19 无障碍；但见 2.4 的不匹配面。

**方案 B：react-konva 做 canvas 场景引擎 + 编辑器 UI 全自绘**

- 原理：Konva 提供 canvas 场景图（Rect/Ellipse/Text/Arrow/Transformer/事件命中检测/拖拽缩放全内建），react-konva 用声明式 JSX 驱动；工具栏、颜色/粗细/字号面板、裁剪遮罩与确认钮全部按本项目 chrome-\* 设计语系自绘，最终 `stage.toDataURL({pixelRatio})` 导出合成位图。
- 来源：<https://github.com/konvajs/react-konva>（MIT，6.4k stars，活跃维护；README 明确版本对齐策略：「React Konva 19.2 对应 React 19.2」——与本项目 `react ^19.2.1` 精确匹配）；Konva 官方演示：<https://konvajs.org/docs/react/Transformer.html>
- 与本项目的适配点：renderer 编辑窗组件内使用，按需 import（`react-konva/lib/ReactKonvaCore` + 按形状注册可裁体积），懒加载分包不进主窗 chunk。

**方案 C：纯手写 Canvas 2D（零依赖）**

- 原理：原生 `<canvas>` 2D context 手写各工具的绘制、命中检测、拖拽调整与导出合成。
- 来源：无外部来源（Canvas 2D 是平台 API，MDN 标准）。
- 与本项目的适配点：零依赖增量，但命中检测/标注拖拽调整/文本 IME 输入浮层/DPR 缩放全手工。

**查过但不采用的（附一行理由）**：

- tui.image-editor（<https://github.com/nhn/tui.image-editor>，MIT）：照片级全家桶（滤镜/翻转/旋转，fabric.js 依赖），npm 最后发布 2022-04 已停更，体量与「轻量标注」错位。
- Pintura（<https://pqina.nl/pintura/>）：商业付费许可，直接排除。
- Syncfusion React Image Editor（<https://ej2.syncfusion.com/react/documentation/image-editor/annotation>）：商业许可体系（社区授权有营收门槛条款），为一组工具引入整套组件库不值。
- realskyrin/capcap（<https://github.com/realskyrin/capcap>）：原生 macOS 截图应用非 JS 组件，仅作功能形态参考。
- ajaichemmanam/ReactImageAnnotation（<https://github.com/ajaichemmanam/ReactImageAnnotation>）：输出标注 JSON 而非合成位图，语义不合。

### 2.5 结论与实施建议

- 结论：**借鉴思路手写**（已经用户批复）——canvas 场景引擎采用现成 `react-konva`（19.2 线，MIT），编辑器交互、工具栏与面板全自绘；现成完整编辑器（方案 A）因工具集/交互/出口/视觉四重固定不直接采用，但其「选区外暗遮罩」裁剪交互与微信工具条信息结构可作实现参考；纯手写（方案 C）放弃。
- 落地路径（粒度到文件与接口，分四步；**视觉部分实现时走 impeccable 技能**——编辑窗与工具栏属新界面，走 new-work 路径）：
  1. **契约层**（`src/shared/capture.ts`）：`CAPTURE_CHANNELS` 增通道——`openEditor`（宿主 shell/主进程：开/聚焦编辑窗）、`getEditImage`（编辑窗 → 主进程：取单槽图，返回 `{captureId, dataUrl, width, height}`）、`editCopy`（编辑窗 → 主进程：`{captureId, dataUrl}`，对账后写剪贴板+回写单槽）、`editDownload`（编辑窗 → 主进程：同载荷，对账后经 downloadNaming 落盘+回写单槽，返回落盘路径）、`editRequest`（主进程 → 宿主 shell：编辑产出后通知宿主重发反馈条）；新增 `CAPTURE_EDITOR_WINDOW_ROLE` 常量与载荷类型。
  2. **主进程**：新 `src/main/browser/captureEditorWindow.ts`（单例子窗，`settingsWindow.ts` 先例：懒建、聚焦复用、尺寸按图像自适应有上限、closed 清理）；`src/main/browser/capture.ts` 的 `registerCaptureIpc` 增 handler——open-editor（校验来源后开窗）、get-edit-image（单槽现值，空槽如实报错）、edit-copy / edit-download（captureId 对账 → 解析 dataUrl 为 PNG Buffer → 回写单槽（**换新 captureId**、保留 sessionName）→ 各自产出动作 → 通知宿主重发反馈）。编辑图下载复用 `saveLastCapture` 的串行链与唯一路径解析（serializeSave 防同秒同名竞态）。
  3. **入口**（反馈条）：`CaptureFeedbackWindow.tsx` 在「下载」左侧加「编辑」链接式钮（kind=copied 与 saved 两态显示，danger 不显示——单槽有图才可编辑），点击走既有 `feedback-action` 增 `edit` action → 主进程直接开编辑窗；i18n `browser.capture.edit` 三语；`.chrome-capturebar-save` 样式复用。
  4. **编辑器本体**（renderer）：`main.tsx` 增 `role=capture-editor` 分流（React.lazy 懒加载，konva 不进主包）；新 `src/renderer/src/components/browser/captureEditor/`——`EditorWindow.tsx`（取图；窗内右上「复制到剪贴板」「下载」两 icon 钮（@ant-design/icons），成功后关窗、失败窗内如实报错留在编辑态）、`EditorToolbar.tsx`（六工具 + 粗细三档 + 色板 + 字号档 + 撤销/重做，chrome-\* 语系）、`AnnotationStage.tsx`（react-konva Stage：底图层 + 标注层 + 裁剪遮罩层；标注画后可拖动/调整；马赛克区块节点见 §3；文本工具 Konva 官方可编辑文本模式——canvas 上叠 DOM textarea 承接 IME）。默认值常量入模块头：粗细三档拟 **2/5/10 px**、字号三档拟 **14/18/24 px**（均图像像素空间，随导出 pixelRatio 换算）、马赛克块径拟固定 10px、文本字体栈 `-apple-system, "PingFang SC", "Microsoft YaHei", sans-serif`（对齐微信观感），具体取值 impeccable 轮可视校准。

## 3. 调研单元 2：箭头与马赛克（用户 2026-10-14 批复追加，anysearch 补研）

### 3.1 该部分要做什么

在单元 1 已定的 react-konva 编辑器里补两件微信工具：**箭头**（拖拽画箭头，实心三角头，与矩形/椭圆共用三档粗细与色板）与**马赛克**（拖框区域像素化打码，微信语义块径固定不换色）。边界外：马赛克不做模糊/高斯变体，不做涂抹式画笔打码（只做拖框区域式）。

### 3.2 项目现状

同单元 1 §2.2（引擎、单槽、编辑窗承载已定）。马赛克的数据源即编辑窗底图的 `Konva.Image`——区域打码通过对底图做 crop 副本 + 滤镜实现，不引入第二份图像数据。

### 3.3 候选方案

**箭头——Konva.Arrow 内建形状（采用现成）**

- 原理：Konva 原生 `Arrow` 形状，`points` 定两端、`pointerLength/pointerWidth` 定箭头头、`stroke/fill/strokeWidth` 与 Rect/Ellipse 完全同模型——三档粗细与色板零适配直接吃。
- 来源：官方文档 <https://konvajs.org/docs/shapes/Arrow.html>（"Create arrows with customizable pointers, stroke, and fill using the Konva.Arrow shape"）；源码 <https://github.com/konvajs/konva/blob/master/src/shapes/Arrow.ts>

**马赛克主路线——Konva.Filters.Pixelate + 底图裁剪副本**

- 原理：每个马赛克区一个 `Konva.Image` 节点，`crop = {x, y, width, height}` 取底图对应区域，`cache()` 后挂 `filters([Konva.Filters.Pixelate])` 并设 `pixelSize`（块径）；滤镜渲染进画布，`stage.toDataURL` 导出时自然合成。
- 来源：官方文档 <https://konvajs.org/docs/filters/Pixelate.html>（含 react-konva 版示例：`imageRef.current.cache()` + `filters={[Konva.Filters.Pixelate]}` + `pixelSize`）；react 滤镜总览 <https://konvajs.org/docs/react/Filters.html>
- **已知坑与官方修复（关键证据）**：konva issue #1591「Pixelate Filter Does Not Render Using Specified Pixel Size and Creates Dark Lines」（2023-06 提出、2023-11 关闭）——对**裁剪图**应用 Pixelate 且系统显示缩放/浏览器缩放 ≠100%（即 devicePixelRatio ≠1）时，块径不等于设定值且右/下缘出暗线；Konva 维护者 lavrton 给出官方修复 `node.cache({ pixelRatio: 1 })`，提交者验证有效（"that did it!!!"）。来源：<https://github.com/konvajs/konva/issues/1591>

**马赛克兜底路线——手写降采样/升采样像素化**

- 原理：offscreen canvas 将区域缩小 N 倍再放大绘回，`imageSmoothingEnabled = false` 保证硬边块状——经典像素化技法，约 15 行，无滤镜/cache 机制。
- 来源：MDN `imageSmoothingEnabled` <https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled>；中文实现参考：张鑫旭《如何用简单的 Web 方法实现图片的马赛克效果》（2024-05）<https://www.zhangxinxu.com/wordpress/2024/05/js-web-svg-canvas-image-mosaic/>

**市面佐证**：单元 1 已查的 `react-screenshots`（<https://github.com/nashaofu/screenshots>）工具条原生含箭头与马赛克（微信式交互的开源实证）；桌面截图工具普遍以 pixelate/blur 做区域打码（GitHub image-annotation 主题下的 Scap 等）。两工具均为截图标注领域的标配能力，无实现先例风险。

### 3.4 可行性分析

| 维度 | 箭头：Konva.Arrow | 马赛克主路线：Pixelate+crop | 马赛克兜底：手写降采样 |
| --- | --- | --- | --- |
| 技术匹配 | 内建形状，与既有 Rect/Ellipse 同 API 模型，React 19/konva 版本无虞 | 官方滤镜 + react-konva 官方示例；唯一已知坑（DPR 缩放下块径漂移/暗边）有维护者修复注记 `cache({ pixelRatio: 1 })`，按注记执行即避坑 | 平台 API 零版本风险；区域任意尺寸/N 值均确定性输出 |
| 规则冲突 | 无（自绘工具栏接入，图标/文案/i18n 全走仓库单源） | 无（滤镜为渲染机制非 UI，不触任何约定） | 无 |
| 成本 | 零增量 | 零依赖增量（Konva 自带滤镜）；每马赛克区一个 Image 节点 + cache，区域数量级为个位数，性能无虞 | 零依赖；~15 行工具函数 + 导出时逐区合成（自管合成顺序，略繁于滤镜路线） |

### 3.5 结论与实施建议

- 结论：**采用现成**——箭头直接用 `Konva.Arrow` 形状（挂既有三档粗细+色板体系，仅导出时箭头头实心填充同色）；马赛克主路线用 `Konva.Filters.Pixelate` + 底图裁剪副本，**实现时强制 `cache({ pixelRatio: 1 })`**（issue #1591 官方修复，规避 DPR 缩放下块径漂移/暗边）；手写降采样作为 Pixelate 在导出链路上行为不达标时的兜底（实现轮以真实导出图验证块径与边缘后二选一定稿）。
- 落地路径：并入单元 1 §2.5 第 4 步的 `AnnotationStage.tsx`——箭头 = 标注层一个 shape 分支（与 Rect/Ellipse 并列）；马赛克 = 标注层独立 `MosaicRegion` 子组件（crop Image + Pixelate，draggable 可拖调整）；工具栏 `EditorToolbar.tsx` 六工具位次拟微信序：矩形/椭圆/箭头/马赛克/文本 + 裁剪。i18n `browser.captureEditor.*` 三语。

## 4. 风险与开放问题

- **React 次版本锁定**：react-konva 按 React 次版本对齐发版（19.2 ↔ React ^19.2.x），将来升 React 19.3 需同步升 react-konva，属可预期常规升级成本。
- **马赛克 DPR 坑**：已定位官方修复（`cache({ pixelRatio: 1 })`）；实现轮必须以「编辑窗在 Retina 屏 + 导出 PNG」实测块径与边缘作为验收点。
- **滤镜进导出链**：Pixelate 效果经 Konva 缓存画布渲染，`stage.toDataURL` 应含滤镜结果——实现轮以真实导出图验证（若不达标切换 §3.3 兜底路线）。
- **大图性能**：4K 级 Tab 截图单图层 + 个位数标注对象，Konva 场景图重绘无压力；导出 `pixelRatio` 按原图像素/显示尺寸换算，保证标注导出后不糊。
- **编辑期并发**：编辑窗开着时又截新图——单槽被覆盖，编辑窗内产出（edit-copy/edit-download）时 captureId 对账失败如实报「截图已过期」，与 save-last 既有竞态语义一致，无新增风险面。
- **文本 IME**：中文输入法在 canvas 上无原生输入，用 Konva 官方模式叠 DOM textarea 承接（有官方演示背书），是六件套里唯一有实现细节风险的工具，实现轮重点验证。

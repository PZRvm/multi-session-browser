## 1. 需求理解

### 1.1 功能目标

测试人员把本机 Google Chrome 某个 profile 的两类数据导入到**指定的某个会话**：浏览历史（成为该会话地址栏建议的数据源——在地址栏输入时给出补全提示，复用既有建议下拉，不新增任何历史列表界面）与 localStorage（站点前端状态随导入延续到会话里）。合并语义：与目标会话已有数据按数据类型合并，冲突项弹一个确认框由用户按类型一次裁决「以 Chrome 为准 / 以当前会话为准」。

**范围说明（2026-09-30 批复）**：Cookie 导入移出本期。后果需知悉——多数网站的登录态主要靠 Cookie 承载，localStorage 只承载前端状态与部分令牌，因此本期导入**不带来「免登录」效果**，价值定位是「输入提示 + 站点前端状态延续」；Cookie 路线的调研结论完整保留在单元 B，后续要做时可直接续用。

导入是会话级、显式触发的一次性动作（点一次导一次），符合「一会话一分区完全隔离」的产品底线：只向目标会话分区写入，不产生任何跨会话共享。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] Chrome 的历史 / Cookie / localStorage 在本机存在哪、什么格式？→ 各单元 2.2/2.3；路径见单元 A 方案 A1。
- [x] Cookie 是加密的，第三方应用能解吗？各平台现状（Windows app-bound、macOS 钥匙串、Chrome 130+ 域名哈希前缀）？→ 单元 B。
- [x] 能否走 CDP 远程调试让 Chrome 运行时自己吐解密数据？→ 单元 B 方案 B2，**已否决**（Chrome 136 官方封堵）。
- [x] Electron 会话分区如何接收这些数据（cookies.set / 文件级复制）？→ 单元 B / C。
- [x] 搜索历史的「输入提示」怎么接？有无现成链路可复用？→ 单元 A，**项目已有完整建议链路，导入数据源即自动生效**。
- [x] 读 Chrome 的 SQLite 库需要引入什么依赖？→ 单元 A，**Electron 内嵌 node:sqlite 零依赖可用（已在本项目 Electron 二进制内实测）**。
- [x] 与领域红线（会话隔离等）是否冲突？→ 各单元 2.4，均不冲突（导入是向单一分区的写入动作）。
- [x] （2026-09-30 追问）目标会话已有数据时能否**合并**而非覆盖？冲突项能否弹框由用户裁决「以 Chrome 为准 / 以当前会话为准」？→ 单元 B/C 结论更新 + 第 5 节冲突裁决流程：历史天然合并；Cookie 用既有 `cookies.get` 对齐冲突，低风险；localStorage 需记录级 LevelDB 手术，可行但新增一个依赖。

### 1.3 拆分判断

原拆 3 个调研单元；2026-09-30 批复后**本期实施 2 个**：

- **单元 A：搜索历史导入与地址栏建议**（读 Chrome History SQLite → 并入既有 history 数据层）

## 2. 调研单元 A：搜索历史导入与地址栏建议

### 2.1 该部分要做什么

把 Chrome 某个 profile 的浏览历史（URL + 标题 + 访问次数 + 最后访问时间）一次性并入目标会话的历史数据层。**不新增任何历史列表界面**——导入后唯一可见效果是地址栏输入时建议下拉出现 Chrome 历史条目（含 Google 搜索 URL）。边界：不导入 Chrome 的「Shortcuts/Top Sites」等 omnibox 专有库；不做持续同步。

### 2.2 项目现状

- **建议链路已完整存在，本单元本质只是「喂数据」**：
  - 数据层 `src/main/browser/history.ts`：`BrowserHistory` 接口（`recordVisit`/`getEntries`/`cloneHistory`/`dropHistory`/`flushAll`/`onEntryChanged`），每会话独立落盘 `userData/history/<sessionId>.json`（去抖 + 原子写），注册表 `src/main/browser/registry.ts:215` 创建、`manager.onVisit` 接线采集。
  - 共享契约 `src/shared/history.ts`：`HistoryEntry{url,title,faviconUrl,visitCount,lastVisitedAt}`、`HISTORY_MAX_ENTRIES=2000`（超限按 lastVisitedAt 淘汰最旧）、`HISTORY_URL_MAX=2000`、重复 url 合并规则（保留 lastVisitedAt 较新）。
  - 检索与展示：`src/renderer/src/components/browser/omniboxSuggest.ts` 纯函数建议（域名前缀 > URL 前缀 > URL 子串 > 标题子串，新近度 7 天半衰 + log2 频次排序）；面板由原生子窗承载（`src/main/browser/omniboxSuggest.ts`、`src/shared/omniboxSuggest.ts`）。**导入的条目只要落进 history 数据层，建议链路全自动生效，零 UI 改动。**
- 版本事实：Electron 39.8.10（内嵌 **Chromium 142.0.7444.265**、**Node 22.22.1**）；已在本项目 Electron 二进制内实测 `node:sqlite` 可直接 `require` 并读写（仅 ExperimentalWarning，无 flag）。

### 2.3 候选方案

**方案 A1：拷贝 History 库 + node:sqlite 读取，映射写入既有 history 数据层**

- 原理：Chrome 浏览历史存于 profile 目录下明文 SQLite 库 `History`（`urls` 表：`url/title/visit_count/last_visit_time` 等列），无加密。主进程把该文件拷贝到临时目录后用 Node 内置 `node:sqlite` 打开读取（拷贝是为了绕开 Chrome 运行中的库锁，且 SQLite 日志回放保证崩溃一致性），按 `last_visit_time` 倒序取最多 2000 条，时间戳从 WebKit 纪元（µs since 1601-01-01）换算为 ms（`t/1000 - 11644473600000`），映射成 `HistoryEntry` 并入既有数据层。Chrome 历史中的搜索记录以 `google.com/search?q=...` URL 形态存在，导入后即可被建议命中。
- 来源：
  - Chrome user data 目录结构与各平台路径（官方）：https://chromium.googlesource.com/chromium/src.git/+/HEAD/docs/user_data_dir.md
  - WebKit 时间戳换算：https://stackoverflow.com/questions/20458406/what-is-the-format-of-chromes-timestamps 、https://github.com/osquery/osquery/issues/6390
  - `urls` 表结构实例：https://en.wikiversity.org/wiki/Chromium_browsing_history_database
  - node:sqlite 官方文档：https://nodejs.org/api/sqlite.html （Electron ≥35 内嵌 Node 22 系自带，社区佐证 https://rxdb.info/articles/electron-sqlite.html ）
- 与本项目的适配点：主进程纯 Node 代码，零新依赖；写入端在 `history.ts` 加一个批量导入入口即可，`HISTORY_MAX_ENTRIES` 上限与合并规则现成。

**方案 A2：better-sqlite3 原生依赖**

- 原理：成熟 SQLite 绑定，读同库。来源：https://github.com/WiseLibs/better-sqlite3
- 看过、不选：引入原生模块构建链（项目 postinstall 的 `electron-builder install-app-deps` 可构建，但无必要）——`node:sqlite` 内置已满足，多一个原生依赖只增加打包与 ABI 维护成本。

**方案 A3：sql.js（WASM SQLite）**

- 看过、不选：WASM 包体大、API 需手动管理内存，同样被内置方案覆盖。

### 2.4 可行性分析

| 维度 | 方案 A1（node:sqlite） | 方案 A2（better-sqlite3） |
| --- | --- | --- |
| 技术匹配 | 内置模块与 Electron 39 内嵌 Node 22.22 实测可用；明文库直接读，全平台无障碍 | 功能等价，需 electron-rebuild |
| 规则冲突 | 无（主进程 Node API 自由使用；数据只写目标会话文件） | 无 |
| 成本 | 零依赖；~百行级读库映射代码 | 新增原生依赖与构建链 |

### 2.5 结论与实施建议

- 结论：**借鉴思路手写**——SQLite 读取用内置 `node:sqlite`（零依赖），读库/映射/合并逻辑自写（无值得引入的现成「Chrome 历史导入」库）。
- 落地路径：
  1. `src/main/browser/history.ts`：新增 `importEntries(sessionId, entries: HistoryEntry[]): Promise<number>` 批量合并入口——沿用 `parseStored` 同源合并规则（同 url：visitCount 取 max、lastVisitedAt 取较新、title/favicon 保留非空新值），超限淘汰最旧，合并后走既有推送（镜像即时可被建议）。
  2. 新模块 `src/main/browser/chromeImport/`（底座随本单元建立，B/C 复用）：`detect.ts`（定位 Chrome 安装 + 枚举 profile：macOS `~/Library/Application Support/Google/Chrome`、Windows `%LOCALAPPDATA%\Google\Chrome\User Data`、Linux `~/.config/google-chrome`，profile 目录名与显示名来自 `Local State` 的 `profile.info_cache`）；`historySource.ts`（拷贝 `History` → 读 `urls` 表 → 换算映射）。
  3. Windows 上拷贝被 Chrome 文件锁拒绝时返回明确错误（提示「关闭 Chrome 后重试」），不静默。

## 3. 调研单元 B：Cookie 导入

> **2026-09-30 用户批复：本期不做。** 本节保留为完整调研记录（含否决方案与平台能力矩阵），后续要恢复 Cookie 导入时可直接续用，无需重新调研。

### 3.1 该部分要做什么

把 Chrome 某个 profile 的持久化 Cookie（含 httpOnly，登录态核心）解密后逐条注入目标会话分区，使目标会话免登录。边界：会话级（非持久）Cookie 无落盘可导，不在范围；只处理 Chrome 官方安装的默认用户目录。

### 3.2 项目现状

- 分区机制：`src/main/browser/registry.ts:42` `partitionFor` 拼装 `persist:sess-<id>`（唯一拼装点，`SESSION_ID_RE` 守卫）；`session.fromPartition` 惰性建分区。Cookie 由 Chromium 管理，写入用 Electron 官方 `session.cookies.set`（支持 `httpOnly`/`secure`/`sameSite`/`expires`）：https://electronjs.org/docs/latest/api/cookies
- 领域红线：一会话一分区禁止共享——本单元是「向指定分区注入」，天然合规；无跨分区读。
- preload 无任何 cookie 通道（符合现状：renderer 不需要碰 cookie，导入全程在主进程）。

### 3.3 候选方案

**方案 B1：直接文件级复制 Cookies SQLite 库** —— 看过、**否决**。

- 原理：把 Chrome 的 `Cookies` 库拷进分区目录。
- 否决理由：cookie `encrypted_value` 的解密密钥是**应用绑定**的——macOS 上 Chromium 用各自钥匙串项（Chrome 用 "Chrome Safe Storage"，Electron 用自己的 "Electron Safe Storage"），Windows 上是安装级 `Local State` 的 `os_crypt.encrypted_key`。Electron 打开 Chrome 加密的库无法解开，拷过去即死数据。格式佐证：https://gist.github.com/creachadair/937179894a24571ce9860e2475a2d2ec

**方案 B2：CDP 远程调试（让 Chrome 运行时吐解密 cookie）** —— 看过、**否决**。

- 原理：让用户以 `--remote-debugging-port` 重启 Chrome，经 DevTools 协议 `Storage.getCookies` 拿解密 cookie。
- 否决理由：**Chrome 136（2025-03）起官方封堵**——对默认用户数据目录不再尊重 `--remote-debugging-port/-pipe`，必须配非默认 `--user-data-dir`（即拿不到用户真实数据）：https://developer.chrome.com/blog/remote-debugging-port ；且该方案需强制用户完全退出并重启 Chrome，体验差、时序脆。官方动机正是防 infostealer 借此路径偷 cookie（同页）。

**方案 B3：离线解密 + `session.cookies.set` 逐条注入**（候选中唯一可行）

- 原理：拷贝 `Cookies` 库 → 读 `cookies` 表（`host_key/name/value/encrypted_value/path/expires_utc/is_secure/is_httponly/samesite/source_scheme`，`value` 非空即明文直用）→ 按平台解出明文 → `cookies.set({ url, domain, path, name, value, expirationDate, secure, httpOnly, sameSite })` 逐条注入目标分区。解密全部可用 Node 内置 `crypto`（`pbkdf2` + `createDecipheriv`）。
- 来源：
  - 格式全解（CBC 参数、PKCS#5 padding、DB version≥24 的域名哈希前缀）：https://gist.github.com/creachadair/937179894a24571ce9860e2475a2d2ec （含 Chromium 提交佐证 https://github.com/chromium/chromium/commit/5ea6d65c622a3d5ff75db9dc0257ea3869f31289 ）
  - Windows App-Bound 加密官方公告（Chrome 127）：https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html
  - v20 离线解密被阻断的现状佐证（2026-01 取证业）：https://blog.elcomsoft.com/2026/01/browser-forensics-in-2026-app-bound-encryption-and-live-triage/ 、https://github.com/steipete/sweet-cookie/issues/23
  - Chromium cookie schema 与 samesite 枚举：同 gist；Electron Cookies API：https://electronjs.org/docs/latest/api/cookies
- 平台能力矩阵（关键事实）：

| 平台 | 机制 | 可行性 |
| --- | --- | --- |
| macOS | 钥匙串项 "Chrome Safe Storage"（首次访问弹系统授权）→ PBKDF2-HMAC-SHA1(pass, `saltysalt`, 1003 次) 取 16B → AES-128-CBC（IV=16 个空格，PKCS#5 去 padding；DB version≥24 再剥明文前 32B SHA256(host_key)） | ✅ 当前 Chrome 仍此机制（App-Bound 仅 Windows） |
| Linux | v10/v11 固定口令 `peanuts`（PBKDF2 1 次）为默认；配置 GNOME keyring/KWallet 后端的分支不支持即诚实报错 | ✅（尽力支持） |
| Windows | Chrome <127：v10 = AES-256-GCM，密钥在 `Local State` `os_crypt.encrypted_key`（DPAPI 包裹，需原生通道解 DPAPI，如 `@primno/dpapi` 或 PowerShell 一次调用） | ⚠️ 可做，但覆盖面已小 |
| Windows | Chrome ≥127：v20 **App-Bound Encryption**，第三方离线解密被官方系统性阻断，现存绕过属攻击级手段（SYSTEM 服务劫持等），不适合产品采用 | ❌ 不支持，UI 明示 |

### 3.4 可行性分析

| 维度 | 方案 B1（拷库） | 方案 B2（CDP） | 方案 B3（解密+注入） |
| --- | --- | --- | --- |
| 技术匹配 | ❌ 密钥应用绑定，拷过去解不开 | ❌ Chrome 136+ 对默认 profile 失效 | ✅ macOS/Linux 全量；Windows 分版本 |
| 规则冲突 | 无 | 强制重启用户 Chrome，且官方定性为攻击面 | 无（单分区写入） |
| 成本 | — | — | 每平台解密 ~50-80 行纯 crypto；Windows DPAPI 需一条原生通道；npm 现成库（chrome-cookies-secure 等）停更或依赖 Puppeteer，不值得引入 |

### 3.5 结论与实施建议

- 结论：**借鉴思路手写**（方案 B3）。解密算法短、稳定性依赖 Chromium os_crypt 源码事实而非任何库；按平台矩阵诚实降级，不追 Windows v20。
- 合并语义（2026-09-30 追问后定稿）：导入 = **并集合并**。注入前用 `session.cookies.get({})`（官方 Cookies 类查询接口，https://electronjs.org/docs/latest/api/cookies ）枚举目标分区现有 Cookie，与 Chrome 解密结果按 `(domain, name, path)` 三元组对齐：分区没有的直接注入；两边都有且值不同 → 计入冲突集，交由裁决弹窗统一处置（以 Chrome 为准 / 以当前会话为准，见第 5 节）；值相同视为非冲突。
- 落地路径（并入单元 A 建立的底座）：
  1. `src/main/browser/chromeImport/cookieDecrypt.ts`：分平台取密钥 + 解密（Node `crypto`；Windows DPAPI 走 `@primno/dpapi` 依赖或 PowerShell 子进程，实现期定夺）。
  2. `src/main/browser/chromeImport/import.ts` 编排：`fromPartition` 建分区 → `cookies.get({})` 读分区现状 → 冲突集分离（非冲突直注入、冲突等裁决）→ 按裁决结果逐条 `cookies.set` 或跳过（`host_key` 保留前导点作 domain、`expires_utc` 换算 `expirationDate`、samesite 整数枚举映射、`is_secure`/`is_httponly` 直传；Chrome 侧已过期的条目跳过）→ 汇总成功/失败/冲突计数。
  3. macOS 钥匙串授权被拒：cookie 导入失败，历史/localStorage 不受影响（分项独立）。

## 4. 调研单元 C：localStorage 导入

### 4.1 该部分要做什么

把 Chrome 某个 profile 的 localStorage（站点键值数据）整批落到目标会话分区，使站点侧的「记住的状态」（前端令牌、界面偏好等）随导入生效。边界：sessionStorage 不落盘无导可言；IndexedDB 同机制可扩，本期不做（列为可选）。

### 4.2 项目现状

- 分区目录结构：`userData/Partitions/sess-<id>`（`registry.ts:49` `partitionDir`）。分区内本就含 Chromium 同构的 `Local Storage/leveldb` 目录——`registry.ts:69` 的 `CLONE_EXCLUDED_DIR_BASENAMES` 注释明确「Cookies / Local Storage / IndexedDB 等登录态与站点数据」走全量保真复制，即**克隆功能已经在做分区内站点数据的文件级复制**。
- 活库收尾先例：`closeSession`（close-then-copy，`registry.ts:618`）保证复制前分区无活 webContents 写入；`cloningIds` 窗口期守卫（`registry.ts:254`）防止复制期间重建分区。导入可整体复用这套模式。
- Electron **没有**任何向 localStorage 写入的进程 API（无此接口），排除「API 注入」路线。

### 4.3 候选方案

**方案 C1：`Local Storage/leveldb` 目录文件级整替（close-then-copy 模式）**

- 原理：导入前先 `closeSession` 收尾目标分区（复用既有机制），把 Chrome profile 的 `Local Storage/leveldb` 目录拷贝替换到分区对应目录，下次激活分区时 Chromium 按常加载。两侧同为 Chromium localStorage v2 LevelDB 格式（Chrome 与 Electron 39/Chromium 142 同源），磁盘格式多年稳定；LevelDB 自身崩溃安全（日志回放），Chrome 运行中拷贝≈崩溃时点快照，一致性可接受。
- 来源：
  - Chromium localStorage/IndexedDB 存于 LevelDB 及磁盘格式（CURRENT/MANIFEST/.log/.ldb）：https://www.browserforensics.app/en/blog/chromium-leveldb-format
  - 直接改写/搬运 Chrome localStorage LevelDB 的先例：https://gist.github.com/bojanrajkovic/bf3cef8dbc6f360d03030eecfc9d79ea
  - 实验性开关把 LS 换 SQLite 后端（默认未启用，版本风险注记）：https://peter.sh/experiments/chromium-command-line-switches/
- 与本项目的适配点：主进程 fs 操作 + 复用 `closeSession`/窗口期守卫先例；与克隆同构，无新机制。

**方案 C2：逐 origin 导航 + `executeJavaScript('localStorage.setItem…')`**

- 看过、否决：需对每个 origin 真实导航（触发网络请求、慢、污染历史采集与状态条），origin 多时不可行，数据保真差。

**方案 C3：经某种 Electron API 注入**

- 看过、否决：Electron 无 localStorage 写入 API，该路线不存在。

**方案 C4：LevelDB 记录级合并手术（2026-09-30 追问新增，服务「合并 + 冲突裁决」语义）**

- 原理：不整目录替换，而是用 `level`（内核 `classic-level`，N-API 预编译、Electron 免重编）直接打开分区关闭状态下的 `Local Storage/leveldb`，把 Chrome 侧记录按 Chromium 键值格式**逐条移植**：数据记录键为 `_<origin>\x00\x01<key>`，另有 `META:<origin>` / `METAACCESS:<origin>` 簿记键——值字节**原样拷贝不解码**（编码前缀 `\x00` Latin1 / `\x01` UTF-8 随字节保留），仅在冲突键上按裁决决定 `put`（Chrome 为准）或跳过（当前为准）。分区已有该 origin 则保留分区 META 只移植数据键；分区没有的 origin 连 META 整体移植。`batch` 原子写入，手术前先备份分区 LS 目录（失败整体还原）。
- 来源：
  - 直接改写 Chrome localStorage LevelDB 的完整先例（`level` 包 batch put `_<origin>\x00\x01<key>` / `META:` 记录，Chrome 重新打开即识别）：https://gist.github.com/bojanrajkovic/bf3cef8dbc6f360d03030eecfc9d79ea
  - Chromium localStorage/sessionStorage 键值编码格式（`_https://example` 键、编码前缀字节）：https://cdn.prod.website-files.com/5f02f2ca454c471870e42fe3/60ed4b9585dae9c79fbe331d_CCL_Tech_paper_Chromium_Storage.pdf
  - classic-level（N-API 预编译）：https://www.npmjs.com/package/classic-level ；Electron 原生模块官方说明（N-API 无需 rebuild）：https://electronjs.org/docs/latest/tutorial/using-native-node-modules
- 与本项目的适配点：读侧（冲突检测）与写侧（合并手术）同一依赖；分区关闭守卫复用 `closeSession`/窗口期先例。代价：新增一个原生依赖（预编译免构建）+ 自担记录格式正确性风险（有先例与字节级移植策略兜底）。

### 4.4 可行性分析

| 维度 | 方案 C1（目录整替） | 方案 C2（逐 origin 注入） | 方案 C4（记录级合并） |
| --- | --- | --- | --- |
| 技术匹配 | ✅ 同构格式 + 克隆同款机制已有 | origin 级导航不可扩展 | ✅ 先例充分；分区关闭 + 备份还原兜底 |
| 规则冲突 | 无 | 污染历史采集与导航状态 | 无（写入单一分区；关闭守卫复用） |
| 成本 | 零依赖；**无冲突裁决能力**（粒度 = 整目录二选一） | 高且脆弱 | 新增 `classic-level` 依赖；冲突粒度到键，支撑合并语义 |

### 4.5 结论与实施建议

- 结论：**借鉴思路手写**（方案 C4 记录级合并，按用户 2026-09-30 追问的「合并 + 冲突裁决」语义）。方案 C1 保留为降级路径：若实施中发现记录移植在真实数据上不稳，回退整目录替换（弹窗粒度退化为「localStorage 以 Chrome 为准 / 以当前会话为准」整目录二选一）。
- 落地路径：
  1. `src/main/browser/chromeImport/siteData.ts`：编排「`closeSession`(如该会话有 manager) → 备份分区 LS 目录 → classic-level 打开两侧 → 冲突检测（同 origin 同 key 且值不同）→ 非冲突移植 + 冲突按裁决写入/跳过 → 失败还原备份」；导入期间会话 id 计入窗口期守卫集合（照 `cloningIds` 先例）。
  2. 冲突集与裁决交互走第 5 节的统一弹窗（本模块只产出 `冲突清单` 与消费裁决结果）。

## 5. 共享底座与界面（随单元 A 建立，单元 C 复用）

- 主进程 `src/main/browser/chromeImport/`：`detect.ts`（探测 + 枚举）、`historySource.ts`（History 读取）、`siteData.ts`（LS 记录级合并）、`index.ts` 编排 + `src/main/index.ts` 注册 IPC；`src/preload/index.ts` 增 `api.chromeImport` 分组并同步 `index.d.ts`。
- 界面入口：会话行右键菜单（`src/renderer/src/components/SessionRow.tsx:177` 既有 menuItems）新增「导入 Chrome 数据…」项；导入对话框 = profile 下拉（`Local State` 显示名）+ 内容勾选（历史 / localStorage 两项）+ 结果反馈（antd message，失败文案区分「未检测到 Google Chrome」「Chrome 文件被占用，请关闭 Chrome 后重试」）。**界面为新增视觉改动，实现时走 impeccable 技能（polish 路径）**；文案 zh/en 双语落 `src/shared/i18n/`。

### 5.1 冲突裁决弹窗（粒度已批复：会话级一次二选一，不按站点分组）

流程编排（主进程先行「干跑」，renderer 只做展示与裁决）：

1. 用户在导入对话框点「导入」后，主进程先完成**只读阶段**：拷贝读取 Chrome 两类数据 + 读分区现状（历史内存条目、classic-level 只读打开分区 LS），算出冲突集——localStorage 按「同 origin 同 key 值不同」计数；历史无冲突概念（同 URL 按既有规则静默合并，**不弹窗**——访问记录不是配置项，合并规则天然合理）。
2. localStorage 冲突集非空时弹**一个**确认弹窗（antd Modal）：展示「发现 localStorage 冲突 M 键（涉及 K 个站点）」，单选二项：**以 Chrome 为准 / 以当前会话为准**；无冲突则不弹窗直接执行。会话级一次裁决，不提供逐条/逐站点粒度（已批复；明细可加只读的按 origin 分组折叠预览，不下决）。
3. 用户确认后主进程执行写入阶段（非冲突项照常合并移植，冲突项按裁决处置），全程分区关闭 + 备份兜底；结果反馈汇总「新增 / 合并 / 冲突按裁决处置 / 失败」计数。

### 5.2 本机未检测到 Chrome 的交互（2026-09-30 批复定案）

- 检测时机 = 打开导入对话框时主进程现做（fs 检查默认用户数据目录 + 枚举 profile，毫秒级），不做启动期常驻探测。「Chrome 未安装」与「已安装但从未运行/无任何 profile 数据」同一口径呈现。
- 未检测到时：对话框内如实显示「未检测到 Google Chrome」，导入按钮禁用、勾选项置灰。菜单入口保持可点（对话框是检测状态的唯一出口，避免菜单构建期检测的时序成本），用户点开即得明确状态。
- 不写引导式文案（不提示「请先安装 Chrome」，PRODUCT.md 产品原则：面向专业测试人员）；不提供自定义安装路径选择（与假设 1 的「仅默认目录」口径一致，自定义路径留作后续可选增量）。

## 6. 风险与开放问题

1. **数据格式版本演进风险**：Chrome 持续演进存储层（History SQLite 列扩展、localStorage LevelDB 存在换 SQLite 后端的实验开关但默认未启用、130 加域名哈希前缀等）。对策：读取失败分项如实报错降级，绝不产生「看似成功」的假象；平台能力矩阵相关的最大风险源（Cookie 加密）已随范围裁剪移出。
2. **Chrome 运行中读取一致性**：History 为 SQLite、localStorage 为 LevelDB，均为日志回放的崩溃安全设计，运行中拷贝可用；Windows 上可能遇文件锁，失败时提示关闭 Chrome 重试（文案已列）。
3. **隐私敏感性**：本功能读取用户真实浏览数据，必须显式触发 + 明示读取范围（勾选项即范围），不做任何静默读取；导入数据仅写入本应用会话分区，不落日志。
4. **localStorage 记录手术风险**：C4 直接写分区的 LevelDB，记录格式正确性自担（值字节原样移植策略已把风险压到最低，且有改写先例佐证）；兜底 = 手术前整体备份分区 LS 目录、失败整体还原。`classic-level` 为 N-API 预编译原生依赖（免 rebuild），与项目 `electron-builder install-app-deps` 管线无冲突——**用户已批复认可（2026-09-30）**。
5. **覆盖冲突**：已由合并方案消解（记录级合并 + 冲突裁决）；C1 整目录替换仅保留为降级路径。
6. **「免登录」效果说明（非风险，预期管理）**：Cookie 移出后，多数站点登录态不会随导入延续（登录态主要由 Cookie 承载）；本期的价值定位 = 地址栏输入提示 + localStorage 承载的站点前端状态延续。

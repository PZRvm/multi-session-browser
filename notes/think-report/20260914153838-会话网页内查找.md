# 会话网页内查找（Ctrl/Cmd+F find in page）功能调研报告

> 创建时间：2026-09-14 15:38（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户原话——「在 chrome 浏览器中，点击 ctrl + f 能够查找网页中的元素，我希望在这个应用程序中加上这个操作」
> 调研单元：1 个（小功能）
> 状态：调研完成，待用户确认（未实施）

## 1. 需求理解

### 1.1 功能目标

在会话浏览区对齐 Chrome 的页内查找（find in page）：用户在任意宿主窗口（主窗口或独立窗口）的浏览场景下按下 Ctrl+F（Windows/Linux）/ Cmd+F（macOS），在内容区顶部弹出查找栏；输入关键词即时在页面内高亮全部匹配（Chromium 原生高亮），显示「当前序号/总数」计数，Enter / Shift+Enter 在匹配间前后跳转，Esc 或点关闭钮退出并清除高亮。

用户是专业测试人员，典型场景是在隔离会话里核对页面文案、定位断言目标、在长页面中快速找元素。效率优先，交互按 Chrome 惯例，不做引导式提示。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 未知点 1：Electron 对 WebContents 有没有内建页内查找 API（含原生高亮与计数）？——**有**：`webContents.findInPage` / `found-in-page` / `stopFindInPage` 三件套，官方 API、无废弃标记，与项目 Electron ^39.2.6 完全匹配（见 2.3 方案 A）。
- [x] 未知点 2：页面聚焦时（焦点在 WebContentsView 内）按 Cmd/Ctrl+F，应用怎么捕获？——复用既有页面侧快捷键通道：manager 的 `before-input-event`（shared 键位表命中即吞键），再仿 focus-address 定向推送唤起 shell 查找栏（见 2.2）。
- [x] 未知点 3：查找栏 UI 放哪？WebContentsView 原生层覆盖内容区，DOM 浮层会被遮挡——**停靠条**：查找栏作为内容区顶部的常驻条插入 chrome-body，内容锚点被压缩后 ResizeObserver 自动重报 bounds、原生 view 自行下移，零新增 bounds 机制（见 2.2 / 2.5）。
- [x] 未知点 4：查找作用域怎么界定（切 Tab / 切会话 / 独立窗口）？——作用域 = 触发窗口的激活 Tab（`getActiveWebContents(windowId)` 既有口径）；切 Tab/切会话关栏清高亮（Chrome 对齐）；独立窗口 shell 与主窗同构、命令经 sender 作用域路由，天然覆盖（见 2.2 / 2.5）。
- [x] 未知点 5：键位表「明确不做」清单里的 Ctrl+F 解禁要动哪些单源文件？——`src/shared/browserShortcuts.ts` 键位表与头注（该文件本就是两侧共用的唯一键位事实源，改动单点）（见 2.2 / 2.5）。

### 1.3 拆分判断

整体作为 1 个调研单元：触发（键位）→ 执行（主进程引擎）→ 计数回传（推送）→ 查找栏 UI（renderer）是一条强耦合链路，横跨三层但每一层都是既有模式的同构复用，一屏内说得清，不拆。

## 2. 调研单元：会话网页内查找（find in page）

### 2.1 该部分要做什么

负责：键位触发（页面聚焦 + shell 聚焦两侧）、查找执行与匹配计数（主进程）、查找栏 UI 与交互（renderer）、生命周期收尾（切 Tab/切会话/关 Tab/导航/关栏时的清理）。

不负责：页面内高亮样式的自定义（Chromium 原生黄/橙高亮，不可换肤——Chrome 本身也是如此）；DevTools 内的查找（DevTools webContents 自带，本功能不触碰）；大小写开关与替换（Chrome 常规查找条即无）；跨 iframe 特殊处理（内建 API 天然覆盖子框架）。

### 2.2 项目现状

- **键位单源**：`src/shared/browserShortcuts.ts` 是页面侧与 shell 侧共用的唯一键位表 + 匹配函数（`matchBrowserShortcut`，字母键要求 ctrl||meta 且无 shift/alt）。其头注第 15 行把「Ctrl+F 页内查找」明确列在**有意不做清单**——本功能即解禁该项，需同步改键位表与头注。modifier 语义平台无关（macOS meta / 其他平台 ctrl），Cmd+F 与 Ctrl+F 天然双覆盖。
- **页面侧快捷键通道**：`src/main/browser/manager.ts:371` 在每个 Tab 的 webContents 上挂 `before-input-event`，命中键位表即吞键并执行动作——新增 `find` 动作在此接线。
- **页面侧 → shell 的动作推送先例**：`manager.ts:177` `requestFocusAddress` + `onFocusAddressRequest` 订阅，`src/main/browser/ipc.ts:96` 经 `windowForId(windowId)` 定向转发 `browser:focus-address`——页面侧 Cmd+F 唤起 shell 查找栏完全同构（新推送 `findRequest`）。`src/main/browser/registry.ts:417` 的 ensureManager 接线含会话归属守卫（主窗要求激活会话相符、独立窗要求绑定会话相符），照抄即可。
- **命令执行口**：`manager.getActiveWebContents(windowId)`（`manager.ts:622`）是 navigate/back/forward/reload/stop 等导航类命令的统一取用口（`ipc.ts:195-242`），`findStart`/`findStop` 同口取激活 Tab 的 webContents，越权防护由 `resolveSenderScope`（`registry.ts:867`，按 `event.sender` 解析窗口作用域）既有承担。
- **主进程事件 → renderer 推送先例**：manager 的 Tab 事件区（`manager.ts:320-367`）挂 `wc.on(...)` 后经监听器集合上抛，ipc 层定向转发——`found-in-page` 结果推送（`findResult`）照此走，推送目标 = 该 Tab 归属窗口 `tab.windowId`。
- **preload 桥**：`src/preload/index.ts` browser 域现 18 条 + 历史 2 条共 20 通道，推送订阅 `onXxx(callback) → 退订函数` 惯例；类型镜像 `src/preload/index.d.ts` 同步维护。renderer 消费入口全部经 `window.api`（分层红线）。
- **renderer 镜像与守卫**：`src/renderer/src/stores/browser.ts`（411 行）是主进程快照的纯镜像，推送守卫按 windowId/sessionId 双校验防过期回填（`browser.ts:252` focusAddress/dragHover 订阅先例）；查找栏瞬态（开合/关键词/计数）属 renderer 本地 UI 态，比照拖拽瞬态的「不进快照契约」先例（`browser.ts:14-19` 注释）处理。
- **shell 侧快捷键**：`src/renderer/src/components/browser/useBrowserShortcuts.ts` 消费同一键位表；已有两条可复用豁免先例——`overlayDepth > 0` 冻结（L46）、`close-devtools` 的 ESC 在地址栏聚焦态放行（L53 `isOmniboxFocused`）。查找栏输入框聚焦时的 ESC 让位照此办理。
- **查找栏落位（关键适配点）**：`BrowserFrame.tsx` 与 `IndependentWindowFrame.tsx` 同构三段（TabStrip + Toolbar + chrome-body）；chrome-body 内是 `BrowserContentAnchor`（`browser/BrowserContentAnchor.tsx`）→ `useBrowserBounds.ts` 以 ResizeObserver + rAF 观察锚点矩形上报主进程。**查找栏以停靠条形式插在锚点上方即可**：锚点高度变化自动触发 bounds 重报，原生 view 随之让位，零新增布局机制。不能走 `ui store overlayDepth` 收起路线（`stores/ui.ts`）——那条路把整页收成零矩形，与「查找时必须看见页面」直接矛盾。
- **红线条目对照**：会话分区隔离不触碰（查找只作用于具体 Tab 的 webContents，不涉分区）；WebContentsView 架构不动（查找栏停靠方案正是对该架构约束的顺应）；一期不引入 Playwright（不涉及）；界面文案全中文（`PRODUCT.md`）。
- **文档事实**：`docs/PRD.md`、`PRODUCT.md`、`DESIGN.md` 经检索均无「查找/find」条目——本功能是 PRD 未覆盖的新需求（是否补录 PRD 见第 4 节）；`DESIGN.md:289` 地址栏建议下拉是查找栏视觉的最近先例（chrome-surface 底 + chrome-line 发丝线 + 8px 圆角无阴影 + 亮暗双 token）。
- **契约纪律**：`src/shared/browser.ts:2-3` 头注要求改通道契约前先修订 `notes/plans/20260913200109-阶段10跨窗口转移与生命周期收尾开发计划.md` 第 3 节——新增 4 条 find 通道属契约扩展，列入实施步骤。
- **版本事实**：`package.json` Electron ^39.2.6 / React ^19.2.1 / antd ^6.6.3 / zustand ^5.0.15——findInPage 家族 API 在 Electron 39 文档中完整存在且无废弃标记（见 2.3 来源）。

### 2.3 候选方案

**方案 A：Electron 内建 findInPage 引擎 + shell 手写查找栏 UI**

- 原理：renderer 发查找命令 → 主进程对触发窗口激活 Tab 的 webContents 调 `findInPage(text, { forward, findNext })`（返回 requestId）；该 webContents 的 `found-in-page` 事件回传 `{ requestId, activeMatchOrdinal, matches, finalUpdate }`，经定向推送更新查找栏计数「3/17」；页面内高亮由 Chromium 原生绘制（普通匹配黄底、当前匹配橙底），应用零自绘；关栏调 `stopFindInPage('clearSelection')` 清除高亮。这正是 Chrome 查找条的同款 Chromium 内建机制——`findInPage` 就是把 Chromium find bar 的引擎暴露给了应用层。
- 来源：
  - 官方 API：https://www.electronjs.org/docs/latest/api/web-contents#contentsfindinpagemetext-options （`found-in-page` 事件与 `stopFindInPage` 在同页相邻条目）
  - 真实用法/IPC 接线问答：https://stackoverflow.com/questions/57100685/
  - 已知上游风险：https://github.com/electron/electron/issues/20602 （findInPage 在特定条件下可冻结应用，2019 年旧 issue，列入冒烟观察）
- 与本项目的适配点：主进程接口恰好挂在既有 `getActiveWebContents(windowId)` 取用口上；计数事件按 Tab 归属窗口定向推送复用 focus-address/dragHover 通道形态；Electron 39 全量支持。

**方案 B：executeJavaScript 注入页面脚本自研引擎（window.find / TreeWalker + 自绘高亮）**

- 原理：向页面注入搜索脚本，遍历 DOM 文本节点做匹配并包裹高亮元素，计数与跳转全自管。
- 来源：`window.find` 为 Chromium 非标准 API（无规范文档）；注入式方案的可靠性讨论见 https://stackoverflow.com/questions/57100685/ 下的对照答案。
- 与本项目的适配点：需向**不可信页面**注入代码——严格 CSP 站点直接失效，页面脚本可探测/篡改注入逻辑，iframe/Shadow DOM/虚拟滚动全要自己扛；与本产品「网页内容不可信」（manager.ts 新建 view 只设分区不放开能力的既有取向）冲突。
- 看过不选：方案 A 内建能力完全覆盖，注入式无任何增量收益。

**方案 C：第三方查找库**

- 原理：引入 npm 库提供查找条组件。
- 来源：检索（WebSearch「Electron findInPage find bar implementation example」）结果全部指向官方内建 API 与教程实现，无针对 WebContentsView 多会话架构的成熟维护库；查找引擎本就是 Electron 内建 API，第三方库至多提供一个 UI 壳。
- 看过不选：UI 壳仅几十行 React（参照 `OmniboxSuggestPanel` 先例），引依赖是负收益；issue #20602 属引擎行为，与库选型无关。

### 2.4 可行性分析

| 维度 | 方案 A（内建引擎 + 手写 UI） | 方案 B（注入自研） |
| --- | --- | --- |
| 技术匹配 | Electron 39 官方 API，无废弃；原生高亮/子框架/计数全内建；计数事件与 UI 解耦，恰好匹配本项目「主进程事实源 + renderer 镜像」架构 | `window.find` 非标准；iframe/Shadow DOM/CSP 全是坑；大页面遍历卡主进程→页面 |
| 规则冲突 | 无：不碰分区红线、不动 WebContentsView 架构、renderer 仍只走 `window.api` 白名单 | 向不可信页面注入脚本，与产品安全取向冲突；主进程 executeJavaScript 也开了一个新的页面控制面 |
| 成本 | 零依赖；约 4 条 IPC 通道 + 1 个组件 + manager/registry/ipc 各一小段接线；上游 issue #20602 列入冒烟 | 引擎完全手写，成本最高且可靠性最差 |

### 2.5 结论与实施建议

- 结论：**采用现成方案**——查找引擎用 Electron 内建 `findInPage` / `found-in-page` / `stopFindInPage`；查找栏 UI 无现成可用件，**借鉴 Chrome 交互手写** React 组件（受 WebContentsView 架构约束做停靠条而非浮层）。一句话理由：这是 Chromium find bar 的官方暴露面，保真度与成本均最优。
- 落地路径（粒度到文件与接口，4 步）：
  1. **shared 契约**：`src/shared/browserShortcuts.ts` 键位表增 `{ id: 'find', key: 'f' }`，头注「明确不做」清单移除 Ctrl+F 条目并注明本期实现；`src/shared/browser.ts` 的 `BROWSER_CHANNELS` 增 4 通道——命令 `findStart`（payload `{ text: string, forward?: boolean, findNext?: boolean }`）与 `findStop`（payload `{ action?: 'clearSelection' | 'keepSelection' }`，缺省 clearSelection），推送 `findRequest`（无 payload，仿 focus-address）与 `findResult`（payload 对齐官方 `found-in-page` 事件的 `{ requestId, activeMatchOrdinal, matches, finalUpdate }`），通道总数 20 → 24；按该文件头注契约纪律先修订阶段 10 计划第 3 节。
  2. **主进程**：`src/main/browser/manager.ts` —— newTab 事件区挂 `wc.on('found-in-page')` 经新 `FindResultListener`（携带 `tab.windowId`）上抛；`before-input-event` 的 switch 增 `find` 动作，经新 `FindRequestListener` 上抛（`requestFindBar(windowId)`，`requestFocusAddress` 同构）；`src/main/browser/registry.ts` ensureManager 接线两类订阅（会话归属守卫照抄 focusAddress 段）；`src/main/browser/ipc.ts` 增 2 个 handler（findStart/findStop 走 `getActiveWebContents(scope.windowId)`，text 非空 + 长度上限守卫）与 2 条推送桥（`windowForId` 定向）。
  3. **preload + renderer 状态**：`src/preload/index.ts` 增 `findStart`/`findStop` 命令与 `onFindRequest`/`onFindResult` 订阅，`src/preload/index.d.ts` 同步；查找栏瞬态（开合/关键词/序号/总数）入 `src/renderer/src/stores/browser.ts`（比照拖拽瞬态「不进快照契约」口径）；store 内订阅快照变化——activeTabId/sessionId 变化即关栏并发 `findStop`（**stop 先于 switch 发出**，保证清的是旧 Tab 的高亮）；`useBrowserShortcuts.ts` 增 `find` 分支（shell 聚焦时直接开栏，免一次主进程往返）+ 查找栏输入聚焦时 ESC 放行（`isOmniboxFocused` 同款豁免）。
  4. **UI 组件**：新增 `src/renderer/src/components/browser/FindBar.tsx`，在 `BrowserFrame.tsx` 与 `IndependentWindowFrame.tsx` 的 chrome-body 内、`BrowserContentAnchor` 上方各插一行（组件自治，随锚点压缩自动让位原生层）；交互全对齐 Chrome——打开即聚焦输入框、输入即搜（findNext 首搜 + 换向跳转）、Enter/Shift+Enter 前后跳、Esc/关闭钮关栏清高亮、计数「n/m」无匹配灰显、关键词清空即清高亮；`findStop` 的主进程语义含清高亮后对目标 webContents `focus()`（焦点归还页面，Chrome 对齐）。**视觉实现走 impeccable 技能**：chrome-surface 底 + chrome-line 发丝线 + 8px 圆角无阴影 + 亮暗双 token（`DESIGN.md` 地址栏建议下拉先例），定稿后 DESIGN.md 补「页内查找条」条目。
- 验证建议（延续仓库惯例）：typecheck/lint/build 全绿 + 隔离实例 CDP 冒烟（计数到达/换向/关栏清高亮/切 Tab 关栏/切会话关栏/独立窗同链路）+ CDP UI 级真键验证（页面聚焦态 Cmd+F、shell 聚焦态 Cmd+F、大页面查找观察 #20602 类卡顿）。

## 3. 风险与开放问题

- 上游已知问题 electron/electron#20602：`findInPage` 在特定条件下可能冻结应用（2019 年旧 issue，复现条件未明）。缓解：验收冒烟加超大页面查找项；行为属引擎内部，应用层无规避手段。
- Chromium 原生高亮配色固定（黄底/橙底），与本应用灰阶设计语言不一致——这是 Chrome 自身行为，对齐 Chrome 即接受，不自绘高亮。
- 停靠条使页面 reflow（内容区高度减约 36px）——与 Chrome 浮层形态的可见差异，是 WebContentsView 架构下 DOM 层无法浮于原生 view 之上的固有取舍（与 `DESIGN.md:289` 面板收起原生层同源约束的另一种解）。
- HTML 全屏（如视频全屏）期间原生 view 独占窗口，查找栏不可达——Chrome 全屏下同样不可用，接受不处理。
- 页面聚焦 + 查找栏开着时按 ESC：MVP 只在查找栏聚焦态处理（shell 键盘事件可达）；若要页面聚焦态也 ESC 关栏，需 manager 记每窗口查找开关态，列为可选增强不在本期。
- PRD 无此功能条目：需求超出现有 PRD 覆盖，是否补录 PRD 由用户裁决（AGENTS.md 以 PRD 为需求唯一依据）。

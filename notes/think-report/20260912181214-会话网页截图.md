# 会话网页整页截图保存 功能调研报告

> 创建时间：2026-09-12 18:12（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户原话要点——把当前会话正在浏览的网页整页截图，保存到本地选定目录，方便写测试报告时贴图；不清楚 Electron 里该怎么实现
> 调研单元：2 个
> 状态：调研完成，待用户确认（未实施）

## 1. 需求理解

### 1.1 功能目标

测试人员撰写测试报告时需要把"当前会话正在浏览的页面"截成图片贴进报告，目前只能用系统截屏工具手动框选，效率低且截不到视口外的内容。本功能要在应用内提供一条路径：对当前激活会话的当前页面执行截图，图片落到用户选定的本地目录。用户是专业测试人员（效率优先、不做引导式设计）；页面必须来自会话强绑定的真实 webContents（含该会话登录态的渲染结果），不能用独立无头浏览器另开一份。

对应 PRD 定位：本功能即 PRD 3.5"测试辅助扩展功能（二期迭代）"中的"网页截图：快速截取当前会话页面，绑定会话备注"（docs/PRD.md），与 notes/steps/step-07-测试辅助功能二期.md、PRODUCT.md"二期规划（未实现，不要提前做）"三处一致。本次只做调研，不实现；实现排期见"待确认假设"。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 未知点 1：Electron 有没有官方的页面截图 API？——有，`webContents.capturePage()`，但只能截"整个可视区"（结论见单元 1 方案 A）
- [x] 未知点 2："整页"（超出视口的可滚动部分）能否截到？靠什么机制？——原生 capturePage 截不到（官方 issue 证实），须走 Chrome DevTools Protocol 的 `Page.captureScreenshot` + `captureBeyondViewport`（见单元 1 方案 B 与 2.4）
- [x] 未知点 3：图片如何落到用户选定的本地目录？——主进程 `dialog.showSaveDialog`（或选目录方案）+ `fs.writeFile`，全部官方 API（见单元 2）
- [x] 未知点 4：截图发生在"会话强绑定"架构里，会不会破坏会话隔离或 DevTools 绑定？——不会：只读取当前激活 webContents 的像素输出，不触碰分区与 DevTools 实例；与 DevTools 同开的交互时序列入风险（见第 3 节）
- [x] 未知点 5：有没有现成 npm 库可直接装？——没有适配"既有分区会话"的库，候选均已排除（见单元 1 方案 C"看过不选"）

### 1.3 拆分判断

拆为 2 个调研单元：

| 单元 | 内容 | 依赖 |
| --- | --- | --- |
| 单元 1 | 会话页面截图捕获（视口档 + 整页档的技术选型） | 独立 |
| 单元 2 | 截图落盘到用户选定目录（保存交互 + UI 入口） | 依赖单元 1 的产物形式（PNG 数据从哪来） |

拆分理由：截图捕获是本次唯一有真实技术选型之争的部分（三个候选互斥）；落盘与入口是另一个能力点，选型（保存对话框 vs 固定目录）不随捕获方案变化，仅依赖捕获产物是图片 Buffer 这一事实。

## 2. 调研单元 1：会话页面截图捕获

### 2.1 该部分要做什么

负责：从当前激活会话、当前激活 Tab 的 webContents 拿到页面位图（PNG 数据），支持两档——"当前可视区"与"整页（完整可滚动文档）"。不负责：文件保存交互、UI 入口（单元 2）；不给后台会话截图。

### 2.2 项目现状

- 接入点现成：`src/main/browser/manager.ts` 的 `TabManager.getActiveWebContents()`（返回激活 Tab 的 `WebContents`，无激活 Tab 返回 null），注册表层 `src/main/browser/registry.ts` 已将命令面统一路由到当前激活会话的同名方法——截图调用可直接复用这条取用口，无需新暴露 view 引用。
- 每 Tab 一个 `WebContentsView`，分区由 registry 注入 `persist:sess-<id>`（`src/main/browser/registry.ts` `partitionFor()`，一会话一分区）；截图读的是该 webContents 的渲染输出，天然带会话登录态，且不触碰分区数据，不违反隔离红线。
- DevTools 是"原生受管"模式：`src/main/browser/manager.ts` `openTabDevTools()` 直接 `wc.openDevTools()`，DevTools 随页面 webContents 生命周期走——截图方案不得引入第二个调试宿主（与 DESIGN.md"原生 DevTools"条目的定案一致）。
- 共享契约惯例：IPC 通道名一律收口在 `src/shared/browser.ts` 的 `BROWSER_CHANNELS`；该文件头注释要求改动前先修订 `notes/plans/20260911191316-阶段4多会话浏览器绑定开发计划.md` 第 3 节。
- 版本事实：`package.json` 锁 Electron ^39.2.6，实际安装 39.8.10（node_modules/electron/package.json）。本地 `node_modules/electron/electron.d.ts` 已核实（下述 API 签名均出自该文件，行号为当时快照）：
  - `capturePage(rect?, opts?): Promise<NativeImage>`（5309 行），注释明确"Omitting rect will capture the whole visible page. If the page is not visible, rect may be empty"；
  - `Debugger` 类（7339 行）含 `attach(protocolVersion?)`（7453 行）、`sendCommand(method, params?, sessionId?): Promise<any>`（7469 行）、`isAttached()`、`detach()`；`detach` 事件注释："happens either when webContents is closed or devtools is invoked for the attached webContents"。
- 红线对照：本单元不引入 Playwright（AGENTS.md 坑点：一期不使用）、不动 BrowserView（现实现已是 WebContentsView）、不注入 DevTools——无触碰。

### 2.3 候选方案

**方案 A：`webContents.capturePage()` 官方截图 API（仅可视区）**

- 原理：对激活 webContents 调 `capturePage()`，返回 `NativeImage`，再 `toPNG()` 得 Buffer。零依赖、调用一步。
- 来源：<https://electronjs.org/docs/latest/api/web-contents>（capturePage 小节）；版本匹配以本地 electron.d.ts 39.8.10 为准。
- 局限（官方与社区一致证实）：只截"whole visible page"，页面超出视口的部分截不到——electron/electron#8587 <https://github.com/electron/electron/issues/8587>、#4417 <https://github.com/electron/electron/issues/4417>、#17834 <https://github.com/electron/electron/issues/17834>。
- 与本项目适配：接入点是 `getActiveWebContents()`，签名与 Electron 39 匹配，零成本。但用户需求原话是"整页截图"，本方案不覆盖未知点 2。

**方案 B：`webContents.debugger` + Chrome DevTools Protocol `Page.captureScreenshot`（整页）**

- 原理：在激活 webContents 的 `debugger` 上 attach CDP 1.3，先 `Page.getLayoutMetrics` 取 `cssContentSize`（页面完整可滚动尺寸），再 `Page.captureScreenshot({ format: 'png', clip, captureBeyondViewport: true })`，返回 base64 PNG——这正是 Chrome DevTools 面板里"Capture full size screenshot"按钮的底层机制。调用序列示意（说明可行性，非实现代码）：

  ```ts
  wc.debugger.attach('1.3')
  const { cssContentSize } = await wc.debugger.sendCommand('Page.getLayoutMetrics')
  const { data } = await wc.debugger.sendCommand('Page.captureScreenshot', {
    format: 'png', clip: { x: 0, y: 0, ...cssContentSize, scale: 1 },
    captureBeyondViewport: true
  })
  ```

- 来源：CDP 官方文档 <https://chromedevtools.github.io/devtools-protocol/1-3/Page/#method-captureScreenshot>（已核实参数 `format`/`quality`/`clip`/`fromSurface`/`captureBeyondViewport`，返回 base64 `data`；`Page.getLayoutMetrics` 返回 `contentSize`——已标注 Deprecated、推荐 `cssContentSize`）；Electron Debugger API <https://electronjs.org/docs/api/debugger>；机制同源性佐证：Chrome 官方博客"4 ways to capture screenshots with DevTools" <https://developer.chrome.com/blog/devtools-tips-33>、captureBeyondViewport 机制解析 <https://screenshotone.com/blog/capture-beyond-viewport-in-puppeteer-and-chrome-devtools-protocol/>。
- 已知坑：截图尺寸超过 8192 物理像素时 Chromium 输出损坏（重复左上角内容），官方 issue <https://issues.chromium.org/40724721>；DevTools 打开/关闭与 debugger 附加存在交互（d.ts detach 事件注释、源码 <https://github.com/electron/electron/blob/master/shell/browser/api/electron_api_debugger.cc> 中 "Debugger is already attached to the target" 抛错），实现须按"按需 attach、用完即 detach、失败 catch"处理，详见第 3 节。
- 与本项目适配：`webContents.debugger` 是 Electron 内置能力（39.8.10 类型在档），零第三方依赖；作用于激活 Tab 的 webContents，不碰分区、不另建调试宿主，与 DevTools 强绑定规则不冲突。

**方案 C（看过、不采用）**

- `printToPDF`：能整页输出但产物是 PDF，不满足"贴图"场景；如未来要"长页留档"可作降级备选（同一 web-contents 文档页：<https://electronjs.org/docs/latest/api/web-contents>）。
- 外部无头方案（Playwright / Puppeteer / pageres 类）：需要另起浏览器实例加载同一 URL——拿不到 `persist:sess-<id>` 分区里的登录态，截图不是用户看到的会话页面；且 AGENTS.md 坑点明确一期不引入 Playwright。直接否掉。
- npm 现成库：`electron-screenshots` 类是"桌面截屏/贴图"工具（截的是屏幕，不是网页整页）；`capture-electron` 等是起独立 Electron 实例截 URL，不带本应用会话分区且多年未维护。均不满足，看过不选。

### 2.4 可行性分析

| 维度 | 方案 A（capturePage 视口档） | 方案 B（debugger + CDP 整页档） |
| --- | --- | --- |
| 技术匹配 | Electron 39.8.10 在档，签名已核实；但只截可视区，不覆盖"整页"需求原文；页面不可见（悬挂收起/遮挡）时可能拿到空图（d.ts 注释明示） | Electron 39.8.10 内置 debugger，CDP 1.3 为稳定协议版本；`captureBeyondViewport` 覆盖整页；边界坑有二——超 8192 物理像素损坏（Chromium issue）、与 DevTools 同开的 attach/detach 时序，均可工程化处理 |
| 规则冲突 | 无（官方 API，读渲染输出） | 无：不碰分区、不引入 Playwright、不建第二个调试宿主；attach 是 Chromium 对该 webContents 的官方调试通道，与"DevTools 挂在具体 webContents 上"的规则同源而非违背 |
| 成本 | 零依赖、一行调用 | 零新依赖（内置模块）；代码量为一段 API 编排（attach→取布局→截图→detach，约十余行）+ 异常处理；无许可证/维护负担（Chromium 内建能力） |

### 2.5 结论与实施建议

- 结论：**采用现成方案**——全部由官方 API 直接覆盖，零第三方依赖：整页档用 Electron 内置 `webContents.debugger` + CDP `Page.captureScreenshot`（`captureBeyondViewport: true`），视口档用 `webContents.capturePage()`。没有可直接安装的第三方库能带上本产品的会话分区，而整页能力是 Chromium 官方协议参数，不需要任何自研渲染/拼接逻辑，故不归"借鉴/完全手写"。两档并存的理由：可视区档快且无 debugger 交互成本，适合报告贴图的高频日常；整页档覆盖需求原话。
- 落地路径（粒度到文件与接口，不写实现）：
  1. `src/shared/browser.ts`：`BROWSER_CHANNELS` 新增 `capturePage: 'browser:capture-page'`；新增捕获档位参数（`viewport` / `fullPage`）与结果类型（保存成功路径 / 用户取消）；按该文件头注释要求，先修订 `notes/plans/20260911191316-阶段4多会话浏览器绑定开发计划.md` 第 3 节契约。
  2. `src/main/browser/manager.ts`：`TabManager` 新增捕获方法：经 `getActiveWebContents()` 取激活 webContents，按档位执行方案 A / 方案 B，返回 PNG Buffer；整页档含"attach 前查 `isAttached()`、用完 `detach()`、attach 抛错转中文错误、超 8192px 检测告警"。
  3. `src/main/browser/registry.ts`：零改动（命令面经既有 `getActiveWebContents` 路由已够用）。

## 3. 调研单元 2：截图落盘到用户选定目录（含 UI 入口）

### 3.1 该部分要做什么

负责：把单元 1 产出的 PNG 数据写到用户指定的本地位置，并在浏览器工具栏提供截图入口；向用户反馈保存结果。不负责：位图捕获本身（单元 1）。

### 3.2 项目现状

- 分层规则：主进程自由使用 Node API（AGENTS.md），文件写入与目录选择必须放主进程；renderer 禁碰 Node，一切经 `src/preload/index.ts` 暴露的 `window.api`——该文件已是 `browser` 命名空间白名单桥模式（14 条通道先例），同步维护 `src/preload/index.d.ts` 是 AGENTS.md 明文要求。
- IPC handler 惯例：`src/main/browser/ipc.ts` 统一注册，通道名取自 `BROWSER_CHANNELS`，入参先过运行时守卫，`requireActiveSession()` 守卫拒绝零会话空态（截图入口应复用同款守卫），错误文案中文。
- 会话元数据可用于默认文件名：`src/main/store.ts` 落盘的 sessions.json 含会话名/账号备注（PRD 3.5"绑定会话备注"的素材来源）；激活 Tab 的 url/title 在 `BrowserSnapshot`（`src/shared/browser.ts`）里现成。
- UI 入口惯例：`src/renderer/src/components/browser/Toolbar.tsx` 已有按钮带与禁用链（`!activeTab`、`sessionId === null` 时禁用，DevTools 开关按钮即先例）；DESIGN.md 规定右侧 Chrome 语系图标一律 `@ant-design/icons`（有 `CameraOutlined`）、琥珀不进右侧、无阴影；状态反馈走 antd（`App.useApp()` 承载 message 等）。
- 保存对话框 API 已核实：`dialog.showSaveDialog(window, options)` / `showOpenDialog` 均在 39.8.10 类型（electron.d.ts 7656/7752 行，`SaveDialogOptions` 含 `defaultPath`/`filters`/`properties`），官方文档 <https://electronjs.org/docs/latest/api/dialog>。

### 3.3 候选方案

**方案 A：`dialog.showSaveDialog` 保存文件对话框（每次选目录与文件名）**

- 原理：主进程拿到 PNG 后弹系统保存对话框（`defaultPath` 预填"会话名-页面标题-时间戳.png"、`filters` 限 PNG），用户确认后 `fs.writeFile` 落盘。与 Chrome"下载/另存为"心智一致。
- 来源：<https://electronjs.org/docs/latest/api/dialog#dialogshowsavedialogbrowserwindow-options>
- 与本项目的适配点：主进程一条 handler 串联（守卫→捕获→对话框→写入），返回"已保存路径/取消"给 renderer 反馈；用户每次可控位置，符合"保存到本地选定目录"原话。

**方案 B：`dialog.showOpenDialog({ properties: ['openDirectory'] })` 选定报告目录 + 应用自动命名**

- 原理：用户一次性选定报告目录，此后截图静默落盘该目录（文件名自动生成），免每次弹窗；目录需持久化记忆。
- 来源：<https://electronjs.org/docs/latest/api/dialog#dialogshowopendialogbrowserwindow-options>
- 与本项目的适配点：高频连截场景更顺，但需要新增"偏好目录"的持久化（现应用偏好只有外观三模式一处先例，见 `src/main/appearance.ts` + `src/shared/appearance.ts`），复杂度高于方案 A；且 PRD 3.5 原文"绑定会话备注"的显式确认感更强。

**方案 C（看过、不选）**：renderer 侧 `<a download>` 或 data URL 下载——绕道临时文件/编码，且把文件语义泄漏进 renderer 层，违反分层惯例；主进程 Save Dialog 就是 Chrome 惯例本身。

### 3.4 可行性分析

| 维度 | 方案 A（保存对话框） | 方案 B（固定目录自动命名） |
| --- | --- | --- |
| 技术匹配 | 官方 API，39.8.10 在档；覆盖"选定目录"原话；每次确认防误存 | 覆盖高频连截；但需新增偏好持久化与目录失效处理（目录被删） |
| 规则冲突 | 无（主进程承担文件 IO，renderer 只收结果） | 无硬冲突；偏好文件需与 sessions.json/分区数据独立读写（对齐 PRD 4.4 外观偏好的隔离惯例） |
| 成本 | 一条 IPC handler + 一次对话框调用，最小实现 | 多一套偏好存储与设置入口；维护面更大 |

### 3.5 结论与实施建议

- 结论：**采用现成方案**——`dialog.showSaveDialog` + `fs.writeFile` 官方 API 组合，直接满足"保存到本地选定目录"；方案 B 留作二期高频连截的后续增强（若用户确认需要"固定报告目录"，见待确认假设 4）。
- 落地路径（接单元 1 的 1—2 步之后）：
  1. `src/main/browser/ipc.ts`：注册 `browser:capture-page` handler：`requireActiveSession` 守卫 → manager 捕获得 PNG → `dialog.showSaveDialog(主窗口, { title: '保存网页截图', defaultPath: 会话名-标题-时间戳.png, filters: [{ name: 'PNG 图片', extensions: ['png'] }] })` → `fs.writeFile` → 返回结果（成功路径/取消）；失败走既有 `logFailure` 链路，文案中文。
  2. `src/preload/index.ts` 与 `src/preload/index.d.ts`：`api.browser.capturePage(...)` 白名单方法与类型，对齐既有 `browser` 命名空间模式。
  3. `src/renderer/src/stores/browser.ts`：新增 capturePage action（不乐观更新，结果回传组件）。
  4. `src/renderer/src/components/browser/Toolbar.tsx`：工具栏新增截图按钮（`CameraOutlined`，禁用链随 `!activeTab`，中文 `aria-label`/title），保存成功/取消反馈用 antd message；视觉与反馈样式实现时走 impeccable 技能（polish 路径），遵守 DESIGN.md 约束。
  5. 实施顺序：shared 契约 → manager 捕获能力（冒烟：视口档/整页档/DevTools 同开/超长页）→ ipc + 对话框 + 落盘 → preload/renderer 入口。

## 4. 风险与开放问题

- **超长页截图损坏**：CDP `Page.captureScreenshot` 产出超过 8192 物理像素时，超出部分重复左上角内容（<https://issues.chromium.org/40724721>）。整页档必须按 `cssContentSize` × devicePixelRatio 预检，超限时明确告警并降级（仅视口档或提示改用打印为 PDF），不可静默出坏图。
- **与 DevTools 同开的时序**：本产品 F12 DevTools 是核心高频功能。d.ts 文档注明 DevTools 被唤起会使已附加的 debugger detach，attach 自身也可能因占用抛错（源码 "Debugger is already attached to the target"）。实现须"按需 attach、用完即 detach、监听 detach 防悬挂、attach 失败给中文错误"，并把"DevTools 开启状态下整页截图"列为必测冒烟项。
- **空图边界**：页面不可见时 `capturePage` 可能返回空图（d.ts 注释）。本产品存在"弹层悬挂收起 view（零矩形）"的既有机制（manager `suspended` 态），视口档在该态下应拒绝并提示；CDP 整页档 `fromSurface` 不依赖窗口遮挡，具体以冒烟为准。
- **竞态**：截图 await 期间会话被删除/切换/克隆（registry 已有 `cloningIds` 守卫与 dispose 机制先例），捕获前后须复核 webContents 存活与会话激活态。
- **DPR 差异**：保存的 PNG 是物理像素尺寸（Retina 下放大一倍），不影响贴图使用，但与视口 CSS 尺寸不一致，属如实行为，文档说明即可。
- **归期冲突（开放问题）**：本功能在 PRD 3.5 / step-07 / PRODUCT.md 三处均定为二期且明言"不要提前做"。本次仅产出调研；何时实现（现在实现 vs 留待二期排期）必须由用户拍板，见待确认假设 5。
- **后续开放问题**：批量场景（多个会话已批量打开同一测试地址后"逐会话整页截图"）与本需求相邻但超出本次范围，未调研。

## 1. 地址栏残留复现结论

### 1.1 复现成功的残留路径（两条）

**S1 未提交草稿残留（FAIL→确认为缺陷）**：会话 1 地址栏输入「残留草稿测试example」不提交，DOM click 新建会话（不触发 blur 的切换路径）→ 新会话地址栏 value 仍为旧草稿，焦点仍在输入框。根因：`Toolbar.tsx` 的 `draft` 状态无 `(sessionId, activeTabId)` 归属，组件跨会话复用时不清除。

**S2 已提交待导航残留 + 粘滞（FAIL→确认为缺陷，真实用户点击路径必现）**：会话 about:blank Tab 提交 `http://127.0.0.1:48191/slow`（5s 慢页）→ 120ms 内新建会话 → 新会话地址栏显示旧会话的待导航文本；等慢页落地后 A/B/A 往返切换，残留**始终存在**（`pending` 永不过期）。根因链：
- Tab id 为每会话独立计数器（`manager.ts` `tab-${seq}`），**新会话首 Tab 与旧会话 Tab 同名 `tab-1`**；
- `pending` 判据 `pending.tabId === activeTabId && pending.baselineUrl === mainUrl` 无会话维度——新会话首 Tab 同名 + 同为空 URL 基线即命中；
- blur 只清 `draft` 不清 `pending`，故真实鼠标点击新建按钮同样触发。

**S3b 主页场景残留永久粘滞（FAIL）**：配置主页后上述残留从「瞬态」变「永久」——新会话首 Tab 的 URL 恒等于主页 URL，与旧会话提交时的 `baselineUrl`（主页会话内再次提交）持续匹配。

### 1.2 排除项与对照（PASS）

- **S3 主页语义正常**：配置主页 `http://127.0.0.1:48191/instant-home` 后新建会话，落地后地址栏显示该会话自己的主页 URL（PASS）；主页留空时新会话地址栏为空（新建空白 Tab 推 focus-address 聚焦，代码链路成立）。

- **重挂载假设排除（diag3）**：输入框节点身份标记跨会话创建保持同一节点——残留非组件重挂载所致。

## 2. Cookie 源侧读取与 Mac 解密验证

### 2.1 源库事实（Chrome 156，独立测试 profile，干净退出后读取）

- **库位置**：`<profile>/Default/Cookies`（本机 Chrome 156 无 `Network/` 子目录；引擎探测须兼容两种布局）。schema：`meta.version = 24`（`last_compatible_version` 同为 24）。
- **列清单**：`creation_utc, host_key, top_frame_site_key, name, value, encrypted_value, path, expires_utc, is_secure, is_httponly, last_access_utc, has_expires, is_persistent, priority, samesite, source_scheme, source_port, last_update_utc, source_type, has_cross_site_ancestor`。
- **时间戳为 1601 元年微秒**，超 JS 安全整数——`node:sqlite` 直读抛 `ERR_OUT_OF_RANGE`，须 BigInt/CAST 处理（与 `historySource.ts` readBigInts 同坑）。
- **属性编码实测**：`samesite`：-1 未指定 / 1 Lax / 2 Strict；`source_scheme`：1 NonSecure / 2 Secure；host-only 记录 `host_key` 无前导点、domain 记录带前导点（`.msbtest.example`）；同名不同 path 两行并存。
- **Mac 全量加密**：植入的 6 条 Cookie `value` 列全部为空、`encrypted_value` 全部带 `v10` 前缀（hex `763130`）——**真实 Mac Chrome 无明文 Cookie 记录**，「有效明文」分支为兼容保留路径。

### 2.2 密文结构与解密算法（自造 v10 往返正例；结构已于 2026-10-28 晚修正）

**结构（修正后定案，三重独立证据）**：`v10(3B) + AES-128-CBC(明文, 固定 IV) 整段密文`，其中**明文 = SHA-256(host_key) 前 32B ‖ cookie 值**——不存在尾部 HMAC（初版误判的「尾 32B」实为域名哈希头在长度阶梯上的投影）。证据：①长度阶梯——值 1..15→密文 48B、16..31→64B、32..47→80B、48→96B，与「32B 哈希 + 值」的 PKCS7 阶梯逐级吻合（若结构为 ct+32B 尾则阶梯应为每 16 字符级差 16 的 ct + 恒 32，与「值 16→64」观测不符）；②同值同 host 两次加密密文逐字节全同（确定性、固定 IV、无随机盐）；③同值异 host 三枚密文互不相同（明文含 host 依赖成分）；④chromium-safestorage 公开实现佐证（"Newer Chromium prepends a 32-byte SHA-256(host_key) domain hash to the plaintext"）。派生（Chromium os_crypt，源码 v156 tag 核对）：PBKDF2-HMAC-SHA1（口令 = 钥匙串 Chrome Safe Storage 条目**原始字节**——不必然为文本，任何按 UTF-8 文本解码/编码的中转会损坏密钥材料；盐 `saltysalt`，1003 轮，16B 密钥），IV = 16 × 0x20，解密后前 32B 与 SHA-256(host_key) 比对不符即判失败（内置自校验）。

- 往返 6 例全过（空串/1 字符/中文/31 字符/植入样本值）；
- **结构与真实库逐字节对齐**：11 字符明文 → 51B（=3+16+32）、21 字符 → 67B（=3+32+32），与 Chrome 156 库中实测长度一致（Node webcrypto 自带 PKCS7，勿手工预填充——双重 padding 是本轮踩过的实现坑）。

### 2.3 解密正例（浏览器自身闭环）与授权反例

- **正例（重启解密回读）**：测试 Chrome 干净退出（库中 6 条 v10 密文）→ 重启 → CDP `Network.getCookies`（带 urls）回读，**HttpOnly / Secure+Strict / domain / 双 path / 中文值的明文全部与植入值一致**——证明「磁盘 v10 密文 + Keychain 密钥 → 正确明文」链路成立。注意 `Storage.getCookies`（无 urls）会漏报，不能作为回读探针。
- **反例（授权拒绝/未处理）**：本进程 `security find-generic-password -w -a Chrome -s "Chrome Safe Storage"` 触发系统授权弹窗，25s 无人处理超时——如实记录为授权拒绝路径证据（后经用户在场点击授权验证弹窗可正常渲染）。
- **真实密钥解密正例（2026-10-28 晚定案，原「待操作」项闭环）**：经用户批准取得钥匙串口令（24 字节纯 ASCII），以修正后结构（§2.2 明文 = SHA-256(host_key)32B + 值）+ 源码口径派生（PBKDF2-HMAC-SHA1/saltysalt/1003/16B）对**用户终端 Chrome 现场加密的新鲜密文与 Zcode 环境加密的冻结密文**共 12 个样本矩阵验证：**12/12 域名哈希校验通过、明文逐字还原**（含同值异 host 对照组各自通过）。根因定案：初版全不中系密文结构误判（把明文头部的域名哈希误判为尾部 HMAC），口令与派生口径从头正确。

### 2.4 会话 Cookie 落盘事实

运行期与会话 Cookie **会写入库**（`is_persistent=0`、`has_expires=0` 但行存在）；干净退出后立即读库仍存在；**下次启动被清除**（重启后 6 行 → 5 行）。「仅导入源快照中实际存在者」的语义成立：对干净退出的源库做快照可取到退出时点的会话 Cookie。

## 3. IndexedDB 文件快照验证

### 3.1 源布局事实（Chrome 156，双源种子：127.0.0.1 与 localhost 同端口）

- 站点快照单位 = **成对目录**：`<origin>.indexeddb.leveldb/`（CURRENT/LOCK/LOG/LOG.old/MANIFEST-000001/000003.log）+ `<origin>.indexeddb.blob/<N>/<nn>/<file>`（Blob 落盘嵌套编号路径，实测 `1/00/2`）。只复制 `.leveldb` 不完整。
- Chrome 156 仍以 **LevelDB** 为默认后端（SQLite 后端迁移进行中，chromestatus 2026-04；不能把 LevelDB 布局当长期接口，think-report 判断获佐证）。
- 种子数据含 2 对象仓库 + 2 索引 + Date/Blob/ArrayBuffer/嵌套对象，页内校验全过。

### 3.2 兼容性边界（本步骤最重要的负结论，字节级证据）

**Chrome 156 → Electron 39（Chromium 142.0.7444.265）不兼容，且 142 对不兼容库静默重置**：

- 同一分区、同一目录、同一 MANIFEST（逐字节相同）下：142 自写库可读；Chrome 156 快照拷入后页面 `indexedDB.open()` 得到**空库**（NotFoundError），且 6124B 的 WAL 被重写为 218B 空库日志——数据被静默蒸发，无任何错误 surfaced（leveldb LOG 仅 "Creating DB / Reusing MANIFEST" 两行）。
- 差异定位（手工解码 WAL，LevelDB 记录格式 + WriteBatch）：全局元数据键 `00 00 00 00 02` 的 schema version——**142 写 15（0x0f），Chrome 156 写 16（0x10）**；且**每条 IDB 值信封**尾部版本标记 `ff 0f`（142）vs `ff 10`（156），156 与 142 的记录集还有结构性差异（142 有一族 protobuf 编码记录为 156 所无）。
- 诊断性单点补丁（仅改全局 schema version 16→15 并重算记录 CRC32C）**不足以**救活——值信封逐条携带版本，逐值改写即原始记录拼接，计划 2.2 明令不做。
- **结论：文件快照导入必须按 schema 版本门禁**。源 schema version ≤ 目标 Chromium 支持版本方可导入；更高版本如实报「不支持（源版本过新）」。本机用户真实 Chrome 156 的 IndexedDB 在 Electron 39 上即属不支持，待应用未来升级 Electron 后自然放开。

### 3.3 正例（同代源，v15/142 世代）

- **空目标导入**：142 自写源快照（2 用户/2 索引/3 仓库/版本 2）拷入新会话分区 → 页面读取 userCount=2、idxByName=2、version=2、**Blob 字节逐位一致**（`0,3,6,9,12,15,18,21`）、ArrayBuffer 10B、Date ISO 保真——PASS。
- **续写**：导入库上 `put` 新记录成功（count 3）。
- **重启持久（T3）**：导入 + 续写标记后重启应用 → 同会话读取数据完整、标记值逐字恢复——PASS。
- **已有目标整快照替换**：目标侧先种含 `id=99` 标记的库 → 备份 → rm+cp 换入源快照 → 读取 userCount=2 且标记 absent（目标专有数据按「整份替换」语义移除）、源 Blob 保真——PASS；**回滚**：恢复备份后 userCount=3 标记回归——PASS。
- **句柄释放**：页面导航离开（不销毁 webContents）约 3s 后 `rm -rf` 站点目录无 EBUSY——runImportQuiesced 的静默窗口 + 短等待足以替换文件。
- **邻站隔离**：同分区再导入 localhost 源快照，两站点库互不影响——PASS。
- **损坏样本行为**：MANIFEST 截断后 142 页面报 NotFoundError 并重建空库——佐证「不预校验就导入 = 数据静默丢失」。

### 3.4 对步骤 5 的硬性设计输入

1. **预校验必须自实现**：classic-level 打不开 IDB 库（MANIFEST 声明比较器 `idb_cmp1`，classic-level 仅支持 bytewise——实测报错）。预校验须手工读 WAL（LevelDB 记录格式解码，本轮已验证可行）提取 schema version 键 `00 00 00 00 02`，并与目标支持版本比对；不匹配整站点拒绝，**绝不可拷入后让 Chromium 自行打开**（静默重置风险）。
2. 快照单位 = `.leveldb + .blob` 成对目录；路径由受控清单生成，拒绝逃逸/符号链接。
3. 写入流程：备份目标成对目录 → rm → cp → 校验；失败恢复备份；类型内不留半次提交。
4. 版本判定按**字节**而非 Chrome 版本号映射（156 只是本机实测值；引入 schema 16 的具体 Chrome 版本未考证）。
5. QuotaManager 未参与也未被需要（导入/续写/重启均正常）——维持不复制 QuotaManager 的计划红线。

## 五、执行期发现与处理

1. **Chromium find 瞬时假阴性**（引擎级，非本实现缺陷）：实验证实同一加载完成的页面，findInPage 首搜偶发 0 命中、稍后同参重搜全量命中。处理：renderer 在 finalUpdate 且 0 命中收尾时，同 query 自动重发一次初搜（有界、诚实——重搜仍 0 如实显 0/0）；真实无匹配场景行为不变。
2. 测试支架两处缺陷（会话行点选顺序、omnibox 残留草稿追加 URL）已修正，均非应用缺陷。
3. **真实站点补充验证（2026-09-14 18:1x，用户反馈「百度/知乎/自研项目没用」后的排查结论）**：用户报障时段与本专项的调试进程严重冲突——调试用 pkill 按模式误杀了用户正开着的实例（反复强制重启），且其实例尚 running 无重搜兜底的旧代码；另发现 CDP 合成 Cmd+A 在本应用内不产生全选、导致测试支架把多条 URL 追加拼接（garbage URL → 搜索词 legitimately 0 命中），多轮「复现失败」均属环境/支架污染。清理全部调试进程后以单一干净实例（应用自身 navigate 路径 + 真实按键）复验：**example.org 搜 Example = 1/2、百度首页搜 百度 = 1/4、本地文件页搜 findme = 1/8，全部通过**；「新闻」0/0 为该页面真实无此词（如实显示）。知乎未单独复验（与百度同类的动态 https 站点，机制已覆盖），用户重启动实例后可自测。
4. **二次 Cmd+F 全选但不聚焦（2026-09-14 18:22 用户报障，已修复）**：根因是 Chromium 焦点控制的跨 webContents 约束——页面 webContents 持有原生键盘焦点时，shell 渲染层 `input.focus()` 抢不回焦点（select() 仍生效，故「全选但打字进不去」）。第一次正常是因为经地址栏导航后焦点本就在 shell；Esc 关栏时 findStop 把焦点归还页面，二次 Cmd+F 起点即页面持焦，必现。修复：ipc.ts 的 findRequest 与 focusAddress 两处推送桥在 send 前由主进程 `win.webContents.focus()` 把宿主窗口焦点交还 shell（后者系同款潜伏问题一并修复）。验证（9223 隔离实例，真实焦点转移路径）：第一次 Cmd+F 开栏聚焦计数 OK → Esc 后确认 shell 失焦 → 从页面 target 发 Cmd+F → 查找框聚焦 true + 选区 6/6 + 真实按键 z 替换全选 value='z' → 页面持焦 Cmd+L 地址栏聚焦 true，5/5 PASS；typecheck/lint 复跑全绿。

### 2.3 竞态条件

结论：发现 4 个问题（高-1、中-1、中-2、中-3）。

- [ ] **[高]** check-proxy 探测的 finally 恢复覆盖并发落地的代理应用，引擎幂等守卫掩盖分歧
  - 位置：`src/main/browser/proxy.ts:236-266`（probeOnSession；:243 捕获 prev、:249-256 finally 无条件按捕获值恢复）
  - 描述：probeOnSession 在探测开始时捕获 `prev = applied.get(id)`，finally 恢复**不复查**该分区当前登记值。探测窗口（最长 8s）内任何并发完成的 applySessionProxy 都会被回写覆盖，而 `applied` 表已登记新值，此后一切幂等路径（激活链 applyProxyFromStore、下次 set-proxy 同值）都因 sameProxy 判等**跳过重放**——分歧无法自愈，直到配置再变更或重启。两条现实触发路径：① sheet 内先点「检测」再点「保存/清除」（保存钮检测中不禁用，`WorkspacePickerWindow.tsx:597-598` 仅 `disabled={!normalizedProxy}`）：pick → set-proxy 落盘 N → applySessionProxy(N) 生效后，探测 finally 把分区恢复为旧值 O——落盘 N / 引擎登记 N / 分区生效 O；② 对从未应用过的会话检测（prev=undefined）后取消 sheet、8s 内点击该会话激活：prepareActivation 应用落盘值完成后，探测 finally 恢复 `{mode:'system'}` 覆盖之。净效果声明（「探测期临时应用、结束恢复原状，不改变该会话当前生效配置」）被打破，主进程侧只有 console.warn（恢复失败才有，此路径恢复本身"成功"连 warn 都无）。
  - 证据：proxy.ts:243 `const prev = id !== null ? applied.get(id) : undefined`；:250-255 finally `await target.setProxy(prev === undefined ? { mode: 'system' } : ...)`；registry.ts:110 `if (prev !== undefined && sameProxy(prev, config)) return`（幂等跳过）。
  - 建议方向：恢复时**现读** `applied.get(id)`（探测期维护一个每会话应用版本号，finally 比对版本后再恢复），或把 apply 与 probe 按会话串行化（同会话互斥链，probe 排队等 apply、apply 排队等 probe）；同时评估保存/清除动作在检测进行中直接作废在途探测（abort）而非并发赛跑。
- [ ] **[中]** switchSession 早退路径不推进 generation，在途 prepareActivation 不被取消
  - 位置：`src/main/browser/registry.ts:613`（`if (id === activeSessionId) return` 同 id no-op 早退）、:630-638（generation 只在非早退路径 ++）、:642-658（prepareActivation 仅以 generation 判定弃权）
  - 描述：prepareActivation await 期间（读盘 + setProxy + closeAllConnections，忙分区可达数十至数百 ms），用户再点击**当前激活会话**（落盘 activeId 已被 setActive 改回）时 switchSession 走同 id no-op 早退——不 bump generation——随后在途的 prepareActivation(B) 通过代号复验提交切换。两个后果：① 落盘 activeId=A、registry activeSessionId=B、面板选中 A、浏览器区显示 B、命令作用域路由 B 的三方失配，直到用户再次点击才收敛；② 在途激活目标 B 被删除且删除级联 switchSession(nextActiveId) 恰为当前激活位时同样 no-op 不 bump——stale prepareActivation 若其 loadSnapshot 读在删除提交前完成（alive=true）可 commitSwitch 已删除会话（ensureManager 复活 ghost 分区 + 残留分区目录）。②的 UI 可达窗口极窄（确认对话框在途），①在快速连点下现实可达。
  - 证据：registry.ts:613 早退在 generation 自增之前；index.ts:481-491（onDeleted 级联 switchSession 同 id 时同样早退）。
  - 建议方向：同 id no-op 早退前也 `++switchGeneration`（取消一切在途激活——语义上"留在当前"即最后一次切换意图）；或引入 pendingActivationId 参与 no-op 判定（pending 目标 ≠ 当前激活位时按新切换处理）。
- [ ] **[中]** sheet 检测中编辑草稿，迟到结论覆盖占位——旧草稿结论呈现给新草稿
  - 位置：`src/renderer/src/components/WorkspacePickerWindow.tsx:203-206`（updateProxyDraft 重置 idle）、:211-222（runProxyCheck 的 then/catch 无令牌比对）
  - 描述：检测发起后用户继续编辑表单，updateProxyDraft 把结论行重置回占位（自述「旧结论对新草稿失真，不滞留误导」），但 8s 内到达的 then 回调无条件 setCheckState——按**旧草稿**得出的结论（含 ok + 出口 IP）显示在**新草稿**下，恰是被防的失真场景；用户可能据此保存一个未检测过的地址。违反数据原则「探测结果如实呈现」。
  - 建议方向：检测发起时闭包捕获草稿指纹/检测序号，回调到达先比对当前草稿指纹（或 useRef 令牌），不一致即丢弃。
- [ ] **[中]** 批量打开路径的代理应用是 fire-and-forget，首个页面请求可先于 setProxy 直连发出
  - 位置：`src/main/browser/registry.ts:509-514`（ensureManager 内 `void applyProxyFromStore(id).catch(...)`）与 :929-968（openUrlInSessions 同步 newTab/loadURL）
  - 描述：主路径（激活链 await / 克隆预应用）保证了「分区首个 loadURL 前应用」，但批量打开直接调 ensureManager：applyProxyFromStore 异步放行的同时 newTab(url)/loadURL 同步先行。对**本次运行从未激活且配了代理**的会话（新 Session 实例、代理未设置），首个页面请求与 setProxy 竞速——DNS/建连先走一步即直连泄漏真实 IP，closeAllConnections 只能收尾已建连接、无法追回已发出的请求。计划风险表「恢复/懒激活路径先直连后应用」点名防的正是此类，批量打开路径被降级为"尽力"。概率性（setProxy 通常快于 DNS），但 PRD 验收 40 的「配代理会话出口 IP = 代理出口」在该路径无保证。
  - 建议方向：openUrlInSessions 对落盘有 proxy 配置的会话先 await 应用再 newTab（可只读一次快照短路：全部 null 时保持同步快路径）；或在 ensureManager 中把「代理未应用且落盘有配置」识别为需阻塞首航的前置。
- 其余核查：prepareActivation 的 generation 复验 + alive 复验 + 克隆/导入窗口期复验时序正确（复验与 commitSwitch 间无 await）；requestExitIp 的 settled 守卫 / clearTimeout / abort 兜底完整；ensureManager 的补载判据未受影响。

## 审查摘要

## 问题详情

### P1【高 · 竞态条件/事务边界】主进程 handler 并发交错可丢失更新，且固定临时文件名可致整包损坏

- 位置：`src/main/sessions.ts:30-44`（create，rename/delete/setActive 同构，53-60、68-75、84-89）；`src/main/store.ts:75-79`；触达路径 `src/renderer/src/components/SessionPanel.tsx:152` + `src/renderer/src/stores/sessions.ts:47-55`
- 描述：五条 handler 均为「await 读盘 → 内存改 → await 写盘」，两次 await 之间事件循环可被其他 invoke 插入，无任何串行化。「新建会话」按钮 onClick 直连 `addSession` 无防抖，双击即并发两条 `sessions:create`。并发时两条 `saveSnapshot` 共用固定临时文件 `sessions.json.tmp`，writeFile 截断/交错后 rename 可把混杂内容原子搬为正式文件。
- 证据：
  ```ts
  // src/main/sessions.ts:30-44 —— load 与 save 之间可被其他 handler 插入
  const snapshot = await loadSnapshot()
  ...
  snapshot.sessions.push(session)
  await saveSnapshot(snapshot)
  ```
  ```ts
  // src/main/store.ts:76 —— 并发 save 共用同一临时路径
  const tmp = `${target}.tmp`
  await writeFile(tmp, JSON.stringify(snapshot, null, 2), 'utf-8')
  await rename(tmp, target)
  ```
  时序：双击 → create#1、create#2 各自 `loadSnapshot` 均读到旧快照 → 各自 push 自己的新会话 → 后完成的写覆盖先完成的写。结果一（必然）：磁盘只存 1 条，UI 本轮显示 2 条，重启后丢 1 条。结果二（低概率）：交错写同一 tmp → 正式文件损坏 → 下次启动 `JSON.parse` 失败 → 整包回退空快照，全部会话丢失。
- 建议处理方向：把「读-改-写穿」在主进程内收敛为串行执行（如按通道互斥的 promise 链或单一写队列）；`saveSnapshot` 改用唯一临时文件名（进程 id + 随机后缀）再原子改名；renderer 侧可加在途防重入，但根因修复应在主进程。

### P2【中 · 边界遗漏】handler 层对 IPC payload 无运行时校验，坏输入触发 TypeError 且主进程零日志

- 位置：`src/main/sessions.ts:39`（`payload.name?.trim()`）、`53`（`payload.name.trim()`）、`85`（`payload.id !== null` 判断）
- 描述：shared 中的 payload 类型是编译期约定，`ipcMain.handle` 收到的实参无任何运行时守卫。payload 缺失或 `name` 非 string 时抛 `TypeError: Cannot read properties of undefined`，invoke 以无意义消息 reject；`setActive({ id: undefined })` 因 `undefined !== null` 成立而误报「会话不存在」；`name`/`note`/`pageTitle` 无长度上限，超长字符串（MB 级）会直接写入落盘文件。
- 证据：
  ```ts
  // src/main/sessions.ts:39 —— payload 缺失或 name 非 string 时此处 TypeError
  name: payload.name?.trim() || `会话 ${seq}`,
  ```
  触达路径：常规 UI 不会发坏类型，但 renderer 暴露的 `window.electron.ipcRenderer`（脚手架既有）允许在 dev console 直接 `invoke(SESSIONS_CHANNELS.create, 任意值)` 注入。
- 建议处理方向：handler 入口加一层运行时守卫（手写类型守卫或轻量校验），非法 payload 抛统一业务错误文案；为 name/note/pageTitle 设长度上限；`setActive` 对非 `string | null` 的 id 显式拒绝。

### P3【低 · 通知遗漏】handler 抛错路径主进程无日志，renderer 失败仅 console.error 无 UI 反馈

- 位置：`src/main/sessions.ts:54、57、70、86`（四处 throw）；`src/renderer/src/stores/sessions.ts:41、52、66、81、93`（五处 catch）
- 描述：handler 抛出的业务错误（「会话不存在」「会话名称不能为空」）与 P2 的 TypeError 都只体现在 renderer console，主进程侧无任何日志，问题发生时主进程日志不可追溯。renderer 各 action 捕获后仅 `console.error`，用户对新建/删除/重命名失败无感知——此点与计划步骤 6/7 的约定（捕获、不乐观更新、不伪造）一致，记录备查。
- 证据：
  ```ts
  // src/main/sessions.ts:57 —— 直接 throw，主进程无日志
  if (!target) throw new Error('会话不存在')
  ```
- 建议处理方向：main 侧统一 catch 后 `console.warn`（含通道名与 payload 摘要）再 rethrow；是否补 UI 级失败反馈由产品权衡（PRODUCT.md 面向专业测试人员，可不弹窗，但至少日志可查）。

### P5【低 · 作用域外/依赖】electron-store 退路 A 后未从 dependencies 移除

### P6【低 · 竞态/状态脱节，罕见路径】init 失败后永不重试，此后 create 会使 UI 与磁盘短期脱节

- 位置：`src/renderer/src/stores/sessions.ts:20、28-29`
- 描述：`initialized` 标志在 await 前置位且任何路径不复位，init 失败（list invoke 被 reject）后本次页面生命周期不会重试，列表定格为空；但磁盘数据仍在，此时新建会话的 handler 基于磁盘旧快照追加并写穿，UI 只显示新建项，重启后旧会话"复活"。触发前提是 `list()` reject，而 `loadSnapshot` 对读写错误与坏数据均内部消化，实际概率极低。
- 证据：
  ```ts
  let initialized = false
  init: async () => {
    if (initialized) return
    initialized = true // 失败路径也不复位，永不重试
  ```
- 建议处理方向：失败路径复位 `initialized` 以允许重试，或 create 成功后以主进程返回值对齐全量列表（而非仅追加单项）。

- 新增四通道 sender 身份白名单齐备：show/hide 经 `requireOwnerWindow`（仅主窗或登记独立窗，ipc.ts requireOwnerWindow 实现）、hover/pick 经 `requireChildOwner`（仅池内子窗 webContents）；payload 全部过结构守卫并归一化（parseSuggestShow：items ≤ SUGGEST_MAX_RESULTS、url 非空、activeIndex 越界拒绝）。

- faviconUrl 渲染受 index.html CSP（img-src https: data:）约束，img 不执行 javascript: 协议；title/url 经 React 转义。

- 日志无敏感内容（仅 windowId 与通道名；logFailure 摘要仅在失败路径打印，url/title 属本地工具非敏感域）。

### 2.3 竞态条件

结论：发现 2 个问题（中 1、低 1）。

- [x] **[中]** 子窗首开的数据推送与渲染端 onData 订阅无结构性就绪保证
  - 位置：`src/main/browser/omniboxSuggest.ts`（ready-to-show 回调内 flush + showInactive）
  - 描述：首帧 paint 触发 ready-to-show 后主进程立即 send data，而渲染端 `OmniboxSuggestWindow` 的 `useEffect` 订阅在首次提交后的 effect flush 时才挂上。按任务队列顺序推理（effect flush 在 commit 时入队，先于跨进程 IPC 送达）订阅应先就位，且 E2E 多轮未复现空面板，但这是时序巧合而非结构性保证——一旦失效表现为首开空面板（透明空窗悬于页面上方），直到下次状态变化重发才恢复。
  - 证据：`ready-to-show` 语义为「已绘制首帧」，与 React passive effect flush 无先后契约；drive.mjs E2E 9/9 未复现（样本量有限）。
  - 建议方向：子窗挂载完成后经 invoke 回发 ready 信号，主进程收到后才 flush pendingData 并 showInactive（信号语义与 manager 的 ready-to-show 挂 view 先例同构）；或 shell 侧对首开做一次兜底重发。
- [x] **[低]** 建窗在途 loadURL 未接 rejection：dispose/销毁落在加载窗口期时为 unhandled rejection
  - 位置：`src/main/browser/omniboxSuggest.ts`（show 内 `void win.loadURL(...)` 两分支）
  - 描述：`win.destroy()` 会使在途 loadURL 的 promise reject，`void` 只丢弃值不处理 rejection，极端时序（子窗创建后毫秒级被 dispose）触发 unhandled rejection 警告。与 `windows.ts:188-194` 既有裸调用口径一致，现实可达性极低。
  - 证据：`void win.loadURL(...)` 无 .catch；对照 windows.ts 同模式。
  - 建议方向：接 `.catch(() => {})`（ERR_ABORTED 静默口径与 manager 的 logLoadFailure 惯例对齐）。

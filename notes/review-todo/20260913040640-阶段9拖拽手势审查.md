## 问题明细

### [低] L1：重复 dragstart 覆盖 docDragOverRef 致 document 监听潜在泄漏

- 位置：`src/renderer/src/components/browser/TabStrip.tsx:76-84`（onDragStart）
- 证据：onDragStart 每次都新建 allowDrop 监听并赋给 docDragOverRef；若上一次 dragend 真丢失（主进程为此有 60s 过期兜底）后又发生新 dragstart，旧监听被覆盖失去引用，仅剩组件卸载时无法触达的清理。真实 HTML5 手势下 dragstart 之间必有 dragend（document dragover 技巧正为此设），实际触发面为合成事件/平台极端场景；影响限于 shell 文档层 dragover preventDefault（浏览器内容 view 是独立 webContents 不受影响）。
- 建议方向：置新监听前若 ref 已有则先移除旧的（幂等配对，3 行）。

### [低] L2：registry.tearOffTab 与 moveTabToWindow 的作用域校验前导重复

- 位置：`src/main/browser/registry.ts:718-745` 与 `744-763`
- 证据：两函数前导同为「作用域→会话解析 + manager 取用 + tab-in-scope 三查」约 10 行，注释已声明"与 tearOffTab 同一解析口径"；tearOffTab 的 windowId 默认值与 moveTabToWindow 的目标窗强校验使两者无法直接互相替代。
- 建议方向：可抽 resolveTabScopeForWindow(windowId) 小函数；当前两处注释互指口径，可维护，不阻塞。

### [低] L3：dragStart IPC 失败无用户可见反馈（观察项）

- 位置：`src/renderer/src/stores/browser.ts:268-275`（dragStart catch）
- 证据：失败仅 console.error + 本地清态；对照阶段 7—8 L3 定案的命令失败 message 提示惯例，此处无 UI 反馈。拖拽失败的表现是 Tab 随 dragend 自然回位（Chrome 同款静默行为），语义自洽；且拖拽进行中弹 message 会与手势抢注意力。
- 建议方向：维持现状（观察项）；若后续用户反馈"拖不动无提示"再补 message。

### [低] L4：拖拽中切换/删除激活会话后主窗悬停高亮可能滞留（观察项 + 微加固）

- 位置：`src/main/browser/ipc.ts:63-71`（hover 桥接的 activeSessionId 发送侧过滤）与 `src/renderer/src/stores/browser.ts:118-131`（applyDragHover 的同判丢弃）
- 证据：悬停终态 null 广播经双重会话守卫（发送侧比对主进程 activeSessionId、接收侧比对 sessions 镜像 activeId）。若主窗已是悬停落点（高亮亮起）后激活会话中途切走/删除，null 终态因守卫不符被双双侧丢弃，主窗 hoverWindowId 滞留，Tab 栏高亮不清（下次任意合法悬停推送或重启才清）。真实手势下鼠标被拖拽捕获、无法同时操作会话面板，触发面为合成交错/发送与接收时点的主/镜像 activeId 漂移；影响纯视觉。
- 建议方向：applyDragHover 的会话不符分支由"丢弃"改"清本窗高亮"（set hoverWindowId: null）——任何不属本窗会话的悬停推送到达即意味着本窗高亮已过期，清比丢严格更安全且修掉发送/接收时点漂移。

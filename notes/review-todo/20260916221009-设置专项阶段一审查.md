## 2. 八项必查结论

### 2.1 重复代码

结论：发现 1 个问题。

- [ ] **[低]** `writeSettingsFile` 手写 tmp+rename，旁路 `fs-utils.atomicWriteJson` 单源
  - 位置：`src/main/settings.ts:66-77`
  - 描述：`atomicWriteJson` 是仓库既定的 JSON 原子写唯一事实源（`store.ts` 与 `browser/history.ts` 共用；地址栏历史补全专项修复轮 L1 曾专门将原子写收敛至此）。新代码复制了同一逻辑（tmp 命名还比单源多一段 `process.pid`），形成第三份副本（`appearance.ts` 为历史旁路副本）。
  - 证据：`src/main/fs-utils.ts:12-23`（单源实现）vs `src/main/settings.ts:66-77`（结构等价的复制）。
  - 建议方向：`writeSettingsFile` 改为一行 `atomicWriteJson(settingsPath(), settings)`（本阶段无写路径，风险为零，阶段二首次调用前收敛即可；顺带可评估 `appearance.ts` 的同类旁路是否一并收敛，属独立决策）。

### 2.2 权限漏洞

结论：已查，未发现问题。

- `settings:open` 经 sender 白名单（`event.sender !== mainWindow?.webContents` 即拒绝，含 null/destroyed 判空），设置窗自身与其他任意来源无法驱动开窗（`src/main/settingsWindow.ts:128-137`）。
- 设置窗 renderer 共用同一 preload，理论上持有完整 `window.api` 面——browser 域命令经 `resolveSenderScope` 按来源窗口解析作用域，未知窗口（含设置窗）一律中文错误拒绝（`src/main/browser/ipc.ts:3-6` 注释与实现核对）；会话域命令的 `requireActiveSession`/作用域守卫同源。外观域 `setMode` 无 sender 校验为既有行为（非本阶段引入，全局偏好无会话隔离语义）。
- 建窗 `webPreferences` 与主窗完全一致（preload + `sandbox: false`，contextIsolation 默认开），无削弱；`page-title-updated` 拦截不涉及安全面。

### 2.3 竞态条件

结论：已查，未发现问题。

### 2.5 通知遗漏

结论：发现 1 个问题。

- [ ] **[低]** 板头齿轮 `void window.api.settings.open()` 吞掉 rejected promise
  - 位置：`src/renderer/src/components/SessionPanel.tsx:428-431`
  - 描述：`settings:open` 的 IPC handler 在 sender 拒绝或主进程异常时 reject；`void` 前缀使 rejection 成为未处理拒绝，用户与控制台均无反馈路径。合法路径（主窗 shell 点击齿轮）白名单恒过、实际不触发，但异常路径（主进程 handler 抛错、窗口半销毁期点击）会产生静默噪音，违反「失败须有反馈」的项目惯例。
  - 证据：对照 `AppearanceEntry.tsx:53-57` 的 `void setAppearanceMode(key)`——后者在 store 层有失败回退处理，齿轮直调无兜底。
  - 建议方向：`.catch` 后经 antd `message` 或 `console.warn` 给中文反馈（对齐地址栏无效提示惯例的最低配）。
